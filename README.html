CNCSIM — 五轴联动 CNC 切割仿真

五轴仿真BevyRust

状态：实现阶段（L0–L2 内核全部落地；设计比对/非线性误差/STL 设计模型/后台任务与回放已接；L4 渲染：Bevy 外壳已接） 日期：2026-10-30

这是什么

基于 Bevy 0.20 的五轴加工仿真与刀路验证工具。不是 CAM（不生成刀路），是刀路验证器：会不会撞、会不会过切、实际要跑多久、哪里会出问题。

纯自用，不对外分发。

核心决策（一句话版）

# 决策 理由
1 引擎用 Bevy 0.20，UI 用 bevy_egui 0.20 内置 CAD 相机，省两周
2 L2 领域内核全自研（数学/运动学/G代码/体素/碰撞） 领域是护城河；引擎层可替换
3 材料去除用自研稀疏 SDF，不用网格布尔 网格布尔无法自研（退化情形是加工常态）
4 体素结构借鉴 OpenVDB（三级树 + 位掩码 + tile/background） 根条目从 12.5 万降到 1 条
5 碰撞方向 B（刀柄表面 → 毛坯 SDF）+ 保守推进 采样密度 h²/2R ≈ 0.17 µm；实际下限 = i8 量化 1.58 µm + 重建 h²/(8R_c) → 平面 1.6 µm、曲面 2.0 µm；不漏报
6 机床模型 = 运动学 / 外观 / 碰撞代理 三表示一真相源 三者不可能互相说谎
7 先算后播，不追求实时 五轴布尔物理上快不过真实加工

inverse() 用解耦两步法：Newton（阻尼最小二乘）解两个旋转轴 → 直线轴用 3×3 仿射一次解出。 rtcp_inverse() 只解直线轴——旋转角由程序给定，不求解。

check(topo, q, κ_limit) 产出运动学诊断：

KinFinding::NearSingular { kappa, a_deg }      // KIN-001，κ > 阈值
KinFinding::AxisLimit { joint, value, limit }  // KIN-002，超出行程

κ 用数值雅可比的条件数 σ_max/σ_min 算，不是硬编码 |sin A| < eps——前者对任何「2 旋转」构型都成立。摇篮式 κ = 1/|sin A|：A=0 → ∞，A=90° → 1。

一个刻意的设计：inverse / rtcp_inverse 不检查轴限位。 None 只表示"运动学上无解"（雅可比退化 / 不收敛）；超程用 violated_joints() 单独报。 两者对用户的含义不同，不能混成一个 None。

机床配置（cncsim-config，第 13 个 crate）

换机床只改 RON，不重新编译：

cargo run -- --machine assets/machines/ac_trunnion.machine.ron

为什么单独一个 crate：磁盘上的配置是跨层的——chain 归 kin，parts 归 render/collide， motion 归 sim。让 kin 去读整个文件，它就得知道 Shape::Box 和 ColliderSpec::Derived，耦合立刻变高。 所以只有 config 知道"文件长什么样"，各领域 crate 只接收自己的类型。

v1 只解析运动学部分（name / chain / tool_length / pivot_distance）， parts 与 motion 被 serde 静默忽略——这不是遗漏，是分层：等 render/collide 有了自己的类型再在这里补，各层代码不动。

校验的不是语法，是语义：必须「2 旋转 + 3 直线」、限位不能反向、sign 只能是 ±1。

一条锁漂移的测试：kin::MachineTopology::ac_trunnion() 是测试用的硬编码夹具（测试不该依赖文件 I/O）， hardcoded_matches_file 断言它与真实 .ron 逐字段一致。改了一处忘了另一处会立刻红—— 已实测：把 A 轴 sign 从 −1 改成 +1，报 关节 A 的 sign: left 1.0, right -1.0。

G 代码解释器（cncsim-gcode，117 个测试）

只做"文本 → 位姿"，不做运动学。 一旦这里调 kin::inverse，解释器就绑死在某台机床上。

模块 职责
lex 一行 → 字序列（letter, value），处理 (...)、;、%、* 校验和
modal GCode 用十分之一定点整数存（43.4 → 434，不用浮点比较）、15 个 G 模态组、8 个 M 模态组
order 块内执行顺序（25 个 Phase），照搬 LinuxCNC 权威清单
interp 逐块 fold，产出 Block

两条从权威原文核实过的语义（refs/linuxcnc/overview.adoc）：

  1. 块内字序无关。 原文："The first group (the words) may be reordered in any way without changing the meaning of the line." 所以 G91 G1 X10 与 G1 X10 G91 完全等价。 实现上不是靠代码摆放顺序，而是把一行里的操作收进 Vec<Op> 按 Phase 排序后执行—— 顺序是结构保证，不是约定。
  2. 组 0 轴字代码挂起组 1。 涉及 G10/G28/G30/G52/G92。不实现则 G28 X0 Y0 之后会多走一段。

文档更正两处：早期设计文档说 G91 G1 X10 与 G1 X10 G91 结果不同（错）， 以及把 G4 停延排在最后（错——权威清单里它在平面/单位/补偿/距离模式之前）。均已改。

可信度分级：跳过影响几何的代码（G41/G42 刀补、G5.x 样条、G10/G92 坐标修改、G68.2 倾斜平面） 会标 Trust::Unreliable——因为这些一漏，后面所有位置都静默偏移。跳过冷却/主轴这类不影响几何的则不标。

每条 issue 都有稳定编号 + hint：GCODE-001（未知代码）到 GCODE-010（组 1 被挂起）。 测试断言编号不断言消息文本，且有 every_issue_has_a_hint 作为质量门。

五轴与隐式运动

能力 做法 关键坑
A/B/C 轴 解析成绝对角（弧度、模态、受 G90/G91 影响），刀轴由角度推出 同一个 A30. 在双转台和双摆头上刀轴反号
G68.2 倾斜平面 折算成 TwpFrame { origin, rot }，作用在后续所有坐标上 绝对模式下没给的轴要保持程序坐标，不是工件坐标
隐式模态运动 只有轴字、没有组 1 的 G 代码时，按 st.motion 补一个 G68.2 的 X/Y/Z 是平面原点，不是运动轴字
M0/M1/M2/M30 记成 StopPoint { block, line_no, kind } 它们常常独占一行，不产生运动块——挂在 Block 上会丢

刀轴方向由三步复合，顺序不能换：

① 旋转轴：双转台用 Rᵀ·Z（工件转、刀轴在工件系里反向转），双摆头用 R·Z
② 倾斜平面：G68.2 的程序坐标系再转一次
③ 归一化

R = Rz(C)·Ry(B)·Rx(A)（ZYX 欧拉序，对应双转台 C 在 A 上面的物理堆叠）。 Block.angles 存轴角而不是方向——因为轴角无歧义，方向取决于机床构型。

隐式运动是这一轮最要命的一条：真实后处理的绝大多数行是这样的——

G1 X10 F100
X20            ← 隐式 G1，必须走
Y5             ← 必须走

不支持它，整份程序只有"带 G 字的那些行"会动，而且不报任何错，只是切出来的东西不对。

G68.2 的欧拉角是 I→绕 Z、J→绕 X、K→绕 Y，复合顺序 Z→X→Y（Fanuc 原文）。

稀疏体素（cncsim-voxel，56 个测试）

存储层是地基，先树后算法。 结构照搬 OpenVDB Tree4<T,5,4,3>（数字从叶往根读）：

root（哈希，通常 1 条）→ level2 32³ → level1 16³ → leaf 8³

关键：每一级都能存 tile 值。 这不是优化，是能不能表达的问题——

方案 200×200×100 毛坯（40 亿体素）
只存叶 1560 万个叶，无法接受
叶 + 叶级 tile 仍然 1560 万个 Constant 叶
三级都能 tile root 1 条、叶 0 个、2.0 MB

实测（cargo run 会打印）：40 亿体素分层填充 5.6 ms，实心毛坯完全由 tile 表达。

索引全是位运算，无哈希：ijk >> 12 找 root、>>7 &31 找 level2 槽、>>3 &15 找 level1 槽、&7 找叶内体素；子节点取 children[popcount(mask & 低位)]。

负坐标必须用算术右移与按位与：-1 >> 3 == -1、-1 & 7 == 7，于是体素 -1 落在叶 -1 的索引 7。 用 / 和 % 会让 -1 和 1 落进同一格——已用测试 negative_coordinates_use_floor_semantics 锁住（把 >> 换成 / 会报 left [0,0,0] vs right [-1,0,0]）。

prune 是正确性要求不是内存优化：切空的叶若仍是 Dense，碰撞检测会认为那里还有材料。 测试 prune_restores_constant_after_full_cut 就是这条的存储层版本。

i8 / i16 是同一个泛型参数，不是两套代码——SparseGrid<i8> 每档 3.15 µm，SparseGrid<i16> 12.2 nm（258×）。

与影子模型对拍：traversal_matches_shadow_model 用独立的 HashMap 做 oracle，3000 次随机写入（跨 level 边界、含负坐标）后逐点比对——不共享任何索引代码。

扫掠 SDF 与 CSG 去除（19 个测试）

材料去除就两步：

sd_sweep(p) = min_{t∈[0,1]} sd_tool(p, pose(t))      ← 扫掠体的有符号距离
d_new       = max(d_old, -sd_sweep)                  ← CSG 减法

min over t 对凸刀具是精确的：到沿直线平移的凸集的距离，是平移参数的凸函数，黄金分割能取到真极值。凹母线刀具（T 形刀、燕尾刀）不成立——v1 的刀型都是凸的。

每次求值不算三角函数（这一条省掉 ~20%）。原来 eval(t) = sd_tool(p, lerp_pose(t))， 而 slerp 开头就 acos(dot)——刀轴根本没转也照算一次。现在按"轴是否变"分两条路， 两条都把 t 的依赖提成标量多项式：

每次求值
纯平移 z = z0 + zd·t、r² = a0 + b·t + c·t² → 零三角函数，一次 sqrt
平移 + 转 cos(tθ)、sin(tθ) 各一次（cosθ/sinθ/u 在循环外算好）

顺带加了 sd_profile_rz(r, z)：内层已经有 (r, z)，不该再走一次 hypot（libm 调用，约 7 ns， 占平移路径单次求值的四成）。实测每次求值 19.0 → 14.7 ns（平移）、32.5 → 21.0 ns（带转）。

补了一条测试 rotating_sweep_matches_sampled_oracle：把 sin_cos 的返回顺序写反过一次， 当时全部测试都是绿的——因为它们只用 +Z 刀轴，而平移路径已经不碰三角函数了。 现在让刀轴转 30° 对拍暴力采样，故意写反会报「差 1.98 mm」。

迭代次数必须按行程自适应（6–24 次），这是实测出来的：

行程 固定 6 次 自适应
0.05 mm（真实段长） < 1 µm ✓ 6 次，同上
200 mm 16 µm ✗（量化档的 5 倍） ~17 次，< 5 µm ✓

迭代数只依赖几何（行程 + 刀半径），不依赖时间，结果仍逐位可复现。

切完自动 prune——切空的叶若不折叠，碰撞会认为那里还有材料（ADR-004 §5.4）。

切削 AABB 必须外扩一个窄带宽度（这一条是显示 LOD 逼出来的，见 ADR-008 §4）： 扫掠体边界就是新表面所在，所以"到新表面距离 < band"的体素一定落在"扫掠体 ∪ band 邻域"里。 不外扩的话，刀尖平面以下的材料侧只有 1 个体素拿到真实距离，往下全是切前的饱和值 −band—— 窄带单边完整等于没有窄带，跨界插值会把表面往材料侧拽。 代价是遍历体素 +54%，但碰撞用的也是同一套插值（ADR-004 §2.5），所以这不是显示层的账。

口径：cut_segment 从调用到返回，含求值 + 并行落盘 + 增量 prune，不含转 mesh、不含渲染。 24 线程（8 P 核 + 8 E 核）。单刀数字有 ±20% 的运行间抖动（线程池唤醒延迟），看量级。

比初版快 19 倍（20 mm 一刀 11.9 → 0.6 ms）。十四个优化，按收益排序：

  1. blind 元数据的"每刀重算"整体拆除——prune_touched 每刀把涉及的一级块全部 重算 blind（4096 槽 × 512 体素），而 blind 在全项目没有任何读取者。 铣光 200 刀实测这一项占 272 ms / 344 ms（79%）。改为"写时标脏（u8::MAX）， 离线 prune() 才重算"，铣光 344 → 67 ms。
  2. 平底刀纯平移走闭式解（sd_flat_prism）——扫掠体是"径向 2D 胶囊 × 轴向区间" 的笛卡尔积，盒公式直接算，跳过 13 次黄金分割。sd_sweep 从 34 → 5 ns/体素。
  3. 短段的端头圆帽特化（FlatSweep）——单轴共享只对"刀心路径正上方"的叶成立， 短段走刀（精加工 0.05 mm）时 90% 的叶落在端头圆帽区，全部掉进逐体素 sd_sweep_with（VTune 实测占 50%）。把段级常量折叠成标量后每体素 ~15 次浮点， 200 段小段 55 → 34 ms。
  4. 行级分类——平底刀沿单轴走刀时一行 8 个体素共用同一个 sd，一行只有三种 命运：够不着（整行不碰）、埋在刀体深处（整行一次 8 字节填空气）、表面行 （新值是行常量，逐点只剩一次比较）。粗加工里 75% 的体素走第二类。
  5. 中转缓冲按上限预留——CutPart::pool 从 0 翻倍长到 300 KB，中途要搬 600 KB； 铣光实测 200 刀 61 ms 花在 realloc，比写叶本身还多。
  6. 整块值的 arena（CutPart::pool）——求值加速比 4.8× → 5.6×。
  7. 增量 prune（prune_leaves）——只折叠真正写过的叶，且直接吃叶下标 （落盘本来就知道），不再按坐标回查三级（铣光 800 叶 × 67 ns = 54 µs/刀）。
  8. 沿单轴走刀的截面共享（sweep_axis）——见「沿单轴走刀」一节。铣光 -15%。
  9. 叶级整块写回（LeafBlock + blit_leaf / blit_leaves_parallel）。
  10. 整叶短路走并行落盘——有下标的叶不再走串行 fill_leaf，而是产出一份 512 个同值的整块混进并行 blit 队列（write_leaf_block 识别全同值，落成 Constant 叶，不碰分配器）；串行路径只剩"槽位还是 tile"的叶。
  11. WriteCache 块级缓存——一个 level-1 块管 4096 个叶，落盘按 z/y/x 走时 相邻叶几乎同块，命中跳过 root 哈希 + ensure_l1。
  12. 量化系数外提（k_dist / k_value）——to_value 每次都调 band_mm() 再做除法， 逐体素两次调用；换成循环外算好的两个乘法。
  13. set_cached / leaf_or_tile——跳过三级查找。
  14. AVX2 量化（update4_i8）——4 路 SIMD 处理量化 + clamp。只有 2.5%，见下； 行级分类（第 4 条）落地后已删除。

四件要记住的事：

  1. 耗时由 AABB 决定，不由"走了多长"决定。 1 mm 的刀也要 0.52 ms。
  2. 空刀很便宜（0.28 ms）：值没变，落盘全跳过；求值仍要跑。
  3. 短刀并行效率差：1 mm 段只有 14 层可切（nz < 2×线程数）。
  4. 首次一刀的 changed 大多是"从饱和值 −127 变精确窄带值"，不是变空气。

批量切削：cut_batch——多刀一次遍历

仿真主循环必须一刀一刀切（每段之后要拿当前网格查碰撞），那是 cut_segment。 但"只关心最终形状"的场合（粗加工预览、材料去除率、过切检查）可以攒批： cut_batch(&[(from, to)], profile) 一次遍历套完一批刀路。

语义：与按顺序逐段调用 cut_segment 逐位相同（tests/cut.rs batch_matches_one_cut_at_a_time 逐体素对拍，铣光场景抽查 1 万点 0 差异）。 原理：CSG 是 max（交换律 + 结合律）且量化幂等，批内段顺序不影响结果； 批量只是把"每个叶从树里取 k 次、写回 k 次、prune k 次"变成各 1 次。

实测（50×50×100 铣光 200 刀，见 tests/millout.rs）：

方式 耗时 每刀
逐刀 cut_segment 48 ms 0.24 ms
按层攒批（20 批 × 10 刀） 26 ms 0.13 ms
整批一次（200 刀） 16 ms 0.08 ms

批越大省得越多：批量把 AABB 取并集后一次并行求值，落盘、prune、线程派发各付一次。 代价是批内不能插入别的操作——碰撞检查、进给采样都得等整批切完。

建场：只扫表面壳 + 并行求值

毛坯初始化（fill_box_exact，写精确盒 SDF 的边界壳）原本遍历 [lo−pad, hi+pad) 的整个立方体：50×50×100 的毛坯是 3125 万次盒 SDF 求值，其中 99.7% 算完 就被 |d| < band 丢掉（内部一律饱和、远处一律背景）。

两个改动：

  1. 只扫 6 个面片（各 pad 层厚）——采样量 3125 万 → 330 万（363×）。 棱和角会被两个/三个面重复扫到，值相同，重复写无害。
  2. 并行求值、串行写盘——盒 SDF 是纯函数（只依赖坐标），按 z 切片并行算； 写入受树结构限制只能串行。
改前 只扫表面壳 + 并行求值 + 按叶写回（2026-11-01）
50×50×100 建场 145 ms 84 ms 56 ms 14 ms

这是本轮最大的一笔（fill_box_exact 一次性的，但铣光场景里它占三成时间）。

几个"以为有用、实测没用（或帮倒忙）"的优化

诚实记录，免得以后重犯：

改动 预期 实测
饱和捷径：−sd ≥ band 时直接写 S::MAX，跳过 round/clamp 省 75% 体素的量化 0%
内联 sd_flat_prism（叶在段内时省掉 origin_to_segment 的 clamp） 省函数调用与分支 0%

前三条都指向同一个结论：切削循环的瓶颈是访存，不是算术。 每体素 3 ns 里，读 vals、写 vals、d_cur < band 的比较、nv != cur 的比较 才是主体；sd_flat_prism 本身只占 2%（VTune 实测），量化也只有个位数。 SIMD 打的是算术，靶子选错了。行级分类（整行填空气 / 整行跳过）之所以有效， 正是因为它减的是访存与分支，不是算术。

后两条是另一个教训：先确认有读取者，再决定维护成本。blind 重算在 VTune 里根本不显形（它是干净的顺序扫描，没有 cache miss），只有 CNCSIM_PROF 的阶段计时把它揪出来——铣光 200 刀 344 ms 里占 272 ms。

AVX2 路径已随行级分类删除（它服务的"表面行逐点量化"现在每行只算一次 round）。

沿单轴走刀：SDF 在走刀方向上是常数

立铣刀的绝大多数切削是沿一个轴走直刀（x 或 y）、刀轴竖直不动。这时扫掠体是 "圆柱沿该轴拉伸"，而 sd_flat_prism 的公式里：

dz  只依赖 z           ← 与走刀方向无关
dr  是到走刀线段的距离  ← 叶完全落在段内时退化成 |py|，与走刀方向无关

所以叶完全落在走刀段内时，SDF 只取决于截面 (y, z)。 叶的 512 次求值降到 64 次（8×8 截面），沿走刀方向原样复用。

沿 x 走刀：每个 (y,z) 算一次 sd → 内层 8 个 x 复用      512 → 64 次
沿 y 走刀：每层 8 个 x 算 sd → 中层 8 个 y 复用          512 → 64 次

条件刻意保守，任一不满足就回退通用逐体素路径：

  • 刀轴竖直（±Z）且两端一致
  • 位移只沿一个轴（斜向进给时径向和轴向共享同一个 t，没有这个性质）
  • 不是沿 z（钻孔的扫掠体沿刀轴延伸，不是横向拉伸）
  • 叶整个落在走刀段内（跨段边界的叶两端有端盖效应）

正确性锁：tests/cut.rs::axis_sharing_matches_general_path —— 同一条扫掠线 一次切完（走共享路径）vs 拆成五段（叶跨段，走通用路径），几何等价， 逐位相同（抽查 1.4 万个体素）。全库 16 个 cut 测试也都走 x 轴，双重覆盖。

收益（实测）：铣光 434 → 371 ms（-15%），20 mm 一刀 0.97 → 0.84 ms。 没有预期的 8×，因为 sd_sweep 只占串行开销的约 26%——剩下是体素值读写、 量化转换、循环开销，这些按体素算，省不掉。

多线程：无锁、数据竞争隔离

结构：求值并行 + 落盘并行，两段都没有锁、没有原子操作、没有 CAS 重试。

阶段 并行方式 争用点
求值 按叶层最多的轴切片 → rayon map_indexed 只读树 + 各片自己的 arena
落盘 按叶索引排序 → par_chunks_mut 切段 → 每线程写自己那段 无（段物理不相交）

为什么是 5.6× 而不是 24×：i7-13700K 是 8 P 核 + 8 E 核（24 逻辑线程）。 8 线程时全是 P 核，5.2× 已经贴近 8 个物理核的上限；再往上 E 核频率低一半， 加上调度开销，16 线程反而略慢（1.08 > 0.93）。这已经是这台机器的硬件上限附近。

踩过的两个坑，都是"看起来并行、实际不并行"：

  1. 分片轴选错。为让整块写回生效，分片改成按叶层切——但 z 方向只有 5 个叶层， 片数被 clamp 到 5，24 线程只有 5 个在跑（求值只加速 4.9×）。 改成按"叶层最多的轴"切（铣光的 AABB 是 284×34×38，x 方向 36 个叶层）才喂满。
  2. 每叶一次 malloc。整块缓冲原本是每叶一个 Box<[S; 512]>，一刀 3920 次分配， 24 线程并发打到同一把分配器锁上——加速比卡在 4.8×，8 线程之后再也不涨。 改成每片一个大 Vec（arena）+ LeafBlock::offset 之后，24 线程到 5.6×。

顺带一个反例：试过在切削前预创建 AABB 内所有叶，好让落盘全走并行路径。 实测是负优化（铣光 439 → 444 ms）——arena 之后落盘已经不是瓶颈，预创建白付 每刀 750 次三级查找。已回退，代码里留了注释。

修法是加一个按总字节数的门槛（不是按块数：i16 时一块是 1 KB）：

建场按叶写回：532 万次单点写 → 1.5 万次整块写（2026-11-01）

上一节把切削从 56 ms 压到 48 ms 之后，建场（47 ms）反而成了最大的一项。 CNCSIM_PROF=1 的建场拆分把问题指得很清楚：

写入 532 万个体素 / 31 ms = 5.8 ns/次

每次 set 只写 1 个字节，却要走一次三级查找 + 缓存判断。而边界壳的体素 天然按叶聚集（一片 8³ 叶里平均有 532 个体素要精确化，接近满叶）。

改成按叶遍历：

  1. 枚举 6 个面片覆盖的叶（棱角处会被两三个面重复枚举，sort + dedup 去重）；
  2. 每叶先按现状取一份 512 值作初值（tile / Constant / Dense 三种都要处理—— 叶内不在面片上的体素必须保持原值，这是最容易写错的地方）；
  3. 只覆盖落在面片上的那些体素，any 标记"这片叶有没有改到"；
  4. 一次 blit_leaf 整块写回。

一个必须处理的细节：去重不能省。并行时同一片叶被两个面各处理一次，第二次 读到的是第一次之前的旧值，后写的会把前面的精确值覆盖掉——而结果看起来 "大部分是对的"，只有棱角上几十个体素错。

第二个细节：末尾的 prune() 改成增量的 prune_leaves(&touched, &[])。 全量版要遍历整棵树 + 重算所有 level-1 的 blind，而建场刚结束时树里只有 fill_box 造的 tile（不需要折叠）和这里刚写的边界叶（any 保证不可能全同）。 实测全量 prune 4.7 ms/轮，占建场剩下的四分之一。

原来用 a/b/c 三元组循环算 12 条棱，每条棱现构造 u/w 坐标再调 corner_index （3 次移位 + 2 次或）——24 次调用占 1.4% CPU。展开成编译期常量索引后：

// a = x：u = (0, ib, ic) = ib<<1 | ic<<2，w = u|1
let (vu, vw) = (corners[iu], corners[iu | 1]);

累加顺序与原实现逐位相同（x 轴 4 条 → y 轴 4 条 → z 轴 4 条），所以顶点坐标 一个 ulp 都没变——测试断言顶点数 16 000 002 完全一致。

四边形发射时每格查 3 次（p−e_b、p−e_b−e_c、p−e_c），而遍历按块序推进， 相邻格几乎总在同一块。缓存块坐标 + 序号，命中就跳过哈希。收益小（2%）—— 因为 p−e_b−e_c 经常跨块。

四个值得记的点：

  1. 体积误差 ∝ h²：1.35% → 1.16% → 0.05%。h 缩小 20 倍，误差缩小 27 倍。 0.1 mm 时误差 36.6 mm³ / 79235 mm³ = 0.05%，比"一个体素层的体积"还小—— 因为窄带里存的是真实距离，体积积分用的不是体素化近似。
  2. 体素化与三角形数成正比、与体素数几乎无关：h 从 2 到 0.1，体素数涨 12 600 倍， 时间只从 30 s 涨到 41 s。瓶颈是"190 万个三角形每个都要遍历自己的 AABB+band"， 不是域的大小。
  3. 提取是另一个量级：792 万三角形只要 193 ms（4100 万面/秒），因为候选格 从叶反推（20 万叶 → 候选格 297 万个，而全空间是 5.56 亿）。
  4. 开洞恒为 0，但非流形边随 h 减小而增多（138 → 513 → 4276）。已确认 不是三角形重复发射（7 924 700 个三角形里 0 个重复）——是 Surface Nets 在 薄壁/尖角处的对偶网格非流形：两个面靠得比体素还近时，对偶顶点重合。 不影响渲染。

顺手做的一个优化：distance_pass 里先用"点到三角形 AABB 的距离"筛两道 （下界 ≥ band 就不必 get；下界 ≥ 当前 |v| 就算出真值也不会更新）。体素化 56.8 → 41.1 s（-28%），结果逐位不变。

窄带越薄，体素化越快、量化越细（2026-11-01）

上面 41 s 是 band_voxels = 4（切削用的默认值）。但体素化设计模型不需要那么宽的带， 而 distance_pass 的成本 ∝ (三角形尺寸 + 2·band)³——band 减半，AABB 体积降到 1/3。

同一个模型（h=0.1、190 万三角形）：

band_voxels 体素化 体积误差 LOD 上限 用途
4 41.1 s −0.05% k=4 切削（要精确距离）
2 15.2 s −0.01% k=2 设计模型 / 显示
1 8.2 s +0.003% k=1 只做比对/体积

反直觉的地方：带越薄，体积误差反而越小。 因为量化档是 2·band·h/254—— band 减半，档距也减半。所以 band=1 的误差是 band=4 的 1/4。

代价是"距离可信范围"变小：band=1 时带外一律钳到 ±0.1 mm，只有表面 1 个体素内 的距离是真的。所以：

  • 切削 / 碰撞必须 band=4（刀要深入材料，带外要保守钳制）
  • 设计模型用 band=2（过切深度走解析扫掠点测试，不经过体素；残留厚度是 mm 级）
  • max_lod_factor() == band_voxels，所以 band=1/2 时 LOD 只能到 k=1/k=2

app 的 --design 路径已改成 band=2：过切深度 707.1 mm³ 与 band=4 完全一致 （走解析测试），体素化快 2.7 倍。

两个 --export 场景的数字不要混：无 --design 时用解析盒（30×30×11 实心）， 残留 10.92 mm³（面铣四角的料）；带 --design testdata/design_box.stl 时那个 STL 是 薄壁盒，内腔被判定为"设计气区"，毛坯在内腔的料全算残留（5179 mm³）。 两个都对，只是问的问题不同。

  • 切削保持 band=4（它换来的是检出下限和下面那条一致性，不是速度）
  • 体素化才是 band 的杠杆（41 → 15 s，上一节）

一个被 band 卡住的指标：残留厚度

residual_max_thickness 是 设计场距离 + h/2，而那个距离来自设计模型：

设计模型 距离来源 有上限吗
DesignModel::Box（默认） 解析盒 SDF 没有（实测 1.000 mm 是真实厚度）
DesignModel::Field（--design x.stl） 体素场查询 有，= band + h/2（0.450 mm @ band=4）

所以 --design 时这个指标会饱和：比 band + h/2 更厚的残留一律报成上限。 stl_field_design_agrees_with_box_design 就是被这条卡住的——band 改成 2 时上限从 0.45 降到 0.25，同一个设计用解析盒和 STL 两种表示会给出不同的残留厚度。

现在报告里会标出来：

残留 5179.29 mm³，最厚 0.450 mm（**已饱和**：Field 设计的上限 0.450 = band + h/2，真实更厚）

现在这个"饱和"是显式状态，不是靠打印时猜：

pub fn distance_cap(&self) -> Option<f64>   // 设计距离有无上限
// SimReport 里：
pub residual_thickness_capped: bool,        // 最厚那点是否饱和
pub residual_thickness_cap: Option<f64>,    // 上限是多少

voxel_compare 在记录最大厚度时同时判断 dd >= cap，所以：

  • DesignModel::Box → capped = false，厚度精确
  • DesignModel::Field → capped = true，厚度是下限

注意上限要用"设计场"的 band 算，不是毛坯场的——两者是独立网格，band 可以不同 （--design 用 2、毛坯用 4，拿错就会把 0.25 的上限印成 0.45，这个坑踩过一次）。

所以 --design 现在用 band=2：体素化 41 → 15 s，残留厚度标"已饱和（上限 0.250）"。 stl_field_design_agrees_with_box_design 也从"必须等于 0.5"改成"要么等于 0.5， 要么明确标了饱和"——这不是放宽断言，是把饱和变成可检查的状态： capped=false 却对不上 0.5，或者 capped=true 却报了个离谱的值，都会红。

要根治得让 Field 的残留厚度走解析距离（对残留体素求最近设计三角形）， 那样 band 就与这个指标彻底解耦。

先说清楚这个对比的边界：

  • 小盒子上 OpenVDB 也不快（53 vs 38 ms），所以差距不是"大模型才出现"。
  • 截断三角形做 scaling 的尝试无效：截断后模型不闭合，OpenVDB 的符号判定会 退化（2000 个三角形也跑不完），而完整模型是水密的（95 万顶点、285.6 万条边、 开洞 0、只有 2 条非流形边——用 numpy 独立验过）。

但不能因此说"我们比 OpenVDB 强"：它输出的是通用带符号距离场（任意带宽、 自适应、支持 CSG 管线），我们只做窄带 SDF。它的设计目标不是"190 万三角形一次 转窄带"。

顺带发现：design_box.stl 是单层壳（只有外表面，没有内表面）。视差法下 射线只穿一次，奇偶判成"内部是材料"，所以体积算成实心（1266.7 → 3760.0 mm³， +196%）。这个模型的体积指标无效——它只适合当"设计面"用（ovdb_parity 就是 这么用的，只看表面位置）。

三个必须说清的点：

  1. OpenVDB 的 CSG 极快（0.3 ms），但它要求刀具体已经是 level set。 OpenVDB 没有"解析扫掠 SDF"——必须先把扫掠体逐体素写成 level set， 这一步 ValueAccessor::setValue 实测 78 ns/体素（254k 体素要 20 ms）。 我们的解析求值 4.7 ns/体素（落盘后 13.8 ns），快 5.5×。 这个对比不是"我们比 OpenVDB 强"，而是两种范式：它优化了 CSG，代价是必须先把形状体素化。

  2. 如果刀具形状能在多刀间复用，OpenVDB 会赢。 固定形状（球头刀）+ 平移变换， 只跑 csgDifference 就是 0.3 ms/刀，比我们快一个数量级。 但扫掠体随刀路变化，真实场景里每刀都得重建——这才是本表的口径。

  3. CNCSIM 的"空刀"是 0.66 ms，与 OpenVDB 的纯 CSG（0.3 ms）同一量级。 说明我们慢的部分全在"求值 + 落盘"，不在 CSG 本身。

如果哪天需要更快：把解析 SDF 预烘焙成 level set 再复用（就是 OpenVDB 的路子）， 但会失去"设计模型解析比对"和"任意刀型零预处理"这两个能力。

几何结果一致吗？——一致到量化精度

速度只是硬币的一面。crates/voxel/tests/ovdb_parity.rs 做了逐点对拍： 同样的毛坯/刀具/刀路，在槽底与槽壁上按体素索引采样，比较两边的 SDF 值。

指标 结果
表面位置（槽底 z=11.5 / 左壁 y=19.0 / 右壁 y=25.0） 差 0.0 µm（三个过零点全部精确命中）
带内逐点差（27 个采样点） 最大 1.18 µm、中位 0.39 µm

1.18 µm 就是 i8 量化步长（2×0.4/255 = 3.15 µm）的半步——不是算法差异，是表示精度。 带外的绝对值不同（CNCSIM 钳到 ±0.4，OpenVDB 钳到 ±0.45/±0.55），那是各自的饱和约定， 符号永远一致，不影响任何下游计算。

对拍抓到的真问题：fill_box 只写饱和值，毛坯边界不写精确 SDF， 于是未切削面的插值位置依赖"体素中心恰好落在边界上"——实测左侧壁因此偏了 25 µm。 修法是新增 fill_box_exact（边界壳写真实盒 SDF，内部仍是饱和 tile，内存不变）， 换上之后三个过零点全部归零。默认仍用 fill_box（建场几乎免费）， 需要亚体素精度的场景显式用精确版。

精度上限：能到多少

两个概念要分开：几何分辨（能不能表示细节，由 h 决定）与数值精度 （表面位置准不准，由量化决定）。后者有闭式：

量化步长 = 2 · band_voxels · h / steps      (steps: I8=254, I16=65534)

crates/voxel/tests/precision.rs 实测（槽底故意放在 13.3h，落在体素中心之间）：

h (mm) I8 误差 I16 误差 30×30×12 毛坯内存
0.100 0.65 µm 0.0024 µm 1.2 MB
0.050 0.32 µm 0.0012 µm 5 MB
0.020 0.13 µm 0.0005 µm 31 MB
0.010 0.065 µm 0.0002 µm 125 MB

误差 / h 恒为 0.0065（I8、band=4），即误差严格正比于 h、正比于 band_voxels、 反比于档位数。三个旋钮的实测性价比：

旋钮 精度收益 代价
h 减半 误差减半 内存 ∝ 1/h²（表面积），切削 ∝ 1/h³
I8 → I16 误差 ÷258 内存 ×2
band_voxels 减半 误差减半 窄带变薄，曲率大的地方距离不准

结论：

  • 实用上限：h=0.01 + I8 → 65 nm，比机床定位精度（~1 µm）高 15 倍，内存 125 MB。
  • 理论极限：h=0.01 + I16 → 0.2 nm，已经小于原子直径，没有工程意义。
  • mesh 顶点与 SDF 查询同精度（实测两者都是 0.65 µm @ h=0.1）——Surface Nets 没有引入额外误差，至少在平面上如此。

别忽略的另一半：以上是平面的精度。曲面上还有体素化本身的弦高误差 ≈ h²/(8R)（h=0.1, R=3 时 0.4 µm），与量化误差同量级。 所以真实零件上，h=0.1 的总误差约 1 µm，仍远优于工艺公差。

问题 修法 效果

prune_touched 每刀重算 blind 元数据（全项目无读取者） 写时标脏，离线 prune() 才重算 344 → 67 ms（-79%）
get(ijk) 每体素走完整三级查找 leaf_or_tile：一次拿到叶，512 体素直读叶缓冲 单刀 2.3 → 2.1 ms
fill_box_exact 用无缓存 set 改走 set_cached_in_bounds 建场 240 → 147 ms
中转缓冲从 0 翻倍 realloc 按叶数上限一次预留 -61 ms/200 刀

结论：prune 的全量重算是比"求值"大得多的隐藏成本——它在每刀都触发， 而切削只碰 AABB 里的一小块。任何"每刀都要遍历整个场"的操作都得改成增量； 而"没人读的元数据"是最贵的那种——删之前先全局搜一遍读取者。

建场差距的原因：OpenVDB 的 fill 走 tile（O(1) 每块），我们精确化边界壳时要 逐个体素算盒 SDF（3125 万次）。用 fill_box（饱和、不精确化）建场是毫秒级， 但未切削面的插值位置会偏——见上面「几何结果一致吗」一节。

测试量的是表面位置，不是"有没有变化"：开一条 6mm 宽、2mm 深的槽，断言槽底在 z=3（±5 µm）、槽壁在 y=2、槽外材料一动不动。把 CSG 公式的负号去掉会报「槽内应为正（无材料），实际 −0.4」。

实测精度：R=3 的球，有向体积 112.97 vs 解析 113.10，误差 0.11%。

三条硬指标都有测试：水密（每条边恰好共享 2 次）、有向体积为正（绕序）、体积数值对（位置）。 把绕序翻反会报「绕序反了：体积为 −112.97」；去掉 tile 的边界余量会报「丢洞 298」。

三个踩到的坑（都写进了 ADR-006 §7.1）

  1. tile 紧贴填充边界会让网格漏洞——单元格跨 2 个体素，"tile 的最后一个体素 ↔ 盒外背景"这条符号变化落在没有叶子的区域，谁都遍历不到。修法：tile 判定留 1 体素余量，边界那层槽建成常量叶（16 字节而不是 528），把 130 MB 压回 4 MB。
  2. halo 重叠导致四边形重复发射——顶点有 entry() 去重所以无害，四边形没有 → 边被共享 4~6 次。修法：按顶点创建顺序遍历。
  3. HashMap 迭代顺序破坏可复现性——for_each_leaf 走 HashMap，顶点顺序每次不同。修法：叶坐标先排序。

单元格索引：块 + 位掩码（4 个测试）

顶点是"每个单元格一个"，所以要有 单元格 → 顶点索引 的映射。第一版用的是一张 FxHashMap<[i32;3], u32>：200 mm 毛坯 1600 万条、310 MB，每次查找都是 DRAM 延迟—— 提取 3.0 s 里有 2.0 s 花在这上面。

改成 每 8³ 个单元格一个块 + 512 位掩码，索引 = base + popcount(掩码前缀)：

方案 每块开销 25 万块合计
稠密 [u32; 512] 2 KB 500 MB（比哈希表还差）
位掩码 [u64; 8] + base 68 B 17 MB

块内占用率只有 12.5%（表面在体素空间里是二维的），所以"有没有"用 1 bit 存、"是多少"用前缀和算， 信息量一样、内存差 12 倍。这是从 OpenVDB 抄的——它的树里只有 root 是哈希表， 往下一律 children[popcount(mask & 低位)]。

代价：顶点下标变成"块序 + 槽序"的空间序（不再是叶迭代顺序）。这对渲染无影响， 但细格与 LOD 必须走同一个构建器，否则 k=1 与细格逐位一致那条测试立刻红。 副产品是"顺序与分块数无关"由构造保证，不再依赖"合并顺序恰好等于串行顺序"。

实测：200 mm 提取 3.09 s → 0.81 s，索引 310 MB → 25 MB，另外省掉原来那张 192 MB 的 cells 数组（单元格靠掩码反推）。顶点数 / 三角形数 / 丢洞数与改前完全一致（16 000 002 / 32 000 000 / 0）。 细节见 ADR-010。

显示 LOD：粗格重采样（11 个测试）

不是网格抽稀，是重新采样——输入是 2 MB 的稀疏树，不是 834 MB 的细网格。 水密性照样由 Surface Nets 的结构保证，绕序逻辑与细格共用同一段代码（vertex_of / emit_quads）。

网格抽稀（QEM） 粗格重采样
输入 先得造出 3200 万面 稀疏树，2 MB
水密 抽稀会开洞 结构保证
可复现 依赖误差度量与堆序 纯函数，逐位可复现

k ≤ band_voxels 是几何约束，不是调参旋钮。 跨符号的棱两端各在表面一侧， 所以各自到表面的距离 ≤ h_c = k·h；窄带只有 band_voxels·h 宽。于是：

  • k ≤ band：两端都在带内 → 值是真实距离 → 插值误差只剩 O(h_c²/R)。
  • k > band：远端被钳制到 ±band → 插值不再等于真实距离，偏差随 (h_c − band)² 长。

实测 R=6 球的最大径向偏差：k=1 1.8 µm、k=2 3.3、k=3 6.2、k=4 9.8，越界后 k=5 15.5、k=6 34.2。 不是断崖，但没有上界，而且网格看起来照样水密——所以 extract_surface_lod 超限直接 panic， 不警告、不静默降级。想再少面只能加宽 band（内存换），不能加大 k。

段内并行：零依赖 fork-join（6 个测试）

段与段之间仍然串行（第 N+1 段要读第 N 段切完的毛坯），但段内是并行的： 一次切削里每个体素只读自己那一个值，max(d_cur, −sd_sweep) 与邻居无关。 《并发与性能》原文说"材料去除不能并行"，那句话要读成段间。

形状统一成"只读并行 + 按块号归位"，SparseGrid 全程单一所有者——不需要 Arc<Mutex<_>>，也不需要 unsafe：

① 并行求值：&self 只读，每块产出自己的结果（顶点 / 改变列表 / 索引）
② 串行归并：按块号顺序合并 → 与线程调度无关

voxel::par 只有 70 行：std::thread::scope + fetch_add 动态领号 + slots[块号] 落位。 池是 rayon 的（ThreadPoolBuilder + par_iter）：第一版手写 std::thread::scope， 每次 fork-join 491 µs，真实段长 7.4 ms 里占 7%——10 万段就是 50 秒。换成常驻池后降到 ~5 µs。 数据面的规矩没变：仍然只读并行、按块号归位，池只负责分 CPU。

确定性是硬门槛：分块数从 1 拧到 97，顶点/法向/索引/体素值必须逐位相同。 所以把"分块数"做成显式参数（extract_surface_chunks(n) / cut_segment_with(.., slices)， 0 = 自动），4 条测试拿它当旋钮对拍（tests/parallel.rs）。线程数是进程级全局，测试里改不了， 但块数 1 就是串行路径——这才测得到"合并顺序与调度无关"。

碰撞：保守推进 + GJK + EPA + episode（34 个测试）

collide 的第一片：连续化。这是 ADR-004 §3 认定的"真正的风险点"。

100 m/min 快移 = 1.67 mm/ms，薄壁/压板边缘能薄到 1–2 mm。按固定时间步采样， 2 mm 的薄壁会被整步跳过——报"无碰撞"而实际撞了。漏报比没有检测更危险，因为它给了虚假的安全感。

保守推进用距离下界算安全步长：

t ← t + d_lower(t) / v_max        # 这段时间内不可能撞

只要 d_lower 是下界、v_max 是上界，步长就永远偏小 → 只会迟到，不会跳过。 迭代耗尽时保守报碰撞。

下界怎么来（两处都要减）：刀柄表面是采样的（间隙 δ），最靠近材料的点可能没采到 （1-Lipschitz → 真实距离 ≥ 采样最小值 − δ）；再加上体素场误差 2 µm。所以 Hit 同时给出 clearance（上界，< 0 是确切穿透）与 clearance_lower（下界）， 两者之间就是"无法保证"的区间——默认 δ=0.5 mm 时保守带 ≈ 0.5 mm。

δ 采样点（φ6×20 刀柄） 检出下限（R=3）
0.2 mm ≈ 22 000 6.7 µm
0.5 mm ≈ 3 500 42 µm
1.0 mm ≈ 880 167 µm

v_max 必须含转动项 θ·r_max——五轴摆动时刀柄末端速度可能远大于刀尖，用刀尖速度当上界会漏报。

测试里有两条是对照组：endpoints_only 是"只查两端点"的反例（留在代码里）， 2 mm 竖墙 + 16 mm 单步的场景下它漏，保守推进抓到。

凸体 × 凸体：GJK（解析 support，不做多边形离散）

ADR-004 §2.6 认定"精确"的那一类，用来管刀夹 / 夹具 / 台面 / 机床件—— 这些形状是已知的凸体，没有理由拿体素去估。

为什么不用离散：上一版设计把旋转体切成 16 边棱柱，外切误差 r(1−cos(π/16)) ≈ 0.019r。 对 R=30 的刀夹是 0.57 mm 的系统性误报——每把刀都"差一点点就撞"，报告就没人看了。 GJK 只要一个支持映射，圆台/球/盒的支持映射都是解析的，于是零建模误差。

形状 用途
Cone（圆台 / 圆柱 / 圆锥 / 退化圆盘） 刀柄按母线分段，一段一个
Sphere / Capsule 球头刀、简化主轴鼻端
Box3（有向盒） 夹具、台面、机床铸件
Hull（顶点表） 导入的 STEP 件——只要顶点，不用三角化
Placed<S> 任意局部形状 + 刚体变换

整把刀 = cones_of(profile) 的圆台并集。刀具不必是凸的：凸体并集到另一个体的距离 取各段的最小值，逐段 GJK 再取最小就对了。

实测（release）：

场景 耗时
单对 圆柱 vs 球（平均 7.1 迭代） 297 ns
整把刀（3 段圆台）vs 夹具 1.67 µs
AABB 粗筛 aabb_gap 3.1 ns（比 GJK 便宜 96×）

distance() 永远精确——最近点对就是碰撞报告要的"哪里撞了"，不能拿盒面近似糊过去。 要粗筛用独立的 aabb_gap()，别让两者混在一起。

怎么保证算对（这一片花时间最多的地方）：

  1. 最优性用 KKT 条件自证，不需要 oracle：point_a 必须是 a 沿 −d̂ 的极值点、 point_b 是 b 沿 +d̂ 的极值点，两条成立 ⟺ |pa−pb| 就是最短距离。 随机 400 对（圆台 vs 球 / 盒）跑这套断言。
  2. 采样对拍：圆台表面密集采样 → 每点到盒的解析距离取最小 = 真实距离的上界。 GJK 必须落在 [上界−采样间隙, 上界]。35 例实测偏差 0。
  3. 支撑点合法性（独立于 GJK）：support(d) 必须是沿 d 真正最远的点。

第 3 条抓到过一个只有它才能抓到的 bug：Cone::support 只按轴向正负挑端圆、 没比较半径，对 r_lo ≠ r_hi 的细长圆台返回非最远点——距离虚高 0.06 mm。 第 1 条断言当时全绿，因为断言里的 support 和 GJK 里的是同一个错的实现，两边一起错就自洽了。 凡是"用同一份实现自证"的检查，都必须再配一条独立的 oracle。

实现上没有增量维护单纯形（GJK 最经典的坑：该丢的点没丢），而是每轮穷举含新点的子集 （≤ 8 个）各求一次闭式最近点。定长数组、零堆分配，单次 297 ns 够用； 早版本用 Vec 做这件事是 2313 ns（8×）。

穿透深度：EPA

GJK 只说"撞了"（距离 0）；报告要说"撞进去多深、从哪退"。

在 Minkowski 差 W = A − B 里做：原点在 W 内 ⟺ 相交，原点到 W 边界的最短距离就是穿透深度。 拿 GJK 的单纯形当初始四面体（不够 4 点就自己扩），反复"找最近面 → 沿法向取支撑点 → 撑大"，d(最近面) 单调递增，收敛即答案。

一个容易搞反的符号：point_a − point_b 不是分离方向，而是它的反面。

A 球心 0 半径 3，B 球心 4 半径 3。W 是半径 6、中心 −4 的球，最近边界在 +X、距离 2。 但 A 要往 −X 移 2 才分离。所以字段叫 axis 不叫 normal，分离位移是 −axis · depth。

验收方式是"照着推开"：按报出的 depth / axis 移动 A，两体必须恰好接触。 120 例随机穿透（圆台 vs 盒）全部通过。深度算错、方向反了、接触点错了，这条都会红。

场景 结果
球 vs 球（解析 2.0） 1.99998 mm（平面逼近球面的固有误差）
盒 vs 盒（解析 0.5） 0.50000

曲面精度受平面逼近限制而不是迭代次数：球面 64 次迭代到 2e-5 mm， 再往上只能靠更多面。要 µm 级深度的场景应该用解析特例，不是加迭代。

踩的坑：初始四面体的外法向不能拿原点当参考点判朝向——GJK 留下的单纯形本来就贴着 原点，原点可能正好在某个面的平面上（n·O = 0），判不出哪边是外。判错的后果是最深的面 被当成"最浅出口"，深度直接报 0。改用四面体重心（一定严格在内部）。

episode 聚类

一次真实碰撞会在连续几十个采样点上反复触发，逐条报出来是几百行噪声。 按「同一对部件 + 间隔 ≤ 50 ms」合并之后，一个 episode ≈ 一次事故。

50 ms 不是拍的：100 m/min 快移在这段时间里走 83 mm，比任何真实接触尺度大一个量级， 所以同一次碰撞不会被拆成两段；而两次独立事故基本不会在 50 ms 内重复。

absorb() 取最大穿透而不是最后一次——报告关心"最深扎进去多少"。

毛坯碰撞：两个方向，分工不同

collide 刻意不依赖 voxel（ADR-004 §7.7），依赖方向由 sim::stock 反转： StockField 用 newtype 把 SparseGrid 包成 DistanceField（orphan rule 要求这样）。

方向 做法 保证 成本（φ9×60 刀杆） 干什么
B（主） 刀杆表面采样 → 毛坯 SDF，连续化 δ²/(2R) = 42 µm 0.48 ms 检出
A（辅） 毛坯体素中心 → 刀杆 SDF h/2 = 50 µm 1.30 ms 定位：报"毛坯上哪一块被啃了"

B 便宜 2.7× 且精度高两个数量级，所以 check_shank() 先跑 B；命中后 A 才跑一次， 把结果翻译成体素坐标。刀在空中时两者都是 AABB 预筛秒退（0.03 ms）。

只有刀杆算碰撞：ToolDef::shank（刃长以上那一段）。刀刃切材料是本职工作。

这里有个必须补的下界。 体素场的窄带只有 band 宽（默认 0.4 mm），带外一律返回 钳制的 +band；而采样间隙 δ 默认 0.5 mm。于是"采样最小值 − δ" = −0.1， 任何位置都算"无法保证"——保守推进退化成每段都报碰撞（实测：刀在毛坯上方 40 mm 空走也报）。补一条包围盒下界就好了：采样点全在其世界包围盒里，所以真实距离 ≥「采样点包围盒」到「场包围盒」的距离。同一趟遍历顺手拿到，不用多扫。

先试过"刀尖球"（半径 = reach，O(1)）：φ6×40 的刀杆要包在半径 40 的球里， 球一靠近就是 0，等于没兜。紧的下界必须是形状的下界，不是球的下界。

剖切平面：HTML 预览里能切开看内腔

五轴件的内腔不剖开根本看不见。预览页右下角的 HUD 加了一个滑块：

uniform float uClipZ;
void main(){
  if (uFlat == 1) { o = vec4(0.16, 0.19, 0.23, 1.0); return; }  // 地面先返回
  if (vP.z > uClipZ) discard;
  vec3 n = normalize(vN);
  if (!gl_FrontFacing) n = -n;   // 剖开后看得到背面
  ...
}

三处细节，缺一个都不对：

  1. 地面先 return 再 discard——否则滑块拖到负值地面就整片消失，看起来很怪。
  2. 背面法向要翻转（gl_FrontFacing）——剖开后看到的是内腔的背面，不翻的话两个 方向光都打不到，内腔一片死黑，等于没剖。
  3. 滑块范围取模型 z 包围盒（LO[2]-1 到 HI[2]+1），默认拖到最大 = 不剖， 标签显示 (关)。不写死数值，换个工件范围自动跟着变。

tools/check_preview.mjs 加了三条断言（滑块在、uClipZ 在、discard 在）—— 桩不做 GLSL 编译，所以只能查文本，真正的编译失败由页面的错误浮层兜住。

顺带修了桩的一个坑：原来所有 id 共用同一个 el 对象，缺 addEventListener， 加滑块后直接抛 clipEl.addEventListener is not a function。改成每个 id 一个独立元素 （更接近真实 DOM）。

增量重建：切一刀只重算被扫到的那几块

render::TileCache 是交互式仿真的核心：整体重提一次 200 mm 毛坯要 404 ms， 增量重建一次面铣只要 35 ms（11×），因为只重算 66 / 4017 块。

三条规矩，每条都是踩过坑的：

  1. 分块提取不能有缝：voxel::extract_surface_lod_in 按"发射格"划分——每个四边形 由最小角所在的格发射一次，各块天然不重不漏。有一条测试把整块毛坯切成小块逐块提取， 与整体提取逐三角形比对（坐标按位比较），一处都对得上。
  2. 替换范围要比提取范围小一圈：三角形按质心归属块，而区域边上的格会发射质心 落在区域外的三角形。所以提取范围比"要替换的块"再外扩一块，边界上那些半残的块 直接扔掉——它们离切削足够远，本来就没变。
  3. 没变的块不重传：提取结果逐字节与旧的比，一样就保留版本号；被整块切光的块 从缓存里删掉。上传受 8 MB/帧 预算限制，没传完的要记在队列里——不记的话 "下一帧再传"是假的：下一帧重新提取发现内容没变，那些块永远不会出现在屏幕上。

顶点色也接进了材质：MeshData.colors 的 [调色板索引, 余量偏差+128, …] 编码 （ADR-005）在预览着色器里按调色板展开——R 是索引不是红色分量，G 是偏差。

kin 闭环：G 代码位姿 → 逆解 → 正解

在 sim 的集成测试里（tests/kin_loop.rs，放装配层是因为 kin → gcode 会违反 依赖方向）：解释器算出的每个位姿都要能被机床逆解、正解回到原点、A=0 奇异点要被 check 报出来。

这一片抓到一个真 bug：kin::inverse 的残差用的是 cur × target（叉积）。 叉积在反平行时也归零，而且它指向"转轴"方向，与雅可比的列（轴的切向）正交—— 在 A=0 的奇异点上两者点积恒为 0，牛顿一步都迈不出去，48 次迭代后报"不可达"。 实测：从 A=0 起步解 A=20 的刀轴，永远失败。改成 target − cur（误差向量，与雅可比 同处切平面）后，5 条闭环测试全绿，原有的 500 例随机往返不受影响。

设计比对：过切 / 残留（sim::compare，10 个测试）

程序跑完之后回答最后两个问题：该切掉的是不是都切掉了（残留），不该切的是不是没切（过切）。 比对对象是设计成品——v1 只有轴对齐盒（DesignModel::Box），但口径是通用的：

指标 方法 精度
过切/残留体积 体素积分：毛坯场符号 × 设计 SDF 符号 ± 一个表面层
过切最大深度 解析扫掠点测试：设计面采样点 × 每段 sd_sweep 掠切 ±5 µm（黄金分割收敛限），不经过体素
残留最大厚度 设计气区内材料体素到设计面的距离 + h/2 ± h/2 = 0.05 mm 级 @ h=0.1
过切区域 过切体素的包围盒 一眼看出是哪个特征切多了

为什么过切深度不走体素：i8 量化档 3.15 µm，0.01 mm 的判定会被量化噪声淹没； 解析测试直接问"设计面上的这个点是否曾被刀具包住"（sd_sweep(p) < 0）， 精度只受黄金分割收敛限制。每点先用段扫掠 AABB（外扩 tol）预筛，78k 点 × 110 段也只有几十毫秒。

一个从测试里逼出来的语义坑：盒 SDF 在孔底给的是"到最近的盒面"的距离—— 孔从设计顶切到 z=3（低于顶面 8 mm），SDF 却说 −3.05（到盒底）。 所以"过切体积深度"对贯穿特征会饱和在设计体的内切圆半径上，是个语义混乱的指标。 报告改说过切区域包围盒（gouge_region）：区域 x 5.1..25.0 y 5.1..25.0 z 3.1..11.0 ——直接指出是方槽和孔切进了设计体。

残留的口径：设计气区里的全部材料都算残留，不限工具走廊——设计说"这里不该有料"， 它就是多余的，无论程序有没有试图去切。距离场在材料区内随远离设计面单调增， 最大值自动落在某个表面上（毛坯表面或切削面），所以不需要显式的表面体素判定； +h/2 把体素中心修正到表面位置。

一条强性质测试：完美的面铣（刀底平面 = 设计顶面）过切必须是精确的 0—— 共享边界上毛坯 SDF 与解析设计 SDF 的符号逐体素一致，一层都不该判进去。 实测通过（体素积分与解析测试双双为 0）；切深 0.5 mm 时体积 62.1 mm³（理论值）， 解析深度 0.5 ± 0.005，报警带块号与源文件行号。

报警编号：GOUGE（Error，零件报废）/ RESIDUAL（Warning，没铣到位）/ NONLINEAR（Warning）。

非线性误差：关节空间线性插补的刀尖偏离（kin::nonlinear_error）

五轴联动的经典陷阱：控制器若按关节空间线性插补执行（每个插补周期把 5 个轴各走一步）， 刀尖走的是绕回转中心的空间曲线，偏离 CAM 意图的直线。闭式公式：

非线性误差 ≈ R · (1 − cos(Δθ/2))        # 弧与弦的拱高
  • 口径：默认模拟无补偿裸插补（最坏情况），用来判断后处理的点位密度够不够 （Δθ_max = 2·acos(1−ε/R)：R=175 时 ε=0.01 mm → 每段 ≤1.22°）。RTCP 开启时 控制器在位姿空间插补、刀尖走直线，这一段误差为零——本函数算的是"不补偿会偏多少"。
  • 只用正解：关节值由 sim::run 逐块调 inverse 拿到（上一块的解做下一块的 种子，解不出就复位），函数本身只做 forward 采样（默认 32 点）。
  • 两个早退：旋转轴全程不动 ⇒ 链变换是"常量旋转 × 直线轴仿射"，刀尖恰在弦上， 误差恒 0——三轴程序连采样都不做；起讫点重合（纯回转、刀尖定点）时弦退化为点， 改量到点的距离，不能除零。
  • 闭式对拍到 1e-9：单旋转轴机床，刀尖 (0,0,R) 转 30°，最大偏差必须精确等于 R(1−cos 15°)，出现在 t=0.5。

RunConfig 接线：machine: Option<MachineTopology>（None = 不算，三轴用户不该看到 这个指标）、nonlinear_samples。超 0.01 mm 报 NONLINEAR 报警，worst_pose 记 峰值时刻的实际刀尖位置，max_nonlinear_line 指回源文件。

演示（--export，AC 双转台 L=180）：A 摆 20° 的块，R ≈ 265 mm → 误差 4 mm 量级， 报警直指那一行——后处理该加密点位了。

后台任务与回放（sim::job + sim::playback，12 个测试）

sim 的 crate 文档从第一天就写着"仿真调度、回放缓冲、后台线程"——现在才真正兑现：

  • run_observed（run 变成薄包装）：每块开始前回调一次观察者，返回 false 取消。 观察者只读——同一份输入带不带观察者输出逐位相同（测试锁）。 取消落在块边界，报告从部分状态定稿（体积/报警如实），追加 CANCELLED Info 报警。
  • SimJob：整段仿真挪到工作线程，mpsc 回报 Started → Progress* → Done。 进度按墙钟节流 50 ms（块 0 必发）；Drop 取消并 join，绝不泄漏线程。 异步跑完的结果与同步 run 逐位一致（同一代码路径，测试锁住）。
  • Playback：块 → 时间区间的预计算，与 run 同一套时间口径（同样的圆弧离散、 同样的 segment_time、同样的 M0/M2/M30 截断）。所以 total_time() 与 report.programmed_time_s 逐位相等——报告说 8.64 s，时间轴就必须能拖到 8.64 s。 at(t) 做二分 + tip 线性 + 刀轴 slerp；越界钳制。
  • Hmi::ingest(report)：报警入队（不清旧——多版对比是常见操作）， 有 Error+ 进 Faulted，只升不降（要 reset() 才能离开）。

现在 UI 只差窗口：时间轴拖 Playback::at、进度条接 SimJob 事件、报警列表接 ingest。

解释器问题进报告（Trust 打通）

解释器遇到不认识的代码不中断——跳过、继续、并记一条 ParseIssue（稳定编号 + 严重度 + hint）。 但这套信息之前到不了用户手里：报告只有一个笼统的 GCODE_ERROR 聚合报警，还硬编码 Fatal—— 把 Warning 级的"未知 M 代码"和 Error 级的"圆弧缺圆心"混成一锅。

现在 sim::run 把每条 issue 逐条映射成报警：编号原样（GCODE-008 就是 GCODE-008， 测试断编号不断言文案）、严重度 1:1（两层的 Severity 有意不共享，但四级语义一致）、 行号进 TimeRef（跳回源文件）。overall_severity() 自动给出总体可信度。 外加一条保险丝：解释器判了 Unreliable/Aborted 而报告里却没有 Error+ 报警时（正常不会发生）， 兜底一条 GCODE_TRUST。

设计模型从 STL 加载（voxel::stl + voxel::meshvol）

DesignModel::Field：--design part.stl → 解析 → 体素化 → 与毛坯同网格的设计场。 比对代码一行没改——它只依赖 sdf(p) 和表面采样点。

  • stl 解析（7 测试）：二进制（84+50n 尺寸公式先行——不少二进制文件的 80 字节头 恰好以 "solid" 开头，按内容判别会撞坏，经典陷阱有测试锁）+ ASCII（令牌流，行号精确）。 零依赖；不读法向量（STL 的法向经常是错的）；f32→f64 保持逐位值。
  • meshvol 体素化（5 测试）：两个正交 pass—— ①符号：逐行视差。每行 (y,z) 固定，+X 射线与三角形 (y,z) 投影做 2D 包含测试， 交点排序后行走整行，奇偶定内外。对水密网格精确（凹形、多连通都行）； 每行加 ±0.0005h 的确定性抖动，避免射线恰好擦边。 ②距离：逐三角形把"AABB 外扩 band ∩ 域"内的体素精确化（点-三角形最近距离， clamped barycentric，与暴力采样 oracle 逐位一致）；带外的体素距离 ≥ band， 保持 ±band——与毛坯场的窄带钳制同语义。
  • 互证测试：同一个盒，解析 Box 设计与 STL 文件走完整链路的 Field 设计， 在同一个过切程序上数字一致（深度 ±0.005、体积同区间、残留同精度）—— 两条完全独立的路径互相是对方的 oracle。
  • 坑：桶插入必须每桶一次而不是每格一次——重复插入让同一平面产生几十个相同交点， 奇偶被两两抵消，整场判定为外（实测踩过，探针半小时）。

面板数据层：cncsim-ui 是纯函数，不是 bevy 系统

ui 之前是 28 行的空壳，而 render::shell 里的 egui 面板直接 match ControlState 画颜色——架构铁律第 6 条（ui 只依赖 hmi）形同虚设，因为没有任何东西需要 ui。

这一片把它做实，但刻意不写任何 egui::Ui：UiView 只返回 &'static str、 Tone、Vec<AlarmRow>。理由不是洁癖，而是可测性——

判据 为什么必须"是判据"
六种状态横幅文案互不相同 两态显示同一句话，用户分不出"在跑"和"卡住了"
四级严重度徽标互不相同 两级都用 [!]，"跑完看看就行"和"别上机床"就分不开
报警按严重度降序 一屏 30 条时，"最严重那条在哪"是判据问题不是排版问题
复位键只在卡死时亮 正常运行中摆个亮着的复位键 = 送一个误触机会
位置串是 t / 块 / 行 三元组 只有编号和消息的报警，用户知道错了但不知道去哪改

这五条全都能在没有显示器、没有 Bevy 的 cargo test 里锁定。改排布、改配色不会让测试变红； 改判据才会——这正是 UI 测试该有的信噪比。

render::shell 只做两件适配：Tone → egui::Color32（映射只有一处）、 AlarmRow → colored_label + weak 小字。报警列表因此多了位置与 hint 两行， 而这部分逻辑窗口版和预览版共用同一份。
