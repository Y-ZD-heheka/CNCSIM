## 这是什么

基于 **Bevy 0.20** 的五轴加工仿真与刀路验证工具。不是 CAM（不生成刀路），是**刀路验证器**：会不会撞、会不会过切、实际要跑多久、哪里会出问题。

**这是个人项目，公开只为方便分享与回溯，不提供任何形式的支持或担保。**

## 核心决策（一句话版）

| # | 决策 | 理由 |
|---|---|---|
| 1 | 引擎用 **Bevy 0.20**，UI 用 bevy_egui | 0.20 内置 CAD 相机，省两周 |

| 6 | 机床模型 = **运动学 / 外观 / 碰撞代理** 三表示一真相源 | 三者不可能互相说谎 |
| 7 | **先算后播**，不追求实时 | 五轴布尔物理上快不过真实加工 |

**`inverse()` 用解耦两步法**：Newton（阻尼最小二乘）解两个旋转轴 → 直线轴用 3×3 仿射一次解出。
**`rtcp_inverse()` 只解直线轴**——旋转角由程序给定，不求解。

**`check(topo, q, κ_limit)` 产出运动学诊断**：

```rust
KinFinding::NearSingular { kappa, a_deg }      // KIN-001，κ > 阈值
KinFinding::AxisLimit { joint, value, limit }  // KIN-002，超出行程
```

κ 用**数值雅可比的条件数** `σ_max/σ_min` 算，不是硬编码 `|sin A| < eps`——前者对任何「2 旋转」构型都成立。摇篮式 κ = 1/|sin A|：A=0 → ∞，A=90° → 1。

**一个刻意的设计**：`inverse` / `rtcp_inverse` **不检查轴限位**。
`None` 只表示"运动学上无解"（雅可比退化 / 不收敛）；超程用 `violated_joints()` 单独报。
两者对用户的含义不同，不能混成一个 `None`。

### 机床配置（`cncsim-config`，第 13 个 crate）

换机床**只改 RON，不重新编译**：

```bash
cargo run -- --machine assets/machines/ac_trunnion.machine.ron
```

**为什么单独一个 crate**：磁盘上的配置是**跨层的**——`chain` 归 `kin`，`parts` 归 `render`/`collide`，
`motion` 归 `sim`。让 `kin` 去读整个文件，它就得知道 `Shape::Box` 和 `ColliderSpec::Derived`，耦合立刻变高。
所以**只有 `config` 知道"文件长什么样"**，各领域 crate 只接收自己的类型。

v1 只解析运动学部分（`name` / `chain` / `tool_length` / `pivot_distance`），
`parts` 与 `motion` 被 serde 静默忽略——这不是遗漏，是分层：等 `render`/`collide` 有了自己的类型再在这里补，各层代码不动。

**校验的不是语法，是语义**：必须「2 旋转 + 3 直线」、限位不能反向、`sign` 只能是 ±1。

**一条锁漂移的测试**：`kin::MachineTopology::ac_trunnion()` 是测试用的硬编码夹具（测试不该依赖文件 I/O），
`hardcoded_matches_file` 断言它与真实 `.ron` **逐字段一致**。改了一处忘了另一处会立刻红——
已实测：把 A 轴 `sign` 从 −1 改成 +1，报 `关节 A 的 sign: left 1.0, right -1.0`。

| 项 | 规定 |

代价是 6 个传递包；已在 `check_deps.py` 的 `EXTERNAL` 表白名单登记，理由见 [ADR-009](docs/ADR-009-段内并行.md) §1.1。

`windows-link`（被 windows-sys 钉死 0.2）拖进依赖图，版本守卫因此长期红着。改成
`kin/tests/roundtrip.rs` 里 20 行 xorshift + **固定种子**——顺带把"每次随机种子、
失败了要等缩例"换成"同一份代码永远跑同一批数"。`Cargo.lock` 从 71 个包降到 29 个。

**L0–L3 中只有 `config` 与 `voxel` 碰外部 crate**——`math` / `motion` / `tool` / `kin` / `gcode` / `collide` / `sim` 仍是零外部依赖。
这条现在是**机器判的**：`check_deps.py` 的 `EXTERNAL` 表没有登记的依赖直接判违规退出码 1。
序列化只在**输入边界**出现一次，领域内核仍然只认自己的类型。

### G 代码解释器（`cncsim-gcode`，117 个测试）

**只做"文本 → 位姿"，不做运动学。** 一旦这里调 `kin::inverse`，解释器就绑死在某台机床上。

| 模块 | 职责 |
|---|---|
| `lex` | 一行 → 字序列（`letter, value`），处理 `(...)`、`;`、`%`、`*` 校验和 |
| `modal` | `GCode` 用**十分之一定点整数**存（`43.4 → 434`，不用浮点比较）、15 个 G 模态组、8 个 M 模态组 |
| `order` | 块内执行顺序（25 个 `Phase`），照搬 LinuxCNC 权威清单 |
| `interp` | 逐块 fold，产出 `Block` |

**两条从权威原文核实过的语义**（`refs/linuxcnc/overview.adoc`）：

1. **块内字序无关。** 原文："The first group (the words) may be reordered in any way without
   changing the meaning of the line." 所以 `G91 G1 X10` 与 `G1 X10 G91` **完全等价**。
   实现上不是靠代码摆放顺序，而是把一行里的操作收进 `Vec<Op>` **按 `Phase` 排序后执行**——
   顺序是结构保证，不是约定。
2. **组 0 轴字代码挂起组 1。** 涉及 G10/G28/G30/G52/G92。不实现则 `G28 X0 Y0` 之后会多走一段。

**文档更正两处**：早期设计文档说 `G91 G1 X10` 与 `G1 X10 G91` 结果不同（错），
以及把 G4 停延排在最后（错——权威清单里它在平面/单位/补偿/距离模式**之前**）。均已改。

**可信度分级**：跳过**影响几何**的代码（G41/G42 刀补、G5.x 样条、G10/G92 坐标修改、G68.2 倾斜平面）
会标 `Trust::Unreliable`——因为这些一漏，后面所有位置都静默偏移。跳过冷却/主轴这类不影响几何的则不标。

**每条 issue 都有稳定编号 + hint**：`GCODE-001`（未知代码）到 `GCODE-010`（组 1 被挂起）。
测试断言编号不断言消息文本，且有 `every_issue_has_a_hint` 作为质量门。

#### 五轴与隐式运动

| 能力 | 做法 | 关键坑 |
|---|---|---|
| **A/B/C 轴** | 解析成**绝对角**（弧度、模态、受 G90/G91 影响），刀轴由角度推出 | 同一个 `A30.` 在双转台和双摆头上刀轴**反号** |
| **G68.2 倾斜平面** | 折算成 `TwpFrame { origin, rot }`，作用在后续所有坐标上 | 绝对模式下没给的轴要保持**程序坐标**，不是工件坐标 |
| **隐式模态运动** | 只有轴字、没有组 1 的 G 代码时，按 `st.motion` 补一个 | `G68.2` 的 X/Y/Z 是平面原点，**不是运动轴字** |
| **M0/M1/M2/M30** | 记成 `StopPoint { block, line_no, kind }` | 它们常常独占一行，**不产生运动块**——挂在 `Block` 上会丢 |

**刀轴方向**由三步复合，顺序不能换：

```text
① 旋转轴：双转台用 Rᵀ·Z（工件转、刀轴在工件系里反向转），双摆头用 R·Z
② 倾斜平面：G68.2 的程序坐标系再转一次
③ 归一化
```

`R = Rz(C)·Ry(B)·Rx(A)`（ZYX 欧拉序，对应双转台 C 在 A 上面的物理堆叠）。
`Block.angles` 存**轴角**而不是方向——因为轴角无歧义，方向取决于机床构型。

**隐式运动是这一轮最要命的一条**：真实后处理的绝大多数行是这样的——

```gcode
G1 X10 F100
X20            ← 隐式 G1，必须走
Y5             ← 必须走
```

不支持它，整份程序只有"带 G 字的那些行"会动，**而且不报任何错**，只是切出来的东西不对。

**G68.2 的欧拉角**是 I→绕 Z、J→绕 X、K→绕 Y，复合顺序 **Z→X→Y**（Fanuc 原文）。

#### 固定循环：展开成真实刀路

**不能"跳过"，必须展开**：少钻一个孔，零件就是废的，而报告上看不出异常。

| 循环 | 展开成什么 | 差别 |
|---|---|---|
| G81 | 快移到孔上方 → 快速下到 R → 进给到孔底 → 快速退 | 一次扎到底 |
| G82 | 同上 + **孔底暂停 P** | 沉孔 / 锪平 |
| G83 | 每 `Q` 一刀，刀间**完全退到 R 平面**排屑 | 深孔 |
| G73 | 每 `Q` 一刀，刀间只抬 0.5 mm 断屑 | 深孔、行程短 |
| G84 | 进给进、**进给退**（主轴反转） | 攻丝 |
| G85 / G89 | 进给进、进给退 | 镗孔，孔壁不留退刀痕 |
| G86 / G88 | 进给进、快速退 | 镗孔，效率优先 |
| G76 | 同 G86（孔底让刀不建模） | 精镗 |

**模态是重点**：`G81 Z-10 R2` 之后只写 `X20 Y20` 就是"在那儿再钻一个"。孔阵列的
后处理几乎全是这种行——不认这一条，一个 20 孔的阵列只钻第一个。

```gcode
G0 Z10
G83 Z-8 R2 Q3 F100
X20          ← 第 2 个孔
X40          ← 第 3 个孔
```

**孔间横移发生在起始高度上**，不是 R 平面、也不是孔底——这是不撞夹具的前提。

`G98` / `G99` 决定每孔之间退到哪：`G98` 回起始 Z、`G99` 回 R 平面。一排孔用 `G99`
能省掉大量空行程（一维往返距离 ≤60%）。

**`P` 的单位由小数点决定**（Fanuc）：`P500` 是 500 毫秒，`P0.5` 是 0.5 秒。所以词法
层现在记录"这个数值原文有没有小数点"——丢掉它，孔底暂停会差 1000 倍。孔底暂停与
`G4` 的停延都进报告时间。

**不做的**：G87 反镗（从工件下方向上加工，本版运动模型不支持，报 `GCODE-005` 而不是
假装沿 Z 钻）；G76 的孔底让刀、G84 的主轴反转（不影响几何，只记在文档里）。

#### 坐标改写：G10 / G52 / G92

这三条**不动刀**，只改"程序坐标怎么映射到机床位置"。算错的话每一块的形状都对，
只是整体挪了位置——比少钻一个孔更难发现。

| 层 | 来源 | 怎么改 | 怎么取消 |
|---|---|---|---|
| **WCS 表**（G54–G59.3） | `G10 L2 Pn`（给机床坐标）/ `G10 L20 Pn`（对刀） | 写表 | 再写一次 |
| **G52 局部** | `G52 X..` | 就地叠加 | `G52 X0 Y0 Z0` |
| **G92 临时** | `G92 X..`（把当前位置读作给定值） | 就地叠加 | `G92.1` 清零 / `G92.2` 挂起 / `G92.3` 恢复 |

**三层分开存**，不是合成一个数：G10 写的是机床上的坐标系表（断电保存），G92 只是一次
临时平移。程序里看效果一样，取消方式完全不同——合成一个数就再也分不开了。

`G10` 改的是**解释器内部的副本**：`InterpConfig` 必须保持"程序的初始条件"，同一份配置
跑两遍要给出一模一样的结果。`G10 L20` 还要把 G52/G92 **减掉**——一次 `G52 X5` 之后
对刀，不减的话原点整整差 5 mm。

#### 刀径补偿 G41/G42：整份程序的后处理

不走 `step` 逐行处理，而是**解析完之后再跑一遍**——拐角补偿点取决于前后两段的方向，
逐行时只看得见本段。

| 顶点 | 处理 |
|---|---|
| 共线 | 直接过，法向偏移 r |
| **内角**（偏移侧在转弯内侧） | 两条偏移线求交 |
| **外角**（偏移侧在转弯外侧） | 绕顶点走一段 **r 圆弧** |

外角不能求交：两条偏移线在外侧的交点比顶点远 `r·tan(θ/2)`，90° 拐角就多切 **0.41r**。
真实机床是绕顶点滚过去的。

**正确性判据只有一条，但它覆盖全部**：补偿后每个刀位点到编程路径的距离**恒等于 r**。
内角求交错、外角圆弧错、法向取反、半径符号反，都会在这里红。

```
G41 D3 走 10×10 方框 → 刀心 x ∈ [3.0, 7.0]（内缩一个刀半径）
```

**边界（做不到就报，不猜）**：第一块/最后一块必须是直线（引入引出段）、只支持 G17、
只支持 G1/G2/G3。`D` 给的是寄存器号不是半径，表里没值就报 `GCODE-011` 并把 `Trust`
降级——当 0 处理会让整条路径差一个刀半径，而程序看起来完全正常。

### 稀疏体素（`cncsim-voxel`，56 个测试）

**存储层是地基，先树后算法。** 结构照搬 OpenVDB `Tree4<T,5,4,3>`（数字**从叶往根读**）：

```
root（哈希，通常 1 条）→ level2 32³ → level1 16³ → leaf 8³
```

**关键：每一级都能存 tile 值。** 这不是优化，是能不能表达的问题——

| 方案 | 200×200×100 毛坯（40 亿体素） |
|---|---|
| 只存叶 | 1560 万个叶，无法接受 |
| 叶 + 叶级 tile | 仍然 1560 万个 `Constant` 叶 |
| **三级都能 tile** | **root 1 条、叶 0 个、2.0 MB** |

实测（`cargo run` 会打印）：40 亿体素**分层填充 5.6 ms**，实心毛坯完全由 tile 表达。

**索引全是位运算，无哈希**：`ijk >> 12` 找 root、`>>7 &31` 找 level2 槽、`>>3 &15` 找 level1 槽、`&7` 找叶内体素；子节点取 `children[popcount(mask & 低位)]`。

**负坐标必须用算术右移与按位与**：`-1 >> 3 == -1`、`-1 & 7 == 7`，于是体素 `-1` 落在叶 `-1` 的索引 7。
用 `/` 和 `%` 会让 `-1` 和 `1` 落进同一格——已用测试 `negative_coordinates_use_floor_semantics` 锁住（把 `>>` 换成 `/` 会报 `left [0,0,0] vs right [-1,0,0]`）。

**`prune` 是正确性要求不是内存优化**：切空的叶若仍是 `Dense`，碰撞检测会认为那里还有材料。
测试 `prune_restores_constant_after_full_cut` 就是这条的存储层版本。

**`i8` / `i16` 是同一个泛型参数**，不是两套代码——`SparseGrid<i8>` 每档 3.15 µm，`SparseGrid<i16>` 12.2 nm（258×）。

**与影子模型对拍**：`traversal_matches_shadow_model` 用独立的 `HashMap` 做 oracle，3000 次随机写入（跨 level 边界、含负坐标）后逐点比对——不共享任何索引代码。

### 扫掠 SDF 与 CSG 去除（19 个测试）

材料去除就两步：

```
sd_sweep(p) = min_{t∈[0,1]} sd_tool(p, pose(t))      ← 扫掠体的有符号距离
d_new       = max(d_old, -sd_sweep)                  ← CSG 减法
```

**`min over t` 对凸刀具是精确的**：到沿直线平移的凸集的距离，是平移参数的凸函数，黄金分割能取到真极值。凹母线刀具（T 形刀、燕尾刀）不成立——v1 的刀型都是凸的。

**每次求值不算三角函数**（这一条省掉 ~20%）。原来 `eval(t) = sd_tool(p, lerp_pose(t))`，
而 `slerp` 开头就 `acos(dot)`——**刀轴根本没转也照算一次**。现在按"轴是否变"分两条路，
两条都把 t 的依赖提成标量多项式：

| | 每次求值 |
|---|---|
| 纯平移 | `z = z0 + zd·t`、`r² = a0 + b·t + c·t²` → **零三角函数**，一次 `sqrt` |
| 平移 + 转 | `cos(tθ)`、`sin(tθ)` 各一次（`cosθ/sinθ/u` 在循环外算好） |

顺带加了 `sd_profile_rz(r, z)`：内层已经有 `(r, z)`，不该再走一次 `hypot`（libm 调用，约 7 ns，
占平移路径单次求值的四成）。实测**每次求值 19.0 → 14.7 ns**（平移）、**32.5 → 21.0 ns**（带转）。

> 补了一条测试 `rotating_sweep_matches_sampled_oracle`：把 `sin_cos` 的返回顺序写反过一次，
> 当时**全部测试都是绿的**——因为它们只用 +Z 刀轴，而平移路径已经不碰三角函数了。
> 现在让刀轴转 30° 对拍暴力采样，故意写反会报「差 1.98 mm」。

**迭代次数必须按行程自适应（6–24 次）**，这是实测出来的：

| 行程 | 固定 6 次 | 自适应 |
|---|---|---|
| 0.05 mm（真实段长） | < 1 µm ✓ | 6 次，同上 |
| 200 mm | **16 µm ✗**（量化档的 5 倍） | ~17 次，< 5 µm ✓ |

迭代数只依赖几何（行程 + 刀半径），不依赖时间，**结果仍逐位可复现**。

**切完自动 `prune`**——切空的叶若不折叠，碰撞会认为那里还有材料（ADR-004 §5.4）。

**切削 AABB 必须外扩一个窄带宽度**（这一条是显示 LOD 逼出来的，见 ADR-008 §4）：
扫掠体边界就是新表面所在，所以"到新表面距离 < band"的体素一定落在"扫掠体 ∪ band 邻域"里。
不外扩的话，刀尖平面以下的材料侧只有 1 个体素拿到真实距离，往下全是切前的饱和值 `−band`——
**窄带单边完整等于没有窄带**，跨界插值会把表面往材料侧拽。
代价是遍历体素 +54%，但碰撞用的也是同一套插值（ADR-004 §2.5），所以这不是显示层的账。

**实测性能**（单线程标量 / 24 线程，release）：

| 场景 | 遍历体素 | 串行 | 24 线程 |
|---|---|---|---|
| 200 mm 直槽（φ6，切深 1 mm） | 2.07 M | 1002 ms | **117 ms**（8.6×） |
| 0.05 mm 段（**冷启动**，单段） | 35 k | 13.5 ms | **7.0 ms**（1.9×） |
| 200 段连续（预热后，每段均值） | 35 k | 0.44 ms | **0.18 ms**（2.4×） |
| 外推 10 万段（按预热后） | — | 0.7 min | **0.3 min** |

冷启动单段 7.2 ms 里有首次叶分配的页错误开销；连续跑时相邻段共用 AABB，
大部分体素算出来和原来一样，`set` 直接被跳过。短段性能的提升来自两条：
`FlatSweep` 特化（短段 90% 的叶落在端头圆帽区，共享路径够不着）与
blind 重算拆除（每段固定成本里最大的一笔）。

段间不能并行（第 N+1 段读第 N 段的毛坯），但**段内体素零依赖**：并行求值 + 串行落盘。
大扫掠（200 mm 直槽）剩下的 87 ms 是落盘（189 万次 `set`），Amdahl 上限就在那儿——
见 [ADR-009](docs/ADR-009-段内并行.md) §3.2。

比早期文档的 5 ms/段乐观估算慢 **1.5×**（并行后）——差距在 `sd_profile` 每次重算母线边距离，没有内联/向量化。那正是性能杠杆表里排第一的那项。

**"切一刀要多久"——纯 SDF 计算口径**（`tests/cut_perf.rs`，
30×30×12 毛坯、h=0.1、φ6 平底刀、切深 0.5 mm）。**不含转 mesh、不含渲染**：

| 刀长 | `cut_segment` 合计 | 遍历体素 | 程序时间 @F300 |
|---|---|---|---|
| 1 mm | **0.7 ms** | 60 k | 0.20 s |
| 10 mm | **0.6 ms** | 146 k | 2.00 s |
| 20 mm | **0.6 ms** | 242 k | 4.00 s |
| 28 mm（切满） | **0.7 ms** | 286 k | 5.60 s |
| 20 mm（切深 2 mm） | **0.7 ms** | 493 k | 4.00 s |
| 20 mm（空刀） | **0.17 ms** | 131 k | — |

口径：`cut_segment` 从调用到返回，**含求值 + 并行落盘 + 增量 prune，不含转 mesh、不含渲染**。
24 线程（8 P 核 + 8 E 核）。单刀数字有 ±20% 的运行间抖动（线程池唤醒延迟），看量级。

**比初版快 19 倍**（20 mm 一刀 11.9 → 0.6 ms）。十四个优化，按收益排序：

1. **blind 元数据的"每刀重算"整体拆除**——`prune_touched` 每刀把涉及的一级块全部
   重算 blind（4096 槽 × 512 体素），而 blind 在**全项目没有任何读取者**。
   铣光 200 刀实测这一项占 **272 ms / 344 ms（79%）**。改为"写时标脏（`u8::MAX`），
   离线 `prune()` 才重算"，铣光 **344 → 67 ms**。
2. **平底刀纯平移走闭式解**（`sd_flat_prism`）——扫掠体是"径向 2D 胶囊 × 轴向区间"
   的**笛卡尔积**，盒公式直接算，跳过 13 次黄金分割。`sd_sweep` 从 34 → 5 ns/体素。
3. **短段的端头圆帽特化**（`FlatSweep`）——单轴共享只对"刀心路径正上方"的叶成立，
   短段走刀（精加工 0.05 mm）时 90% 的叶落在端头圆帽区，全部掉进逐体素
   `sd_sweep_with`（VTune 实测占 50%）。把段级常量折叠成标量后每体素 ~15 次浮点，
   200 段小段 **55 → 34 ms**。
4. **行级分类**——平底刀沿单轴走刀时一行 8 个体素共用同一个 `sd`，一行只有三种
   命运：够不着（整行不碰）、埋在刀体深处（**整行一次 8 字节填空气**）、表面行
   （新值是行常量，逐点只剩一次比较）。粗加工里 75% 的体素走第二类。
5. **中转缓冲按上限预留**——`CutPart::pool` 从 0 翻倍长到 300 KB，中途要搬 600 KB；
   铣光实测 200 刀 **61 ms 花在 realloc**，比写叶本身还多。
6. **整块值的 arena**（`CutPart::pool`）——求值加速比 **4.8× → 5.6×**。
7. **增量 prune**（`prune_leaves`）——只折叠**真正写过的叶**，且直接吃叶**下标**
   （落盘本来就知道），不再按坐标回查三级（铣光 800 叶 × 67 ns = 54 µs/刀）。
8. **沿单轴走刀的截面共享**（`sweep_axis`）——见「沿单轴走刀」一节。铣光 **-15%**。
9. **叶级整块写回**（`LeafBlock` + `blit_leaf` / `blit_leaves_parallel`）。
10. **整叶短路走并行落盘**——有下标的叶不再走串行 `fill_leaf`，而是产出一份
    512 个同值的整块混进并行 blit 队列（`write_leaf_block` 识别全同值，落成
    Constant 叶，不碰分配器）；串行路径只剩"槽位还是 tile"的叶。
11. **`WriteCache` 块级缓存**——一个 level-1 块管 4096 个叶，落盘按 z/y/x 走时
    相邻叶几乎同块，命中跳过 root 哈希 + `ensure_l1`。
12. **量化系数外提**（`k_dist` / `k_value`）——`to_value` 每次都调 `band_mm()` 再做除法，
    逐体素两次调用；换成循环外算好的两个乘法。
13. **`set_cached` / `leaf_or_tile`**——跳过三级查找。
14. **AVX2 量化**（`update4_i8`）——4 路 SIMD 处理量化 + clamp。**只有 2.5%**，见下；
    行级分类（第 4 条）落地后已删除。

**四件要记住的事**：

1. **耗时由 AABB 决定，不由"走了多长"决定。** 1 mm 的刀也要 0.52 ms。
2. **空刀很便宜**（0.28 ms）：值没变，落盘全跳过；求值仍要跑。
3. **短刀并行效率差**：1 mm 段只有 14 层可切（`nz < 2×线程数`）。
4. **首次一刀的 `changed` 大多是"从饱和值 −127 变精确窄带值"**，不是变空气。

演示程序 53 个切削段共 **33 ms**，**平均每刀 0.62 ms**。

### 批量切削：`cut_batch`——多刀一次遍历

仿真主循环必须**一刀一刀切**（每段之后要拿当前网格查碰撞），那是 `cut_segment`。
但"只关心最终形状"的场合（粗加工预览、材料去除率、过切检查）可以攒批：
`cut_batch(&[(from, to)], profile)` 一次遍历套完一批刀路。

**语义**：与按顺序逐段调用 `cut_segment` **逐位相同**（`tests/cut.rs`
`batch_matches_one_cut_at_a_time` 逐体素对拍，铣光场景抽查 1 万点 0 差异）。
原理：CSG 是 `max`（交换律 + 结合律）且量化幂等，批内段顺序不影响结果；
批量只是把"每个叶从树里取 k 次、写回 k 次、prune k 次"变成各 1 次。

**实测**（50×50×100 铣光 200 刀，见 `tests/millout.rs`）：

| 方式 | 耗时 | 每刀 |
|---|---|---|
| 逐刀 `cut_segment` | **48 ms** | **0.24 ms** |
| 按层攒批（20 批 × 10 刀） | 26 ms | 0.13 ms |
| **整批一次（200 刀）** | **16 ms** | **0.08 ms** |

批越大省得越多：批量把 AABB 取并集后一次并行求值，落盘、prune、线程派发各付一次。
代价是**批内不能插入别的操作**——碰撞检查、进给采样都得等整批切完。

### 建场：只扫表面壳 + 并行求值

毛坯初始化（`fill_box_exact`，写精确盒 SDF 的边界壳）原本遍历 `[lo−pad, hi+pad)`
的**整个立方体**：50×50×100 的毛坯是 **3125 万**次盒 SDF 求值，其中 **99.7% 算完
就被 `|d| < band` 丢掉**（内部一律饱和、远处一律背景）。

两个改动：

1. **只扫 6 个面片**（各 `pad` 层厚）——采样量 3125 万 → **330 万**（363×）。
   棱和角会被两个/三个面重复扫到，值相同，重复写无害。
2. **并行求值、串行写盘**——盒 SDF 是纯函数（只依赖坐标），按 z 切片并行算；
   写入受树结构限制只能串行。

| | 改前 | 只扫表面壳 | + 并行求值 | **+ 按叶写回（2026-11-01）** |
|---|---|---|---|---|
| 50×50×100 建场 | 145 ms | 84 ms | 56 ms | **14 ms** |

**这是本轮最大的一笔**（`fill_box_exact` 一次性的，但铣光场景里它占三成时间）。

### 几个"以为有用、实测没用（或帮倒忙）"的优化

诚实记录，免得以后重犯：

| 改动 | 预期 | 实测 |
|---|---|---|
| 饱和捷径：`−sd ≥ band` 时直接写 `S::MAX`，跳过 round/clamp | 省 75% 体素的量化 | **0%** |
| 内联 `sd_flat_prism`（叶在段内时省掉 `origin_to_segment` 的 clamp） | 省函数调用与分支 | **0%** |
| AVX2 4 路量化（`update4_i8`） | 4× 算术 | **2.5%** |
| 预创建 AABB 内所有叶，让落盘全走并行 | 落盘并行化 | **-1%**（预创建付 750 次三级查找/刀） |
| `blind` 元数据（块内最近表面距离下界） | 查询时跳块 | **从未接线**——无读取者，维护却占每刀 79% |

前三条都指向同一个结论：**切削循环的瓶颈是访存，不是算术**。
每体素 `3 ns` 里，读 `vals`、写 `vals`、`d_cur < band` 的比较、`nv != cur` 的比较
才是主体；`sd_flat_prism` 本身只占 2%（VTune 实测），量化也只有个位数。
SIMD 打的是算术，靶子选错了。行级分类（整行填空气 / 整行跳过）之所以有效，
正是因为它减的是**访存与分支**，不是算术。

后两条是另一个教训：**先确认有读取者，再决定维护成本**。`blind` 重算在
VTune 里根本不显形（它是干净的顺序扫描，没有 cache miss），只有
`CNCSIM_PROF` 的阶段计时把它揪出来——铣光 200 刀 344 ms 里占 272 ms。

AVX2 路径已随行级分类删除（它服务的"表面行逐点量化"现在每行只算一次 round）。


### 沿单轴走刀：SDF 在走刀方向上是常数

立铣刀的绝大多数切削是**沿一个轴走直刀**（x 或 y）、刀轴竖直不动。这时扫掠体是
"圆柱沿该轴拉伸"，而 `sd_flat_prism` 的公式里：

```text
dz  只依赖 z           ← 与走刀方向无关
dr  是到走刀线段的距离  ← 叶完全落在段内时退化成 |py|，与走刀方向无关
```

**所以叶完全落在走刀段内时，SDF 只取决于截面 (y, z)。** 叶的 512 次求值降到
**64 次**（8×8 截面），沿走刀方向原样复用。

```text
沿 x 走刀：每个 (y,z) 算一次 sd → 内层 8 个 x 复用      512 → 64 次
沿 y 走刀：每层 8 个 x 算 sd → 中层 8 个 y 复用          512 → 64 次
```

条件刻意保守，任一不满足就回退通用逐体素路径：

- 刀轴**竖直**（±Z）且两端一致
- 位移**只沿一个轴**（斜向进给时径向和轴向共享同一个 t，没有这个性质）
- **不是沿 z**（钻孔的扫掠体沿刀轴延伸，不是横向拉伸）
- 叶**整个落在走刀段内**（跨段边界的叶两端有端盖效应）

**正确性锁**：`tests/cut.rs::axis_sharing_matches_general_path` —— 同一条扫掠线
一次切完（走共享路径）vs 拆成五段（叶跨段，走通用路径），几何等价，
**逐位相同**（抽查 1.4 万个体素）。全库 16 个 cut 测试也都走 x 轴，双重覆盖。

**收益**（实测）：铣光 434 → **371 ms**（-15%），20 mm 一刀 0.97 → 0.84 ms。
没有预期的 8×，因为 `sd_sweep` 只占串行开销的约 26%——剩下是体素值读写、
量化转换、循环开销，这些按体素算，省不掉。


### 多线程：无锁、数据竞争隔离

**结构**：求值并行 + 落盘并行，两段都**没有锁、没有原子操作、没有 CAS 重试**。

| 阶段 | 并行方式 | 争用点 |
|---|---|---|
| 求值 | 按**叶层最多的轴**切片 → rayon `map_indexed` | 只读树 + 各片自己的 arena |
| 落盘 | 按叶索引排序 → `par_chunks_mut` 切段 → 每线程写自己那段 | 无（段物理不相交）|

**伸展性**（20 mm 一刀，`CNCSIM_THREADS` 扫描）：

| 线程 | 1 | 2 | 4 | 8 | 16 | 24 |
|---|---|---|---|---|---|---|
| 耗时 | 4.80 ms | 2.63 | 2.13 | 0.93 | 1.08 | **0.85** |
| 加速 | 1× | 1.8× | 2.3× | 5.2× | 4.4× | **5.6×** |

**为什么是 5.6× 而不是 24×**：i7-13700K 是 **8 P 核 + 8 E 核**（24 逻辑线程）。
8 线程时全是 P 核，5.2× 已经贴近 8 个物理核的上限；再往上 E 核频率低一半，
加上调度开销，16 线程反而略慢（1.08 > 0.93）。**这已经是这台机器的硬件上限附近**。

**踩过的两个坑，都是"看起来并行、实际不并行"**：

1. **分片轴选错**。为让整块写回生效，分片改成按叶层切——但 z 方向只有 5 个叶层，
   片数被 clamp 到 5，**24 线程只有 5 个在跑**（求值只加速 4.9×）。
   改成按"叶层最多的轴"切（铣光的 AABB 是 284×34×38，x 方向 36 个叶层）才喂满。
2. **每叶一次 `malloc`**。整块缓冲原本是每叶一个 `Box<[S; 512]>`，一刀 3920 次分配，
   24 线程并发打到同一把分配器锁上——**加速比卡在 4.8×，8 线程之后再也不涨**。
   改成每片一个大 `Vec`（arena）+ `LeafBlock::offset` 之后，24 线程到 **5.6×**。

**顺带一个反例**：试过在切削前**预创建** AABB 内所有叶，好让落盘全走并行路径。
实测是负优化（铣光 439 → 444 ms）——arena 之后落盘已经不是瓶颈，预创建白付
每刀 750 次三级查找。已回退，代码里留了注释。

#### VTune 实测（2026-11-01，VTune 2026.4）

对铣光 200 刀跑 `hotspots` + `threading`（release 开 `debug = 1` 保行号，不影响优化）：

**抓到一个真 bug**：`Total Thread Count: 50`。rayon 池应该是 24 个线程，
多出来的 24 个是 `blit_leaves_parallel` 里直接调 `par_chunks_mut` ——
它落在 rayon 的**全局池**上，而 `par::pool()` 是自建的**独立池**，
于是进程里同时存在两个 24 线程池，抢 24 个核：

```text
Thread Oversubscription: 88.3% of CPU Time   ← 修复前
Total Thread Count: 50
```

包进 `crate::par::pool().install(...)` 之后降到 **26 个线程 / 79.5%**。
（`par.rs` 里 `pool()` 用 `ThreadPoolBuilder::build()` 而不是 `build_global()`，
任何绕过它直接调 rayon 的地方都会另建全局池——这是个容易反复踩的坑。）

**CPU 利用率只有 6.8%**（24 个逻辑核平均 1.6 个在跑）。原因不是并行写错，
而是**这个负载太小**：

| 环节 | 耗时 | 并行度 |
|---|---|---|
| 建场（精确 level set） | 145 ms | **串行**（1 线程）|
| 切削 200 刀 | 374 ms | 每刀 1.87 ms，切 36 片 → 每片 **52 µs** |
| 抽查 10830 点 | ~30 ms | 串行 |

`rayon` 的 worker 从休眠到干活要 10–50 µs，和每片 52 µs 同量级——
所以线程大部分时间在 `WaitOnAddress`（hotspots 里占 28.6%）。
**这不是浪费，是任务粒度决定的**：绝对时间确实从 4.8 ms 降到 0.84 ms，
但利用率上不去。要更高只有两条路：把多刀批量提交（有数据依赖，难），
或者接受这个粒度。

**热点分布**（内联后按符号拆开）：

| 符号 | CPU 时间 | 说明 |
|---|---|---|
| `WaitOnAddress` + `Condvar::wait` | 39% | 线程池等待（上一条）|
| `f64::min` / `f64::max` | 19% | `sd_flat_prism` 的盒公式（内联后拆出来了）|
| `magnitude` + `slice::fold` | 6% | `blind_min_abs` 与体积统计 |
| `sd_sweep_with` | 2% | 扫掠 SDF 本体（大部分已内联进 min/max）|
| `write_parts` | 4% | 落盘 |

`min`/`max` 占 19% 说明**瓶颈已经从"算 SDF"转到了"逐体素的数值处理"**——
这也解释了为什么沿轴共享 SDF 只有 15% 收益（`sd_sweep` 本身已不是大头）。

**memory-access 采集不可用**：需要 VTune 采样驱动 + 硬件 PMU，
本机装了驱动（`amplxe-sepreg -i`）仍报 "Cannot collect memory bandwidth data"，
多半是虚拟化环境拿不到 PMU。用流量估过：每刀读写约 1 MB（叶 + arena），
1.87 ms → 约 0.5 GB/s，远低于内存带宽，**不是带宽瓶颈**。


### 叶片级优化：刀具只碰到表面那一薄层

直觉上"刀只跟工件的一小片接触，应该只处理那一小片"。实测下来这个直觉**部分成立**，
但落点不在"少算体素"，而在**访存形态**：

50×50×100 铣光、h=0.2、φ6 刀（刃长 6）：每刀 AABB 是 56.8×6.8×7.6 mm = **38 万体素**，
其中真正被切掉的是 5 mm 深 × 6 mm 宽 × 56 mm 长的一条，**23 万个体素确实要改**
（体积算下来 1680 mm³ ÷ h³ = 21 万，对得上）。所以这个场景里没有"算了白算"的余地。

浪费在别处：**改动的表达方式**。

| | 散点（旧） | 整块（新） |
|---|---|---|
| 每条记录 | `([i32;3], i8)` = **16 字节** | 512 字节 / 叶（`n` 条共用） |
| 一刀 23 万改动 | **3.4 MB** 中转缓冲 | 900 叶 × 0.5 KB = **450 KB** |
| 写回 | 23 万次「算下标 + 写 1 字节」 | 900 次 `copy_from_slice` |

3.4 MB 超出 L2，求值时读过的叶到写回时已经被挤出去，**同一个工作集被扫了两遍**。
改成整块之后，叶内布局 `x | y<<3 | z<<6`（x 最内层）让本地缓冲的读写都是**严格顺序**的。

**必须配合的一处改动**：z 方向的分片要按**叶层**切，不能按体素层。
按体素层切 48 片时每片不足一个叶层，每个叶都被切成残块，整块路径一次都走不到
（实测 `整块 0 叶 / 散点 21 万条`，改了 3 行才好）。

**收益**（`crates/voxel/tests/millout.rs`）：

| | 散点 | 叶层分片 + 整块 | + 整块 arena |
|---|---|---|---|
| 铣光 200 刀，切削 | 687 ms（3.43 ms/刀） | 601 ms（3.00） | **434 ms（2.17）** |
| 演示程序 53 刀 | 82 ms（1.55 ms/刀） | 69 ms（1.31） | **37 ms（0.70）** |

**顺带修掉一个真 bug**：`SparseGrid::leaf_slot` 收叶坐标，却把 `root_coord` / `l1_coord` /
`l1_slot(leaf_coord(..))` 都按体素索引算了一遍——坐标一大就定位到错的槽。
小域里恰好偏移为 0，所以一直没暴露；`prune_touched` 折错了叶，`cut_prunes_fully_removed_leaves`
当场抓到。


### 第二轮落盘优化：并行写其实是负优化（2026-11-01）

上一轮把落盘从"散点写"改成"整块并行写"，这一轮用 VTune + 零开销计时重新量了一遍，
**推翻了自己的两个结论**。

#### 先修测量方法，否则量到的都是噪声

原来每刀 `eprintln!` 打印 eval/write 拆分。问题是**格式化 + stderr 写的开销
比被测对象还大**（一刀总共 0.28 ms，一次 eprintln 就要几十 µs）。于是：

- 拆出来的 `write` 占了 90%，而实际上它是被打印自己撑大的；
- 我据此认定"整叶短路（`fill_leaf`）占 18 ms / 32%"，
  花了两轮优化它（tile 直接改值、`count_ne` 分块计数）——**实测它只有 1.9 µs/刀，0.4%**。

改成 `AtomicU64` 累加（~1 ns/次），跑完一次性读，数据才对得上：

```text
20 轮 × 200 刀 = 4000 刀，墙钟 1943 ms
  eval  413 ms（21%）   write 613 ms（32%）   其余 916 ms（建场 47 ms × 20）
  write 内部：whole 7.4  collect 206.6  sort 20.7  blit 219.4  prune 140.6
```

**教训：性能测量的工具本身要先验一遍。** 一个每刀都打印的诊断开关，
测出来的分布一定偏向"打印"而不是"计算"。

#### 真凶：`blit_leaves_parallel` 在小批量上比串行慢 8.4 倍

`CNCSIM_THREADS=1` 一跑，`blit` 从 **202 ms 掉到 24 ms**：

| | 24 线程 | 1 线程 |
|---|---|---|
| `blit` | **202 ms** | **24 ms** |
| `collect` | 200 ms | 146 ms |
| `prune` | 81 ms | 41 ms |

逐刀只有约 500 块 × 512 字节 = **256 KB**，串行写 6 µs（每块 12 ns，源和目标都在 L2）。
而 24 线程 fork-join 光唤醒就 15–50 µs，再加分派和每线程的冷 cache——**并行纯亏**。

修法是加一个**按总字节数**的门槛（不是按块数：`i16` 时一块是 1 KB）：

```rust
const PAR_BLIT_MIN_BYTES: usize = 1 << 20;   // 1 MB 以下走串行
```

只有批量攒到几 MB 时并行才回本。**这是"任务粒度小于调度开销"的又一个实例**，
与 VTune 里 `WaitOnAddress` 占 57% 是同一个病根。

#### 其余四项（按收益）

| 改动 | 收益 |
|---|---|
| **并行写加 1 MB 门槛** | `blit` 202 → **50 ms**（-75%） |
| **`uniform_value` 改 8 字节块比较**（`prune` 每刀调几千次） | `prune` 141 → **78 ms**（-45%） |
| **`collect` 三个 Vec 预分配 + 去掉 O(n) 的 `l1s.contains`** | 单次 `collect` 505 → **70 µs**（7×） |
| **`fill_box_exact` 的 `out` 按片内面片体素数预分配** | 建场 realloc 减少（但墙钟影响小，见下） |

**一个必须诚实说明的负结果**：把 `part.whole` 的预留从 `max_leaves/8` 提到
`max_leaves`（原来只留 69 个、实际用 580 个，翻倍 realloc 三四次），
**实测反而慢了 3 ms**——多分配的成本超过了 realloc 的节省。
所以这一项回退了。**"预留了个零头"确实比"完全不预留"更糟，但"预留到满"也不一定更好**，
得实测。

**VTune 的一个陷阱**：`__rdl_realloc` 占 CPU 时间 4.5%，看起来很大，但那是
**所有线程的 CPU 时间之和**（16 s），墙钟只有 2.2 s。realloc 分散在 48 个并行片上，
换算到墙钟只占 5%。**有并行时，CPU 时间占比不能直接当墙钟占比。**

#### 结果

| | 改前 | 改后 |
|---|---|---|
| 铣光 200 刀逐刀 | 56 ms（0.28 ms/刀） | **48 ms（0.24 ms/刀）** |
| 铣光 200 刀整批 | 18 ms | **16 ms** |
| vs OpenVDB 合计 | 7.4× | **8.0×** |
| 4000 刀累计（含建场） | 1943 ms | **1669 ms**（-14%） |

**瓶颈已经全部转移到"写叶"本身**：`collect`（新建叶 200 ms）+ `blit`（写叶 50 ms）
占 write 的 72%，都是不可避免的 512 字节搬运。再往下只有改数据布局（比如让叶不再是
`Box<[S;512]>` 而是一段连续 arena），那是另一个量级的改动。

### 建场按叶写回：532 万次单点写 → 1.5 万次整块写（2026-11-01）

上一节把切削从 56 ms 压到 48 ms 之后，**建场（47 ms）反而成了最大的一项**。
`CNCSIM_PROF=1` 的建场拆分把问题指得很清楚：

```text
20 轮：eval 126 ms   write 615 ms   prune 92 ms      ← 写入占 69%
写入 532 万个体素 / 31 ms = 5.8 ns/次
```

每次 `set` 只写 **1 个字节**，却要走一次三级查找 + 缓存判断。而边界壳的体素
**天然按叶聚集**（一片 8³ 叶里平均有 532 个体素要精确化，接近满叶）。

改成**按叶遍历**：

1. 枚举 6 个面片覆盖的叶（棱角处会被两三个面重复枚举，`sort + dedup` 去重）；
2. 每叶先按现状取一份 512 值作初值（`tile` / `Constant` / `Dense` 三种都要处理——
   叶内**不在面片上的体素必须保持原值**，这是最容易写错的地方）；
3. 只覆盖落在面片上的那些体素，`any` 标记"这片叶有没有改到"；
4. 一次 `blit_leaf` 整块写回。

**一个必须处理的细节**：去重不能省。并行时同一片叶被两个面各处理一次，第二次
读到的是**第一次之前的旧值**，后写的会把前面的精确值覆盖掉——而结果看起来
"大部分是对的"，只有棱角上几十个体素错。

**第二个细节**：末尾的 `prune()` 改成增量的 `prune_leaves(&touched, &[])`。
全量版要遍历整棵树 + 重算所有 level-1 的 blind，而建场刚结束时树里只有
`fill_box` 造的 tile（不需要折叠）和这里刚写的边界叶（`any` 保证**不可能全同**）。
实测全量 prune 4.7 ms/轮，占建场剩下的四分之一。

| | 改前 | 改后 |
|---|---|---|
| 建场（50×50×100 @ h=0.2） | 47 ms | **14 ms**（-70%） |
| └ 求值 | 6.3 ms | 4.0 ms |
| └ 写入 | **30.8 ms** | **3.0 ms** |
| └ prune | 4.7 ms | **0.3 ms** |
| 4000 刀累计（含 20 次建场） | 1674 ms | **998 ms**（-40%） |
| vs OpenVDB 合计 | 8.0× | **12.3×** |

**安全网先于优化**：改之前先补了一条 `fill_box_exact_matches_pointwise_reference`
——对 3 万多个体素逐个比对解析盒 SDF 的期望值（含带内、带内材料、带外背景三种情形）。
之前只有精度测试（看过零点位置）和 OpenVDB 对拍（看三个过零点），**没有一条测整场**，
"某片叶没写进去"只会表现为精度测试偶然通过。

写这条测试时第一版就把期望写错了：以为盒外是 `0`，实际是 `+MAX`
（`SparseGrid::new` 的 `background = S::MAX`——SDF 语义里"没有数据"就是"没有材料"）。
测试当场报「盒外应为 0，实际 127」，**说明它真的在逐体素比对**。

**这些数字有一个 ±15% 的机器波动**：同一份代码、同一台机器，连续跑几十轮之后
CPU 降频，铣光逐刀从 **47 ms 涨到 56–65 ms**、建场从 14 涨到 18–21。
所以**单次测量不可信**——A/B 对比要在同一时间窗口交替跑，或者看 `perf_cut_loop`
的 20 轮累计值。这条本身就是一次教训：我有两轮"优化后变慢"其实是降频造成的假象。

### 水平集 → 网格：三轮提速 28%（2026-11-01）

细格提取 200 mm 毛坯（3200 万面）原来 **798 ms**，VTune 一跑，热点全在"重复走三级查找"上：

| 符号 | CPU 时间 | 占比 |
|---|---|---|
| `WaitOnAddress` | 13.2 s | 线程空闲 |
| **`SparseGrid::get`** | **12.0 s** | **27%** ← 最大实际热点 |
| `vertex_batch` | 6.6 s | |
| `vertex_of` | 6.0 s | |
| `CellMap::get` | 3.6 s | |
| `corner_index` | 0.63 s | |
| `realloc` + `copy` | 1.1 s | |

**根因**：每片叶要填一个 `10³` 的 halo 缓冲，**1000 个体素逐个走 `get()`**——
每个都是一次 `root` 哈希 → level-2 → level-1 → 叶。而其中 512 个就落在当前叶里。

#### ① 主体 512 从当前叶一次读（798 → 709 ms）

```rust
match self.leaf_view_with_slot(base).0 {
    Some(LeafView::Leaf(Leaf::Dense(a))) => {   // 512 个值直接读缓冲
        for hz in 0..8 { for hy in 0..8 { for hx in 0..8 {
            let d = self.to_distance(a[hx | (hy << 3) | (hz << 6)]);
            ...
```

顺手把 `lo/hi`（判"叶内有没有符号变化"）在填充时累加，省掉后面单独扫 512 个值。

#### ② halo 的 6 个面按邻居叶整面复制（709 → 645 ms）

剩下 488 个 halo 体素里，384 个落在 6 个面的邻居叶上。一次 `leaf_view_with_slot`
拿 8×8 个值，省掉 64 次三级查找。**12 条棱 + 8 个角（104 个）仍逐点查**——
按棱/角批量要写 20 段映射，而总共只有 104 次。

#### ③ `vertex_of` 完全展开（645 → 590 ms）

原来用 `a/b/c` 三元组循环算 12 条棱，每条棱现构造 `u`/`w` 坐标再调 `corner_index`
（3 次移位 + 2 次或）——24 次调用占 1.4% CPU。展开成编译期常量索引后：

```rust
// a = x：u = (0, ib, ic) = ib<<1 | ic<<2，w = u|1
let (vu, vw) = (corners[iu], corners[iu | 1]);
```

**累加顺序与原实现逐位相同**（x 轴 4 条 → y 轴 4 条 → z 轴 4 条），所以顶点坐标
一个 ulp 都没变——测试断言顶点数 `16 000 002` 完全一致。

#### ④ `CellMap` 块查找缓存（590 → 578 ms）

四边形发射时每格查 3 次（`p−e_b`、`p−e_b−e_c`、`p−e_c`），而遍历按块序推进，
相邻格几乎总在同一块。缓存块坐标 + 序号，命中就跳过哈希。收益小（2%）——
因为 `p−e_b−e_c` 经常跨块。

#### 结果

| | 改前 | 改后 |
|---|---|---|
| 细格提取（3200 万面） | 798 ms | **578 ms**（-28%） |
| LOD k=4（200 万面） | 259 ms | 257 ms |
| LOD k=2（800 万面） | 1661 ms | 1707 ms（**未动**） |
| vs OpenVDB `volumeToMesh` | 慢 1.56× | **慢 1.13×** |

#### k=2 为什么比 k=1 还慢（已知问题，未修）

800 万面要 1707 ms，而 3200 万面的细格只要 578 ms。根因在 `lod_vertex_batch`：

```rust
let mut corner_value: FxHashMap<[i32; 3], f64> = FxHashMap::default();
// 每格 8 次 entry().or_insert_with(...)
```

两个问题叠在一起：**① 每格 8 次哈希**（细格用的是栈上数组，零哈希）；
**② 每个粗格角点的 `sdf()` 要 8 次细格 `get` 做三线性插值**——400 万格 × 8 角 × 8 次
= **2.56 亿次 `get`**，比细格的 2.5 亿还多。

修法是把角点缓存从 `FxHashMap` 换成"按细格叶的数组"（和细格的 `10³` 缓冲同一个思路），
改动较大，暂时记在这里。**实用档是 k=4（257 ms）**，k=2 只用于"要比 k=4 精细、
又不想要 3200 万面"的场合。

### 网格 ↔ 体素往返：拿一个 190 万三角形的真实模型试（2026-11-01）

`tests/roundtrip.rs` 支持任意 STL（不依赖仓库文件）：

```bash
CNCSIM_STL=model.stl CNCSIM_H=0.1 \
  cargo test --release -p cncsim-voxel --test roundtrip -- --ignored --nocapture
```

实测一个 **77.9×79.4×86.8 mm、190 万三角形、体积 79 235 mm³** 的模型：

| h | 域 | 叶 | 体素化 | 体积误差 | 细格提取 | 开洞 | 包围盒偏差 |
|---|---|---|---|---|---|---|---|
| 2.0 mm | 48×49×53 | 145 | 30 s | +1.35% | 16 K 面 / 2 ms | 0 | 1.45 mm |
| 1.0 mm | 87×89×96 | 587 | 31 s | +1.16% | 71 K 面 / 3 ms | 0 | 0.28 mm |
| **0.1 mm** | **789×804×877**（5.56 亿） | **200 179** | **41 s** | **−0.05%** | **792 万面 / 193 ms** | **0** | **0.01 mm** |

**四个值得记的点**：

1. **体积误差 ∝ h²**：1.35% → 1.16% → 0.05%。h 缩小 20 倍，误差缩小 27 倍。
   0.1 mm 时误差 36.6 mm³ / 79235 mm³ = **0.05%**，比"一个体素层的体积"还小——
   因为窄带里存的是**真实距离**，体积积分用的不是体素化近似。
2. **体素化与三角形数成正比、与体素数几乎无关**：h 从 2 到 0.1，体素数涨 **12 600 倍**，
   时间只从 30 s 涨到 41 s。瓶颈是"190 万个三角形每个都要遍历自己的 AABB+band"，
   不是域的大小。
3. **提取是另一个量级**：792 万三角形只要 **193 ms**（4100 万面/秒），因为候选格
   从叶反推（20 万叶 → 候选格 297 万个，而全空间是 5.56 亿）。
4. **开洞恒为 0**，但**非流形边随 h 减小而增多**（138 → 513 → 4276）。已确认
   **不是三角形重复发射**（7 924 700 个三角形里 0 个重复）——是 Surface Nets 在
   **薄壁/尖角**处的对偶网格非流形：两个面靠得比体素还近时，对偶顶点重合。
   不影响渲染。

**顺手做的一个优化**：`distance_pass` 里先用"点到三角形 AABB 的距离"筛两道
（下界 ≥ band 就不必 `get`；下界 ≥ 当前 |v| 就算出真值也不会更新）。体素化
**56.8 → 41.1 s（-28%）**，结果逐位不变。

#### 窄带越薄，体素化越快、量化越细（2026-11-01）

上面 41 s 是 `band_voxels = 4`（切削用的默认值）。但**体素化设计模型不需要那么宽的带**，
而 `distance_pass` 的成本 ∝ `(三角形尺寸 + 2·band)³`——band 减半，AABB 体积降到 1/3。

同一个模型（h=0.1、190 万三角形）：

| `band_voxels` | 体素化 | 体积误差 | LOD 上限 | 用途 |
|---|---|---|---|---|
| 4 | 41.1 s | −0.05% | k=4 | 切削（要精确距离）|
| **2** | **15.2 s** | **−0.01%** | k=2 | **设计模型 / 显示** |
| 1 | **8.2 s** | **+0.003%** | k=1 | 只做比对/体积 |

**反直觉的地方：带越薄，体积误差反而越小。** 因为量化档是 `2·band·h/254`——
band 减半，档距也减半。所以 band=1 的误差是 band=4 的 1/4。

**代价是"距离可信范围"变小**：band=1 时带外一律钳到 ±0.1 mm，只有表面 1 个体素内
的距离是真的。所以：

- **切削 / 碰撞**必须 band=4（刀要深入材料，带外要保守钳制）
- **设计模型**用 band=2（过切**深度**走解析扫掠点测试，不经过体素；残留厚度是 mm 级）
- `max_lod_factor() == band_voxels`，所以 band=1/2 时 LOD 只能到 k=1/k=2

`app` 的 `--design` 路径已改成 band=2：**过切深度 707.1 mm³ 与 band=4 完全一致**
（走解析测试），体素化快 2.7 倍。

> **两个 `--export` 场景的数字不要混**：无 `--design` 时用解析盒（30×30×11 实心），
> 残留 10.92 mm³（面铣四角的料）；带 `--design testdata/design_box.stl` 时那个 STL 是
> **薄壁盒**，内腔被判定为"设计气区"，毛坯在内腔的料全算残留（5179 mm³）。
> 两个都对，只是问的问题不同。

#### 但 `band` **不是**切削的杠杆

同样的 A/B（同一时间窗口交替跑，避开 ±15% 的降频漂移）：

| `band_voxels` | 铣光 200 刀逐刀 |
|---|---|
| 4 | 53 / 54 / 55 ms |
| 2 | 53 / 55 / 53 ms |

**没有差异。** 因为切削的成本由"落盘 + 每刀固定开销"主导，AABB 只缩了 12%
（y/z 各减 2 体素），落在噪声里。所以：

- **切削保持 band=4**（它换来的是检出下限和下面那条一致性，不是速度）
- **体素化才是 band 的杠杆**（41 → 15 s，上一节）

#### 一个被 `band` 卡住的指标：残留厚度

`residual_max_thickness` 是 `设计场距离 + h/2`，而那个距离**来自设计模型**：

| 设计模型 | 距离来源 | 有上限吗 |
|---|---|---|
| `DesignModel::Box`（默认） | 解析盒 SDF | **没有**（实测 1.000 mm 是真实厚度）|
| `DesignModel::Field`（`--design x.stl`） | 体素场查询 | **有，= `band + h/2`**（0.450 mm @ band=4）|

所以 `--design` 时这个指标会**饱和**：比 `band + h/2` 更厚的残留一律报成上限。
`stl_field_design_agrees_with_box_design` 就是被这条卡住的——band 改成 2 时上限从
0.45 降到 0.25，同一个设计用解析盒和 STL 两种表示会给出不同的残留厚度。

现在报告里会标出来：

```text
残留 5179.29 mm³，最厚 0.450 mm（**已饱和**：Field 设计的上限 0.450 = band + h/2，真实更厚）
```

**现在这个"饱和"是显式状态**，不是靠打印时猜：

```rust
pub fn distance_cap(&self) -> Option<f64>   // 设计距离有无上限
// SimReport 里：
pub residual_thickness_capped: bool,        // 最厚那点是否饱和
pub residual_thickness_cap: Option<f64>,    // 上限是多少
```

`voxel_compare` 在记录最大厚度时同时判断 `dd >= cap`，所以：

- `DesignModel::Box` → `capped = false`，厚度精确
- `DesignModel::Field` → `capped = true`，厚度是下限

**注意上限要用"设计场"的 band 算，不是毛坯场的**——两者是独立网格，band 可以不同
（`--design` 用 2、毛坯用 4，拿错就会把 0.25 的上限印成 0.45，这个坑踩过一次）。

**所以 `--design` 现在用 band=2**：体素化 **41 → 15 s**，残留厚度标"已饱和（上限 0.250）"。
`stl_field_design_agrees_with_box_design` 也从"必须等于 0.5"改成"要么等于 0.5，
要么明确标了饱和"——**这不是放宽断言，是把饱和变成可检查的状态**：
`capped=false` 却对不上 0.5，或者 `capped=true` 却报了个离谱的值，都会红。

**要根治**得让 Field 的残留厚度走解析距离（对残留体素求最近设计三角形），
那样 band 就与这个指标彻底解耦。

#### 设计场的域：模型 ∪ 毛坯

`--design` 的域原来硬编码 `[300, 300, 120]`（正好等于毛坯域）。78×79×87 mm 的模型
会被**裁掉大半**——而 `voxel_compare` 只在毛坯域内查 `design.sdf(p)`，设计域覆盖不到
的地方返回背景值（空气），把"设计要料"误判成"设计气区"，残留体积虚高。

现在按**并集包围盒**算（各外扩 4 体素），并把尺寸打出来：

```text
模型包围盒 77.9×79.4×86.8 mm → 设计场 788×803×876 体素（78.7×80.2×87.6 mm）
模型包围盒 20.0×20.0×9.5 mm  → 设计场 308×308×128 体素（30.8×30.8×12.8 mm）
```

小模型（20 mm 的盒）时并集就是毛坯域，结果与之前完全一致（过切 707.1、残留 5179.29）；
190 万三角形的大模型从"被裁掉"变成"完整覆盖"。

**注意**：设计模型必须与毛坯在**同一世界坐标系**里。两者不重叠时比对没有意义
（会报满残留），程序不拦，只在报告里显示域尺寸供核对。毛坯尺寸目前仍硬编码
`[300, 300, 120]`——换大模型做设计时毛坯也该跟着大，这条还没做。

**可视化**：

```bash
cargo run --release -p cncsim-render --example stl_roundtrip -- model.stl 0.1 4
# → out/stl_roundtrip.html（单文件、零外链、浏览器直接开）
```

#### 同一份 STL 的 OpenVDB 对比

`tools/ovdb_bench` 新增 `bench_stl`（对齐口径：二进制解析、`halfWidth = 4 体素`、
体素中心 `(i+0.5)h`、只计转换本身）：

| 模型 | h | CNCSIM `mesh_to_field` | OpenVDB `meshToLevelSet` |
|---|---|---|---|
| `design_box.stl`（12 三角形） | 0.2 mm | **38 ms** | 53 ms |
| 大飞鱼（190 万三角形） | 1.0 mm | **30 s** | **> 7 min（超时未完成）** |
| 大飞鱼（190 万三角形） | 0.1 mm | **41 s** | **> 20 min（超时未完成）** |

**先说清楚这个对比的边界**：

- 大模型那两格是**下界**——进程被 `timeout` 杀掉，真实耗时未知。
- 小盒子上 OpenVDB 也**不快**（53 vs 38 ms），所以差距不是"大模型才出现"。
- 截断三角形做 scaling 的尝试**无效**：截断后模型不闭合，OpenVDB 的符号判定会
  退化（2000 个三角形也跑不完），而完整模型是水密的（95 万顶点、285.6 万条边、
  **开洞 0**、只有 2 条非流形边——用 numpy 独立验过）。

**为什么差这么多**（推测，未用 VTune 证实）：`meshToLevelSet` 要先建"顶点 → 叶"
的索引再逐三角形分配 AABB；95 万顶点 + 190 万三角形的中间结构可能是 GB 量级，
触发换页。我们的 `mesh_to_field` 不建顶点表，逐三角形直接光栅化 + 视差定符号，
没有中间结构。

**但不能因此说"我们比 OpenVDB 强"**：它输出的是**通用带符号距离场**（任意带宽、
自适应、支持 CSG 管线），我们只做窄带 SDF。它的设计目标不是"190 万三角形一次
转窄带"。

**顺带发现**：`design_box.stl` 是**单层壳**（只有外表面，没有内表面）。视差法下
射线只穿一次，奇偶判成"内部是材料"，所以体积算成实心（1266.7 → 3760.0 mm³，
+196%）。**这个模型的体积指标无效**——它只适合当"设计面"用（`ovdb_parity` 就是
这么用的，只看表面位置）。

### 与原生 OpenVDB 的对比（2026-10-31 实测）

**环境**：OpenVDB **14.0.0**（最新）+ oneTBB **2023.2.0**（最新），源码编译，
clang++ **23.1.4** `-O3 -march=native`；CNCSIM 侧 rustc release（同为 LLVM 优化后端）。
场景完全对齐：30×30×12 毛坯 / h=0.1 / φ6 平底刀 / 切深 0.5 / 窄带 4 体素 / 每刀换 y 不重叠。
基准源码见 `tools/ovdb_bench/`。

| 刀长 | OpenVDB 刀具体 | OpenVDB CSG | **OpenVDB 端到端** | **CNCSIM** | 比值 |
|---|---|---|---|---|---|
| 1 mm | 8.56 ms | 0.20 ms | **8.75 ms** | **2.03 ms** | 4.3× |
| 10 mm | 13.87 ms | 0.29 ms | **14.16 ms** | **1.51 ms** | 9.4× |
| 20 mm | 19.86 ms | 0.31 ms | **20.16 ms** | **2.33 ms** | **8.7×** |
| 28 mm | 23.68 ms | 0.35 ms | **24.03 ms** | **3.00 ms** | **8.0×** |

**三个必须说清的点**：

1. **OpenVDB 的 CSG 极快（0.3 ms），但它要求刀具体已经是 level set。**
   OpenVDB 没有"解析扫掠 SDF"——必须先把扫掠体逐体素写成 level set，
   这一步 `ValueAccessor::setValue` 实测 **78 ns/体素**（254k 体素要 20 ms）。
   我们的解析求值 **4.7 ns/体素**（落盘后 13.8 ns），快 5.5×。
   *这个对比不是"我们比 OpenVDB 强"，而是**两种范式**：它优化了 CSG，代价是必须先把形状体素化。*

2. **如果刀具形状能在多刀间复用，OpenVDB 会赢。** 固定形状（球头刀）+ 平移变换，
   只跑 `csgDifference` 就是 0.3 ms/刀，比我们快一个数量级。
   但扫掠体随刀路变化，真实场景里每刀都得重建——这才是本表的口径。

3. **CNCSIM 的"空刀"是 0.66 ms**，与 OpenVDB 的纯 CSG（0.3 ms）同一量级。
   说明我们慢的部分全在"求值 + 落盘"，不在 CSG 本身。

**如果哪天需要更快**：把解析 SDF 预烘焙成 level set 再复用（就是 OpenVDB 的路子），
但会失去"设计模型解析比对"和"任意刀型零预处理"这两个能力。

#### 几何结果一致吗？——一致到量化精度

速度只是硬币的一面。`crates/voxel/tests/ovdb_parity.rs` 做了**逐点对拍**：
同样的毛坯/刀具/刀路，在槽底与槽壁上按体素索引采样，比较两边的 SDF 值。

| 指标 | 结果 |
|---|---|
| 表面位置（槽底 z=11.5 / 左壁 y=19.0 / 右壁 y=25.0） | **差 0.0 µm**（三个过零点全部精确命中） |
| 带内逐点差（27 个采样点） | 最大 **1.18 µm**、中位 **0.39 µm** |
| 带外符号（材料 / 空气） | **0 处冲突** |

1.18 µm 就是 `i8` 量化步长（`2×0.4/255 = 3.15 µm`）的半步——**不是算法差异，是表示精度**。
带外的绝对值不同（CNCSIM 钳到 ±0.4，OpenVDB 钳到 ±0.45/±0.55），那是各自的饱和约定，
符号永远一致，不影响任何下游计算。

**对拍抓到的真问题**：`fill_box` 只写饱和值，毛坯边界不写精确 SDF，
于是未切削面的插值位置依赖"体素中心恰好落在边界上"——实测左侧壁因此偏了 **25 µm**。
修法是新增 `fill_box_exact`（边界壳写真实盒 SDF，内部仍是饱和 tile，内存不变），
换上之后三个过零点全部归零。**默认仍用 `fill_box`**（建场几乎免费），
需要亚体素精度的场景显式用精确版。

#### 精度上限：能到多少

两个概念要分开：**几何分辨**（能不能表示细节，由 `h` 决定）与**数值精度**
（表面位置准不准，由量化决定）。后者有闭式：

```text
量化步长 = 2 · band_voxels · h / steps      (steps: I8=254, I16=65534)
```

`crates/voxel/tests/precision.rs` 实测（槽底故意放在 13.3h，落在体素中心之间）：

| h (mm) | I8 误差 | I16 误差 | 30×30×12 毛坯内存 |
|---|---|---|---|
| 0.100 | **0.65 µm** | 0.0024 µm | 1.2 MB |
| 0.050 | 0.32 µm | 0.0012 µm | 5 MB |
| 0.020 | 0.13 µm | 0.0005 µm | 31 MB |
| 0.010 | **0.065 µm** | 0.0002 µm | 125 MB |

**`误差 / h` 恒为 0.0065**（I8、band=4），即误差严格正比于 `h`、正比于 `band_voxels`、
反比于档位数。三个旋钮的实测性价比：

| 旋钮 | 精度收益 | 代价 |
|---|---|---|
| `h` 减半 | 误差减半 | 内存 ∝ 1/h²（表面积），切削 ∝ 1/h³ |
| I8 → I16 | 误差 **÷258** | 内存 ×2 |
| `band_voxels` 减半 | 误差减半 | 窄带变薄，曲率大的地方距离不准 |

**结论**：

- **实用上限：`h=0.01` + I8 → 65 nm**，比机床定位精度（~1 µm）高 15 倍，内存 125 MB。
- **理论极限：`h=0.01` + I16 → 0.2 nm**，已经小于原子直径，没有工程意义。
- **mesh 顶点与 SDF 查询同精度**（实测两者都是 0.65 µm @ h=0.1）——Surface Nets
  没有引入额外误差，至少在平面上如此。

**别忽略的另一半**：以上是**平面**的精度。曲面上还有体素化本身的弦高误差
`≈ h²/(8R)`（`h=0.1, R=3` 时 0.4 µm），与量化误差同量级。
所以真实零件上，`h=0.1` 的总误差约 **1 µm**，仍远优于工艺公差。

### 粗加工全切除：50×50×100 mm 铣光对比

比单刀更能反映真实负载的场景：**50×50×100 mm 毛坯被 φ6 立铣刀（刃长 6）分层铣光**——
20 层 × 每层 10 刀 = **200 刀**，把整块料切空。`h=0.2`（250×250×500 = 3125 万体素），
基准在 `crates/voxel/tests/millout.rs` 与 `tools/ovdb_bench` 的 `MILLOUT` 段。

| 阶段 | CNCSIM | OpenVDB 14 | 比值 |
|---|---|---|---|
| 建场（精确 level set） | **14 ms** | 48 ms | **3.4×** |
| **切削 200 刀（逐刀）** | **48 ms**（0.24 ms/刀） | 717 ms（3.59 ms/刀） | **14.9×** |
| 切削 200 刀（整批） | **16 ms**（0.08 ms/刀） | — | **44.8×** |
| 合计（逐刀） | **62 ms** | 765 ms | **12.3×** |

**水平集 → 网格**（200×200×100 @ h=0.1，同一份场）：

| | CNCSIM `extract_surface` | OpenVDB `volumeToMesh` | 比值 |
|---|---|---|---|
| 细格 | **578 ms** / 3200 万面 | 510 ms / 3200 万面 | 慢 **1.13×** |
| 200 万面档 | **257 ms**（k=4） | 687 ms（adapt=1.0，50 万面） | **快 2.7×** |

**顶点数完全一致**（`16 000 002`）——两条独立实现（Surface Nets vs Marching Cubes）
在同一个盒子上给出同样的拓扑，这是最有力的交叉验证。

细格上输 13% 是 C++ + TBB 十几年优化的差距；但**降面数时我们快 2.7 倍**，
因为 OpenVDB 的 `adaptivity` 是"先建完整细网格再按曲率折叠"（所以 `adapt=0.5`
反而比 `adapt=0` 慢），而我们的 `k` 是"直接在粗格上重采样"——**不用先造出大网格**。

OpenVDB 的 717 ms 里含**每刀重建刀具体** 617 ms（3.09 ms/刀）——它没有解析扫掠 SDF，
只能先把扫掠体逐体素写成 level set 再做 CSG（纯 CSG 75 ms）。我们的刀是解析的，
每刀零预处理，这就是"切削"一列的口径差。

这个场景一开始**我们输 3 倍**（10.6 ms/刀），优化历程：

| 问题 | 修法 | 效果 |
|---|---|---|
| `prune()` 每刀全量扫（15 个 level1 × 4096 叶 × 512 体素 ≈ 3100 万次） | `prune_touched`：只折叠**写过的叶** | **10.3 → 3.4 ms** |
| `prune_touched` 每刀重算 blind 元数据（全项目无读取者） | 写时标脏，离线 `prune()` 才重算 | **344 → 67 ms（-79%）** |
| `get(ijk)` 每体素走完整三级查找 | `leaf_or_tile`：一次拿到叶，512 体素直读叶缓冲 | 单刀 2.3 → 2.1 ms |
| `fill_box_exact` 用无缓存 `set` | 改走 `set_cached_in_bounds` | 建场 240 → 147 ms |
| 中转缓冲从 0 翻倍 realloc | 按叶数上限一次预留 | **-61 ms/200 刀** |
| 整叶短路走串行 `fill_leaf` | 有下标的叶产出整块常量，混进并行 blit | 118 → 40 µs/刀 |

**结论**：`prune` 的全量重算是比"求值"大得多的隐藏成本——它在**每刀**都触发，
而切削只碰 AABB 里的一小块。**任何"每刀都要遍历整个场"的操作都得改成增量**；
而"没人读的元数据"是最贵的那种——删之前先全局搜一遍读取者。

**建场差距的原因**：OpenVDB 的 `fill` 走 tile（O(1) 每块），我们精确化边界壳时要
逐个体素算盒 SDF（3125 万次）。用 `fill_box`（饱和、不精确化）建场是毫秒级，
但未切削面的插值位置会偏——见上面「几何结果一致吗」一节。


**测试量的是表面位置**，不是"有没有变化"：开一条 6mm 宽、2mm 深的槽，断言槽底在 z=3（±5 µm）、槽壁在 y=2、槽外材料一动不动。把 CSG 公式的负号去掉会报「槽内应为正（无材料），实际 −0.4」。

### 表面提取：Surface Nets（16 个测试）

**没有用经典 Marching Cubes。** MC 需要 256 项边表 + 256×16 项三角表，手打必错，
而且**错了没有中间步骤可查**——少一个三角形只是网格上多个小洞，在几千万个三角形里看不出来。

改用**对偶等值面**：每格一个顶点（12 条棱上零点的平均），每条符号变化的棱生成一个四边形。
**水密是结构保证**，表数据为零。

| | 经典 MC | Surface Nets |
|---|---|---|
| 表数据 | 256 + 4096 项 | **0** |
| 水密性 | 靠查表正确 | **结构保证** |
| 顶点位置 | 棱上（贴合） | 格内（误差 `O(h²/R)`） |

**实测精度**：R=3 的球，有向体积 **112.97 vs 解析 113.10，误差 0.11%**。

三条硬指标都有测试：**水密**（每条边恰好共享 2 次）、**有向体积为正**（绕序）、**体积数值对**（位置）。
把绕序翻反会报「绕序反了：体积为 −112.97」；去掉 tile 的边界余量会报「丢洞 298」。

#### 三个踩到的坑（都写进了 ADR-006 §7.1）

1. **tile 紧贴填充边界会让网格漏洞**——单元格跨 2 个体素，"tile 的最后一个体素 ↔ 盒外背景"这条符号变化落在没有叶子的区域，谁都遍历不到。修法：tile 判定留 1 体素余量，边界那层槽建成**常量叶**（16 字节而不是 528），把 130 MB 压回 4 MB。
2. **halo 重叠导致四边形重复发射**——顶点有 `entry()` 去重所以无害，四边形没有 → 边被共享 4~6 次。修法：按顶点创建顺序遍历。
3. **HashMap 迭代顺序破坏可复现性**——`for_each_leaf` 走 HashMap，顶点顺序每次不同。修法：叶坐标先排序。

### 单元格索引：块 + 位掩码（4 个测试）

顶点是"每个单元格一个"，所以要有 `单元格 → 顶点索引` 的映射。第一版用的是一张
`FxHashMap<[i32;3], u32>`：200 mm 毛坯 **1600 万条、310 MB**，每次查找都是 DRAM 延迟——
提取 3.0 s 里有 2.0 s 花在这上面。

改成 **每 8³ 个单元格一个块 + 512 位掩码**，索引 = `base + popcount(掩码前缀)`：

| 方案 | 每块开销 | 25 万块合计 |
|---|---|---|
| 稠密 `[u32; 512]` | 2 KB | 500 MB（比哈希表还差） |
| **位掩码 `[u64; 8]` + base** | **68 B** | **17 MB** |

块内占用率只有 12.5%（表面在体素空间里是二维的），所以"有没有"用 1 bit 存、"是多少"用前缀和算，
信息量一样、内存差 12 倍。这是从 OpenVDB 抄的——它的树里**只有 root 是哈希表**，
往下一律 `children[popcount(mask & 低位)]`。

**代价**：顶点下标变成"块序 + 槽序"的空间序（不再是叶迭代顺序）。这对渲染无影响，
但细格与 LOD **必须走同一个构建器**，否则 `k=1` 与细格逐位一致那条测试立刻红。
副产品是"顺序与分块数无关"由构造保证，不再依赖"合并顺序恰好等于串行顺序"。

**实测**：200 mm 提取 **3.09 s → 0.81 s**，索引 **310 MB → 25 MB**，另外省掉原来那张 192 MB 的
`cells` 数组（单元格靠掩码反推）。顶点数 / 三角形数 / 丢洞数与改前完全一致（16 000 002 / 32 000 000 / 0）。
细节见 [ADR-010](docs/ADR-010-单元格索引.md)。

### 显示 LOD：粗格重采样（11 个测试）

**不是网格抽稀，是重新采样**——输入是 2 MB 的稀疏树，不是 834 MB 的细网格。
水密性照样由 Surface Nets 的结构保证，绕序逻辑与细格共用同一段代码（`vertex_of` / `emit_quads`）。

| | 网格抽稀（QEM） | 粗格重采样 |
|---|---|---|
| 输入 | 先得造出 3200 万面 | 稀疏树，2 MB |
| 水密 | 抽稀会开洞 | **结构保证** |
| 可复现 | 依赖误差度量与堆序 | **纯函数，逐位可复现** |

**`k ≤ band_voxels` 是几何约束，不是调参旋钮。** 跨符号的棱两端各在表面一侧，
所以各自到表面的距离 `≤ h_c = k·h`；窄带只有 `band_voxels·h` 宽。于是：

- `k ≤ band`：两端都在带内 → 值是真实距离 → 插值误差只剩 `O(h_c²/R)`。
- `k > band`：远端被钳制到 `±band` → 插值不再等于真实距离，偏差随 `(h_c − band)²` 长。

实测 R=6 球的最大径向偏差：**k=1 1.8 µm、k=2 3.3、k=3 6.2、k=4 9.8**，越界后 **k=5 15.5、k=6 34.2**。
不是断崖，但**没有上界**，而且网格看起来照样水密——所以 `extract_surface_lod` 超限直接 panic，
不警告、不静默降级。**想再少面只能加宽 band（内存换），不能加大 k。**

| 场景 | 结果（24 线程） |
|---|---|
| 200 mm 毛坯 k=4 | **200 万面 / 52 MB / 0.25 s / 丢洞 0**（细格：3200 万面 / 834 MB / 0.81 s） |
| 200 mm 毛坯 k=2 | 800 万面 / 208 MB / 1.68 s |
| 12×12×8 块 k=4 | 8520 面 / 2.5 ms |

k=2 比 k=4 慢 7 倍而不是 4 倍：800 万顶点的角点缓存把随机访问压到 L2 之外。真要 k=2 得改成按块批处理。

**候选格只取表面附近**：200 mm 毛坯 @ h_c=0.4 有 1.25 亿个粗格，全扫要十几秒；从叶反推实测 **297 万个**（真正出顶点 100 万，3 倍余量），少 42 倍。
判"表面可能穿过这片叶"要用**三档**判据——只看 `|v|` 会漏掉 `fill_box` 的二值毛坯（实测：60 mm 方坯 k=1 提取出 **0 个顶点**），
必须加上"26 邻里有反号叶"。第一版就栽在这里。

**`k=1` 与细格逐位对拍**（`factor_one_is_bit_identical_to_fine_extraction`）：
同一张面、顶点编号不同，所以比较前把三角形三个顶点各自规范化再排序。任何候选集漏格、绕序分叉、
符号约定不一致都会立刻红——这是整套 LOD 唯一有效的回归网。

### 段内并行：零依赖 fork-join（6 个测试）

**段与段之间仍然串行**（第 N+1 段要读第 N 段切完的毛坯），但**段内是并行的**：
一次切削里每个体素只读自己那一个值，`max(d_cur, −sd_sweep)` 与邻居无关。
《并发与性能》原文说"材料去除不能并行"，那句话要读成**段间**。

形状统一成"**只读并行 + 按块号归位**"，`SparseGrid` 全程单一所有者——不需要 `Arc<Mutex<_>>`，也不需要 unsafe：

```
① 并行求值：&self 只读，每块产出自己的结果（顶点 / 改变列表 / 索引）
② 串行归并：按块号顺序合并 → 与线程调度无关
```

`voxel::par` 只有 70 行：`std::thread::scope` + `fetch_add` 动态领号 + `slots[块号]` 落位。
**池是 rayon 的**（`ThreadPoolBuilder` + `par_iter`）：第一版手写 `std::thread::scope`，
每次 fork-join 491 µs，真实段长 7.4 ms 里占 7%——10 万段就是 50 秒。换成常驻池后降到 ~5 µs。
**数据面的规矩没变**：仍然只读并行、按块号归位，池只负责分 CPU。

| 场景 | 串行 | 24 线程 | 倍数 |
|---|---|---|---|
| 200 mm 毛坯提取（3200 万面） | 14.9 s | **0.81 s** | **18×** |
| 200 mm 毛坯 LOD k=4 | 2.15 s | **0.25 s** | 8.6× |
| 200 mm 直槽切削 | 1002 ms | **117 ms** | 8.6× |
| 200 段连续（每段 0.05 mm） | 8.3 ms | **1.55 ms** | 5.3× |

**确定性是硬门槛**：分块数从 1 拧到 97，顶点/法向/索引/体素值必须**逐位相同**。
所以把"分块数"做成显式参数（`extract_surface_chunks(n)` / `cut_segment_with(.., slices)`，
`0` = 自动），4 条测试拿它当旋钮对拍（`tests/parallel.rs`）。线程数是进程级全局，测试里改不了，
但块数 1 就是串行路径——这才测得到"合并顺序与调度无关"。

**代价**：第一版手写 fork-join 每次 491 µs，换成 rayon 常驻池后 ~5 µs（`ThreadPoolBuilder` 单例）。
门槛仍然保留（切削 2 万体素、提取/LOD 128 片叶）：不是因为线程贵，而是块太碎时
每块的结果 `Vec` 分配与合并拷贝会吃掉收益。`CNCSIM_THREADS=1` 可强制串行（对拍、定位性能问题时用）。

### 碰撞：保守推进 + GJK + EPA + episode（34 个测试）

`collide` 的第一片：**连续化**。这是 ADR-004 §3 认定的"真正的风险点"。

100 m/min 快移 = **1.67 mm/ms**，薄壁/压板边缘能薄到 1–2 mm。按固定时间步采样，
2 mm 的薄壁会被整步跳过——报"无碰撞"而实际撞了。**漏报比没有检测更危险**，因为它给了虚假的安全感。

保守推进用距离下界算安全步长：

```text
t ← t + d_lower(t) / v_max        # 这段时间内不可能撞
```

只要 `d_lower` 是下界、`v_max` 是上界，步长就永远偏小 → **只会迟到，不会跳过**。
迭代耗尽时保守报碰撞。

**下界怎么来**（两处都要减）：刀柄表面是**采样**的（间隙 `δ`），最靠近材料的点可能没采到
（1-Lipschitz → 真实距离 ≥ 采样最小值 − δ）；再加上体素场误差 2 µm。所以
`Hit` 同时给出 `clearance`（上界，`< 0` 是确切穿透）与 `clearance_lower`（下界），
两者之间就是"无法保证"的区间——**默认 δ=0.5 mm 时保守带 ≈ 0.5 mm**。

| δ | 采样点（φ6×20 刀柄） | 检出下限（R=3） |
|---|---|---|
| 0.2 mm | ≈ 22 000 | 6.7 µm |
| 0.5 mm | ≈ 3 500 | 42 µm |
| 1.0 mm | ≈ 880 | 167 µm |

`v_max` 必须含转动项 `θ·r_max`——五轴摆动时刀柄末端速度可能远大于刀尖，用刀尖速度当上界会漏报。

**测试里有两条是对照组**：`endpoints_only` 是"只查两端点"的反例（留在代码里），
2 mm 竖墙 + 16 mm 单步的场景下**它漏，保守推进抓到**。

### 凸体 × 凸体：GJK（解析 support，不做多边形离散）

ADR-004 §2.6 认定"精确"的那一类，用来管**刀夹 / 夹具 / 台面 / 机床件**——
这些形状是已知的凸体，没有理由拿体素去估。

**为什么不用离散**：上一版设计把旋转体切成 16 边棱柱，外切误差 `r(1−cos(π/16)) ≈ 0.019r`。
对 R=30 的刀夹是 **0.57 mm 的系统性误报**——每把刀都"差一点点就撞"，报告就没人看了。
GJK 只要一个支持映射，圆台/球/盒的支持映射都是解析的，于是**零建模误差**。

| 形状 | 用途 |
|---|---|
| `Cone`（圆台 / 圆柱 / 圆锥 / 退化圆盘） | 刀柄按母线分段，一段一个 |
| `Sphere` / `Capsule` | 球头刀、简化主轴鼻端 |
| `Box3`（有向盒） | 夹具、台面、机床铸件 |
| `Hull`（顶点表） | 导入的 STEP 件——只要顶点，不用三角化 |
| `Placed<S>` | 任意局部形状 + 刚体变换 |

整把刀 = `cones_of(profile)` 的圆台并集。**刀具不必是凸的**：凸体并集到另一个体的距离
取各段的最小值，逐段 GJK 再取最小就对了。

**实测**（release）：

| 场景 | 耗时 |
|---|---|
| 单对 圆柱 vs 球（平均 7.1 迭代） | **297 ns** |
| 整把刀（3 段圆台）vs 夹具 | **1.67 µs** |
| AABB 粗筛 `aabb_gap` | 3.1 ns（比 GJK 便宜 96×） |

`distance()` **永远精确**——最近点对就是碰撞报告要的"哪里撞了"，不能拿盒面近似糊过去。
要粗筛用独立的 `aabb_gap()`，别让两者混在一起。

**怎么保证算对**（这一片花时间最多的地方）：

1. **最优性用 KKT 条件自证**，不需要 oracle：`point_a` 必须是 `a` 沿 `−d̂` 的极值点、
   `point_b` 是 `b` 沿 `+d̂` 的极值点，两条成立 ⟺ `|pa−pb|` 就是最短距离。
   随机 400 对（圆台 vs 球 / 盒）跑这套断言。
2. **采样对拍**：圆台表面密集采样 → 每点到盒的解析距离取最小 = 真实距离的上界。
   GJK 必须落在 `[上界−采样间隙, 上界]`。35 例实测偏差 **0**。
3. **支撑点合法性**（独立于 GJK）：`support(d)` 必须是沿 `d` 真正最远的点。

第 3 条抓到过一个**只有它才能抓到**的 bug：`Cone::support` 只按轴向正负挑端圆、
没比较半径，对 `r_lo ≠ r_hi` 的细长圆台返回非最远点——距离虚高 0.06 mm。
第 1 条断言当时**全绿**，因为断言里的 `support` 和 GJK 里的是同一个错的实现，两边一起错就自洽了。
**凡是"用同一份实现自证"的检查，都必须再配一条独立的 oracle。**

实现上没有增量维护单纯形（GJK 最经典的坑：该丢的点没丢），而是每轮**穷举含新点的子集**
（≤ 8 个）各求一次闭式最近点。定长数组、零堆分配，单次 297 ns 够用；
早版本用 `Vec` 做这件事是 2313 ns（8×）。


### 穿透深度：EPA

GJK 只说"撞了"（距离 0）；报告要说"**撞进去多深、从哪退**"。

在 Minkowski 差 `W = A − B` 里做：原点在 `W` 内 ⟺ 相交，原点到 `W` 边界的**最短距离**就是穿透深度。
拿 GJK 的单纯形当初始四面体（不够 4 点就自己扩），反复"找最近面 → 沿法向取支撑点 →
撑大"，`d(最近面)` 单调递增，收敛即答案。

**一个容易搞反的符号**：`point_a − point_b` **不是**分离方向，而是它的反面。

> A 球心 0 半径 3，B 球心 4 半径 3。`W` 是半径 6、中心 −4 的球，最近边界在 **+X**、距离 2。
> 但 A 要往 **−X** 移 2 才分离。所以字段叫 `axis` 不叫 `normal`，分离位移是 `−axis · depth`。

**验收方式是"照着推开"**：按报出的 `depth` / `axis` 移动 A，两体必须恰好接触。
120 例随机穿透（圆台 vs 盒）全部通过。深度算错、方向反了、接触点错了，这条都会红。

| 场景 | 结果 |
|---|---|
| 球 vs 球（解析 2.0） | **1.99998 mm**（平面逼近球面的固有误差） |
| 盒 vs 盒（解析 0.5） | 0.50000 |
| φ6 圆柱插板（解析 1.0） | 1.00000 |
| 穿透查询（3 段圆台 vs 盒，平均 5.9 迭代） | **1.70 µs** |

曲面精度受**平面逼近**限制而不是迭代次数：球面 64 次迭代到 2e-5 mm，
再往上只能靠更多面。要 µm 级深度的场景应该用解析特例，不是加迭代。

**踩的坑**：初始四面体的外法向不能拿原点当参考点判朝向——GJK 留下的单纯形本来就贴着
原点，原点可能正好在某个面的平面上（`n·O = 0`），判不出哪边是外。判错的后果是最深的面
被当成"最浅出口"，深度直接报 0。改用四面体**重心**（一定严格在内部）。

### episode 聚类

一次真实碰撞会在连续几十个采样点上反复触发，逐条报出来是几百行噪声。
按「同一对部件 + 间隔 ≤ 50 ms」合并之后，一个 episode ≈ 一次事故。

50 ms 不是拍的：100 m/min 快移在这段时间里走 **83 mm**，比任何真实接触尺度大一个量级，
所以同一次碰撞不会被拆成两段；而两次独立事故基本不会在 50 ms 内重复。

`absorb()` 取**最大**穿透而不是最后一次——报告关心"最深扎进去多少"。


### 毛坯碰撞：两个方向，分工不同

`collide` 刻意不依赖 `voxel`（ADR-004 §7.7），依赖方向由 `sim::stock` 反转：
`StockField` 用 newtype 把 `SparseGrid` 包成 `DistanceField`（orphan rule 要求这样）。

| 方向 | 做法 | 保证 | 成本（φ9×60 刀杆） | 干什么 |
|---|---|---|---|---|
| **B（主）** | 刀杆表面采样 → 毛坯 SDF，连续化 | `δ²/(2R)` = **42 µm** | **0.48 ms** | 检出 |
| **A（辅）** | 毛坯体素中心 → 刀杆 SDF | `h/2` = **50 µm** | 1.30 ms | **定位**：报"毛坯上哪一块被啃了" |

B 便宜 2.7× 且精度高两个数量级，所以 `check_shank()` 先跑 B；命中后 A 才跑一次，
把结果翻译成体素坐标。刀在空中时两者都是 AABB 预筛秒退（**0.03 ms**）。

**只有刀杆算碰撞**：`ToolDef::shank`（刃长以上那一段）。刀刃切材料是本职工作。

**这里有个必须补的下界。** 体素场的窄带只有 `band` 宽（默认 0.4 mm），带外一律返回
钳制的 `+band`；而采样间隙 `δ` 默认 0.5 mm。于是"采样最小值 − δ" = **−0.1**，
**任何位置都算"无法保证"**——保守推进退化成每段都报碰撞（实测：刀在毛坯上方 40 mm
空走也报）。补一条包围盒下界就好了：采样点全在其世界包围盒里，所以真实距离
≥「采样点包围盒」到「场包围盒」的距离。同一趟遍历顺手拿到，不用多扫。

> 先试过"刀尖球"（半径 = `reach`，O(1)）：φ6×40 的刀杆要包在半径 40 的球里，
> 球一靠近就是 0，等于没兜。紧的下界必须是**形状**的下界，不是**球**的下界。


### 端到端：一条程序跑到底

`sim::run` 是装配层，本身不含算法——它只是按块把各个 crate 串起来：

```text
gcode::interpret  →  MotionProgram（已解析、已吸收偏置的位姿序列）
       ↓ 每块
motion::arc       →  圆弧按弦高离散成折线（默认 2 µm）
       ↓ 每段
voxel::cut        →  刀具扫掠减材料
sim::stock        →  刀杆 vs 毛坯（方向 B 检出 + 方向 A 定位）
       ↓
SimReport + CollisionEpisode
```

`cargo run` 的最后一段就是这个（三条槽，第三条刀杆扎穿）：

```text
6 块 → 3 段切削 + 3 段快移
去除材料 100.4 mm³（4000.0 → 3899.6），程序时间 8.64 s
切削 16 ms，碰撞检查 4 ms，墙钟 0.02 s
碰撞：刀杆 × 毛坯 最深 0.40 mm，3.742–7.443 s，首次在第 4 块（第 5 行）
```

**快移也查碰撞**——真实撞机大多是 `G0` 撞夹具，不是切削时撞。

**episode 的口径改了**：一次下扎会横跨 `G0` 和紧随其后的 `G1`，两块之间隔着 70 ms
（超过 50 ms 的合并窗口），但那是**同一个动作**。所以相邻块无条件合并，时间窗口只用来
合并"同一个块里的多段"和"跨了空行程的偶发重复"。

**深度只报下限（0.40 mm = 一整个窄带）**。深埋点的 `sdf` 被钳制到 `−band`，
所以"至少扎进去 0.4 mm"——真实深度更大但体素场说不出来。要知道确切深度得换 `i16`
（带宽不变、档距从 3.15 µm 降到 12 nm）或者走体素遍历拿几何关系。

**还没算的**：残料厚度、过切体积（要跟设计模型比对，`gouge_volume_mm3` 恒 0）、
非线性误差、每转进给的时间（`G95` 的块按 mm/min 估，报告里有计数）。


### 显示层：网格 → GPU 缓冲，以及一个能发给别人的预览

`render` 现在做两件事，**都不需要窗口**：

| 步骤 | 做什么 | 为什么在这里 |
|---|---|---|
| `interleave` | 位置 + 法向交错成 `[x,y,z,nx,ny,nz]` | 一个顶点两个属性通常在同一缓存行；分开存多一次随机访问 |
| `split_tiles` | 按质心把三角形分到 3.2 mm 的块，索引重映射 | 一叶一实体 = 39 万 draw call；分块后只重建被切到的那几块 |

这两步可以脱离引擎验证，所以先把它们写实。Bevy 那一步只是"把 buffer 交给 `Mesh`"，
不改变这里任何一个字节——**这也是为什么现在还没引 Bevy**：它是 L1 的既定选择（ADR-003），
但对"我切出来的东西长什么样"这个问题，一个 2 MB 的 HTML 比一个开不起来的窗口有用。

提取成网格写进**单个 HTML**：

演示程序配了设计盒（顶面 z=11 = 面铣平面）：过切区域正是方槽与四个孔的范围；

8 个角投到 NDC，必须全部落在 `[-1,1]` 内且跨度 > 0.15。**lookAt / perspective / 矩阵
乘法写错在浏览器里就是一片空白**，而这条断言能抓到它；光有桩测试抓不到。

### 顶点色进 Bevy 材质：四个坑

ADR-005 的调色板索引编码（R=索引、G=偏差）在 HTML 预览里早就生效，窗口里一直用
统一灰白的 `StandardMaterial`——**"功能做完但看不见"的唯一缺口**。现在补上了：

`assets/shaders/cut.wesl` + `CutMaterial`（自定义 `Material`，不接 PBR——只要
"顶点色 + 两个方向光"，15 行 WESL 比理解 PBR 扩展点短）。

**四个坑，每个都会让网格静默不渲染**：

| 坑 | 现象 | 修法 |
|---|---|---|
| **`assets/` 路径** | `ERROR: Path not found: crates/app/assets/shaders/cut.wesl` | `AssetPlugin.file_path` 指到项目根（Bevy 默认按可执行文件目录找） |
| **`import bevy_pbr::forward_io`** | `no shader registered for this module path` | 自己声明 `FsIn`，location 按约定编号（0=world_pos / 1=world_normal / 5=color） |
| **`front_facing`** | `no definition in scope for identifier: front_facing` | 它是 builtin：`fn fragment(in: FsIn, @builtin(front_facing) front: bool)` |
| **`AsBindGroup` 单元结构体** | `Expected a struct with named fields` | 加一个占位 `#[uniform(0)] pub unused: u32` |

**前两个最阴**：都只打一条 ERROR 日志，网格**静默不渲染**，画面看起来像"材质全黑"——
和之前那个相机 bug 一样的表现。**没有截图根本分不清是相机错了、材质错了、还是网格没传上去。**

**验证方式**：临时按高度给顶点 0/1/2/3 四个索引，截图应该分出四条水平色带
（浅蓝/浅绿/橙红）。确认管道通了再回退成真实的 `gpu.colors`。

> **数据侧还没接**：`extract_surface` 产出的 `colors` 现在是**常量索引 0**（毛坯灰），
> 要真正看到"按刀着色"还得接 ADR-005 的 `creator` 查询（brick 候选表 → 扫掠 id）。

### 截图验证：`--screenshot` 抓到的第一个 bug 就是"画面全黑"

```bash
cargo run --release --features window -- --screenshot out/shot.png
```

开窗 → 等 30 帧（首次渲染要编译管线、传网格）→ 截一张 → 等 120 帧让异步写盘
完成 → 退出。**这是无显示器环境下验证渲染层的唯一手段**——在此之前 `--window`
只能证明"跑起来不崩"，看不出画面对不对。

**第一次截图就抓到：3D 区一片背景色，只有 egui 面板。**

根因是 `PanOrbitCamera` 的**锚点固定是原点**：

```rust
// 错的写法：相机放在 center + offset，但 last_anchor_depth 用的是 |offset|
let eye = center + offset;
PanOrbitCamera::default().with_initial_anchor_depth(-(offset.length() as f64))
```

它的更新系统会用 `last_anchor_depth`（相机到**原点**的负距离）重算相机位置，
所以 `Transform` 里那个 `center` 被丢掉了。而毛坯中心在 (15, 6, −15)，
相机于是看着空处。

**修法：加一个 root 实体把模型中心搬到原点**，相机老老实实绕原点：

```rust
let root = commands.spawn((
    Transform::from_translation(-center),
    Visibility::default(),
    Name::new("model root"),
)).id();

// 毛坯和工具标记都挂成 root 的子实体
commands.spawn((Mesh3d(mesh), MeshMaterial3d(mat),
                Transform::from_rotation(z_up_to_y_up()), ChildOf(root)));
```

修完毛坯完整可见：面铣的台阶、方槽、四个孔、切削面的明暗过渡都对，
橙色工具标记也落在它该在的位置。

**这个 bug 值得记的原因**：它不会崩、不会报错、日志一切正常，`--window`
跑起来也"没毛病"。**只有截图能看出来**。渲染层之前的所有改动都是在
这个前提下"验证"的。

### 剖切平面：HTML 预览里能切开看内腔

五轴件的内腔不剖开根本看不见。预览页右下角的 HUD 加了一个滑块：

```glsl
uniform float uClipZ;
void main(){
  if (uFlat == 1) { o = vec4(0.16, 0.19, 0.23, 1.0); return; }  // 地面先返回
  if (vP.z > uClipZ) discard;
  vec3 n = normalize(vN);
  if (!gl_FrontFacing) n = -n;   // 剖开后看得到背面
  ...
}
```

**三处细节，缺一个都不对**：

1. **地面先 `return` 再 `discard`**——否则滑块拖到负值地面就整片消失，看起来很怪。
2. **背面法向要翻转**（`gl_FrontFacing`）——剖开后看到的是内腔的背面，不翻的话两个
   方向光都打不到，内腔一片死黑，等于没剖。
3. **滑块范围取模型 z 包围盒**（`LO[2]-1` 到 `HI[2]+1`），默认拖到最大 = 不剖，
   标签显示 `(关)`。**不写死数值**，换个工件范围自动跟着变。

`tools/check_preview.mjs` 加了三条断言（滑块在、`uClipZ` 在、`discard` 在）——
桩不做 GLSL 编译，所以只能查文本，真正的编译失败由页面的错误浮层兜住。

**顺带修了桩的一个坑**：原来所有 id 共用同一个 `el` 对象，缺 `addEventListener`，
加滑块后直接抛 `clipEl.addEventListener is not a function`。改成每个 id 一个独立元素
（更接近真实 DOM）。

### 增量重建：切一刀只重算被扫到的那几块

`render::TileCache` 是交互式仿真的核心：整体重提一次 200 mm 毛坯要 **404 ms**，
增量重建一次面铣只要 **35 ms**（**11×**），因为只重算 66 / 4017 块。

三条规矩，每条都是踩过坑的：

1. **分块提取不能有缝**：`voxel::extract_surface_lod_in` 按"发射格"划分——每个四边形
   由最小角所在的格发射一次，各块天然不重不漏。有一条测试把整块毛坯切成小块逐块提取，
   与整体提取**逐三角形比对**（坐标按位比较），一处都对得上。
2. **替换范围要比提取范围小一圈**：三角形按质心归属块，而区域边上的格会发射质心
   落在区域外的三角形。所以提取范围比"要替换的块"再外扩一块，边界上那些半残的块
   直接扔掉——它们离切削足够远，本来就没变。
3. **没变的块不重传**：提取结果逐字节与旧的比，一样就保留版本号；被整块切光的块
   从缓存里删掉。上传受 8 MB/帧 预算限制，**没传完的要记在队列里**——不记的话
   "下一帧再传"是假的：下一帧重新提取发现内容没变，那些块永远不会出现在屏幕上。

顶点色也接进了材质：`MeshData.colors` 的 `[调色板索引, 余量偏差+128, …]` 编码
（ADR-005）在预览着色器里按调色板展开——R 是索引不是红色分量，G 是偏差。

### kin 闭环：G 代码位姿 → 逆解 → 正解

在 `sim` 的集成测试里（`tests/kin_loop.rs`，放装配层是因为 `kin → gcode` 会违反
依赖方向）：解释器算出的每个位姿都要能被机床逆解、正解回到原点、A=0 奇异点要被
`check` 报出来。

**这一片抓到一个真 bug**：`kin::inverse` 的残差用的是 `cur × target`（叉积）。
叉积在**反平行**时也归零，而且它指向"转轴"方向，与雅可比的列（轴的切向）**正交**——
在 A=0 的奇异点上两者点积恒为 0，牛顿一步都迈不出去，48 次迭代后报"不可达"。
实测：从 A=0 起步解 A=20 的刀轴，永远失败。改成 `target − cur`（误差向量，与雅可比
同处切平面）后，5 条闭环测试全绿，原有的 500 例随机往返不受影响。

### 设计比对：过切 / 残留（`sim::compare`，10 个测试）

程序跑完之后回答最后两个问题：**该切掉的是不是都切掉了（残留），不该切的是不是没切（过切）**。
比对对象是设计成品——v1 只有轴对齐盒（`DesignModel::Box`），但口径是通用的：

| 指标 | 方法 | 精度 |
|---|---|---|
| 过切/残留**体积** | 体素积分：毛坯场符号 × 设计 SDF 符号 | ± 一个表面层 |
| 过切**最大深度** | **解析扫掠点测试**：设计面采样点 × 每段 `sd_sweep` | 掠切 ±5 µm（黄金分割收敛限），**不经过体素** |
| 残留**最大厚度** | 设计气区内材料体素到设计面的距离 + h/2 | ± h/2 = 0.05 mm 级 @ h=0.1 |
| 过切**区域** | 过切体素的包围盒 | 一眼看出是哪个特征切多了 |

**为什么过切深度不走体素**：i8 量化档 3.15 µm，0.01 mm 的判定会被量化噪声淹没；
解析测试直接问"设计面上的这个点是否曾被刀具包住"（`sd_sweep(p) < 0`），
精度只受黄金分割收敛限制。每点先用段扫掠 AABB（外扩 tol）预筛，78k 点 × 110 段也只有几十毫秒。

**一个从测试里逼出来的语义坑**：盒 SDF 在孔底给的是"到最近的盒面"的距离——
孔从设计顶切到 z=3（低于顶面 8 mm），SDF 却说 −3.05（到盒底）。
所以"过切体积深度"对贯穿特征会**饱和在设计体的内切圆半径上**，是个语义混乱的指标。
报告改说过切**区域包围盒**（`gouge_region`）：`区域 x 5.1..25.0 y 5.1..25.0 z 3.1..11.0`
——直接指出是方槽和孔切进了设计体。

**残留的口径**：设计气区里的**全部材料**都算残留，不限工具走廊——设计说"这里不该有料"，
它就是多余的，无论程序有没有试图去切。距离场在材料区内随远离设计面单调增，
最大值自动落在某个表面上（毛坯表面或切削面），所以不需要显式的表面体素判定；
+h/2 把体素中心修正到表面位置。

**一条强性质测试**：完美的面铣（刀底平面 = 设计顶面）过切必须是**精确的 0**——
共享边界上毛坯 SDF 与解析设计 SDF 的符号逐体素一致，一层都不该判进去。
实测通过（体素积分与解析测试双双为 0）；切深 0.5 mm 时体积 62.1 mm³（理论值），
解析深度 0.5 ± 0.005，报警带块号与源文件行号。

**报警编号**：`GOUGE`（Error，零件报废）/ `RESIDUAL`（Warning，没铣到位）/ `NONLINEAR`（Warning）。

### 非线性误差：关节空间线性插补的刀尖偏离（`kin::nonlinear_error`）

五轴联动的经典陷阱：控制器若按**关节空间线性插补**执行（每个插补周期把 5 个轴各走一步），
刀尖走的是绕回转中心的**空间曲线**，偏离 CAM 意图的直线。闭式公式：

```text
非线性误差 ≈ R · (1 − cos(Δθ/2))        # 弧与弦的拱高
```

- **口径**：默认模拟**无补偿裸插补**（最坏情况），用来判断后处理的点位密度够不够
  （Δθ_max = 2·acos(1−ε/R)：R=175 时 ε=0.01 mm → 每段 ≤1.22°）。RTCP 开启时
  控制器在位姿空间插补、刀尖走直线，这一段误差为零——本函数算的是"不补偿会偏多少"。
- **只用正解**：关节值由 `sim::run` 逐块调 `inverse` 拿到（上一块的解做下一块的
  种子，解不出就复位），函数本身只做 `forward` 采样（默认 32 点）。
- **两个早退**：旋转轴全程不动 ⇒ 链变换是"常量旋转 × 直线轴仿射"，刀尖恰在弦上，
  误差恒 0——三轴程序连采样都不做；起讫点重合（纯回转、刀尖定点）时弦退化为点，
  改量到点的距离，不能除零。
- **闭式对拍到 1e-9**：单旋转轴机床，刀尖 (0,0,R) 转 30°，最大偏差必须精确等于
  R(1−cos 15°)，出现在 t=0.5。

`RunConfig` 接线：`machine: Option<MachineTopology>`（`None` = 不算，三轴用户不该看到
这个指标）、`nonlinear_samples`。超 0.01 mm 报 `NONLINEAR` 报警，`worst_pose` 记
峰值时刻的实际刀尖位置，`max_nonlinear_line` 指回源文件。

演示（`--export`，AC 双转台 L=180）：A 摆 20° 的块，R ≈ 265 mm → 误差 4 mm 量级，
报警直指那一行——后处理该加密点位了。

### 后台任务与回放（`sim::job` + `sim::playback`，12 个测试）

`sim` 的 crate 文档从第一天就写着"仿真调度、回放缓冲、后台线程"——现在才真正兑现：

- **`run_observed`**（`run` 变成薄包装）：每块开始前回调一次观察者，返回 `false` 取消。
  **观察者只读**——同一份输入带不带观察者输出逐位相同（测试锁）。
  取消落在块边界，报告从部分状态定稿（体积/报警如实），追加 `CANCELLED` Info 报警。
- **`SimJob`**：整段仿真挪到工作线程，`mpsc` 回报 `Started → Progress* → Done`。
  进度按墙钟节流 50 ms（块 0 必发）；`Drop` 取消并 join，绝不泄漏线程。
  异步跑完的结果与同步 `run` **逐位一致**（同一代码路径，测试锁住）。
- **`Playback`**：块 → 时间区间的预计算，**与 `run` 同一套时间口径**（同样的圆弧离散、
  同样的 `segment_time`、同样的 M0/M2/M30 截断）。所以 `total_time()` 与
  `report.programmed_time_s` 逐位相等——报告说 8.64 s，时间轴就必须能拖到 8.64 s。
  `at(t)` 做二分 + tip 线性 + 刀轴 slerp；越界钳制。
- **`Hmi::ingest(report)`**：报警入队（不清旧——多版对比是常见操作），
  有 Error+ 进 `Faulted`，只升不降（要 `reset()` 才能离开）。

现在 UI 只差窗口：时间轴拖 `Playback::at`、进度条接 `SimJob` 事件、报警列表接 `ingest`。

### 解释器问题进报告（Trust 打通）

解释器遇到不认识的代码**不中断**——跳过、继续、并记一条 `ParseIssue`（稳定编号 + 严重度 + hint）。
但这套信息之前到不了用户手里：报告只有一个笼统的 `GCODE_ERROR` 聚合报警，还硬编码 Fatal——
把 Warning 级的"未知 M 代码"和 Error 级的"圆弧缺圆心"混成一锅。

现在 `sim::run` 把每条 issue 逐条映射成报警：**编号原样**（`GCODE-008` 就是 `GCODE-008`，
测试断编号不断言文案）、**严重度 1:1**（两层的 `Severity` 有意不共享，但四级语义一致）、
**行号进 TimeRef**（跳回源文件）。`overall_severity()` 自动给出总体可信度。
外加一条保险丝：解释器判了 `Unreliable/Aborted` 而报告里却没有 Error+ 报警时（正常不会发生），
兜底一条 `GCODE_TRUST`。

### 设计模型从 STL 加载（`voxel::stl` + `voxel::meshvol`）

`DesignModel::Field`：`--design part.stl` → 解析 → 体素化 → 与毛坯同网格的设计场。
比对代码一行没改——它只依赖 `sdf(p)` 和表面采样点。

- **`stl` 解析**（7 测试）：二进制（84+50n 尺寸公式**先行**——不少二进制文件的 80 字节头
  恰好以 "solid" 开头，按内容判别会撞坏，经典陷阱有测试锁）+ ASCII（令牌流，行号精确）。
  零依赖；不读法向量（STL 的法向经常是错的）；f32→f64 保持逐位值。
- **`meshvol` 体素化**（5 测试）：两个正交 pass——
  ①**符号**：逐行视差。每行 (y,z) 固定，+X 射线与三角形 (y,z) 投影做 2D 包含测试，
  交点排序后行走整行，奇偶定内外。对水密网格精确（凹形、多连通都行）；
  每行加 ±0.0005h 的确定性抖动，避免射线恰好擦边。
  ②**距离**：逐三角形把"AABB 外扩 band ∩ 域"内的体素精确化（点-三角形最近距离，
  clamped barycentric，与暴力采样 oracle 逐位一致）；带外的体素距离 ≥ band，
  保持 ±band——与毛坯场的窄带钳制同语义。
- **互证测试**：同一个盒，解析 `Box` 设计与 STL 文件走完整链路的 `Field` 设计，
  在同一个过切程序上数字一致（深度 ±0.005、体积同区间、残留同精度）——
  两条完全独立的路径互相是对方的 oracle。
- 坑：桶插入必须**每桶一次**而不是每格一次——重复插入让同一平面产生几十个相同交点，
  奇偶被两两抵消，整场判定为外（实测踩过，探针半小时）。

### 面板数据层：`cncsim-ui` 是纯函数，不是 bevy 系统

`ui` 之前是 28 行的空壳，而 `render::shell` 里的 egui 面板**直接 match `ControlState`
画颜色**——架构铁律第 6 条（`ui` 只依赖 `hmi`）形同虚设，因为没有任何东西需要 `ui`。

这一片把它做实，但**刻意不写任何 `egui::Ui`**：`UiView` 只返回 `&'static str`、
`Tone`、`Vec<AlarmRow>`。理由不是洁癖，而是可测性——

| 判据 | 为什么必须"是判据" |
|---|---|
| 六种状态横幅**文案互不相同** | 两态显示同一句话，用户分不出"在跑"和"卡住了" |
| 四级严重度**徽标互不相同** | 两级都用 `[!]`，"跑完看看就行"和"别上机床"就分不开 |
| 报警**按严重度降序** | 一屏 30 条时，"最严重那条在哪"是判据问题不是排版问题 |
| 复位键**只在卡死时亮** | 正常运行中摆个亮着的复位键 = 送一个误触机会 |
| 位置串是 `t / 块 / 行` **三元组** | 只有编号和消息的报警，用户知道错了但不知道去哪改 |

这五条全都能在没有显示器、没有 Bevy 的 `cargo test` 里锁定。**改排布、改配色不会让测试变红；
改判据才会**——这正是 UI 测试该有的信噪比。

`render::shell` 只做两件适配：`Tone → egui::Color32`（映射只有一处）、
`AlarmRow → colored_label + weak 小字`。报警列表因此多了位置与 hint 两行，
而这部分逻辑**窗口版和预览版共用同一份**。

**TDD 记录（红 → 绿 → 证伪）**

1. **红**：先只写 6 个测试，`cargo test` 报 `E0599: no method named status_tone`——
   因为功能不存在，不是拼写错。
2. **绿**：补 `Tone` / `AlarmRow` / `status_tone` / `reset_enabled` / `alarm_rows`。
3. **证伪四轮**（每次改坏一处，跑，复原）：

| 改坏 | 结果 |
|---|---|
| 排序方向反过来 | `left: ["A","C","D","B"] right: ["B","D","C","A"]` |
| `Fatal` 徽标改成 `[E]` | `四级严重度徽标应互不相同，实际 ["[E]","[E]","[W]","[i]"]` |
| `reset_enabled` 恒 `true` | Idle 态断言失败 |
| 位置串块号写成 `0` | **第一次漏掉了** |

第 4 条是我自己写错的测试：原来用 `location.contains('4')` 断言块号，
而 `t=3.742` 里本来就有个 `4`——`块 0` 也能通过。改成**整串相等**
（`"t=3.742s · 块 4 · 行 5"`）之后才抓住。**`contains` 用在拼接串上是假阳性制造机。**

**架构上一处取舍**：`ui` 不能依赖 `sim`，但面板要看 `Alarm`/`Severity`。
解法是让 `hmi` 显式重导出（`pub use cncsim_sim::{Alarm as AlarmView, Severity}`）——
**UI 的唯一入海口就只有这么大**，加宽要改那一行。`check_deps.py` 的白名单同步给
`render` 加了 `hmi`/`ui` 两条边（反向不允许：`ui → render` 会让面板逻辑分裂成两套）。

## 已知问题

**全局统一 k，还没有自适应。** 曲率大的地方（小圆角、尖边）跟平面用同一个 `h_c`，
所以"面数花得不均匀"。自适应 LOD 需要八叉树跨级拼接的过渡格，是另一个量级的复杂度；
当前先保证"进得了预算"和"不说谎"。

**k=2 的缓存局部性差**（800 万顶点，1.68 s）。真要常态化 k=2，角点缓存要换成按 level-1 节点分块。

**块索引的第一遍仍是串行**（1600 万次块表查找，约 0.25 s）。要再快得给块表分片 + 计数归并，
但那已经只占总时间的 30%，收益不如先把 `sd_profile` SIMD 化。

**顶点色还没进 Bevy 材质。** `MeshData.colors` 的调色板索引编码（ADR-005）在 HTML 预览的
着色器里已经生效，但 Bevy 侧还是统一灰白——差一层 `ExtendedMaterial` + WESL。
剖切平面、按视距切 LOD、`TileCache` 增量上传也还没接进窗口。

**网格设计要求水密。** 视差符号对非水密网格不可靠（距离仍精确，内外可能互换）——
CAM/切片器导出的 STL 天然水密；手工网格要先补洞。STEP（B-rep）需要几何内核，不做。
