# 并发与性能

> 日期：2026-10-28
> **修订 2026-10-29**：§2 的"材料去除不能并行"要读成**段间**不能并行。段内是并行的
> （每个体素只读自己那一个值），已实现并实测：200 mm 直槽 1002 → 142 ms（7.1×），
> 200 mm 毛坯提取 14.9 → 3.0 s（5.0×），200 段连续切削 10.35 → 1.89 ms/段（5.5×）。
> 并行池用 **rayon 常驻池**——手写 `thread::scope` 每次 fork 491 µs，在 1.9 ms 的段上占 26%。
> 见 [ADR-009](ADR-009-段内并行.md)。
> 目标：无锁并发、高吞吐、低延迟——但要先说清楚**哪些地方值得做**

---

## 0. 结论

**先说一句可能不中听的：在这条流水线上，把 mutex 换成无锁环形缓冲，对吞吐的贡献约 0.01%。**

四句话：

1. **材料去除在段间是串行的**——第 N+1 段要读第 N 段切完的毛坯。但**段内是并行的**：一次切削里每个体素只读自己那一个值（`max(d_cur, −sd_sweep)` 与邻居无关）。所以粒度是"一次切削内的体素切片"，实测 6.5×（[ADR-009](ADR-009-段内并行.md)）。
2. **真正的并行粒度是 brick，不是段**——brick 之间完全独立，可以 rayon 分片，**零共享、零锁**。这才是"无锁高并发"的正确形态。
3. **SPSC 环形缓冲该做**，但理由是**消除抖动**（避免持锁线程被抢占导致 UI 卡顿），不是提高吞吐。
4. **真正的性能杠杆在别处**：SIMD、避免分配、内存布局。这些比锁优化高一个数量级。

| 手段 | 预期收益 | 备注 |
|---|---|---|
| **SIMD 化 `sd_profile`** | **3–6×** | 最值钱 |
| **热路径零分配** | 1.2–2× | 第二值钱 |
| **brick 级并行（已实现，rayon 池）** | **5.5–7.1×**（实测，24 核） | 见 ADR-009 |
| 缓存对齐（brick 4 KB） | 1.2–1.5× | |
| SPSC 无锁替代 mutex | **0.01%** | 但消抖有价值 |
| 段间并行 | **不可能** | 数据依赖 |

## 1. 先看数据流：哪里真的需要并发

```
预读线程 ──PointStream──▶ 仿真线程 ──TileUpdate──▶ 主线程
   │                        │
   └ 插补+IK ~1µs/点         └ 去除+碰撞 ~0.2ms/子步   ← 唯一的瓶颈
```

**只有三个跨线程交接点**，而且都是 **SPSC**（单生产单消费）：

| 交接 | 类型 | 每段次数 |
|---|---|---|
| 点流 | SPSC | 25 |
| tile 更新 | SPSC | 1–3 |
| 诊断/进度 | SPSC | 1 |

每段约 30 次跨线程操作。假设每次无锁省 10 ns → **0.3 µs/段**。

对比每段 5 ms 的去除：**0.006%**。

> 所以：**无锁不是性能问题。** 但如果目标是"低延迟、无抖动"，它仍然值得做——理由在 §4。

## 2. 材料去除为什么**段间**不能并行

```rust
for pt in point_stream {
    voxel.cut(&tool, &prev, &pt.pose);   // 读上一状态，写新状态
}
```

第 N+1 次切削的输入是第 N 次的输出。**这是严格的串行链**，没有任何办法把两个相邻子步并行。

有人会想：那把 `SparseGrid` 做成 `Arc<Mutex<...>>`，多个线程各切一段？

**不行，两个理由**：

1. **结果不确定**——并行切削的顺序不定，而 CSG 减法不满足交换律在数值上（浮点非结合），毛坯会随运行波动。
2. **锁粒度无法合理**——一次切削要读邻居 brick 的 SDF 做插值，锁住 1 个 brick 不够，锁住一片就等于串行。

**结论：`SparseGrid` 必须单一所有者。** 这不是妥协，是正确性要求。

> **补充（2026-10-29）**：上面说的是**两个相邻子步**不能并行。**一个子步内部**可以：
> 体素之间零依赖，所以"并行求值 + 串行落盘"就够了，`SparseGrid` 依然单一所有者。
> 实测 1002 → 153 ms，剩下的 87 ms 就是串行落盘——这条 Amdahl 上限来自"树必须单写"，
> 而不是来自"没有并发可加"。见 [ADR-009](ADR-009-段内并行.md) §2。

> **最无锁的并发是不共享。** 单一所有者比任何锁都快，而且结果是确定的。

## 3. 真正的并行粒度：brick（零共享）

单次切削内部有并行空间——扫掠体可能覆盖多个 brick：

```rust
// 一个子步：先收集被扫掠体影响的 brick
let dirty: SmallVec<[BrickId; 8]> = sweep.overlapping_bricks(&grid);

// 这些 brick 完全独立（各自的 SDF 数组），可以 rayon 分片
dirty.par_iter().for_each(|&id| {
    grid.apply_cut_to_brick(id, &sweep);     // 只写自己那块
});
```

### 3.1 关键：brick 之间真的没有共享

| 操作 | 是否跨 brick |
|---|---|
| 更新 SDF 值 | ❌ 只写自己 |
| brick 状态迁移（Band→Empty） | ❌ 只看自己 |
| 提取网格 | ❌ 每砖独立 |
| 插值查询 | ⚠️ **跨砖**（读邻居） |

**唯一跨砖的是"查询"**，而查询在切削阶段只用于**刀具 SDF**（解析的，与毛坯无关）。所以切削阶段 brick 之间是**完全独立**的。

这就是"零共享并行"——不需要任何锁，也不需要原子操作。

### 3.2 怎么拿到不重叠的 `&mut`

`rayon` 的 `par_iter_mut` 只能遍历整个切片。要按任意索引取不重叠的可变引用，两个办法：

```rust
// 办法 A（推荐）：排序去重后取裸指针，由不重叠不变量保证安全
let mut ids = dirty.to_vec();
ids.sort_unstable();
ids.dedup();                                    // ← 不重叠的前提
debug_assert!(ids.windows(2).all(|w| w[0] != w[1]));

let ptrs: Vec<*mut Leaf> = ids.iter().map(|&i| &mut leaves[i] as *mut _).collect();
// SAFETY: ids 已排序去重，每个指针指向不同元素
ptrs.par_iter().for_each(|&p| unsafe { (*p).apply_cut(&sweep) });
```

```rust
// 办法 B：脏标记位图 + par_iter_mut（安全但慢）
leaves.par_iter_mut().enumerate()
    .filter(|(i, _)| dirty_bitset.contains(*i))
    .for_each(|(_, leaf)| leaf.apply_cut(&sweep));
// 代价：每子步扫全部 39 万个叶 —— 比切削本身还慢，不可用
```

**选 A**，把"排序去重 ⇒ 索引不重叠"写成不变量注释 + `debug_assert`。

### 3.3 并行有门槛

brick 数少于 4 时 rayon 的分发开销超过收益：

```rust
if dirty.len() >= 4 { parallel } else { serial }
```

典型子步只脏 1–3 个 brick → **大多数时候走串行分支**。只有长距离快移（扫过几十个 brick）才真正并行。

**所以这条优化的实际收益集中在 G0 快移和大切深**，对精细的五轴联动帮助有限。这是实话。

## 4. SPSC 环形缓冲：该做，但为消抖

### 4.1 为什么不是为吞吐

见 §0：0.006%。

### 4.2 为什么仍然值得

| 场景 | mutex 的问题 | 无锁 |
|---|---|---|
| 消费者持锁时被 OS 抢占 | 生产者阻塞到时间片结束（**毫秒级**） | 生产者继续写，直到缓冲满 |
| 优先级反转 | 低优先级持锁，高优先级等 | 不存在 |
| UI 拖时间轴 | 若走锁，可能卡一帧 | 恒定 µs 级 |

**对交互式工具，"最坏延迟"比"平均吞吐"重要。** 这就是无锁的真正理由。

### 4.3 实现要点

```rust
pub struct SpscRing<T, const N: usize> {
    slots: Box<[UnsafeCell<MaybeUninit<T>>]>,   // N 必须是 2 的幂
    /// 消费者写、生产者读
    head: CachePadded<AtomicUsize>,
    /// 生产者写、消费者读
    tail: CachePadded<AtomicUsize>,
}

impl<T, const N: usize> SpscRing<T, N> {
    /// 生产者调用。返回 false 表示满。
    pub fn push(&self, v: T) -> bool {
        let tail = self.tail.load(Relaxed);
        let head = self.head.load(Acquire);          // 看消费者进度
        if tail.wrapping_sub(head) >= N { return false; }
        unsafe { (*self.slots[tail & (N - 1)].get()).write(v); }
        self.tail.store(tail.wrapping_add(1), Release);  // 发布
        true
    }

    /// 消费者调用。
    pub fn pop(&self) -> Option<T> {
        let head = self.head.load(Relaxed);
        let tail = self.tail.load(Acquire);          // 看生产者进度
        if head == tail { return None; }
        let v = unsafe { (*self.slots[head & (N - 1)].get()).assume_init_read() };
        self.head.store(head.wrapping_add(1), Release);
        Some(v)
    }
}
```

**四个必须做对的点**：

1. **`N` 是 2 的幂**，用 `& (N-1)` 代替取模。
2. **`Acquire`/`Release` 配对**，不能全用 `SeqCst`（那是 3–5× 的代价），也不能全用 `Relaxed`（会重排）。
3. **`CachePadded`**——见 §5，这是 SPSC 里最值钱的一行。
4. **索引用 `wrapping_add`**，避免溢出 UB。

### 4.4 不要自己写 MPMC

多生产者/多消费者无锁队列（Vyukov 有界队列）要处理"槽位被回收"的 ABA 问题，正确性极难。**我们的三个交接点全是 SPSC**，不需要 MPMC。

## 5. false sharing：SPSC 里最值钱的优化

生产者只写 `tail`，消费者只写 `head`。如果两个字段在**同一条 cache line**（64 B）里：

```
Core A 写 tail  →  使 Core B 的整条 line 失效
Core B 写 head  →  使 Core A 的整条 line 失效
→ 每次操作都是一次 cache miss，性能掉 3–5 倍
```

```rust
#[repr(align(128))]              // 128 B 更保险（部分 CPU 是 128）
pub struct CachePadded<T>(pub T);
```

**这一行代码通常比"用无锁代替 mutex"带来的收益还大**——因为它影响的是每次内存访问，而不是每次系统调用。

> 判据：如果 benchmark 显示 SPSC 的吞吐远低于理论值（< 5000 万次/秒），先查 false sharing，别怀疑算法。

## 6. 真正的性能杠杆

按"收益/成本"排序：

### 6.1 SIMD 化 `sd_profile`（3–6×）

> **进度 2026-10-29**：先做了"不引 SIMD 的那一半"——去掉每次求值的 `acos`（`slerp` 里的）
> 与 `hypot`，把 t 的依赖提成标量多项式。每次求值 **19.0 → 14.7 ns**（平移）、
> **32.5 → 21.0 ns**（带转），端到端 200 mm 直槽 **139 → 117 ms**。
> 真正的 SIMD（4 个点一批）还没做：那要把切削内层改成 SoA + 掩码处理分支，
> 是另一个量级的改动。

内层循环是每子步几十万次的 SDF 求值，目前是标量。用 4/8 宽 SIMD（`std::simd` 或手写 `_mm256_*`）批处理体素：

```rust
// 标量：一次一个点
for i in 0..n { out[i] = sd_profile(pts[i], &prof); }

// SIMD：一次 8 个点
for i in (0..n).step_by(8) { out[i..i+8].copy_from_slice(&sd_profile_x8(&pts[i..i+8], &prof)); }
```

**前提**：把点数据改成 SoA（`xs: Vec<f32>, ys: Vec<f32>, zs: Vec<f32>`），否则 gather 的开销会吃掉收益。

### 6.2 热路径零分配（1.2–2×）

每子步都会产生一些临时 `Vec`（脏 brick 列表、网格顶点）。全部改成**复用的对象池**：

```rust
struct Scratch {
    dirty: Vec<BrickId>,
    verts: Vec<f32>,
    indices: Vec<u32>,
}
// 每子步 clear() 复用，容量不缩
```

`clear()` 保留容量，比 `Vec::new()` 快一个数量级。

### 6.3 缓存对齐（1.2–1.5×）

- brick 数据 4 KB（16³ × i8... 实际 8³ = 512 B，正好一个 L1 的 1/64）
- **让每个 brick 的数组 64 B 对齐**，避免跨 cache line

### 6.4 减少内存带宽

i8 量化已经做了（ADR-002）。**下一步是压缩 Full/Empty brick**——不分配数组，只存状态。稀疏树已经做了（ADR-006）。

## 7. 低延迟专项

| 目标 | 措施 |
|---|---|
| **UI 帧 < 16.7 ms** | 主线程只做上传与 egui；**不做任何几何计算** |
| **拖时间轴 < 5 ms** | `pose_at` + IK，µs 级；不查点流（见预读文档 §5） |
| **首帧出图 < 500 ms** | 第一个 tile 完成即可播，不等整份算完 |
| **取消 < 1 ms** | 置位 `AtomicBool`，丢缓冲，起新任务；**不 join** |
| **无 GC 停顿** | Rust 天然满足 |

### 7.1 不要用全局 rayon 池做低延迟任务

rayon 的 work-stealing 会带来 **µs 级抖动**（steal 时要锁 victim 的队列）。所以：

- **批量计算**（brick 级并行切削）→ 用 rayon，抖动无所谓
- **低延迟路径**（UI、回放）→ 专用线程，不用 rayon

### 7.2 Bevy 侧

- **`Assets<Mesh>` 内部是 RwLock**。多系统同时上传会竞争。**把 mesh 上传集中到一个系统里**，并且每帧限量（§6.2 的 8 MB 预算）。
- Bevy 的系统调度本身是**无锁的**（基于 archetype 的访问冲突检测），不需要额外优化。

## 8. 反模式

| 反模式 | 为什么错 |
|---|---|
| `Arc<Mutex<SparseGrid>>` | 结果不确定 + 锁粒度无法合理，见 §2 |
| 原子化稀疏树（RCU/epoch） | 复杂度极高，而单一所有者已经是最快 |
| 自己写 MPMC 队列 | 我们全是 SPSC，不需要 |
| 全用 `SeqCst` | 比 `Acquire`/`Release` 慢 3–5×，且无必要 |
| 用 `AtomicUsize` 但忘了 padding | false sharing 吃掉全部收益 |
| 为了"无锁"放弃确定性 | 仿真结果必须可复现，**确定性优先于性能** |
| 用全局 rayon 池跑 UI 路径 | work-stealing 抖动 |

**最后一条最要紧**：这是一个**验证工具**，结果必须可复现。任何引入不确定性的"优化"都应该拒绝——哪怕它更快。

## 11. 吞吐与延迟：两个都要，怎么做到

> 结论：**它们不冲突，除非你让它们抢同一批 CPU 核。** 而这里有一个关键数字让问题消失。

### 11.1 一个让问题消失的数字

| 方案 | 每子步 | 100k 段总耗时 | 相对实时 |
|---|---|---|---|
| 标量现状 | 0.20 ms | 8.3 min | **14×** |
| SIMD 后 | 0.10 ms | 4.2 min | **29×** |
| SIMD + 零分配 | 0.08 ms | 3.3 min | **36×** |

**仿真全速是 14–36 倍实时，而用户回放最快也就 8 倍。**

所以：**交互模式下"全速算"是纯粹的浪费**——算得比看得快 4 倍以上，多出来的算力只是在抢 UI 的核。

这就是"两个都要"能成立的物理基础：**吞吐的"够"是相对回放速度而言的，不是"无限快"。**

### 11.2 收益矩阵：哪些手段双赢，哪些真冲突

| 手段 | 吞吐 | 延迟 | 性质 |
|---|---|---|---|
| **热路径零分配** | ✅ 1.2–2× | ✅ 减少 malloc 抖动 | **双赢** |
| **SIMD 化** | ✅ 3–6× | ✅ 每次操作更短 | **双赢** |
| **缓存对齐 / 数据布局** | ✅ | ✅ | **双赢** |
| SPSC 无锁 | 0.01% | ✅ 消抖 | 主要服务延迟 |
| **brick 级 rayon 并行** | ✅ 1.5–3× | ⚠️ **抢核** | **冲突** |
| **仿真线程全速跑** | ✅ | ⚠️ **抢核 + 抢带宽** | **冲突** |

**只有后两项是真冲突。** 前四项改善吞吐的同时也改善延迟——因为它们减少的是"每次操作的工作量"，而不是"同时占用多少资源"。

**所以：先把前四项做满，冲突就只剩"用多少核"这一个旋钮。**

### 11.3 冲突的三个具体点

| 资源 | 冲突表现 | 量级 |
|---|---|---|
| **CPU 核** | 仿真线程跑满 → 主线程被抢占 → 掉帧 | 主因 |
| **内存带宽** | 仿真 SIMD 打满带宽 → 主线程上传延迟升高 | 次要（上传只占 1%） |
| **分配器** | 多线程 malloc 争全局堆 | 零分配后消失 |

内存带宽算一下：主线程每帧上传 8 MB × 60 fps = 480 MB/s，而 DDR4 双通道约 50 GB/s → **占 1%**。所以带宽不是主要矛盾。

**主因就是 CPU 核。**

### 11.4 解法一：双模式（核心）

```rust
pub enum ComputeMode {
    /// 交互：限速跟随回放，把 CPU 留给 UI
    Interactive { speed_cap: f64 },   // 例如 4.0 倍实时
    /// 批处理：全速，UI 只显示进度
    Batch,
}
```

```rust
// 仿真线程主循环
loop {
    if let ComputeMode::Interactive { speed_cap } = mode {
        let ahead = computed_until - playback_time;
        if ahead > LOOKAHEAD_SECS {
            park_until(playback_time + LOOKAHEAD_SECS);   // 睡到需要为止
        }
        let target_rate = speed_cap;                       // 每秒最多算这么多仿真秒
        throttle(target_rate);
    }
    step_one_substep();                                    // 真正干活
}
```

**两种模式服务不同的用户意图**：

| 模式 | 用户意图 | 总耗时 | 帧率 | 追上计算前沿时 |
|---|---|---|---|---|
| **交互**（限速 4×） | "边看边调" | 30 min（2 小时程序） | **稳定 60 fps** | 偶尔等一下 |
| **批处理** | "先算完再看" | **3.3 min** | 可能掉到 45 fps | 不会 |

**注意交互模式的 30 min 不是损失**——用户本来就要看 120 分钟（1× 回放），限速 4× 仍然远快于观看。

**切换要无感**：用户点"批处理"时不停仿真，只是解除限速；点回"交互"时重新限速。模式是 `AtomicU8`，仿真线程每批读一次。

### 11.5 解法二：线程优先级

即使限速，仿真线程仍会突发占用。用 OS 优先级保证 UI 永远优先：

```rust
use thread_priority::*;

// 主线程 / 渲染线程：高于普通
set_current_thread_priority(ThreadPriority::Crossplatform(50.try_into()?))?;

// 仿真线程：低于普通
std::thread::Builder::new()
    .spawn(|| {
        set_current_thread_priority(ThreadPriority::Crossplatform(20.try_into()?)).ok();
        sim_loop()
    })?;
```

| 平台 | 机制 |
|---|---|
| Windows | `SetThreadPriority`：UI `ABOVE_NORMAL`，仿真 `BELOW_NORMAL` |
| Linux | `nice`：UI 0，仿真 +5 |
| macOS | `pthread_setschedparam` |

**这一条比任何算法优化都直接**——它让 OS 保证 UI 线程不被仿真抢占。代价是仿真在 UI 忙时变慢（正是我们要的）。

### 11.6 解法三：核分配与 rayon 并发度

```rust
// 交互模式：限制 rayon 并发度，给 UI 留核
let pool = ThreadPoolBuilder::new()
    .num_threads(if interactive { 2 } else { num_cpus::get() - 2 })
    .build()?;
```

| 模式 | rayon 线程数 | 理由 |
|---|---|---|
| 交互 | **2** | 留 2 个核给主线程 + 渲染 |
| 批处理 | `ncpu - 2` | 尽量快，UI 掉几帧可以接受 |

**并且 brick 并行只在脏 brick ≥ 4 时启用**（见 §3.3）——典型子步只有 1–3 个砖，根本不进 rayon，所以交互模式下这条路径大部分时候是零开销的。

### 11.7 延迟要看 p99，不看平均

60 fps 的要求是**每一帧**都在 16.7 ms 内，不是平均 16.7 ms。

```
平均 8 ms 但 p99 = 25 ms  →  每秒掉 1–2 帧，用户能感觉到
平均 12 ms 且 p99 = 15 ms →  完全流畅
```

**所以验收指标必须是 p99，不是平均。** 这也解释了为什么 §4 要用无锁而不是 mutex——mutex 的平均开销很低，但**被抢占时会拖到毫秒级**，直接污染 p99。

### 11.8 预算表

**延迟预算（交互模式，60 fps）**

| 项 | 预算 |
|---|---|
| ECS + 渲染 | 8.0 ms |
| egui | 2.0 ms |
| mesh 上传（8 MB） | 3.0 ms |
| **余量** | **3.7 ms** |

余量要覆盖：文件对话框、egui 重排、GPU 驱动抖动。**不要占满。**

**吞吐预算（批处理模式）**

| 项 | 目标 |
|---|---|
| 单子步 | ≤ 0.1 ms（SIMD 后） |
| 100k 段 | ≤ 4.2 min |
| 相对实时 | ≥ 28× |

### 11.9 验收：两个都要测，且分开测

```rust
// 吞吐基准（批处理模式）
fn bench_throughput_batch(c: &mut Criterion) { /* 目标 ≤ 0.1ms/子步 */ }

// 延迟基准（交互模式 + 仿真线程后台跑满）
fn bench_frame_p99_under_load(c: &mut Criterion) {
    // 关键：仿真线程全速跑的同时，测主线程帧时间
    // 目标：p99 ≤ 16.7 ms
}

// 模式切换不产生卡顿
fn bench_mode_switch_no_hitch(c: &mut Criterion) { /* 目标：切换帧 < 20ms */ }
```

**第二条是最容易漏的**：只测空闲帧率没有意义，必须**在仿真满载时测帧时间**。这才是真实场景。

### 11.10 一句话

**"两个都要"能成立，是因为仿真本来就快 14–36 倍，而用户最多看 8 倍——交互模式下"全速"是浪费。**
**双模式 + 线程优先级 + 限制 rayon 并发度**，三个开关就能同时拿到"批处理 3.3 分钟"和"交互稳定 60 fps"。
**而零分配、SIMD、数据布局这三项，本来就是双赢，不需要取舍。**

---

## 12. 一句话

**"无锁"的收益是消抖，不是提速**；**真正的性能来自 SIMD 与零分配**；**吞吐与延迟能同时要，因为仿真本来就快 14–36 倍而用户最多看 8 倍**——交互模式限速、批处理全速，两个开关各服务一种意图。
