G 代码解释器设计

解释器模态机

日期：2026-10-28 对应 crate：cncsim-gcode（依赖 math / motion / tool） 补充主方案 §5

0. 结论

G 代码解释器是继运动学之后最大的正确性风险——解析错一行，后面所有运动都错，而画面依然"在动"。所以它的边界要划得比其它模块更死。

四句话：

  1. 只做"文本 → 运动程序"，不做运动学。 输出的是工件坐标系下的位姿，不是关节值。
  2. TWP（G68.2）归解释器，RTCP（G43.4）归 kin。 前者是坐标变换，后者是机床运动学——混在一起解释器就绑死机床了。
  3. 一次性解析成不可变 MotionProgram，支持按块随机访问。不做流式。
  4. 跳过无法解析的块要标记"程序不可信"，不能只记个警告——G91 下跳过一块会静默污染后面所有位置。

1. 边界

1.1 做什么

职责 说明
词法 字地址 X-1.5、X[#1+2]、注释、行号
块解析 一行 → 若干字地址
模态状态机 G90/G91、G20/G21、G54–G59、G17–G19……
坐标变换 WCS 偏置、TWP（G68.2）、G92 工件坐标设定
刀具补偿语义 G43 刀长、G41/G42 半径补偿（都已实现，见 §8.2）
圆弧参数化 I/J/K 与 R 两种写法 → 圆心 + 起止角
进给模式 G93 倒数时间 / G94 mm·min⁻¹ / G95 mm·rev⁻¹
诊断 不可解析的块、未定义模态、非法参数

1.2 不做什么

不做 归谁 为什么
关节值反解、RTCP cncsim-kin 解释器一旦调 kin，就绑死在某台机床上
段内插补与时间 cncsim-sim 时长取决于轴速上限，那是机床属性
材料去除、碰撞 voxel / collide 完全无关
文件读写 cncsim-app I/O 不进领域层

1.3 关键区分：TWP 与 RTCP 不是一回事

这两者经常被混为一谈，但归属完全不同：

TWP（G68.2 倾斜工作平面） RTCP（G43.4 刀尖跟随）
本质 坐标系变换：程序坐标在一个倾斜的平面里 机床运动学：程序坐标是刀尖位置，控制器反解直线轴
是否依赖机床 不依赖，任何五轴机都一样 强依赖，每种构型公式不同
归谁 解释器 kin

判断标准：如果这个变换只需要知道"工件怎么摆"，就在解释器；如果需要知道"机床有几个轴、轴朝哪"，就在 kin。

2. 输出数据结构

pub struct MotionProgram {
    pub blocks: Vec<Block>,        // 按源文件顺序，不可变
    pub issues: Vec<ParseIssue>,   // 解析问题（不中断）
    pub trust: Trust,              // 结果可信度
}

pub struct Block {
    pub line_no: u32,              // 源文件行号（UI 高亮用）
    pub motion: Motion,            // Rapid / Linear / Arc / Dwell / None
    pub target: Pose,              // 工件坐标系下的目标位姿
    pub feed: Feed,                // 值 + 模式（G93/94/95）
    pub interp: InterpMode,        // RTCP 开/关、精确停/连续
    pub wcs: WcsId,                // 当前工件坐标系（仅显示用，坐标已解析）
    pub tool: ToolNo,
    pub spindle_rpm: Option<f64>,
}

pub enum Motion {
    Rapid,
    Linear,
    Arc { center: DVec3, cw: bool, plane: Plane },
    Dwell { secs: f64 },
    None,                          // 纯状态块（如 G54、M8）
}

/// 关键：位姿已在**单一工件坐标系**下，下游不需要知道 G54 有几个
pub struct Pose { pub tip: DVec3, pub axis: DVec3 }   // axis 由刀尖指向主轴

Block 是"已解析完的语义"，不是"待解释的原文"。下游拿到的块不需要再做任何模态判断。

3. 模态状态机

3.1 结构

struct ModalState {
    distance: DistanceMode,      // G90 / G91
    units: Units,                // G20 / G21
    plane: Plane,                // G17 / G18 / G19
    feed_mode: FeedMode,         // G93 / G94 / G95
    wcs: WcsId,                  // G54–G59, G54.1 P_
    cutter_comp: CutterComp,     // G40 / G41 / G42
    length_comp: LengthComp,     // G43 / G44 / G49 + H 号
    tcpm: Option<TcpmMode>,      // G43.4 / G43.5
    twp: Option<TwpFrame>,       // G68.2 / G68.3
    motion: MotionKind,          // G0 / G1 / G2 / G3（模态）
}

解析是一个 fold：state' = step(state, block)。每个块产出一个 Block，同时更新状态。

3.2 块内执行顺序（最容易被忽略的坑）

一行里可能同时有 G43 H7 G1 Z-5 F200。这些不是同时生效的，有固定顺序。

但顺序与字在行内的位置无关。 overview.adoc §Item order 明文：

The first group (the words) may be reordered in any way without changing the meaning of the line.

所以 G91 G1 X10 与 G1 X10 G91 完全等价，都是增量。 （早期版本这里写"后者按上一状态"——那是错的，已按原文更正。）

顺序由下面这张表（overview.adoc §G-code Order of Execution 的 25 项）决定：

 0  O-word 流程控制
 1  注释 / 消息
 2  进给模式 G93 G94 G95
 3  进给率 F
 4  主轴转速 S
 5  刀具选择 T
 6  HAL 引脚 IO  M62–M68
 7  换刀 M6 / 设定刀号 M61
 8  主轴启停 M3 M4 M5
 9  保存状态 M70 M73 / 恢复 M72 / 作废 M71
10  冷却 M7 M8 M9
11  倍率开关 M48 M49
12  用户自定义 M100–M199
13  停延 G4                    ← 在平面/单位/补偿/距离之前
14  平面选择 G17 G18 G19
15  单位 G20 G21
16  刀径补偿 G40 G41 G42
17  刀长补偿 G43 G49            ← 必须在运动之前
18  坐标系选择 G54–G59.3
19  路径控制 G61 G61.1 G64
20  距离模式 G90 G91            ← 必须在运动之前
21  退刀模式 G98 G99
22  回参考点 G28 G30 / 改坐标数据 G10 / 设轴偏置 G52 G92
23  运动 G0–G3 G33 G38.n G73 G76 G80–G89（受 G53 修饰）
24  停机 M0 M1 M2 M30 M60

为什么必须定死：

  • 17 在 23 之前：G43 H7 G1 Z-5 若先动后补，第一刀会偏一个刀长。
  • 20 在 23 之前：G91 G1 X10 若不生效，会走成绝对坐标。
  • 2 在 3 之前：G93 F0.5 里 F 是倒数时间，不是 mm/min。
  • 13 在 14–20 之前：这是最容易写错的一条——停延排在平面/单位/补偿/距离模式之前，不是最后。

实现方式：让顺序成为结构而不是约定。 一行里的操作先收进 Vec<Op>， 按 Phase 排序后执行，而不是按字出现的顺序执行。这样谁往 ops 里塞东西都不会打乱它。

顺序写错，单字测试全过，只有组合块才会错。所以测试必须专门覆盖"同一行多个模态字"， 并且必须有一条"字序无关"的测试——cncsim-gcode 的 word_order_within_a_block_does_not_matter 就是干这个的。去掉排序后它会报 110.0 vs 10.0，正是"依赖字位置"的症状。

4. 坐标系统一：G54 归谁

这是最容易设计错的地方。

4.1 问题

程序里的 X/Y/Z 是当前工件坐标系下的值。而 cncsim-kin 需要的是相对机床的位姿。中间隔着一个 WCS 偏置。

如果让解释器只输出"程序坐标 + WCS 编号"，那 kin 就得懂 G54 表；如果让解释器输出机床坐标，那它又得懂机床几何。两边都不对。

4.2 解法：解释器解析到单一工件坐标系

  • 机床模型里定义一个工件坐标系（例如摇篮的 C 台面中心），这是 kin 的输入。
  • 解释器接收一张 WCS 偏置表（G54→offset、G55→offset…），把所有坐标解析到那一个工件坐标系。
  • 输出 Block.target 已经是统一坐标系下的位姿，Block.wcs 只作显示。
gcode::interpret(src, &dialect, &WorkOffsets) -> MotionProgram

好处：

  • kin 完全不知道 G54 的存在。
  • 切 G54/G55 不需要下游做任何事——偏置在解析时已吸收。
  • 摇篮机上台面旋转，工件坐标系跟着转，这是机床几何（kin 的事），与 G54 偏置正交。

4.3 TWP 同理

G68.2 定义一个倾斜平面。解释器把它折算成坐标变换矩阵，作用在后续所有 target 上——纯几何，不需要知道机床构型。

G69 取消，恢复。

4.4 三层叠加：WCS 表 + G52 + G92（已实现）

位置 = base + 程序坐标，而 base 是三样东西相加：

层 来源 怎么改 怎么取消
WCS 表 G54–G59.3 G10 L2 Pn（给机床坐标）/ G10 L20 Pn（对刀） 再写一次
G52 局部 G52 X.. Y.. Z.. 就地叠加 G52 X0 Y0 Z0
G92 临时 G92 X..（把当前位置读作给定值） 就地叠加 G92.1（清零）/ G92.2 挂起、G92.3 恢复

三者分开存，不是一个数：G10 写的是"机床上的坐标系表"（断电保存），G92 只是一次 临时平移（不进表）。程序里看效果一样，取消方式完全不同——合成一个数就再也分不开了。

G10 改的是解释器内部的副本，不是 InterpConfig。 配置必须保持"程序的初始条件"： 同一份 InterpConfig 跑第二遍要给出一模一样的结果，否则第二个程序的坐标已经被第一个 污染了（interp_config_stays_clean_across_runs 锁这条）。

G10 L20 要把 G52/G92 减掉：它也参与 位置 = base + 程序坐标。一次 G52 X5 之后对刀，不减的话原点会整整差 5 mm——而程序看起来完全正常，只是整个零件挪了位置。

没有 G10 L20 时的常见写法是 G92 X0 Y0 Z0（把当前位置读作原点）。两者效果 接近，但 G92 是临时的：程序结束、复位之后机床上的坐标系表没变。

5. 错误处理与"可信度"

5.1 不中断，但要分级

G 代码方言差异大，一行不认识就整份失败会让工具不可用。但不能一律"跳过并警告"：

情况 处理 理由
未知 G 代码 / M 代码 跳过，记 ParseIssue 多为无关辅助功能
参数非法（如圆弧半径自相矛盾） 跳过该块，记 issue
在 G91（增量）下跳过运动块 标记 Trust::Unreliable 后续所有绝对位置都会偏移，结果不可信
语法错误 跳过，记 issue

5.2 为什么 G91 下必须升级为"不可信"

G91
G1 X10      ← 这一块解析失败被跳过
G1 X10      ← 实际少走了 10 mm
G90
G1 X100     ← 从这里开始，工件坐标系里的一切都偏了 10 mm

跳过一块增量运动，会让之后所有位置静默偏移。 报告里不能只写"第 3 行有警告"，必须把整份结果标为不可信，UI 顶部横幅提示。

pub enum Trust {
    Reliable,
    /// 有跳过块，且其中包含增量运动 → 后续位置全部不可信
    Unreliable { first_bad_line: u32 },
}

这条设计的价值：它把"能跑但结果错"变成"明确告诉你别信"。仿真工具最危险的输出就是看起来正常但实际错的。

已接线（2026-10-30）：sim::run 把每条 ParseIssue 逐条转成报告报警—— 稳定编号原样（GCODE-008 就是 GCODE-008）、严重度 1:1 映射（两层的 Severity 有意不共享，但四级语义一致）、行号进 TimeRef。Trust ∈ {Unreliable, Aborted} 而报告无 Error+ 报警时兜底 GCODE_TRUST（正常路径不触发——Unreliable 总伴随 Error 级 issue）。总体可信度 = SimReport::overall_severity()。

6. 方言：一个 seam，不是插件系统

pub trait Dialect {
    fn parse_tcpm(&self, block: &WordList) -> Option<TcpmCmd>;
    fn parse_twp(&self, block: &WordList) -> Option<TwpCmd>;
    fn default_feed_mode(&self) -> FeedMode;
    fn arc_ijk_relative(&self) -> bool;      // Fanuc 是相对起点
}

v1 只有一个实现 FanucDialect。

为什么还是用 trait 而不是 enum：

  • 它是测试接缝——可以写一个极简 TestDialect 只认几个字，把模态机的测试与方言细节解耦。
  • 加第二种方言时不用改签名。

但不做插件注册。方言在编译期确定，运行时不加载。

7. 一次性解析，不做流式

pub fn interpret(src: &str, d: &dyn Dialect, wcs: &WorkOffsets) -> MotionProgram

整份读进内存，一次解析完。 理由：

方案 100k 块内存 随机访问第 N 块 复杂度
一次性 约 10 MB O(1) 低
流式迭代器 O(1) 需要重放 高

随机访问是刚需：时间轴拖动、点击报告跳转到某行、断点定位，都要"直接拿到第 N 块"。流式会让这些都变复杂。

10 MB 的代价换掉一整套状态回放逻辑，很划算。

8. 圆弧的表示

圆弧在 Block.motion 里存参数化结果，不存原始字地址：

Arc { center: DVec3, cw: bool, plane: Plane }

解析时要处理三件事：

  1. I/J/K 的含义随平面变：G17（XY）用 I、J；G18（ZX）用 I、K；G19（YZ）用 J、K。写错一个字母整段圆弧就跑偏。
  2. R 形式有两个解：正 R 走劣弧（≤180°），负 R 走优弧（>180°）。
  3. 螺旋：G2/G3 带 Z 字时，是"平面内圆弧 + Z 线性"，不是空间圆弧。

终点与圆心不自洽（起终点距离 ≠ 2R）时要报 issue——这是后处理错误的典型症状，不能静默修正。

8.1 固定循环：展开成显式刀路（已实现）

不能"跳过"，必须展开：少钻一个孔，零件就是废的，而报告上看不出异常。

循环 展开成什么 差别
G81 快移到孔上方 → 快速下到 R → 进给到孔底 → 快速退 一次扎到底
G82 同上 + 孔底暂停 P 沉孔 / 锪平
G83 每 Q 一刀，刀间完全退到 R 平面排屑 深孔
G73 每 Q 一刀，刀间只抬 0.5 mm 断屑 深孔、行程短
G84 进给进、进给退（主轴反转） 攻丝
G85 / G89 进给进、进给退 镗孔，孔壁不留退刀痕
G86 / G88 进给进、快速退 镗孔，效率优先
G76 同 G86（孔底让刀不建模） 精镗

模态复用是重点。孔阵列的后处理几乎全是这种行：

G0 Z10
G83 Z-8 R2 Q3 F100
X20          ← 第 2 个孔，不带任何 G 字
X40          ← 第 3 个孔

只有 X/Y、没有组 1 的 G 代码 ⇒ 在下一个孔位再来一次。实现放在"隐式模态运动"之前 （step 的 ②.4 段），并让隐式运动让位——否则一行会展开成"钻孔 + 一条 G1"。

孔间横移发生在起始高度上，不是 R 平面、也不是孔底。这是不撞夹具的前提， 也是 hole_positions_follow_the_program 断言的东西。

G98 / G99 决定每孔之间退到哪：G98 回起始 Z、G99 回 R 平面。一排孔用 G99 能省掉大量空行程。

P 的单位由小数点决定（Fanuc）：P500 是 500 毫秒，P0.5 是 0.5 秒。 所以 lex::Word 现在带 has_dot——丢掉它，孔底暂停会差 1000 倍，而这种错 在几何上完全看不出来，只在节拍估算里错。孔底暂停与 G4 的停延都进报告时间。

不做的：

  • G87 反镗：从工件下方向上加工，本版运动模型（刀轴沿 Z 向下、从上方进刀） 表达不了，报 GCODE-005 而不是假装沿 Z 钻一个孔。
  • G76 的孔底让刀、G84 的主轴反转：不影响几何，只影响主轴负载，不做假动作。
  • G18/G19 平面下的循环：钻孔方向变成 Y/X，同样超出本版运动模型，报 GCODE-005。
  • G68.2 + 循环：斜孔同理。

8.2 刀径补偿 G41/G42（已实现）

为什么必须单独一遍：拐角的补偿点取决于前后两段的方向——本段偏移线的终点 要么和下一段偏移线求交（内角），要么绕顶点滚一段圆弧（外角）。逐行生成时只看得见 本段，所以补偿是整份程序解析完之后的后处理（comp::apply）。

顶点类型 处理
共线（切向叉积 ≈ 0） 直接过，法向偏移 r
内角（偏移侧在转弯内侧） 两条偏移线求交
外角（偏移侧在转弯外侧） 绕顶点走一段 r 圆弧

外角必须是圆弧，不能求交：两条偏移线在外侧的交点比顶点远 r·tan(θ/2)， 90° 拐角就多切 0.41r。真实机床就是绕顶点滚过去的。

唯一的正确性判据（every_compensated_point_is_exactly_r_from_the_programmed_path）： 补偿后的每个刀位点到编程路径的距离恒等于 r。这一条同时覆盖内角求交、外角圆弧、 法向取反、半径符号——比手算几个点强得多。

边界（做不到就报，不猜）：

  • 第一块必须是直线（引入段）——圆弧引入要新建半径，控制器也是这么要求的
  • 补偿组之后那块也必须是直线（引出段），否则引出弧的起点半径不对
  • 只支持 G17、只支持 G1/G2/G3
  • 补偿半径来自 D 寄存器：D 给的是编号不是半径，表里没值就报 GCODE-011 并把 Trust 降级——当 0 处理会让整条路径差一个刀半径，而且看不出来

任何一条不满足，整组还原成编程路径并报 GCODE-005。宁可说"没补偿"， 也不要交出一条差一个刀半径的路径。

内角求交还有个钳制：交点离顶点超过 10r 就退回法向偏移点（近 180° 折返时）， 并报 GCODE-012 提示该处可能过切。

11. 一句话

解释器只回答"这段代码想让它怎么动"，不回答"机床怎么动"。 前者是文本与坐标的问题，后者是机构与逆解的问题。这条线划清了，换机床不用改解析器，加方言不用碰运动学。

12. 对标 LinuxCNC

本节基于 LinuxCNC 官方文档实测：docs/src/gcode/g-code.adoc（65 条 G 代码速查表）、m-code.adoc、overview.adoc 的模态组定义。已下载到 refs/linuxcnc/。

12.1 对标"语义"，不对标"功能集"

LinuxCNC 是控制器，我们是仿真器。 这决定了四条根本差异：

LinuxCNC（控制器） 我们（仿真器）
时间 实时执行，受伺服周期约束 离线重放，可快进/倒放
硬件 驱动主轴、冷却、I/O、换刀 不驱动任何东西
交互 操作工暂停、倍率、手轮 无操作工
输出 脉冲 诊断报告

所以"对标"的正确含义是：

同一份 G 代码，我们算出的刀位轨迹与 LinuxCNC 一致。

不是"支持同样的指令条数"。凡是不影响刀路几何的功能（冷却、I/O、暂停、倍率），我们都不需要实现——但必须正确跳过，不能报错。

12.4 三个需要决策的点

（1）G41/G42 刀补：已实现（2026-10-30，comp，12 个测试）

当初的判断是"v1 不做，报 issue"——理由是"五轴加工几乎不用刀补，CAM 已经在刀路里补偿了"。 这个判断对五轴连续加工成立，但对两轴半的轮廓工序不成立：现场改刀补修尺寸是常规操作， 而且报 Unsupported 会把整份程序标成不可信，等于白跑。

实现方式与 LinuxCNC 不同：它做在轨迹规划层（要处理自交、过切、内外角切换）， 我们在解释器的后处理里做，只解决"刀心该在哪"，不模拟加减速与拐角过渡。 三种顶点（共线/内角求交/外角圆弧）见 §8.2，正确性判据是"每个刀位点到编程路径 的距离恒等于 r"。

（2）G64 路径模式：默认模拟"理想路径"

LinuxCNC 的 G64 P_ Q_ 是轨迹混合——拐角会按容差切掉，实际路径不是精确折线。

两条路：

方案 优点 缺点
模拟理想路径（精确停在每拐点） 与 CAM 意图一致，报告可读 与实际加工有偏差
按 G64 容差混合 更接近实际 要复现 LinuxCNC 的混合算法，且结论依赖参数

建议 v1 走理想路径，并在报告里注明"未模拟 G64 混合"。理由：验证刀路是否该切到这里，比模拟它实际切到哪里更有价值。v2 再提供开关。

（3）G93 逆时间进给：必须支持

五轴联动常用 G93（F = 1/时间）。不支持的话，所有五轴程序的节拍全错。

时长(分钟) = 1 / F

12.5 重要提醒：LinuxCNC ≠ Fanuc

这是最容易踩的坑。"对标 LinuxCNC" 得到的是语义骨架，不是"支持 Fanuc 后处理"。

项 LinuxCNC Fanuc
G43.4 Tool Length Offset on Primary Kinematics TCPM（刀尖跟随）
G68.2 参数 欧拉角等 X_ Y_ Z_ I_ J_ K_（三点/两向量定义）
G5/G5.1/G5.2 样条 无
M62–M68 数字/模拟 I/O 无（编号含义完全不同）
G12.1/G13.1 极坐标插补 无

结论：方言层（§6 的 Dialect trait）仍然必需。对标 LinuxCNC 让我们有了一套经过验证的语义模型，但实际后处理输出是 Fanuc 方言，两者要分别建模。

12.7 用 LinuxCNC 当 oracle

最有力的验证手段：同一份 G 代码，分别用 LinuxCNC 与我们的解释器跑，比对逐块的刀位。

LinuxCNC 可以在 sim 配置下无硬件运行，并能导出关节位置。与 ADR-003 §8.9「用 LinuxCNC 验证运动学」是同一套路，只是从运动学扩展到整个解释器。

#[test]
fn matches_linuxcnc_interpreter() {
    let ours   = interpret(src, &FanucDialect, &wcs);
    let refr   = load_linuxcnc_trace("testdata/golden/linuxcnc_prog1.csv");  // 逐块刀位
    for (i, (a, b)) in ours.blocks.iter().zip(&refr).enumerate() {
        assert!((a.target.tip - b.tip).length() < 1e-6, "块 {i} 刀位偏差");
    }
}

注意：LinuxCNC 的 G 代码方言与 Fanuc 不同（§12.5），所以这个对拍只能用于用 LinuxCNC 方言写的测试程序。Fanuc 方言的程序只能靠金标准手工核对。
