1. 定位与范围

Bevy + Rust 的五轴 CNC 仿真验证器，不是 CAM。只回答四个问题：会不会撞、会不会过切、实际跑多久、哪里出问题。

纯自用，不对外分发。 由此：

  • GPLv2 义务在"分发 / convey"时触发，私有使用不触发 → 可以读、可以抄 LinuxCNC（vismach、5axiskins.c、g-code.adoc）。
  • 但版权（复制权）与分发是两回事：GrabCAD 的"非商用"限制的是使用场景，公司商用仍适用 → 机床外观一律参数化生成，不用下载模型。
  • 若哪天想保留分发可能，就只把 LinuxCNC 当测试 oracle（测试用 GPL 程序不污染被测代码）。

范围裁剪（自用版）：砍闭式解、产品化、机床自身碰撞、PDF 报告；保留剖切 / 刀路着色 / 过切 / 节拍 / 非线性误差。通用拓扑 + 数值逆解保留——边际成本低，换机床参数不用改代码。

2. 技术栈与依赖策略

原则：L2 领域内核全自研，L1 引擎与呈现用现成（ADR-003）。

层 crate
L0 math（零依赖 f64）、motion、tool
L1 算法 kin、gcode、hmi
L2 几何 voxel（稀疏窄带 SDF）、collide（GJK + EPA + 保守推进）
L3 编排 sim
L4/L5 render（含 Bevy window feature）、ui、app
输入适配 config（RON → MachineTopology，第 13 个 crate）

自研边界的三层论证：自研渲染器 12–18 个月、ECS 3–6 个月、窗口 2 个月 = 2 年以上，等于放弃项目。所以"自研"的实质是领域层 100% 自有、引擎层可替换——真要脱离 Bevy 只重写 render/ui/app。

依赖策略（硬规定）：

  • Edition 2024（resolver = "3"），MSRV 1.99。
  • 第三方只用精确的最新稳定版，写 version = "=x.y.z"，禁止 ^ 区间。
  • 加依赖流程：check_versions.py --show <crate> → 填 [workspace.dependencies] → 复验。
  • 引依赖要"签字"：check_deps.py 的 EXTERNAL 表未登记的外部依赖直接判违规。

当前只有 3 个外部依赖：serde 1.0.229 + ron 0.12.3（仅 config）、rayon 1.12.0（仅 voxel）。 rayon 是唯一进入 L2 的外部依赖，买的是常驻线程池（每次 fork-join 491 µs → ~5 µs）。

proptest 已移除（2026-10-29）：它把 quick-error（被 rusty-fork 钉死 1.x）、windows-link（被 windows-sys 钉死 0.2）拖进依赖图，版本守卫因此长期红着。改成 20 行 xorshift + 固定种子，顺带把"每次随机种子、失败了要等缩例"换成"同一份代码永远跑同一批数"。Cargo.lock 从 71 个包降到 29 个。

3. 架构铁律

  1. 没有 cncsim-core。公共类型按概念簇拆。禁止 common / utils / types / shared——零内聚垃圾场，扇入爆炸还掩盖设计问题。判据是"删掉它耦合会不会变高"。
  2. collide 不依赖 voxel，用 DistanceField trait 反转。副产品：碰撞能脱离体素单测（解析半空间做假实现），正好是随机对拍需要的。接线在 sim::stock（newtype 包 StockField，orphan rule 要求）。
  3. 不建共享 Diagnostic 枚举。各层自带 finding（KinFinding / CollisionEpisode / ParseIssue），sim 组合。"低耦合"最实用的一条：不要在底层造共享词汇，让上层组合。
  4. kin 不知道 voxel 存在，反之亦然，只有 sim 同时知道。
  5. gcode 不做运动学：输出位姿不是关节值；RTCP 归 kin。判据：只需知道"工件怎么摆"→ 解释器；需要知道"机床几个轴"→ kin。
  6. hmi 是独立状态机，ui 只依赖 hmi 不直连 sim。UI 需要的 Alarm/Severity 由 hmi 显式重导出（pub use cncsim_sim::{Alarm as AlarmView, Severity}）——UI 的唯一入海口只有这么大，加宽要改那一行。
  7. L0–L3 零 Bevy 依赖（正确性必须能纯 cargo test 锁定）。
  8. SparseGrid 单一所有者（后台线程），跨线程只走 channel。
  9. Pose.axis 约定：单位向量，由刀尖指向主轴（A=0 → +Z）。

配置单独成 crate，因为磁盘格式是跨层的：chain 归 kin，parts 归 render/collide，motion 归 sim。让 kin 读整个文件，它就得知道 Shape::Box 和 ColliderSpec::Derived —— L1 算法层被磁盘格式污染。只有 config 知道"文件长什么样"，各领域 crate 只接收自己的类型。方向不能反。

守卫：tools/check_deps.py（白名单 + 查 L0–L3 无 bevy + 查禁用名，违规退出码 1）。 架构约束写在文档里会腐化，只有进 CI 才有效。 而且要在只有 3 个 crate 时上线——等 11 个再上就疼了。已用违规样例实测：3 类违规全拦。

4. 精度口径

瓶颈不是 float 宽度，是 i8 量化。

f32 绝对精度（ULP，实测）：30 mm → 1.9 nm；200 mm → 0.015 µm；1000 mm → 0.061 µm；7200 s → 0.49 ms（≈半个插补周期）。够用。

三档类型分工：体素索引用 i32（绝不用 float 当索引——20000 处 f32 ULP 0.0024，取整可能错 1 格 = 0.1 mm）／标量路径 f64／SIMD 热路径 f32／渲染 f32。 关键论据：标量 f64 在 x86-64 上几乎免费（SSE2 标量 double 与 float 同吞吐），代价只在内存和 SIMD 宽度。所以运动学/碰撞用 f64 不亏，SDF 内层用 f32 赚 2×。 全 f32 会废掉什么：与 LinuxCNC oracle 的 1e-6 对拍做不到（oracle 是 double）——这是最有价值的验证手段。

4.1 检出下限 = 量化半档 + 三线性重建

band_voxels = 4、h = 0.1：

误差源 数值 与 h 的关系
i8 量化半档 1.58 µm ∝ h（带宽随 h 缩放）
三线性重建 h²/(8R_c) 平面 0 / R_c=3 → 0.42 µm / R_c=0.25 → 5.0 µm ∝ h²

档距 = 2·band·h/254 = 3.15 µm；i16 = 12.2 nm（258×——满量程是 2×band 不是 band，这里算错过一次）。

口径：平面 1.6 µm ／ R_c ≥ 0.8 mm 曲面 2.0 µm ／ 更小 R_c 按 1.6 + h²/(8R_c) 增长。

三个由此得到的结论：

  1. φ0.5 球刀（R_c=0.25）精加工面是 6.6 µm，不是 1.6 µm。 小刀具精加工面的瓶颈是网格太粗。拿 1.6 µm 去承诺差 4 倍——这是"过度承诺检出能力"，方向危险。
  2. "h 减半精度翻四倍"是错的：h ≤ 0.1 时量化主导，总误差只按 h 线性改善。h 减半、内存 4 倍，误差只降一半。要 h² 的收益必须同时换 i16。
  3. 设计规则：h ≤ 0.11·√R_c（让插值项不超过量化项）；反解 h ≤ min(254ε/band_voxels, √(8·R_c·ε))。ε=2 µm、R_c=3 → h ≤ 0.127（h=0.1 够）；ε=1 µm → h ≤ 0.064（要降到 0.05）。

教训：给"保证"必须列全误差项。早先声称的 0.17 µm 是采样密度不是符号可信度——两个概念别混。只算一项就宣布下限，等于按最乐观的那一项承诺。

residual_max_thickness 的口径分两种（sim::compare）：DesignModel::Box 用解析盒 SDF，精确、无上限（实测 1.000 mm）；DesignModel::Field（STL）用体素场查询，带外钳到 ±band，所以厚度上限 = band + h/2。

饱和已经是显式状态：DesignModel::distance_cap() 给出上限（Box 为 None），SimReport::residual_thickness_capped / residual_thickness_cap 带进报告，voxel_compare 记录最大厚度时顺手判 dd >= cap。上限要用设计场的 band 算，不是毛坯场的（两者独立，--design 用 2、毛坯用 4，拿错会把 0.25 印成 0.45）。要根治得让 Field 的残留厚度走解析距离（对残留体素求最近设计三角形）。

4.2 精度上限（实测）

量化步长 = 2 · band_voxels · h / steps（I8 = 254 档，I16 = 65534 档）；实测误差 ≈ 步长/5（插值有平均效应），即 0.0016 · band_voxels · h。

h (mm) I8 误差 I16 误差
0.100 0.65 µm 0.0024 µm
0.050 0.32 µm —
0.020 0.13 µm 0.0005 µm
0.010 0.065 µm —

误差/h 恒为 0.0065（I8 / band=4）；band 8→4→2 误差 0.62→0.32→0.16 µm（严格 ∝ band）。 mesh 顶点与 SDF 查询同精度——Surface Nets 在平面上不引入额外误差。

  • 实用上限 h=0.01 + I8 → 65 nm（内存 125 MB），比机床定位精度高 15×。
  • 理论极限 h=0.01 + I16 → 0.2 nm（小于原子直径，无工程意义）。
  • 曲面上另有弦高误差 h²/(8R)（h=0.1、R=3 时 0.4 µm），与量化同量级 → h=0.1 的真实零件总误差约 1 µm。

5. 材料去除内核

自研稀疏窄带 SDF，不用网格布尔。 网格布尔无法自研：Manifold 是几十人年鲁棒性工程，而加工天然产生同深度底面 / 同路径侧壁，每次走刀都重合——正是布尔最脆弱的退化情形，是常态而非例外。

（早期调研过 cutrail：它自己的文档就否定了"把多段扫掠先求并集再布尔能省时间"，实测只增加三角面。）

过切判定不走体素，用解析扫掠点测试（±0.001 mm）——i8 量化会被噪声淹没。这是 SDF 精度短板的补救，且是净收益（比网格比对更直接）。

sd_sweep(p) = min_{t∈[0,1]} sd_tool(p, pose(t))      ← 扫掠体的有符号距离
d_new       = max(d_old, -sd_sweep)                  ← CSG 减法

min over t 对凸刀具是精确的（到沿直线平移的凸集的距离，是平移参数的凸函数）；凹母线刀具（T 形刀、燕尾刀）不成立——v1 刀型都是凸的。

内存 mem ≈ 8.25·A/h²（8³ 叶密集分配）：h=0.1 → 206 MB。 早期写的 k·A/h² = 130 MB 低估 1.6 倍——那个公式假设"只分配窄带体素"，而实际存储是 Band([i8;4096]) 全分配。内存估算必须对着实际存储结构算。

迭代次数按行程自适应（6–24）：定位误差 Δx ≈ 行程 × 0.236 × 0.618ⁿ。 0.236 是内点间距不是区间长度——这里错过一次，导致我误判"固定 8 次在 10 mm 上误差 7.6 µm"（实际 0.42 µm）。真正失效点是长行程：200 mm 固定 8 次偏差 16 µm。

切削 AABB 必须外扩一个窄带宽度：扫掠体边界就是新表面所在，不外扩的话刀尖平面以下材料侧只有 1 个体素拿到真实距离，往下全是切前的饱和值 −band——窄带单边完整等于没有窄带，跨界插值把表面往材料侧拽（LOD k=4 槽底偏 97 µm）。代价遍历体素 +54%，但碰撞用的是同一套插值，所以这不是显示层的账。

跳过 d_cur >= band 的体素（已在材料外远处，改不动），但不能跳负值体素——深埋材料（−band）被切到时变成 +band，必须处理。

切完自动 prune——正确性要求，不是优化。

6. 稀疏体素结构（ADR-006）

三级树：root 哈希 → 32³ → 16³ → 8³ 叶。结构照搬 OpenVDB Tree4<T,5,4,3>（数字从叶往根读）。

每一级都能存 tile 值（包括 root：RootEntry<S> = Node(u32) | Tile(S)）。这不是优化，是能不能表达的问题：

方案 200×200×100 毛坯（40 亿体素）
只存叶 1560 万个叶
叶 + 叶级 tile 仍然 1560 万个 Constant 叶
三级都能 tile root 1 条、叶 0 个、2.0 MB

实测：40 亿体素分层填充 5.6 ms，实心毛坯完全由 tile 表达。 fill_box 必须分层（完全覆盖的槽直接写 tile，只有边界壳下降），否则 40 亿次写入根本跑不完。

索引全是位运算，无哈希：ijk >> 12 找 root、>>7 &31 找 level2、>>3 &15 找 level1、&7 找叶内体素；子节点取 children[popcount(mask & 低位)]。

负坐标必须算术右移 + 按位与：-1 >> 3 == -1、-1 & 7 == 7，于是体素 −1 落在叶 −1 的索引 7。用 / 和 % 会让 −1 和 1 落进同一格。

prune 是正确性不是内存优化：切空的叶若仍是 Dense，碰撞会认为那里还有材料。

i8 / i16 是同一个泛型参数（SparseGrid<S: Scalar>），不是两套代码。MIN 取对称量程（−127 / −32767），这样 |v| 可直接当"离表面多远"。

必须在开工时就用树，不要在扁平 HashMap 上迭代——存储层是地基，改一次所有上层重测。

6.1 Surface Nets（不用经典 MC）

256 项边表 + 256×16 三角表手打必错，而且错了没有中间步骤可查——少一个三角形只是网格上多个小洞，在几千万面里看不出来。

改用对偶等值面：每格一个顶点（12 条棱零点的平均），每条符号变化棱生成一个四边形。水密是结构保证，表数据为零。R=3 球：有向体积 112.97 vs 解析 113.10，误差 0.11%。

三个坑（都是"看起来对但网格是坏的"）：

  1. tile 紧贴填充边界 → 网格漏洞（实测丢 298 个四边形）。单元格跨 2 体素，"tile 最后一个体素 ↔ 盒外背景"这条符号变化落在没有叶子的区域，谁都遍历不到。修法：tile_safe 要求四周留 1 体素余量，边界那层槽建成常量叶（16 B vs 528 B，200 mm 毛坯从 130 MB 压回 4 MB）。
  2. halo 重叠 → 四边形重复发射。顶点有 entry() 去重所以无害，四边形没有 → 边被共享 4~6 次（实测 28318 条边）。修法：按顶点创建顺序遍历。
  3. HashMap 迭代顺序破坏可复现性。for_each_leaf 走 HashMap，顶点顺序每次不同 → 项目硬门槛"逐位可复现"被破坏。修法：叶坐标先 sort_unstable()。

显示必须走 LOD：200 mm 毛坯细格提取 1600 万顶点 / 3200 万面 / 834 MB / 43 s。三角形数 ≈ A/h² × 2，render 预算 200 万面 → 显示用的 h 必须 ≈ 0.4 mm。这不是优化，是能不能渲染的问题。

k ≤ band_voxels 是几何约束不是旋钮：跨符号棱两端到表面距离各 ≤ h_c，窄带只有 band 宽。越界后远端被钳制，插值不再等于真实距离，偏差随 (h_c − band)² 长，没有上界，而且网格看起来照样水密。 实测 R=6 球顶点偏差：k=1 1.8 µm、k=2 3.3、k=3 6.2、k=4 9.8；越界 k=5 15.5、k=6 34.2。 → extract_surface_lod 超限直接 panic，不警告、不静默降级。想再少面只能加宽 band（内存换），不能加大 k。

候选格判"表面可能穿过这片叶"要三档：① 叶内混号 ② 叶内有窄带体素 ③ 26 邻里有反号叶。 只看 |v| 会漏 fill_box 的二值毛坯——实测 60 mm 方坯 k=1 提取出 0 个顶点。

6.2 单元格索引（ADR-010）

FxHashMap<[i32;3], u32> → 每 8³ 单元格一块 + 512 位掩码 + popcount 前缀和。 索引 = base + popcount(掩码前缀)。块内占用率只有 12.5%（表面在体素空间里是二维的），所以"有没有"用 1 bit、"是多少"用前缀和算。

方案 每块开销 25 万块合计
稠密 [u32; 512] 2 KB 500 MB
位掩码 [u64; 8] + base 68 B 17 MB

200 mm 提取 3.09 s → 0.81 s，索引 310 MB → 25 MB，另外省掉原来 192 MB 的 cells 数组。

代价：顶点下标变成"块序 + 槽序"的空间序（不再是叶迭代顺序）。对渲染无影响，但细格与 LOD 必须走同一个构建器，否则 k=1 与细格逐位一致那条测试立刻红。副产品是"顺序与分块数无关"由构造保证。

  • cut_segment（逐刀）：仿真主循环用，每段之后要拿当前网格查碰撞。

7.2 优化排序（按实测收益）

  1. 体素化用 band=2 而不是 4（2026-11-01）：distance_pass 成本 ∝ (三角形尺寸 + 2·band)³，190 万三角形 h=0.1 时 41 → 15 s（band=2）/ 8.2 s（band=1）。带越薄量化档越细（2·band·h/254），体积误差反而从 −0.05% 降到 −0.01%。代价是 max_lod_factor == band、且带外距离被钳制——切削/碰撞必须 band=4。
  2. 提取的主体 512 体素从当前叶一次读（2026-11-01）：每片叶原来 1000 次 get（三级查找），其中 512 个就在当前叶里。细格提取 798 → 709 ms。
  3. 提取的 halo 按 6 个面批量（2026-11-01）：384 个 halo 体素按邻居叶整面复制，再降到 645 ms；vertex_of 展开成常量索引 → 590 ms；CellMap 块缓存 → 578 ms。累计 -28%，与 OpenVDB volumeToMesh 从慢 1.56× 收到 1.13×。
  4. 建场改按叶写回（2026-11-01）：532 万次单点 set → 1.5 万次整块 blit_leaf，建场 47 → 14 ms（-70%）。同时把末尾全量 prune() 换成增量 prune_leaves（4.7 → 0.3 ms）。
  5. 并行写加 1 MB 门槛（2026-11-01）：blit 202 → 50 ms。小批量并行是负优化，见 §7.3。
  6. 拆 blind 每刀重算（占铣光 79%，而全项目无读取者）：344 → 67 ms。
  7. 平底刀纯平移走闭式解（sd_flat_prism）：扫掠体是"径向 2D 胶囊 × 轴向区间"的笛卡尔积，跳过 13 次黄金分割。34 → 5 ns/体素。
  8. 短段端头圆帽特化（FlatSweep）：单轴共享只对"刀心路径正上方"的叶成立，短段 90% 的叶在端头圆帽区。200 小段 55 → 34 ms。
  9. 行级分类：一行 8 体素共用同一个 sd，只有三种命运——够不着整行不碰 / 埋在刀体深处整行一次 8 字节填空气 / 表面行（新值是行常量，逐点只剩一次比较）。粗加工里 75% 走第二类。
  10. 中转缓冲按上限预留：pool 从 0 翻倍长到 300 KB，中途要搬 600 KB；铣光实测 200 刀 61 ms 花在 realloc。
  11. 整块值的 arena（CutPart::pool）：求值加速比 4.8× → 5.6×。
  12. uniform_value 改 8 字节块比较（2026-11-01）：prune 每刀调几千次，141 → 78 ms（-45%）。
  13. 增量 prune（prune_leaves）：只折叠真正写过的叶，且直接吃叶下标。
  14. 沿单轴走刀的截面共享（sweep_axis）：-15%。
  15. 叶级整块写回 / 整叶短路走并行 blit / WriteCache 块级缓存 / 量化系数外提 / set_cached。

7.4 与 OpenVDB 14 的对比（诚实边界）

环境：OpenVDB 14.0.0 + oneTBB 2023.2.0 源码编译，clang++ 23.1.4 -O3 -march=native；CNCSIM 侧 rustc release（同为 LLVM 后端）。

必须说清的三点：

  1. OpenVDB 的 CSG 极快（0.3 ms），但它要求刀具体已经是 level set。 它没有"解析扫掠 SDF"——必须先把扫掠体逐体素写成 level set，ValueAccessor::setValue 实测 78 ns/体素（比我们优化前的 34 ns 还慢 2.3×）。我们的解析求值 4.7 ns/体素。 这个对比不是"我们比 OpenVDB 强"，而是两种范式：它优化了 CSG，代价是必须先把形状体素化。
  2. 如果刀具形状能在多刀间复用（固定球头刀 + 平移变换），只跑 csgDifference 就是 0.3 ms/刀，OpenVDB 快一个数量级。但扫掠体随刀路变化，真实场景里每刀都得重建——这才是本表的口径。
  3. 我们的"空刀"是 0.66 ms，与 OpenVDB 的纯 CSG（0.3 ms）同一量级。说明慢的部分全在"求值 + 落盘"，不在 CSG 本身。

几何结果一致到量化精度：表面位置（槽底 / 左壁 / 右壁）三个过零点差 0.0 µm；带内逐点最大 1.18 µm（= i8 量化步长 3.15 µm 的半步，不是算法差异）、中位 0.39 µm；带外符号冲突 0。

对拍抓到三个真问题（都值得记）： 1. OpenVDB 基准的刀具体是空心的——只写窄带壳，内部落在背景值 +band（空气），于是 csgDifference 把刀具内部当空腔，槽底报"材料"。修法：先 fill AABB 为 −band（inactive tile），再覆盖窄带。副作用：OpenVDB 变慢了，之前的性能对比低估了它。 2. OpenVDB 基准的毛坯窄带不完整——只写盒内，外侧是背景值，插值过零点偏 0.04 mm。修法：窄带范围外扩 PAD 个体素。 3. CNCSIM 的 fill_box 不写精确边界 SDF——未切削面的插值依赖"体素中心恰好落在盒边界上"，实测左侧壁偏 25 µm。新增 fill_box_exact（边界壳写真实盒 SDF，内部仍饱和 tile，内存不变）→ 三个过零点全部归零。默认仍用 fill_box（建场几乎免费），亚体素精度场景显式用精确版。

8. 并发

无锁在这里的收益是"消抖"不是"提速"：每段约 30 次跨线程操作，省 10 ns/次 = 0.3 µs，对比 5 ms/段 = 0.006%。

材料去除天然串行——但那句话要读成段间：第 N+1 段要读第 N 段切完的毛坯。段内是并行的：一次切削里每个体素只读自己那一个值，max(d_cur, −sd_sweep) 与邻居无关。

形状统一成"只读并行 + 按块号归位"，SparseGrid 全程单一所有者——不需要 Arc<Mutex<_>>，也不需要 unsafe。 反模式：Arc<Mutex<SparseGrid>>、原子化稀疏树（RCU/epoch）。最无锁的并发是不共享。

线程池唯一实例：par::pool() 用 ThreadPoolBuilder::build()（不是 build_global()）。 任何绕过它直接调 rayon 的地方都会另建全局池 → VTune 实测 50 线程抢 24 核、88.3% oversubscription。blit_leaves_parallel 里的 par_chunks_mut 必须包进 pool().install(...)，修后降到 26 线程 / 79.5%。这是个容易反复踩的坑。

为什么 5.6× 而不是 24×：8 线程时全是 P 核，5.2× 已贴近 8 个物理核的上限；再往上 E 核频率低一半，16 线程反而略慢（1.08 > 0.93 ms）。这已经是这台机器的硬件上限附近。

CPU 利用率只有 6.8% 不是写错了：每刀 1.87 ms 切 36 片 = 每片 52 µs，与 rayon worker 唤醒延迟（10–50 µs）同量级 → WaitOnAddress 占 hotspots 28.6%。是任务粒度决定的，绝对时间确实从 4.8 ms 降到 0.84 ms。要更高只有两条路：把多刀批量提交（有数据依赖），或者接受这个粒度。

硬门槛：结果必须逐位可复现。 分块数从 1 拧到 97，顶点/法向/索引/体素值必须逐位相同。所以把"分块数"做成显式参数（0 = 自动），4 条测试拿它当旋钮对拍。任何破坏确定性的优化都不接受，哪怕更快。

吞吐与延迟的冲突只剩"用多少核"一个旋钮：仿真全速 14–36× 实时，而用户回放最多 8×——交互模式下"全速算"是浪费。解法：双模式 Interactive{speed_cap} / Batch、线程优先级（UI ABOVE_NORMAL、仿真 BELOW_NORMAL，比任何算法优化都直接）、rayon 并发度。 延迟看 p99 不看平均——这也是用无锁而非 mutex 的原因（mutex 平均低但被抢占拖到毫秒级，污染 p99）。验收必须在仿真满载时测帧时间。

分块的越界坑：per = ceil(len/chunks)，末尾块 s = i*per 可能超过 len → &leaves[s..e] panic。所有分块入口都要先 if s >= e { return 默认值 }。

9. 碰撞检查（ADR-004）

  1. 不需要通用网格碰撞：毛坯 = SDF、夹具/机床 = OBB、刀具 = 旋转体，没有"网格 vs 网格"。v1 不建 BVH，AABB 粗筛够（n≈50，1250 次测试/步可忽略）。
  2. 必须做保守推进（CA）：100 m/min = 1.67 mm/ms，2 mm 薄壁会整步跳过。漏报比没有检测更危险，因为它给了虚假的安全感。
  3. 方向 B（刀柄表面 → 毛坯 SDF）是主力：穿透区在毛坯体素格上是三维薄片（要 ε > h 才能保证命中），在刀柄表面上却是二维补丁（周向宽 2√(2Rε)，只需 ε > δ²/(2R)）——二维采样阈值按 δ² 缩小，三维按 δ，差三个数量级。方向 A 只用来定位。

t ← t + d_lower(t) / v_max；v_max 必须含转动项 θ·r_max——五轴摆动时刀柄末端速度可能远大于刀尖，用刀尖速度当上界会漏报。迭代耗尽时保守报碰撞。

给"保证"必须按最坏情况（对抗性放置）推导，不能按期望值——曾用均匀分布假设推出 0.6 µm（要求 ≥8 个体素中心落入穿透区），差 50 倍。最坏情况下毛坯表面正好卡在两个体素层正中间，穿透薄片 ε < h/2 时一个体素中心都不在里面。

CA 能成立的前提（深层论证）：CA 在段内亚采样查询 d(t)，但毛坯只有段级更新——时间分辨率不一致，严格说会漏报。可以忽略，因为两种效应不同源： - 材料去除速率 ∝ 刀尖进给：G1 3000 mm/min = 0.05 mm/ms，即使 10000 mm/min 也只 0.167 mm/ms。 - 刀柄运动速率 ∝ 刀尖速度 + |ω|·r_max：快移 100 m/min = 1.67 mm/ms。 - 而 G0 快移不切削，毛坯完全静止。 → 穿透风险只存在于快移段（毛坯静止），毛坯演化只存在于切削段（速度极慢）。两者永远不同时放大。

brick 重分类是正确性问题：切空的 Band/Full 砖必须降级 Empty。残留 Full 砖会让"穿过空腔的刀杆"被持续误报。Empty 砖可永久跳过（单调性，只去料不加料）。

Full brick 不能跳过（真漏洞已修）：let Some(Band) = ... else { continue } 把 Full 一起跳过，刀杆斜插实体区时周围全 Full 无 Band → 整段漏报。

凸体碰撞不要 polygonize：16 边形外切误差 r(1−cos(π/16)) ≈ 0.019r，对 R=30 的刀夹是 0.57 mm 系统性误报——每把刀都"差一点点就撞"，报告就没人看了。GJK 只要一个支持映射，圆台/球/盒的支持映射都是解析的 → 零建模误差。

GJK 自证的陷阱：Cone::support 只按轴向正负挑端圆、没比较半径，对 r_lo ≠ r_hi 的细长圆台返回非最远点（距离虚高 0.06 mm）。KKT 最优性断言当时全绿——因为断言里的 support 和 GJK 里的是同一个错的实现，两边一起错就自洽。 凡是"用同一份实现自证"的检查，都必须再配一条独立的 oracle。

GJK 的经典坑（自己撞上了）：收窄单纯形时必须剔除零权重点（四面体不含原点时返回的 4 元权重里恰有一个 0），否则下一轮 push 变 5 点越界——这就是"该丢的点没丢"。

EPA 符号：point_a − point_b 在穿透时不是"从 b 指向 a"（point_a 是"扎得最深的点"而非"最近的点"）→ 字段叫 axis 不叫 normal，分离位移 −axis·depth。 初始四面体外法向不能用原点判朝向：GJK 的单纯形贴着原点，原点可能正好在某个面的平面上（n·O = 0），判不出哪边是外 → 最深的面被当"最浅出口"，深度报 0。改用四面体重心。

验收方式是"照着推开"：按报出的 depth/axis 移动 A，两体必须恰好接触。比"和解析解比"覆盖更广（解析解只对球/盒存在）。

窄带比采样间隙还窄（必须记住）：band = 0.4 mm < δ = 0.5 mm，带外一律钳制成 +band → min_sdf − δ = −0.1 恒负 → 保守推进退化成"每段都报碰撞"（实测刀在毛坯上方 40 mm 空走也报）。 修法：给 DistanceField 加 aabb()，clearance_lower 取 max(采样下界, 采样点包围盒 ↔ 场包围盒距离)。 先试过"刀尖球"（半径 = reach）：φ6×40 刀杆要包在半径 40 的球里，球一靠近就是 0，等于没兜。紧的下界必须是形状的下界，不是球的下界。

episode 聚类：按「同一对部件 + 间隔 ≤ 50 ms」合并。50 ms 不是拍的：100 m/min 快移在这段时间走 83 mm，比任何真实接触尺度大一个量级，所以同一次碰撞不会被拆成两段。 但相邻块无条件合并——一次下扎会横跨 G0 和紧随其后的 G1，两块间隔 70 ms 超过窗口，可那是同一个动作。 absorb() 取最大穿透而不是最后一次——报告关心"最深扎进去多少"。

测试必须成对：漏报 + 误报。只有漏报测试会诱导出"永远报碰撞"。endpoints_only 作对照组留在代码里。 穿透测试要先写朴素离散实现确认它漏报（红），再换 CA 转绿——否则无法证明 CA 真的解决了问题。

本质是溯源不是渲染。SDF 架构下几乎免费——毛坯表面本身就是"若干扫掠面的并集 + 原始毛坯面"：

creator(p) = 时间最晚的 sweep t，使得 |sdf_t(p)| < 0.5h

（网格布尔架构下必须由布尔运算逐三角形携带 provenance，自研做不到，所以自研路线反而更简单。）

交互才是价值：点选面 → 反查 brick → 反查 creator → 显示"刀具 T7 / 第 3 序 / N1240–N1380"。

关键测试 second_tool_overwrites_first：粗 z=−5、精 z=−6，底面归精加工。取最早也"看起来对"，只有断言具体 sweep id 才能抓到语义错误。

10.1 已实现（2026-11-01）：叶级溯源，不是 brick 候选表

上面 ①②③ 是 ADR 的设计目标；落地时选了更省的一档：

方案 额外内存 分辨率 解析时机
ADR 的每 brick 候选表 + 扫掠注册表 +2 MB 表 + 12 MB 注册表 1.6 mm 提取时对每个三角形求最近扫掠面
实际：每叶 1 字节 creator +250 KB（25 万叶） 8h = 0.8 mm 提取时直接读

叶级比 brick 级还细（一片叶 0.8 mm < 一个 brick 1.6 mm），而且不需要扫掠注册表—— cut 落盘时就把标记盖上去，提取时直接读，没有"反查最近扫掠面"这一步。 代价是同一片叶里被两把刀切过时只留后一把（与 ADR 的"取时间最晚"一致）。

链路（每一环都有测试）：

run.rs        每个 G 代码块开始时 grid.set_creator(creator_of_block(bi))
cut.rs        write_parts 末尾给 touched 里的每片叶写 creator
extract.rs    vertex_batch 读叶的 creator → VertexRecord.creator
cellmap.rs    build 用 fetch_min 合并（并行写同一格也要逐位可复现）
render        CutMaterial 的调色板 uniform → 顶点色 R 当索引

"刀刃颜色 = 切面颜色"是构造保证的：两边都调 cncsim_voxel::creator_of_block， 颜色表只有一份（render::PALETTE），并且作为同一个 uniform 上传给毛坯和刀具 两个材质。不是"两份常量保持一致"这种约定。

已知特性：着色会向未切区域溢出最多一个叶宽（8h）。因为标记是叶级的，叶里 只要有一个体素变了，整片叶就盖上颜色。h=0.1 时是 0.8 mm（看不见），h=0.5 的测试 里是 4 mm——写测试时"未切区域"的判据要把这一圈排除掉，否则会把正确实现判成错的。

粒度是"刀"不是"块"，也不是"段"： - 按段着色不行：一段圆弧会离散成几十段，同一刀内部会变成噪点。 - 按块着色也不行：块之间夹着的 G0 抬刀/横移会占掉颜色索引，渐变跳号 （实测面铣十刀会变成 2,4,6,8,10,12 六种色）。所以只数 G1/G2/G3， 第 n 个切削块 = 第 n 刀。 - 于是"每切一条换一种颜色"成立：一条带子 = 一刀 = 一个索引。

判据在 crates/sim/tests/facing.rs：十刀必须正好十种色、索引 1..=10 各一次。 把计数改回 bi（块号）这条测试立刻报"实际 6：[2,4,6,8,10,12]"。

10.2b 颜色溢出：成因与四档粒度（2026-11-01）

现象：面铣一层之后，没被切到的侧壁顶边也被染上了切面色。查下来是两件事叠加。

原因 ①：溯源标记的粒度

标记按叶（或叶的子块）存，一片叶里只要有一个体素变了，整个子块就盖上这一刀的颜色， 子块内没被切到的顶点也跟着变色。

原因 ②：窄带填充

cut 会把新切面周围 ±band 的距离场重新精确化（值从饱和的 -band 变成准确值）， 那些体素确实变了。只判"变了"就把它们算成"这一刀在这里造出了面"—— 于是切面下方 0.4 mm 以内的体素全被染色。

修法：加一条"变了 且 贴面"的判据

新造出的面一定在刀面上，所以那个体素的新值必然满足 |v| < h （面在 A、B 两体素之间 ⟹ |v_A| + |v_B| = h ⟹ 必有一侧 < h）。 把盖章条件从「变了」收紧成「变了 且 |v| < h」，窄带填充就被排除掉了。 n（要不要写回）仍然数全部改动——只数贴面改动会让整块窄带填充被跳过，几何都会变。

窗口里多出来的 0.3 mm：不是判据问题，是两套粒度（2026-11-01）

用户报"有轻微的切割颜色溢出"。量下来窗口 0.30 mm、--export 0.10 mm。 第一版诊断写成"判据分不清造新面与把旧面算准"，还提了个 |sd_sweep| < h 的改法—— 那是错的。真正的原因用一行对比就查出来了：

[cmp-grid] 仿真网格 34802 顶点，切色最低 10.900；LiveCut 网格 34802 顶点，切色最低 10.700
  creator 不同 @(0,0,104)：仿真 0 / LiveCut 1
  ...
  creator 不同的采样点：65400

根因：接 TileCache 时新写的 LiveCut::new 自己 SparseGrid::new 之后漏了 set_creator_sub，退回默认的 1（每叶一个标记，8h = 0.8 mm）；而 sim::run 里 是 grid.set_creator_sub(cfg.creator_sub)（默认 4，2h = 0.2 mm）。 于是窗口按 0.8 mm 粒度着色、导出按 0.2 mm 粒度着色。

台阶竖直面是灰的：LOD 取色按了"格角"而不是"顶点"（2026-11-01）

现象：切削过程中，已铣区域与未铣毛坯之间的台阶竖直面中间是毛坯灰。

根因在 LOD 的取色位置：原来查的是格的最小角 [p*k]。

  • 格边长 k·h（k=3 时 0.3 mm），面可能落在格的远端，最小角离它最远 0.3 mm；
  • 溯源子块只有 sub·h（sub=4 时 0.2 mm），盖不到那么远 → 查到 0（毛坯灰）。
  • 地平面恰好凑巧（面落在最小角所在的子块里），所以只有竖直面暴露。

修法：按顶点位置取色——顶点本身就在面上，离它最近的体素必然 |v| ≤ h/2 < h，一定被这一刀盖过章，所以这是精确的、不是近似。

let v = self.to_voxel_space(pos);
self.creator_of_voxel_cached([v.x.floor(), v.y.floor(), v.z.floor()], &mut cur)

修完：台阶竖直面与最后一刀同色；切面颜色分布表没变（889.0 / 朝上 882.2 mm²， Z 10.90–11.00）。

残留：竖直面与顶面的共用边上有一条极细的浅色缝——那是"灰色顶面 ↔ 彩色立面" 在一条边上逐顶点插值出来的，属于顶点色方案的固有代价，不是 bug。

顶棱那条线：先修颜色，再修法向（2026-11-01）

用户连续报了两次"第一刀的深蓝色围了一圈"。拆开是两个独立问题：

① 颜色：外棱上取到了 0。顶点正好落在 v = 0 的边界上，floor() 会掉到外侧 （浮点 −1e−9 也 floor 成 −1），而外侧体素是空气、永远是 creator 0。 修法：沿法线反方向挪半个体素再查（pos − normal·h/2 一定落在材料侧）。 实测四条外棱从"全灰"变成"逐带正确"。

② 法向：棱上被平均成 45°。Surface Nets 一格一个顶点，地板与立面共用同一个 顶点，法向只能折中——实测顶棱 108 个顶点里 107 个法向被平均。两个方向光在 45° 上都变暗，于是棱上塌出一条暗线。未切削时两侧同色看不出来，一侧变彩色后就显眼。

修法：MeshData::split_crease_normals(cos 45°)——法向与面法向夹角超阈值的角， 为该三角形复制一份顶点并用面法向。平面区域一个顶点都不多，曲面（相邻面夹角 只有几度）不受影响。

关键：这个拆分只做在渲染层（shell::tile_mesh 与 preview::build_html）， 不能放进 voxel 的提取里——拆完索引级就不共享边了，cut_slot_surface_is_watertight （每条边恰好共享两次）当场失败。数据层保持"索引级水密"，显示层自己拆。

代价：顶点数 34 802 → 38 392（+10%，只在棱上），逐刀更新 14.4 → 15.6 ms。

三条结论：

第四处：排序改用 rayon 的并行排序

手写并行归并失败的原因很具体：最后一轮归并必须串行。而 rayon 自带的 par_sort_unstable 已经把这个问题解决了（内部是并行归并 + 阈值切分）。

    use rayon::slice::ParallelSliceMut;

第三处：sdf() 每次插值做 8 次根哈希查找

顶点阶段 53 万次 sdf，每次三线性插值要问 8 个体素，每个体素走一次 FxHashMap 查 root → 430 万次哈希查找。

逐位一致性有测试锁着：sdf_cached_is_bit_identical_to_sdf 拿 4 万个采样点 （含跨叶/跨根的弯曲表面）比 to_bits()。这条是必须的——两个版本一旦有差异， LOD 顶点就会和 extract_surface 对不上，而画面上只是"有点不对"，很难查。

试过但不划算的四条（别重走）

  • u32 键（21 位塞得进 32 位）：实测 21.0/23.4/22.5 vs u64 的 21.4/23.4/23.6—— 噪声内。比较次数没变，省下的只是数组体积，不是瓶颈。
  • LSD 基数排序：21 位要 3 趟、每趟全量散射，实测 5.9 ms，比 sort_unstable 的 5.6 ms 还慢。键只有 21 位时基数排序的优势建立不起来。
  • 手写并行归并排序（分块排 + 逐轮两两归并）：分块排只要 0.2 ms，但最后一轮 归并本质是 O(n) 串行，合计 3.7–5.1 ms，省不下多少却多 50 行。撤了。 （后来直接用 rayon 的 par_sort_unstable 就解决了——见下。）
  • 去掉块内 FxHashSet（"反正最后要全局排序去重"）：原始格从 41.9 万涨到 81.9 万，排序从 5.7 涨到 18.4 ms。花 2.7 ms 的哈希插入省下 12 ms 排序， 这块不能省。
  • "按所有者发射格"消掉重复：让每个叶只发射"最小角落在本叶内"的格，重复从 源头消失——原始格 41.9 万 → 19.2 万、排序 5.7 → 2.8 ms、提取 16.5 → 13.8 ms （再快 18%），顶点数与几何完全不变（34 802），full_update_matches_a_single_extraction 也过。但它改变了"分块区间提取"的格归属，fully_cut_away_tiles_are_dropped 的两条断言挂了（铣平的顶面质心恰好落在块边界上，按 floor 规则归到上层那块， 于是那块不再空、块数也没变少）。那是 TileCache 的内存行为约定，不该为了让路 而削弱，而 TileCache 又还没接进渲染、无法目视验证——先撤回。 要捡回来，得先把 TileCache 接进窗口并把"块归属按发射格、不按质心"落实 （split_tiles 现在用的是质心，与 extract_surface_lod_in 文档里写的 "按发射它的格划"并不一致）。

10.2 调色板：有序渐变，不是定性色板

第一版用了 ADR 推荐的 ColorBrewer 式 12 个定性色（色相均匀铺满一圈）。 结果是用户第一句反馈就是"切割颜色过于混乱"。

原因很清楚：定性色板的前提是"一屏里只出现 3–5 个类别"。刀路把整块顶面铺满时， 相邻两刀是任意色相跳变（红→蓝→绿→紫），看起来就是打翻的调色盘。 区分度不该靠撞色相。

改成一条有序渐变：色相 212°（蓝）→ 45°（沙黄），明度 0.50→0.72， 饱和度只从 0.42 动到 0.46。相邻两刀只差一点点，整块面读起来是 "从哪切到哪"的梯度，而不是互不相干的色块；要定位某一刀，看它在梯度上的位置。

配套的一条：索引走往返（1,2,…,12,11,…,2,1，周期 2N−2 = 22）而不是取模。 取模的话渐变最亮端之后直接跳回最暗端，面上会出现一条突变的分界线。

教训：颜色数量不是混乱的根源，相邻颜色之间有没有序才是。 写测试时把这条钉住——creator_of_block_walks_the_ramp_and_back 断言 "相邻块的索引只能差 1"，差 2 以上就是一次跳变。

2026-11-02 再进一步：从「一刀一色」改成「每工序 10 档」

有序渐变解决了"色相乱跳"，但没解决"刀数太多"。半球凸台的精加工是 3008 条 G1、每条 1.2 mm：每 1.2 mm 换一次色，12 色装不下 3008 刀，球面上仍是一片 找不出规律的彩虹，刀刃每秒闪好几次。

改成按工序内进度分 10 档（creator_of_progress(done, total)）：粗加工 0→100%、 精加工 0→100%，各自从第 1 档走到第 10 档。整段加工只换 9 次色，球面上是 10 条 宽色带，"这一片是前 30% 还是后 30%"一眼可读。

代价：同一档内的多刀同色，不能再靠颜色反查"第几刀"。换来的是阶段感—— 而且换刀处颜色从第 10 档跳回第 1 档，工序分界反而更醒目。

测试从"相邻两刀不同色"改成"单调不减 + 整段只换 9 次"。

11. 机床模型（ADR-007）

机床模型是三个不同的东西，必须分开表示，但只允许一份真相源。

表示 用途 精度
运动学链 Vec<Joint> FK/IK/RTCP f64 精确
显示外形 Part::shape 渲染 厘米级
碰撞代理 Collider 碰撞 保守（可大不可小）

结构约束（最有价值的一条）：三者都 add_child 到同一个 joint_entity，用关节索引关联，各自不存世界变换。于是"外观说还有 5 mm、碰撞说撞了"这类矛盾从结构上不可能发生。

碰撞代理方向不能反：必须外接（circumscribe），内接会漏报。L 形立柱、带圆鼻主轴头给 3–6 个凸体拼接，否则单个外接 OBB 过松会大量误报。防护罩/拖链/线缆一律 Collider::None。

参数必须实测校准（手册名义值 + 打表核对，1 小时），不要从 CAD 反推 pivot。 给错的 pivot 比让人手填更危险——手填时人会去打表量，自动生成的数值人不会怀疑。所以导入工具只做"局部变换 + 碰撞代理"，不猜运动学。

rest pose 陷阱：模型在非零位姿导出会把偏移固化——C 转 30° 导出，之后转 30° 显示 60°。导出前必须回零。

顺序铁律：先方块跑通再换精细模型。 精细模型掩盖运动学错误——方块转错轴一眼看出，真实模型转错可能只是"钣金穿模"，被当成美术问题。换模型只替换 Shape，对比两次刀尖轨迹必须 1e-9 一致。

关键测试 every_part_follows_its_joint：转 C 90°，挂 C 的部件跟着转、挂父关节的不动。写错成挂世界坐标时画面静止完全正常，一动就露馅。

精细 ≠ 准确：模型精细度只影响观感（碰撞用 OBB）；模型尺寸真实性在 collider=Derived 时直接影响碰撞正确性。尺寸随意的漂亮模型比方块更糟——方块尺寸是用户按手册填的，假模型会让碰撞去测一台假机床。折中：模型只做外观，collider 一律 Explicit 手填实测 OBB。

模型来源实测结论：参数齐全和精美是两个来源。运动学认 LinuxCNC 参数（refs/linuxcnc/），外观挂 glTF，碰撞用 Explicit 手填。 - LinuxCNC vismach 的 .xml 不是 3D 模型，是 pyvcp 控制面板定义；真模型在 *gui.py 里用 Box/CylinderZ + HAL 拼出来。 - 其中 pivot_len = 250 # to agree with default in 5axiskins.c —— 模型尺寸与运动学参数是同一个数，"配置即模型"的现成证据。 - Sketchfab 用公开 API 查了 6 个关键词，去重 84 个，全部 CC-BY，没有一个五轴整机；下载需 OAuth，拿不到文件本体。 - GrabCAD 条款页返回 403，未能核实具体条文——只能说"逐模型确认"，不能说"禁止再分发"这种具体结论。

12. G 代码解释器（gcode，117 测试）

只做"文本 → 位姿"，不做运动学。 一旦这里调 kin::inverse，解释器就绑死在某台机床上。

对标的是"语义"不是"功能集"：正确含义是同一份 G 代码算出同样的刀位轨迹，不是支持同样多指令。不影响几何的（冷却/IO/暂停/倍率）正确跳过即可。

两条从 LinuxCNC 原文核实的语义：

  1. 块内字序无关 → 实现是收进 Vec<Op> 按 Phase 排序（25 项，G4 在第 13 位不是最后）。顺序是结构保证，不是代码摆放顺序。
  2. 组 0 轴字代码挂起组 1（G10/G28/G30/G52/G92）。不实现则 G28 X0 Y0 之后多走一段。

三个"静默错误"最要命：

  • 隐式模态运动：X20 单独一行必须走。不支持则整份程序只有带 G 字的行会动，且不报任何错，切出来的东西静默不对。
  • 固定循环必须展开不能跳过：少钻一个孔，零件就是废的，而报告上看不出异常。
  • 坐标改写（G10/G52/G92）算错：每一块的形状都对，只是整体挪了位置——比少钻一个孔更难发现。

具体规则：

  • P 的单位由小数点决定（Fanuc）：P500 = 500 ms，P0.5 = 0.5 s。词法层必须记录"原文有没有小数点"——丢掉它，孔底暂停差 1000 倍，而几何上完全看不出来。
  • G10 L20 要减去 G52 + G92：它们也参与 位置 = base + 程序坐标，不减的话一次 G52 X5 之后对刀，原点整整差 5 mm。
  • InterpConfig 必须保持"程序初始条件"：work_offsets 是副本，同一份 cfg 跑两遍要给出一模一样的结果。
  • 三层分开存（WCS 表 / G52 局部 / G92 临时），不合成一个数——取消方式完全不同，合成一个数就再也分不开了。
  • GCode 用十分之一定点整数存（43.4 → 434），不用浮点比较——43.4 与 43.399999 在浮点下不相等，这种 bug 只在特定代码上偶发。
  • 刀径补偿是整份程序的后处理，不是逐行：拐角补偿点取决于前后两段方向，逐行时只看得见本段。 外角必须走圆弧：两条偏移线在外侧的交点比顶点远 r·tan(θ/2)，90° 拐角就多切 0.41r。真实机床是绕顶点滚过去的。 正确性判据只有一条，但它覆盖全部：补偿后每个刀位点到编程路径的距离恒等于 r。内角求交错、外角圆弧错、法向取反、半径符号反，都会在这里红。
  • 拐角的"出向"要用下一段起点的切向，不是下一段终点的切向——对折线没事（两端相同），对圆弧就完全错了。
  • 跳过影响几何的代码必须标 Trust::Unreliable——一漏后面所有位置静默偏移。

不做（都报 issue 并标不可信，而不是假装）：G87 反镗、G18/G19 平面下的循环、G68.2 + 循环（斜孔）、车削、攻丝、探测、G5.x 样条。

LinuxCNC ≠ Fanuc：G43.4 语义不同、G68.2 参数定义不同（欧拉角 vs 三点 IJK）、M62–M68 是 LinuxCNC 特有 IO。对标得到语义骨架，方言层仍必需。

13. 运动学与非线性误差

forward（矩阵连乘）/ inverse（Newton 阻尼最小二乘解两旋转 + 3×3 仿射解直线）/ rtcp_inverse（旋转角由程序给，只解直线）/ check（KinFinding）。

奇异的判据用条件数不是 |sin A|：rotary_condition() 算 ∂(刀轴)/∂(旋转) 的 κ = σmax/σmin，对任何"2 旋转"构型都成立。摇篮解析值 κ = 1/|sin A|（A=0→∞，A=90°→1），用它跟数值实现对拍。阈值 100 ⇒ |sin A| < 0.01 ⇒ A < 0.57°。

刻意设计：inverse / rtcp_inverse 不检查轴限位。 None 只表示"运动学上无解"（雅可比退化 / 不收敛）；超程用 violated_joints() 单独报。两者对用户含义不同，不能混成一个 None。

q() 按轴名构造——q 顺序是链顺序（摇篮 [C,A,X,Y,Z]），不是 XYZAC。手写数组必错。

inverse 残差不能用叉积（真 bug）：cur × target 在反平行时也归零，而且它指向"转轴"方向，与雅可比的列（轴的切向）正交——在 A=0 的奇异点上两者点积恒为 0，牛顿一步都迈不出去，48 次迭代后报"不可达"。实测：从 A=0 起步解 A=20 的刀轴，永远失败。改成 target − cur（误差向量，与雅可比同处切平面）。

13.1 插补空间由程序的 RTCP 状态自动决定，不设开关

RTCP 开 → 位姿空间插补（刀尖走直线，每周期逆解）；关 → 关节空间插补（各轴匀速，刀尖走弧线）。用错就仿真的不是同一个程序。

算例（摇篮 L=180，G1 从 (0,0,−5,A0) 到 (50,0,−5,A30)）：关节空间中点刀尖 (25,0,−10.963) → 偏差 5.963 mm；位姿空间中点精确 (25,0,−5)。

非线性误差闭式 ε ≈ R·(1 − cos(Δθ/2))（弧与弦的拱高）。反解后处理密度：Δθ_max = 2·acos(1−ε/R)。R=175：ε=0.1 → 3.87°、ε=0.01 → 1.22°（弧长 3.7 mm）、ε=0.001 → 0.39°。这就是"后处理要多密"的硬指标。

两个早退：旋转轴全程不动 ⇒ 链变换是"常量旋转 × 直线轴仿射"，刀尖恰在弦上，误差恒 0（三轴程序连采样都不做）；起讫点重合（纯回转、刀尖定点）时弦退化为点，改量到点的距离，不能除零。

13.2 点流密度：弦高容差，不是固定 1 ms

生产比消费快约 200 倍（100k 段：插补+IK ~2.5 s，去除+碰撞 ~500 s）。所以缓冲不是性能问题，是响应性问题——小比大好。

修正：需要控制器行为的三个量（非线性误差、轴速降额、伺服周期）都有闭式公式，用端点就能算；几何精度由弦高容差定。按 1 ms 算，3 秒段 3000 子步 → 10 万段 16.7 小时（荒谬）；弦高容差下 25 子步 → 8 分钟（120×）。

n = ceil(Δθ / (2·acos(1−ε/R)))，R=175、ε=0.01 → 摆 5/15/30/60° → 5/13/25/49 子步。 推论：5 轴去除成本由"摆角 / 弦高容差"驱动，要写进 UI 预估。

两个缓冲背压相反（易混）：PointStream（预读→仿真）满了阻塞生产者；PlaybackBuffer（仿真→回放）满了丢弃旧的（否则被"用户没在看"拖死）。

回放不走点流：pose_at 是闭式函数，每帧直接求值；拖时间轴不需重算点流。 取消语义：置 AtomicBool → 丢缓冲 → 起新任务 → 旧线程自然结束。不要 join()（UI 会卡）。

13.3 加工包络：不是长方体，是一组随姿态变化的盒子

Φ400 工件、求最不利点可达（tools/envelope.py）：

A 可用高度
0° 340（Z 限）
30° 420（峰值）
90° 只剩 120（Y 限）

两个反直觉结论：① A=30 比 A=0 能加工的工件更高（倾斜后顶点落进 Z 富余区）；② A=90 时瓶颈是 Y 不是 Z（工件伸出 180=L 就吃满 Y 行程）。

三条 caveat：点可达 ≠ 能加工（没算碰撞）、数字贴着限位（实际留 10–20%）、假设工件居中。 离散化：C 采样 36 档会把 A=30° 从 420 低估到 410；72 档已收敛。低估方向安全（不过度承诺）。

14. HMI 与报错

HMI 不是 UI 的一部分，是独立状态机。 hmi 依赖 sim；ui 只依赖 hmi。

两个状态机必须分开：SimState（Idle/Parsing/Ready/Computing/Done/Failed，"后台在算什么"）vs ControlState（Idle/Ready/Running/Paused/EStopped/Faulted，"用户在看什么"）。 暂停只停回放，计算继续——先算后播的自然结果。EStopped / Faulted 必须复位才能离开。

急停在仿真里是"可撤销的带时间戳事件"：控制器里急停不可逆，仿真器里如果也做成不可逆，用户就没法反复试"第 30 秒急停会撞吗"。所以做成事件 + 记录 {at, block, tip} + 程序标不可信。这把"急停"从按钮变成可编程的仿真输入。

倍率三种（进给/快移/主轴）。v1 走理想路径 → 只改时间不改几何。但实际进给 = min(程序×倍率, 轴速限)，报告要给"程序倍率"和"实际达成率"——用户想知道"为什么拉到 150% 只快了 8%"。倍率时间线比实时滑块有用得多。

统一报错三条硬要求：

  1. 编号是稳定契约，消息可以改（GCODE-012 / KIN-001 / COLL-003 / HMI-001）。测试断言编号，不断言消息文本。
  2. 位置三元组：sim_time + block + line，缺一不可。
  3. 每条必须有 hint。不合格："未知 G 代码 G123"；合格："…不在 Fanuc 子集内，已跳过；若是自定义循环请检查后处理配置"。报错的价值在于"下一步做什么"。

severity 四级：Info / Warning / Error（能继续但结果不可信） / Fatal。Error 专门用来避免把"能跑但结果错"伪装成成功。 聚合：同一 alarm 触发 1000 次 → 1 条带 count。every_alarm_has_hint 是质量门测试——把口头要求变成 CI 检查。

面板是纯数据层（cncsim-ui）：UiView 只返回 &'static str / Tone / Vec<AlarmRow>，一个 egui::Ui 都不碰。因为「该显示什么」是可判定的，「怎么画」不是——改排布/配色不该让测试变红，改判据才该。 被锁住的五条判据：六态横幅互不相同 / 四级徽标互不相同 / 报警按严重度降序 / 复位键只在卡死时亮 / 位置串是三元组。

15. 显示层（ADR-011）

先不引 Bevy 的理由：这一层难的不是窗口，是"体素网格 → 能画的三角形"。前两步（交错顶点、分块）能脱离引擎验证，第三步只是适配。

  • interleave：位置+法向交错 [x,y,z,nx,ny,nz]，顶点顺序与索引原样不动（可逐位对回提取结果）。
  • split_tiles：按三角形质心分块（每三角形恰好属一块），块内顶点重映射；块号必须排序（HashMap 迭代顺序不定会破坏逐位复现）。
  • tiles_per_frame：8 MB 预算，至少返回 1（否则永远卡住）。
  • preview：单文件 HTML + 200 行原生 WebGL2，数据内嵌 base64，零外链（CDN 一离线就白屏）。

怎么验证一个打不开的页面：tools/check_preview.mjs 用桩 WebGL 跑页面里的 JS（抓语法错、API 拼错、draw call 数不对）。 再加一条几何探针：把包围盒 8 角投到 NDC，必须全在 [-1,1] 且跨度 > 0.15。lookAt / perspective / 矩阵乘法写错在浏览器里就是一片空白，而这条断言能抓到它；光有桩测试抓不到。

15.1 增量重建（render::TileCache）

整体重提 200 mm 毛坯 404 ms，增量重建一次面铣 35 ms（11×），只重算 66 / 4017 块。

三条规矩，每条都是踩过坑的：

  1. 分块提取不能有缝：按"发射格"划分——每个四边形由最小角所在的格发射一次，各块天然不重不漏。
  2. 替换范围要比提取范围小一圈：三角形按质心归属块，区域边上的格会发射质心落在区域外的三角形。所以提取范围外扩一块，边界上那些半残的块直接扔掉。
  3. 没变的块不重传：逐字节比较 + 版本号。上传受预算限制，没传完的必须记在队列里——不记的话"下一帧再传"是假的：下一帧重新提取发现内容没变，那些块永远不会出现在屏幕上。

自定义材质失败是静默的：着色器路径错、模块路径错、AsBindGroup 形状错，都只打一条 ERROR 日志，然后网格不渲染——画面看起来和"相机对着空处"一模一样。所以 --screenshot 不是锦上添花，是这一层唯一的验证手段。

四条已经踩过的（详见开发日志第十二、十三轮）：

  1. AssetPlugin.file_path 必须指到项目根的 assets/（默认按可执行文件目录找，cargo run 时是 crates/app/assets/）。
  2. 不 import bevy_pbr::forward_io（0.20 的注册表里没有），自己按约定声明 FsIn：@location(0) 世界坐标、(1) 世界法向、(5) 顶点色。
  3. front_facing 是 builtin，写成参数：fn fragment(in: FsIn, @builtin(front_facing) front: bool)。
  4. AsBindGroup 的 derive 不认单元结构体，加个占位 #[uniform(0)] unused: u32。

相机锚点固定在原点：PanOrbitCamera 的更新系统用 last_anchor_depth（相机到原点的距离）重算位置，会丢掉 Transform.translation。模型中心不在原点时必须加一个 model root 实体把模型搬到原点，相机绕原点转。

颜色：着色器里的常量是 sRGB 数值，片元输出是线性空间。直接输出等于编码两次，浅灰变近白——必须 pow(base, 2.2)。

刀具显示：Profile 母线绕局部 +Z 旋成旋转体，网格原点是刀尖，所以 translation = to_world_model(pose.tip)、rotation = Quat::from_rotation_arc(Vec3::Z, to_world_dir(pose.axis))。 母线端点在轴上时四边形会塌成三角形，必须只发一个三角形——否则 compute_normals 给面积 0 的三角形算出零法向（端面上出现黑斑）。

材质别用 metallic: 0.9：没有环境贴图时全金属只剩两盏方向光的镜面高光，圆柱渲染成一根发白的亮柱子，在浅灰毛坯上反而认不出是刀。

17. 测试方法论（从踩坑里提炼）

每条规则都对应一次真实的漏检。

  1. 每个测试必须能被证伪：断言要具体到能区分"做对了"和"做错了"。assert!(result.is_ok()) 无法区分正确与错误的 Ok。
  2. contains 用在拼接串上是假阳性制造机：断言位置串的块号用 contains('4')，而 t=3.742 里本来就有 4 → 块号写成 0 也能通过。改成整串相等。
  3. 测试阈值必须由保证下限反推：ADR-004 曾写 1 µm（"留 6 倍裕度"），而保证下限是 1.6 µm——这个断言按定义就可能合法失败，随机对拍会间歇性红，失败原因看起来像实现有 bug。改成 truth > 5e-3。
  4. 用同一份实现自证必须再配独立 oracle：KKT 断言和 GJK 用的是同一个错的 support，两边一起错就自洽。
  5. 新路径必须有专门踩它的用例：sin_cos 返回顺序写反过一次，全部测试都是绿的——因为它们只用 +Z 刀轴，而平移路径已经不碰三角函数了。
  6. 测试必须成对：漏报 + 误报。只有漏报测试会诱导出"永远报碰撞"。
  7. 先写朴素实现确认它漏报（红），再换正确实现（绿）——否则无法证明新方案真的解决了问题。
  8. 强性质测试优于数值比对：完美面铣（刀底=设计顶）过切必须精确为 0；补偿后每个刀位点到编程路径距离恒等于 r；按报出的 depth/axis 把 A 推开，两体必须恰好接触。
  9. 测试自己写错的几种模式（都实际发生过）： - 用对称矩阵测 inverse，抓不到转置错 → 换非对称并同时验 M·M⁻¹ 与 M⁻¹·M。 - 手写数组传参顺序错 → 加 q() 按名构造。 - 断言"内部是 Constant 叶"，实际连叶都没分配（是 tile，更好的结果）。 - 用 fill_box(0..128)³ 造数据，而 128³ 恰好是一个完整 level-1 块 → 被合成 tile，没有 Level1 节点可查。 - 探针落在刀轴内部 / 两刀表面交线 / 交线角点。 - 精度测试把槽底放在 13.5h——正好是体素中心，插值不需要跨格点，误差测出来全是 0.000 µm（假象）。改成 13.3h 才暴露量化误差。
  10. 整段替换前先确认截断点之后没有别的东西：改 split_quads 时用 s[:i] + new 把文件末尾的 #[cfg(test)] mod tests 截掉了，4 条单元测试静默消失（总数没变因为同期加了 4 条新的）。
  11. 报错要能二分：先自研数学/运动学/G代码/碰撞，材料去除暂借外部当脚手架——若同时面对"运动学对不对"和"内核对不对"两个未知数，出问题无法二分。
  12. "数学上等价"的改写要实测验证，不能推导完就信：cur * k_dist < neg_sd 与 cur < ceil(neg_sd * k_value) 在实数上等价（k_dist·k_value = 1），但浮点下两条路径的舍入不同——81 * (0.8/127) 是"除法 + 乘法"两次舍入，neg_sd * (127/0.8) 是反推回档位。实测在量化档边界上分歧（sd=-0.510236220472, cur=81：浮点说不改、整数说要改）。把这种"不能做的优化"写成反向测试（断言"确实存在分歧"），哪天它变绿就说明前提变了。
  13. 性能数字必须注明机器状态：同一份代码、同一台机器，连续跑几十轮之后 CPU 降频，铣光逐刀从 47 ms 涨到 56–65 ms（±15%），建场从 14 涨到 18–21。单次测量不可信，A/B 对比必须在同一时间窗口内交替跑，或者用多轮累计值（perf_cut_loop）。这也是为什么"优化后看起来更慢"经常是假的。

18.1 VTune 提权（要硬件计数器必须看这几条）

-collect memory-access 想拿到 LLC / L1/2/3 Bound，一路踩了三个坑：

  1. 采样驱动要注册。sepdrv5.sys / sepdal.sys 文件在 System32\drivers 里， 但服务没注册（Get-Service 里没有任何匹配项）。用 VTune 自带的 bin64\amplxe-sepreg.exe -i 注册，必须提权（连 -c 查询都要求提升）。
  2. 采集器本身也要提权。驱动装好之后不提权仍会报 Microarchitecture performance insights will not be available + Level 2/3 capability: not detected——那是用户态采样，不是 PMU。
  3. 提权启动时路径必须加引号。Start-Process -Verb RunAs 走的是 ShellExecute， -ArgumentList 数组拼出来的命令行不会给含空格的路径自动加引号， 而本项目路径是 C:\Users\15796\WorkBuddy AI\CNCSIM\…（带空格）—— 表现是 vtune 静默 exit=1、结果目录不生成。要自己拼成带引号的字符串：
$argline = "-collect memory-access -result-dir `"$res`" -- `"$exe`" profile_s4 --ignored --nocapture"
Start-Process -FilePath $vt -ArgumentList $argline -WorkingDirectory $root -Verb RunAs -Wait

另外两条：提权拉起解释器被安全策略拦，所以配置只能靠测试名传 （profile_off / profile_s1 / profile_s4），不能靠环境变量——提权进程不继承环境。 运行时间要 ≥ 2 s，否则 VTune 自己会报 metrics data may be unreliable （0.35 s 时三组的 LLC miss 竟然完全相同，就是样本太少）。

21. 刀具与换刀 · 半球凸台（2026-11-02）

锥度球头刀的母线：切点必须相切，不能取球心高度

规格表 R0.5*30.5*D6*75 / 单边斜角 4.69° 里，4.69° 是从刀尖量到刃顶的弦角 （atan(2.5/30.5) = 4.687°），不是球头切点处的锥面角。球面与锥面相切的条件是 切点 (r·cos α, r(1−sin α))；直接取 (r, r) 会在刃口留一圈 α 大小的折角 （4.69° 的刀在 0.5 mm 球头上是一道肉眼可见的棱），仿真里就是一圈 0.5 mm 宽的假过切。 两种口径的刃顶半径只差 0.037 mm（Ø5.926 vs Ø6），所以按表里的角度建模是忠实的。

换刀：ToolTable + Block::tool，一份程序一条时间轴

  • ToolTable 按刀号查，不是按下标——程序里 T1 → T2 → T1 是合法的。
  • T 字是可选：Block::tool 初值 0 = "没指定" → 取第一把，不是缺刀。 早先按 0 查表 → None → 每块报一次 TOOL_MISSING，面铣演示满屏红字。 写了刀库里没有的刀号（T7）才是真错：退回第一把 + Error 级报警。
  • CutSegment.tool 一路带到设计比对：过切判定必须用这一段真正那把刀的母线。
  • 时间轴、溯源刀号、报警都不分段：换刀不重启仿真，cut_ordinal 继续往下数。
  • 窗口里每个刀号一个骨架实体，回放按当前块切可见性。

刃长 20 > 加工深度 15，所以底层（z=85）那一刀的刀身覆盖 85..105，半径 ≥ 内缘 的部分在整个高度上被它一次清完。上层只需要补 [r_in(z), 底层的刀内缘] 这段环带， 很多层（88/87/86）的环带直接是空的、可以整层跳过。路径长差 4 倍（15.5 min vs 3.9 min）。

r_in(z) = √((R+a)² − d²)，d = z − 85；最后一层 a 取 0.02 把底面铣平。

球顶那一块灰斑：不是漏算，是几何够不到

球顶若与毛坯顶面平齐（球心 z=85、顶 100），球顶周围半径 √(2R·a) ≈ 3.9 的 那层球冠任何刀具都够不到：要切它，刀就必须比它更靠近球顶，而一靠近就切进球。 实测成品球顶留一块 6 mm 见方的毛坯面（色索引 0，灰的），12.8 mm³。

平底刀能，球头刀不能——平的刀底与球顶相切不算切球，所以修法是让球心降 1 mm （球顶 99 = 毛坯顶 − 1），第一刀面铣把顶面切到球顶平面。这一步是必需的， 不是"顺带光一刀"。

三个真坑

  1. 同心圆只走到边 = 四角全留。方块对角 √2·25 = 35.4 比边长 41%。第一版把 最大半径取 26，四个角留下 3169 mm³、残留最厚 15.000 mm（报在 (1.1,1.1,100)）。 改 36 之后残留掉到 12.8 mm³。判据要写成测试：四个角点必须被某一段刀具覆盖。
  2. 整圆 G2 I- 的 I 是相对起点的。连着写 G2 I-r 时，第二圈的圆心落在 「上一圈终点 − r」上（实测偏到 21 而不是 25）：圆的大小对、位置全错，看起来像 "刀路莫名其妙歪了"。每个整圆前必须 G1 X{cx+r} Y{cy} 先把刀移到该圈起点。
  3. Cavity/Boss 的盒面采样容差必须是 0。给"半个采样步"会把球口内侧的 空气点当成设计面，精加工球扫过去就报假过切（实测 1.2 mm³ / 0.25 mm）。

Unity/Unreal 那套调试视图（法线、深度、面朝向、overdraw）能看出"哪里不对"， 但看不出"错多少"。我们的着色是自写的（CutMaterial 按 creator 索引查调色板）， 所以把检查下沉到数据层：tools/check_mesh.py 直接解析导出页里的顶点缓冲。

--ref-sphere 是解析参考：给一个球，直接算每个球面顶点的法线与理想法线的 夹角、径向误差。这是把"看起来有波纹"变成"1.94°"的办法。

麻点的四个根因（都不是渲染器的问题，是着色索引）

  1. 取色兜底方向反了。lod_vertex_batch 里"取不到就往 -normal 探一格"， 理由是"毛坯外棱外侧是空气、内侧是料"。这条对台阶成立，对凸台相反： -normal 是从没被切过的原始料，creator 恒 0，越探越 0。 实测 12935 个球面顶点里 411 个取到 0（灰点）。改成"先往外、再往里"， 偏移取 h 的奇数倍（0.5/1.5/2.5）避开格面。
  2. 染色只盖一格。changed_mask 只给 |sd| < h 的子块盖章。顶点是从粗格 （k=4）插值来的，位置带 0.1–0.3 mm 误差，一偏出那一格就取到上一个工序的旧色。 放宽到 band（4h），颜色带覆盖窄带全宽。
  3. 球顶螺旋 n = 1。2ρ ≤ 弦长 → 一段就够 把"直径"当成了最大弦长， 而一圈的周长是 2πρ：θ<2.2° 那几圈变成"一段直线跨过整圈"，中间整片漏切。 下限改 3；真正的判据是圈间间隙 gap = 行距 + ρ(1−cos(π/n)) < 刀半径， ρ<2 时弦长收到 0.45（n=8）。测试 finish_rings_never_leave_a_gap_wider_than_the_tool。
  4. 值不变但擦面不盖章。球顶正好是面铣层的切点，两次切削的等距面重合 → 场值不需要改 → n == 0 → 不盖章 → 永远保留面铣的 creator=1。 改成"值没变但 |旧值| < h 也盖章"。

结果：球面 creator=0 从 411 → 0，球冠全部是最后一档，孤立色点 456 → 12。

试过但失败：细步长梯度重算法线

想法：vertex_of 用 8 个粗格角点的中心差分（步长 k·h = 0.4），SDF 本身是精确场， 梯度不该跟着降采样。改成 0.8h 的 sdf_cached 差分后：

  • 球面法线偏差确实降了，但
  • 顶点数 145214 → 867699，HTML 10 MB → 37 MB

原因：sdf 是三线性插值的体素场，格面处梯度不连续。细差分把每个格面的折痕 都放大成 >45° 的法线跳变，split_crease_normals(0.707) 把它们全当硬边拆开。 粗步长差分在这里恰好是低通滤波。要更光滑只能提高网格精度（k=2，文件 4 倍）。

球面那层「同心波纹」的来源不是 LOD 本身，是顶点法线：提取时用的是 SDF 的粗格中心差分（步长 k·h），带格子尺度的噪声。

新方法 MeshData::recompute_smooth_normals：面积加权的面法线平均。未归一化的 叉积长度 = 2×面积，所以"直接累加不归一化"天然是面积权重。必须在 split_crease_normals 之后调——硬边已经按夹角拆成独立顶点，每个顶点只累加 同一侧的面，平均不会把棱角抹圆。

23. 切割染色改为体素级（2026-11-04）

§22 里“值不变也盖章 / 重合精切取最新”的做法已被本节推翻：现在只有真正 去除材料的体素才改色，擦过旧面不改色。

注意：本节「材料→空气」的判据在 §24 又被修正为「场值变了且新面在一格内」—— 0.02 mm 的最后一层留量不会让格心跨零，但仍是真的削出了面。

用户报「染色做不到只染切割处，相邻切割互相侵染」。根因不是调色板：

  1. 默认 creator_sub = 1，一片叶（8h = 0.8 mm）只有一个色号；
  2. changed_mask 把「旧值贴面」当成「当前刀造面」，同叶任何变化都会重盖旧刀痕和原始面；
  3. 两条渲染链插值色号，跨色三角形的片元会出现第三种颜色。

修法

  • 默认 creator_sub = 8，每体素一个 creator。需要时仍可显式调小。
  • 盖章只认材料去除：旧值 < 0、新值 >= 0、新面仍在窄带内。 重合刀、擦边刀、只修正邻近场但仍是材料的体素一律保留旧色。
  • 提取颜色取 8 角中 SDF 最大（空气侧） 的体素；取材料侧会得到 0/旧色。
  • WebGL/WGSL 顶点色都声明 flat；same_mesh 比较法向与颜色。

25. 简化 CAM：STL → 高度场 → G 代码（2026-11-04 晚）

用户要「输入毛坯，输出 G 代码，用现有解释器和仿真验证」。做了 cncsim-cam （第 14 个 crate，依赖只有 math + tool），生成器不认识解释器/仿真器， 验收放在 crates/cam/tests/e2e.rs。

输入与假设

  • 输入是三角网格 + 轴对齐毛坯。.stl 由 app 读（voxel::stl）； .stp/.step 是 B-rep，CAM 明确拒绝：需要先三角化为 STL（FreeCAD 另存）。
  • 3 轴、+Z 可加工：每个 XY 列只能有一个上表面。中空/薄壁/倒扣件不适用。
  • 没有命中的高度场列 = 不是零件，不加工（保留毛坯）。

算法

  1. 高度场：三角形按 XY 包围盒分桶，逐列向下射线求交；取最高 z 与法向。 z 的梯度做中心差分得到平滑法向（用命中三角形的面法向会在相邻折面上 啃出 0.03 mm 过切，实测）。
  2. 粗加工：平底刀 Z 层行切。可下刀判据是刀盘腐蚀—— max(z within r) <= level - allowance + 0.05；只看列本身会让刀盘边缘 啃进旁边更高的材料。下刀用 G1（G0 在仿真里不算切削）。
  3. 精加工：球头刀平行行切，每点 tip = surface + R·n − (0,0,R)； 行距 = finish_stepover，沿走刀方向采样更密（sample_mm）： 球心走直线，弦高 ≈ dx²/(8(R+ρ))，用行距当采样步长会过切 0.03 mm。
  4. 每列统计独立表面层数（命中 z 相差 >10 µm 才算一层，共边三角形会 重复命中同一个面）：封闭实体通常 2 层（顶+底），>2 层且超过 2% 的列 直接拒绝。流云花瓶.stl 实测 21564/29045 列（74%）多层 → 拒绝。

与原始模型的对比

--cam 跑完后除了解释器/仿真的过切/残留，还做逐列高度差：

  • 加工顶面 = 网格从上往下第一个材料体素中心；
  • 设计顶面 = 设计 SDF 从上往下第一次变负的体素中心；
  • Δz = 加工 − 设计：正 = 残料，负 = 过切；两者同量化，体素误差抵消。
  • 输出 *.diff.html：顶视热力图（绿 ±0.1、红残料、蓝过切、灰无数据）。

assets/models/relief.stl（16×16×3.5 的凸包板）实测：平均 |Δz| 0.002 mm， P95 0.000，最大残料 0.250 mm，过切 0，99.0% 的列在 ±0.1 mm 内； 仿真过切体积 0 / 最大 0.022 mm，残留 3.97 mm³ / 0.18 mm。

27. 怎么判断"加工完还像不像原版"（11-04 深夜）

这是被直接问到的：你如何判断加工后的模型与原版形状保持尽可能一致。答案不是 一个数，而是三层口径 + 一类不测数值的护栏。三层各能发现不同的病，换层就会换结论 ——花瓶就是活例子：旧口径 48.6% 合格，新口径 24.9%，而两者的差值本身就是诊断信息。

三层口径

层 量什么 能发现 盲区
① 单向几何量 3 轴：每列顶面 Δz（height_diff）；回转：θ×z 格点上的最外层 Δr 系统性让刀、整圈偏深/偏浅 只量一个方向：Δz 看不见侧壁，Δr 看不见端面/底面/轴向错位；格点之间（2.5° ≈ 2.4 mm 弧长）的小坑读不出来
② 整实体体积 compare_with_design：过切体积+最大深度+包围盒+源行号；残料体积+最大厚度 "料留在设计面之外很远的地方"（方料四角）、成片的多切/少切、能定位回 G 代码 比的是体积不是曲面位置：0.1 mm 的整体让刀在体积上几乎不动，装配上却致命
③ 名义曲面逐点 sim::surface_dev：设计面按 0.8 mm 采点，逐点查实际毛坯场 SDF 的有符号距离 形状保真度本身；过切/残料深度分布；按 A 角/曲率分组定位 单边采样看不见"远处残留的料"；窄带 4 mm 以外读数被钳制；采样密度随三角形大小变（非等面积加权）

③ 的符号约定：d > 0 = 该点已是空气（材料被切掉，过切深度）；d < 0 = 还在 材料里（残料厚度）；|d| ≥ band = 钳制值，只表示"至少差这么多"。这就是三坐标 /全尺寸检测的做法——在名义曲面上打点，量有符号偏差，而不是量体积。

为什么不能只报一个合格率

  1. 公差带可调：同样一件活，±0.5 报 48.6%、±0.15 报 24.9%。阈值必须按工艺给 （粗加工 0.5、精加工 0.05~0.1），并且在报告里写出来，否则数字没有意义。
  2. P95 掩盖局部：95% 的点贴得很准 + 5% 挖穿 4 mm，P95 会很漂亮。所以必须同时 给 最大过切、最大残料、超窄带点数。
  3. P95 要取 |d| 的分位：直接对带符号序列取 95 分位，读出来的是"有 5% 比它更负"， 跟"偏差多大"不是一回事。这个坑在 Δr 上踩过一次（P95 显示 3.5 = 窗口边缘， 而实际有一半是 −3.5 的饱和值）。
  4. 平均值会把"够不到的一片"摊到"够得到的一片"上：所以要做分组——按所需 A 角、 按曲率符号分组，让"某一类面整体不达标"自己显形。

三类不测数值的护栏（都在 crates/cam/tests/）

数值度量只能告诉你"差多少"，说不出"为什么差"。三坐标式的护栏跑得快（合计 20 s）， 专抓整类错误，不必等 2 分钟的仿真：

  • rotary_rtcp.rs：圆锥试件，检查解释后的位姿——刀尖落在解析轮廓上、球心必须在 轮廓外侧。刀轴反了是五轴最典型的翻车方式（R 的两倍过切，看起来像"整体缩水"）。
  • rotary_cylinder.rs：圆柱闭环（生成→解释→仿真→反量）。现在同时用两种口径： 沿半径二分（最差 0.12 以内）+ 名义面打点（P95 0.067、100% 落在 ±0.15）。已知答案的试件是唯一能 校准度量本身的东西——度量错了，花瓶上的数字全是噪声。
  • roughing_keeps_the_allowance：逐条 G1 反算刀轴与球心，到轮廓的距离不得小于余量。

三条独立证据指向同一个机制——球头半径放不进漩涡的凹谷：

  1. 偏差图（out/vase_rotary.diff.html）上，合格区是沿漩涡脊线的斜条，谷底整片 饱和到 −3.5：凸脊能保住、凹谷被整段架桥切掉，是典型的"刀大谷窄"。
  2. 关掉粗加工（--no-rough）反而更差：平均 |d| 1.932、过切 99.9%。方料全是实心时， Ø4 球头带 5 mm 刃部的圆柱段一路扫过去，把刃部能碰到的地方全啃了；有粗加工时 凹谷之外的材料已被清掉，刃部才没那么凶。→ 过切不是粗加工留下的余量。
  3. 过切在 A 各区间均匀 → 不是行程/位姿问题。

结论：这件件的漩涡谷宽和起伏（~1 mm 级、坡度到 60°+）小于 Ø4 球头的可及尺度。 要真的保持形状，只能换小刀（Ø1 球头配 ~1° × 0.5 mm 步距，刀点数 ×4、仿真 ~9 min）， 或者承认这道工序只做"外形近似"，把验收标准改成"无过切 + 残料 ≤0.5"而不是"贴面"。 没有第三条路——球头半径是物理下限，刀路再密也补不回来。

度量本身的校准

  • 圆柱（已知答案）上：① P95 0.067、③ 100% 合格 → 说明运动学、扫掠、SDF 查询都对。 花瓶上 24.9% 不是度量坏了。
  • 窄带是 4 体素 = 4 mm（h=1）：|d| ≥ 4 的点只能报"至少 4 mm"。要看得更深就得 加带宽或降 h，两者都直接涨内存/时间。
  • ③ 只统计外轮廓面（r ≥ R(θ,z) − 1.5）：内腔本工序不加工，算进去只会得到 "残料 100%" 的假数字。花瓶有 152022 个内腔点被排除，这个数字要一并报，不能藏。

30. 多线程利用率：批量切削（11-05 凌晨）

现象：回转件 12 万段刀路，仿真 CPU 利用率很低。

CNCSIM_CUT_BATCH=256（批量） 21.3 s 34.4%

33. 任意刀轴角度 + 刀杆碰撞（11-05 深夜）

两条要求：「加工角度只要满足机床运动学限制、G54/G53 要求，就可以任意角度」、 「刀路规划还要考虑刀杆与切割中工件的碰撞」。

任意角度：不是"凑 90° 的倍数"

轴向 5 道（±X/±Y/±Z）配 45° 坡度门槛，覆盖的是「法向与某根轴夹角 ≤45°」的面； 剩下的洞在体对角线附近。补的斜向道可以取任意倾角：

# 默认 --tilt 54.7356 --tilt-n 4 = 四条体对角线

唯一约束是机床：A = acos(dir.z) 必须 ≤ A_LIMIT_DEG（110°），超了直接丢掉并报 A>110° 运动学挡掉 N 道。约定上仍走 Head（双摆头）——Table 那套里 C 角对 刀轴没有影响，表达不了任意方向。

  • 程序头 (WORK OFFSET G54) + G54：所有坐标都在工件坐标系里。
  • 程序尾 G49 → G53 Z{毛坯顶+30} → M5 → M30：回参考点必须用机床坐标， 工件坐标系在换装夹/换工序后会变。数值按「G54 的 Z 偏置 = 0」给，机床偏置不同时 按机床改（注释里写明了，没有假装通用）。

  • 普通球头/平底刀 + 无倒扣 ⇒ 不需要查（need_shank 直接 false，零开销）；
  • 锥度刀（锥颈比尖端粗）或零件有倒扣（undercut > 2%）⇒ 建 MeshIndex （XY 分桶 + 点—三角形距离，Ericson 5.1.5），沿刀轴取样，刃长以上每点要求 距离 ≥ 刀杆半径 + 间隙，撞到就放弃该刀点、留料并计入 Stats::shank_skips。

两条都留成了 CLI 旋钮（--finish-step、--slope），默认不启用更贵的那档。

结论：这时候的瓶颈是验证分辨率，不是刀路

h=0.6 时 ±0.15 mm 的判据只有半个体素宽，SDF 量化本身就贡献了大半读数； 把行距减半只换来 2 个点，正是"量化噪声盖住了刀路误差"的表现。要让"更像原版" 再上一个台阶，只有两条路：

  1. 降 h（h=0.3 时判据才等于一个体素，读数才有分辨力）——代价是仿真时间 ×4；
  2. 处理够不到的面：残料集中在底面附近的凹角（(-6, 9.5, -28.5)）， 那是 5 个轴向 + 4 条斜向都看不到的区域，只能靠五轴联动或翻面装夹。

所以这一轮真正的改动是"把接近程度变成可量的数 + 两个旋钮 + 明确的结论"， 没有假装把 81.6% 调成 95%。

37. 可达性 + 工序编排：让几何自己决定用几道（11-05 深夜）

要求：不要限定加工方式，三轴 / 3+2 / 五轴 RTCP，只要能让结果更接近原版都可以用。 上一轮已经能从"残料"里看出够不到的面；这一轮把它变成决策依据。

做法：一次可见性矩阵 + 贪心集合覆盖

crates/sim/src/reach.rs：

  1. visibility(design, samples, dirs, cfg) — 对每个设计面采样点、每个候选方向， 判两件事：面朝（n·d ≥ cos45°）和射线不被挡（沿 d 球体追踪，每步 0.8·sdf）。两个位图分别存 facing 和 masks。
  2. Visibility::greedy(base, max_extra, min_gain) — 带权集合覆盖，每次挑"新覆盖 面积最大"的方向，新增不足总面积 0.4% 就停。这一层才是"用哪种工艺"的判据： 3 轴就是 +Z，3+2 就是任意倾角定轴，两者是同一套高度场，只是方向不同。
  3. report_with(vis, mask) — 按最终方向集出报告，够不到的面按空间连通块分组 （并查集，格距 = 2.5×采样间距），每片给建议方向、A/C 角、区域 bbox。

RTCP 的位置：真正的五轴（刀轴逐点跟法向）只在回转件上有实现（--rotary），判据是 rotationality ≥ 0.85。--multi 现在会先打印这条判断，回转件直接告诉你该走 RTCP； 非回转件用足够密的方向集逼近，本质区别是每一刀仍是定轴，没有"沿法向恒接触"的 光洁度优势。这句话写在输出里，不含糊。

38. 特征级形位公差（11-06）

"继续添加模型差异对比算法"——上一轮列的下一步 #5：平面度 / 圆柱度，按 ISO 1101 最小区域法。新增 crates/sim/src/form.rs（7 个测试）。

定义与基准

平面度 = max(n·q) − min(n·q)     圆柱度 = max(r_i) − min(r_i)

是区域宽度，不是"最大偏差"。基准要优化到最小区域：八方向模式搜索 （±e₁、±e₂、四条对角），改进不足千分之一就缩步长。LSQ 基准同时算， form_lsq ≥ form_mz 是构造上成立的，差值只说明"LSQ 高估了多少"。

表面点：设计面采样沿实际场梯度投影（q = p + d·∇d/|∇d|），一阶精确，无需最近邻。

39. 三个口径：把"过切 6.4%"拆成 0.9% + 判据误差（11-06）

上一轮留下的问题：可达面上 6.4% 的过切（最大 +1.55 mm）到底是刀路还是判据？ 这一轮把它查清，并顺手改掉了真正决定保真度的那一项。

加了两件量具

  1. compare::attribute_points（逐点扫掠体归因）：对每个设计面点问"哪一段 刀具扫过了它、侵入多深"，返回 tool / block / line / 深度。刀号在多工序 里就是 2i+1 / 2i+2，所以能直接反过来认出是第几道、粗还是精。
  2. compare::sweep_deviation（解析口径，与 h 无关）：设计面点到 "刀具扫掠体并集"的有符号距离。<0 过切、≈0 切到位、>0 残料、+∞ 刀具从没接近过。它就是三坐标测量在仿真里的对应物。

结论一：6.4% 里只有 0.9% 是真的

同一份刀路、同一批点，两个口径：

口径 合格 过切 残料 最大过切
体素（h=0.6） 81.6% 5.8% 12.6% +1.55 mm
解析（与 h 无关） 85.0% 0.6% 14.4% +0.27 mm
可达面：体素 86.0% 6.4% 7.6%
可达面：解析 90.7% 0.9% 8.3%

逐点归因给出直接证据：h=1.0 时体素报过切的 14834 点里，11699 点（79%） 没有任何一段刀具扫掠体碰过。那些点全在薄于一个体素的尖角上——体素把 整格判成空气，读数就变成"过切 2.1 mm"。

所以口径的正确用法是：验收看解析值，体素值只用来定位体积/残料分布。 h 不再卡验收（h=0.6 与 h=1.0 的解析数字完全一致），只影响体积积分。

结论二：残料不是刀花，是凹角圆角

残料按厚度分档（Ø3 基线，h=0.6，共 22869 点）：

0.15–0.25 mm  5302 点   ← 刚出公差带：凹角圆角的浅带
0.25–0.50 mm  9262 点   ← 同一类，深一点
0.50–1.00 mm  3710 点
>1 mm         4595 点   ← 全部是"刀具从没接近过"（reach 判不可达）

可达面上的残料再分一次：3308 点是"刀走过了但切不到"（凹角圆角）， 只有 232 点是"工序没走到"。也就是说残料不是覆盖率问题， 是球头在凹角处必然留下的 R(1/sin(θ/2)−1)（90° 角 = 0.41R）。

换成 Ø1.5 后同一批数字是 4951 / 2721 / 685 / 3039：0.5 mm 以上的档位 被吃掉了（3710 → 685），剩下的 63% 集中在 0.15–0.5 的浅带里—— 正是小半径球头能把圆角收细的那一段。

结论三：刀径是唯一有效的那根杠杆（实测三次）

  • 翻转装夹（13.6% 几何不可达）仍然没做：不可达面里 60.8% 是残料， 解析口径下这部分折算约 17% 的面积，是剩下最大的一块。
