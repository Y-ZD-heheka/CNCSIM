## 2026-10-28 —— 设计阶段：从方案到 11 个 ADR

一天之内从"调研"走到"架构定型 + 骨架代码"。没有写业务逻辑，但定下的每一条都在后面兑现了。

### 方案与 ADR

| 产出 | 核心判断 |
|---|---|
| `技术方案-五轴CNC仿真.md`（~900 行） | "先算后播"而非实时；五轴特有三角（非线性误差 / 轴速降额 / 奇异点）做成一等公民 |
| **ADR-002** 材料去除内核 | SDF 的结构性优势是真的（单段成本与已加工细节无关），但精度天花板是硬的 → 一度结论"只能做预览" |
| **ADR-003** 自研边界 | L0/L1 不自研，L2 全自研；**不能自研网格布尔**（退化情形是加工常态） |
| **ADR-004** 碰撞 | 不需要通用网格碰撞；必须保守推进；方向 B 是主力 |
| **ADR-005** 切割面着色 | 本质是**溯源**不是渲染 |
| **ADR-006** 稀疏树 | 三级都能存 tile；必须在开工时就用树 |
| **ADR-007** 机床模型 | 三种表示一真相源，都 `add_child` 到同一 `joint_entity` |

**核实到的关键事实**：Bevy 0.20.0（2026-10-08）、`bevy_egui` 0.43.x 对应 0.20、0.20 起自定义着色器必须 WESL、`PanOrbitCamera` feature 默认关闭。
`cutrail` 0.1.1（纯 Rust 网格布尔）实测 2–6 ms/段、内存 92 MB——调研过，最终弃用。

**两次"用户一句话推翻结论"**：

1. **"纯自用"** → 范围 60 → 40 人日。关键法理点：GPLv2 义务在"分发"时触发，私有使用不触发；但**版权与分发是两回事**，GrabCAD 的"非商用"限制的是使用场景。
2. **"sdf 精度 0.1mm"** → 直接戳破 ADR-004 的"0.6 µm 必定检出"。**我错在用均匀分布假设推"保证"**——最坏情况下毛坯表面正好卡在两个体素层正中间，穿透薄片 ε < h/2 时一个体素中心都不在里面。
   修正后：方向 A（毛坯体素 → 刀柄 SDF）严格保证只有 **h/2 = 0.05 mm**；方向 B（**刀柄表面 → 毛坯 SDF**）**0.17 µm**。
   **为什么差三个数量级**：穿透区在毛坯体素格上是**三维薄片**（要 ε > h），在刀柄表面上却是**二维补丁**（周向宽 `2√(2Rε)`，只需 `ε > δ²/(2R)`）。

**顺带修掉一个真漏洞**：`revbody_vs_stock` 用 `let Some(Band) = ... else { continue }`，把 `Full` brick 一起跳过了 → 刀杆斜插实体区时整段漏报。

**碰撞的成本控制**：整根刀柄表面 δ=0.1 时约 94 万点，不可接受。按 brick 裁剪——只在与 Band brick 相交的那部分表面上生成采样点，实际接触面积通常 <200 mm² → 2 万点。

### 机床建模

**核心洞察：摇篮式的运动学只有一个几何参数 L。** 常被当参数的"H（Z 参考面 → A 轴中心）"不影响刀尖相对工件的位姿——把 Z=0 定在 A 轴中心就吸收了。

**查出两个错误**（手算锚点与程序对不上才暴露）：

1. RTCP 写成 `(z−L)`，应为 `(z+L)` → Z 整体偏 360 mm，**画面完全正常**。
2. `n_W` 的 Y 分量写成 `−sinA·cosC`，应为 `+sinA·cosC`。

**教训：手推公式后必须用独立实现（齐次矩阵连乘）跑锚点。**

**golden 基准的诚实性**：543 行里前 3 行是真 oracle（手推 + 独立矩阵双确认），后 540 行只是回归锁。

**加工包络**：A=0 → 340、**A=30 → 420（峰值）**、A=90 → **只剩 120**。A=90 时瓶颈是 **Y 不是 Z**。

**`tip_w` 约定坑**：我最初写 `tip_w = −Rᵀ·t`，A=0 算出 300（应 340）、A=45 算出 0。查 `verify_trunnion.py` 才发现它用 `tip = t[:3,3]`——**因为 RON 里旋转轴 `sign = −1`，链乘积实际是「刀具 → 工件」的变换**，不是文档写的"工件 → 刀具"。

### 架构定型

指出初版分层两处硬伤：`cncsim-core` 是类型垃圾场（高扇入零内聚，还掩盖设计问题）、`cncsim-sim` 是杂货铺（去除调度 + 碰撞 + 精度 + 节拍四个不相干关注点）。

**`check_deps.py` 用违规样例实测过**：3 类违规全拦，退出码 1。**架构守卫要在只有 3 个 crate 时上线。**

### 开始写代码

12 crate 骨架、1747 行、零外部依赖。**33 绿 + 4 红**（红的是 `kin/anchors`，`not implemented`——TDD 的合法红态）。

**三个真 bug（都是我自己写的，被测试抓出来）**：

1. **`DMat3::transpose()` 写成恒等**——列主序下把 col 当 row 读了。
2. **`sd_profile` 把母线闭合边当真实表面**——平底刀 φ6 轴线上返回 −0（应 −3）。
3. **i16 精度算错 2 倍**——满量程是 `2×band`（−band…+band），不是 band。i16 实为 **12.2 nm**（不是 24），比 i8 精细 **258×**（不是 65×）。

**教训：如果只测 `M·M⁻¹ = I` 而不测转置本身，会绕过去。**

### 运动学落地（49 绿）

`forward` 25 行、`inverse` 90 行（Newton 解两旋转 + 3×3 仿射解直线），一次通过锚点。

**又两个真 bug**：

1. **锚点测试传参顺序错**——`q` 是**链顺序** `[C,A,X,Y,Z]`，我按 `[X,Y,Z,A,C]` 传。暴露 API 缺陷 → 加 `MachineTopology::q(&[("X", ..), ..])` 按名构造。
2. **`DMat3::inverse()` 返回的是 `(Mᵀ)⁻¹`**——伴随矩阵按行填进 `from_cols`。直线轴解出 (22.8, −110.5, −13.07) 而非 (100, 50, −20)。
   **原测试用了对称矩阵，正好抓不到转置错**。换非对称 + 同时验 `M·M⁻¹` 与 `M⁻¹·M` 才暴露。

**共同点：测试本身太弱。**

**奇异点用条件数不用 `|sin A|`**：`κ = σmax/σmin`（数值雅可比 3×2 → JᵀJ 的 2×2 特征值）。摇篮解析值 `κ = 1/|sin A|` 用它对拍数值实现，8 个测试一次通过。

**RTCP 的一个设计决定**：最初断言 X=5000 返回 `None`，实现返回 `Some(X=5000)`。想清楚后**这是对的**：`None` 只表示"运动学无解"，超程是**诊断**不是无解——调用方要能区分"机床走不到"和"算不出来"。

## 2026-10-29 —— 内核全链路（58 → 191 测试）

这一天的两份笔记分处两个目录：上午到傍晚在 `.workbuddy-ai`（配置 / G 代码 / 存储层 / 扫掠 / 提取），晚上在 `.workbuddy`（LOD / 并行 / cellmap / collide / sim）。

### 配置 crate（第 13 个，58 绿）

**起因**：`.machine.ron` 是死数据，`ac_trunnion()` 是硬编码的，每加一种机床都要改代码重编译。

**核心测试 `hardcoded_matches_file`**：断言硬编码夹具与真实 `.ron` **逐字段一致**（测试不该依赖文件 I/O，但两份数据会悄悄分家）。**验证了能证伪**：把 A 轴 `sign` 从 −1 改成 +1 → 报 `关节 A 的 sign: left 1.0, right -1.0`，同时 `parsed_topology_is_usable` 也红（说明它真在跑运动学，不是空断言）。

**顺手修的两个文档错误**：

1. README 碰撞检出下限写 0.17 µm（那是采样密度）→ 改 1.6 µm。
2. **ADR-004 的随机对拍阈值是 1 µm，低于 1.6 µm 保证下限**——这个断言按定义就可能合法失败，随机对拍会间歇性红，而失败原因看起来像实现有 bug。改成 `truth > 5e-3`，测试名 `..._above_5um`。
   **教训：测试阈值必须由保证下限反推，不能凭"看起来很小"来定。**

### i8 精度口径修正

用户问"i8 能表示多少的精度"，算的时候发现文档只算了**量化**，漏了**三线性重建**——后者在曲面上比量化还大。

**三个结论**（详见项目记忆 §4）：φ0.5 球刀精加工面是 6.6 µm 不是 1.6 µm；"h 减半精度翻四倍"是错的（量化主导时只按 h 线性）；设计规则 `h ≤ 0.11·√R_c`。

**教训：给"保证"必须列全误差项。只算一项就宣布下限，等于按最乐观的那一项承诺。**

### G 代码解释器第一版（104 绿）

**动手前查 `refs/linuxcnc/overview.adoc`，抓出设计文档三处错误**：

1. 文档说 `G91 G1 X10` 与 `G1 X10 G91` 结果不同——原文 §Item order 明说字序无关，**两者完全等价**。
2. 文档把 G4 停延排在最后（第 12 位）——权威 25 项清单里**排第 13 位**，在平面/单位/补偿/距离模式之前。
3. 文档说"16 个 G 模态组"——权威表只有 **15 个**（编号 0–15，**11 未使用**）。

**教训：设计文档里的"权威清单"必须能在 `refs/` 里逐条对上。凭记忆复述清单，条目顺序和数量都会错。**

**红阶段抓到真 bug**：词法器允许空白穿过数字，于是 `G1 10` 被静默拼成 `G110`。LinuxCNC 的 Best Practices 说"允许数字中间插空白"，但那条一照做，**一个字的错误就变成另一个合法字的错误**，比报错难查得多。改成**空白终止字**。

**证伪（去掉 `ops.sort_by_key`）**：

```
word_order_within_a_block_does_not_matter  FAILED
  第 2 块目标点不同：x: 110.0 vs x: 10.0
feed_mode_g93_is_inverse_time             FAILED
```

注意 `incremental_mode_applies_to_the_same_block` **仍然绿**——因为那行 `G91` 恰好写在前面。**这就是为什么必须有"字序无关"那条测试。**

### 稀疏体素存储层（124 绿）

**动手时发现 ADR-006 草图漏了一处**：`root: HashMap<[i32;3], u32>` 假定 root 每条都是节点。但实心毛坯的一个 level-2 块整块同值，强行建节点要为 32768 个槽分配 tile 数组（32 KB）。
改成 `RootEntry<S> = Node(u32) | Tile(S)`，与 OpenVDB 的 `RootNode` 一致。

**实测**：40 亿体素分层填充 **5.6 ms**，root 1 条、**叶 0 个**、2.0 MB（稠密需 4.0 GB）。

**两个测试自己写错了**：`uniform_interior_stays_constant` 期望内部是 `Constant` 叶，实际连叶都没分配（是 tile，更好的结果）；`blind_metadata_tracks_nearest_surface` 用 `fill_box(0..128)³`，而 128³ 恰好是一个完整 level-1 块 → 被合成 tile。

**两次证伪**：`prune` 改空操作 → 只有 `prune_restores_constant_after_full_cut` 红；`>>` 换 `/` → `negative_coordinates_use_floor_semantics` 报 `left [0,0,0] vs right [-1,0,0]`，**影子模型对拍也一起红**（盒子有负坐标）——两个独立测试同时抓到。

### 扫掠 SDF 与 CSG（142 绿）

**一次自我更正（重要）**：我断言"固定 8 次黄金分割在 10 mm 行程上误差 7.6 µm"，并据此改成自适应。**这个诊断是错的。**
把迭代次数钉回 8，13 个测试**全绿**——说明 8 次本来就够。错在公式：黄金分割的极值被夹在**两个内点之间**，内点间距是 `0.236 × 0.618ⁿ`，不是 `0.618ⁿ`。10 mm / 8 次 → 误差 **0.42 µm**。
**真正的失效点是长行程**：200 mm 固定 8 次实测偏差 **16 µm**。
**教训：误差量级要先验证再据以改代码。** 我当时凭一次失败断言（`golden <= sampled` 不成立）就编出一个 7.6 µm 的解释——而那次失败的真实原因是那条断言本身无效（两个都是"从上方逼近"的近似值，谁更近取决于采样格点）。

**实现要点**：AABB 的径向投影按 `r·√(1−axis_a²)`，不是每轴都减 r（刀轴沿 Z 时 Z 向投影为 0）。

**证伪**：CSG 漏负号 → 「槽内应为正（无材料），实际 −0.4」= 什么都没切掉；固定 8 次 → 「200mm 行程下侧面应在 0 附近，实际 0.016」。

**实测（单线程标量）**：200 mm 直槽 893 ms、0.05 mm 段 11.0 ms → 外推 10 万段 **18.3 分钟**。比早期估算慢 2.2×。

### 表面提取：Surface Nets（158 绿）

**三个坑（都是"看起来对但网格是坏的"）**：tile 紧贴边界丢 298 个四边形；halo 重叠让边被共享 4~6 次；HashMap 迭代顺序破坏可复现性。

**调试过程值得记**：诊断"哪条边缺顶点"时，加 `MC_DEBUG` 打印 p/pb/pbc/pc 的"是否有顶点 / 是否访问过 / 归属叶是否已分配"——**三列一起看**才定位到根因（`in_set=false` 说明归属叶不存在），而不是靠猜。

**一个必须承认的发现**：200 mm 毛坯 **1600 万顶点 / 3200 万面 / 834 MB / 43 秒**。**这不是优化，是能不能渲染的问题。**

### 显示 LOD（178 绿）

`k ≤ band_voxels` 是几何约束（详见项目记忆 §6.1）。实测 R=6 球：k=1 1.8 µm … k=4 9.8、越界 k=5 15.5 / k=6 34.2。
200 mm k=4：**200 万面 / 52 MB / 2.24 s**；候选格 297 万 vs 全空间 1.25 亿。

**顺带修的 bug（重要）**：`cut_segment` 的扫掠 AABB 原来只到刀尖平面 → 窄带只在切面一侧完整，材料侧只有 1 个体素拿到真实距离。表现：LOD k=4 槽底偏 **97 µm**；细格靠那 1 个体素侥幸正确。**碰撞用同一套插值，所以这不是显示问题。**

**判 hot leaf 必须三档**：只看 `|v|` 会漏 `fill_box` 的二值场——60 mm 方坯 k=1 提取出 **0 个顶点**。

### 段内并行 + rayon（191 绿）

手写 `std::thread::scope` 每次 fork-join **491 µs**，而预热后一段 0.05 mm 切削只有 1.89 ms → **26% 是建线程**。换 rayon 常驻池后 ~5 µs，**对外 API 没变**。

**实测**：提取 14.9 s → 3.0 s；200 段连续切削 10.35 → **1.89 ms/段**（外推 10 万段 3.2 分钟）。
**重要更正**：冷启动单段 7.2 ms 含首次叶分配页错误，**拿它外推会高估 4 倍**。

**踩的坑**：分块时 `per = ceil(len/chunks)`，末尾块 `s = i*per` 可能**超过 len** → 越界 panic。所有分块入口都要先 `if s >= e { return 默认值 }`。

### 移除 proptest（186 绿）

`check_versions --transitive` 报 quick-error / r-efi / windows-link 落后，`cargo tree -i` 查出两条链全来自 proptest，且都被上游锁死版本——**改不了版本，只能去掉依赖**。
换成 20 行 xorshift64\* + 固定种子，500 例/条，失败信息带「第 N 例」与全部关节值。`Cargo.lock` **71 → 29 个包**。
**代价**：丢了自动缩例。判断：500 例里挑出的反例已经够小，且**固定种子比随机种子更符合"逐位可复现"的硬门槛**。

### 单元格索引（190 绿）

1600 万条 / 310 MB 的 `FxHashMap` → 每 8³ 单元格一块 + 512 位掩码 + popcount 前缀。
**200 mm 提取 3.09 s → 0.81 s**（对串行基线 18×），索引 **310 MB → 25 MB**。

**踩的坑**：改 `split_quads` 时用 `s[:i] + new` 把文件末尾的 `#[cfg(test)] mod tests` 截掉了，**4 条单元测试静默消失**（总数没变因为同期加了 4 条新的）。
**教训：整段替换前先确认截断点之后没有别的东西。**

### 扫掠求值去三角函数

**发现**：`slerp` 开头就 `acos(dot)`——**刀轴根本没转也照算一次**。实测每次求值 19 ns，其中一半是它。
按"轴是否变"分两条路，把 t 的依赖提成标量多项式：平移路径**零三角函数**；带转路径 1 次 `sin_cos`。
实测 19.0 → **14.7 ns**（平移）、32.5 → **21.0 ns**（带转）。

**教训（重要）**：`sin_cos` 返回 `(sin, cos)`，我写反过一次，**全部测试都是绿的**——因为所有扫掠测试都用 +Z 刀轴，而平移路径已经不碰三角函数了。补的旋转对拍测试故意写反会报「差 1.98 mm」。

### collide 三片（224 绿）

**第一片保守推进**：`SurfaceBody::revolve` 采样刀柄表面；`clearance` 是上界、`clearance_lower` 是下界（上界 − gap − 2 µm）。
**反例 `endpoints_only()` 留在代码里当对照**：2 mm 竖墙 + 16 mm 单步，**端点采样漏、CA 抓到**。

**第二片 GJK**：不用增量单纯形维护，每轮**穷举含最新点的子集**（≤8）各求闭式最近点。定长数组零堆分配——Vec 版 2313 ns → **297 ns**。
**四个坑**：退化圆台（平底刀端面）不能按 d 正负挑端圆；非退化圆台也必须比较两端（半径差会翻盘，让随机用例虚高 **0.06 mm**）；**上面两条只有"支撑点合法性"测试能抓到**（KKT 断言全绿因为两边用同一份错实现）；收窄单纯形时必须**剔除零权重点**，否则下一轮 push 变 5 点越界。

**第三片 EPA**：初始多面体从 GJK 留下的单纯形扩成四面体。实测平均 5.9 迭代 / 1.70 µs。
**两个坑**：`point_a − point_b` 在穿透时不是分离方向 → 字段叫 `axis`；外法向不能用原点判朝向（`n·O = 0` 判不出）→ 改用四面体**重心**。
**验收方式是"照着推开"**：按报出的 depth/axis 移动 A，两体必须恰好接触。120 例随机穿透全过。比"和解析解比"覆盖更广。

### 毛坯碰撞接线 + 端到端主循环（246 绿）

### 性能战役（385 → 396）

| 刀长 | 求值串行 | 求值并行 | 落盘 | prune | 合计 | ns/体素 |
|---|---|---|---|---|---|---|
| 1 mm | 10.5 | 2.3 | 0.87 | 0.35 | 3.5 | 37 |

**优化序列**（每项都实测过）：

1. **平底刀纯平移闭式解**：病根是纯平移路径仍跑 13 次黄金分割（34 ns/体素）。关键洞察——扫掠体是"径向 2D 胶囊 × 轴向区间"的**笛卡尔积**，盒公式直接算。**34 → 5 ns**。
2. **`set_cached` 复用叶查找**：`set` 每次走三级查找 15.8 ns；切削的 `changed` 天然按 z/y/x 顺序，同一叶的写入相邻。**15.8 → 9.3 ns**。
3. **`voxel_compare` 并行**：122 → 17 ms。**确定性**：归约按片序、片内 z 递增 → 累加顺序与串行完全一致。
4. **`set_cached_in_bounds`**：切削的 ijk 必然在 bounds 内，每体素白跑 6 次 min/max。**15.8 → 6.9 ns**。
5. **叶优先遍历 + 整叶短路**：8 个角点的 sd 都 < −band ⇒ 整叶都深（**SDF 是凸函数，凸函数在立方体上的最大值取在顶点**）。深腔 1.8×。
   **限制**：切深 < 叶高 0.8 mm 时 z 方向没有完整深叶 → 短路不触发，面铣/精加工吃不到。
   **两个当场抓到的 bug**：`to_value(-band)` 写成负值（把材料留住）；`fill_leaf` 无条件返回 512（`cut_is_idempotent` 报错）——改成返回**实际改动数**。

**结果**：20 mm 一刀 11.9 → **2.33 ms**（5.1×）；vs OpenVDB **8.7×**；空刀 4.4 → 0.67 ms。

### 多线程利用率 4.8× → 5.6×（395 绿）

**先量后改**：`CNCSIM_THREADS` 扫伸展性，24 线程只有 4.8×。两个根因，都是"看起来并行、实际不并行"：

1. **分片轴选错**：z 方向只有 5 个叶层，片数被 clamp 到 5，**24 线程只有 5 个在跑**。改成选**叶层最多的轴**（铣光 x 方向 36 个叶层）。
2. **每叶一次 `malloc`**：一刀 3920 次分配，24 线程并发打到同一把分配器锁上，**加速比卡在 4.8×**。改成 arena（所有叶的 512 值平铺 + offset 索引），`LeafBlock` 从 528 字节缩到 24 字节。

**结果**：20 mm 一刀 2.57 → **0.97 ms**；铣光 601 → **434 ms**；累计对初版 **12.3×**。
**为什么是 5.6× 不是 24×**：8 线程全 P 核时 5.2×，已贴近 8 物理核上限；E 核频率低一半，16 线程反而略慢。

**bench 也修了**：**不能预热同一刀**——预热会让第二遍变成"重复切"，遍历数掉三成、数字虚高（0.44 vs 实际 0.97）。

### 沿单轴走刀的截面共享（396 绿）

**数学依据**：立铣刀正交直刀 + 刀轴竖直时，`dz` 只依赖 z、`dr` 是到走刀线段的距离——**叶完全落在走刀段内时 `dr` 退化成 |py|，SDF 与走刀方向的那个坐标完全无关**。512 次求值 → **64 次**（8×8 截面）。

条件保守：刀轴竖直且两端一致、位移只沿一个轴、**不是沿 z**（钻孔的扫掠体沿刀轴延伸）、叶整个在段内。

**收益**：铣光 434 → **371 ms**（−15%）。
**为什么不是 8×**：`sd_sweep` 只占串行开销约 26%，共享最多省 26% × 7/8 ≈ 23%，实测 15%。

**correctness 锁**：`axis_sharing_matches_general_path`——同一条扫掠线一次切完 vs 拆成五段，逐位相同（抽查 1.4 万体素）。

**CPU 利用率只有 6.8% 不是写错了**：建场 145 ms 串行（占 28%）；切削每刀 1.87 ms 切 36 片 → 每片 **52 µs**，与 worker 唤醒延迟（10–50 µs）同量级 → `WaitOnAddress` 占 hotspots 28.6%。

**热点分布**：`WaitOnAddress` + `Condvar::wait` 39% / `f64::min`+`max` 19% / `magnitude`+`slice::fold` 6% / `sd_sweep_with` 2% / `write_parts` 4%。
**`min`/`max` 占 19% 说明瓶颈已从"算 SDF"转到"逐体素的数值处理"**——这也解释了沿轴共享 SDF 只有 15% 收益。

**失败的实验**：片数扫描（worker × 1/2/4）都被 `nleaf_axis` clamp 成 36 片，0.98 vs 0.75 是噪声；memory-access 采集不可用（虚拟化环境拿不到 PMU），用流量估算每刀约 1 MB、0.5 GB/s，**不是带宽瓶颈**。

### 建场只扫表面壳（最大一笔）

`fill_box_exact` 原本遍历 `[lo−pad, hi+pad)` 整个立方体：50×50×100 是 **3125 万**次盒 SDF，**99.7% 算完就被 `|d| < band` 丢掉**。

1. 只扫 6 个面片（各 pad 层厚）→ 3125 万 → **330 万**（363×）。
2. 并行求值 + 串行写盘（盒 SDF 是纯函数，按 z 切 48 片）。

**145 → 56 ms**。坑：hits Vec 不预分配会翻倍 realloc 到 53 MB。

### 三个"以为有用、实测没用"

| 改动 | 预期 | 实测 |
|---|---|---|
| 饱和捷径 `−sd ≥ band → S::MAX` | 省 75% 体素量化 | **0%** |
| 内联 `sd_flat_prism` | 省调用+分支 | **0%** |
| AVX2 4 路量化 `update4_i8` | 4× 算术 | **2.5%** |

**结论：切削循环的瓶颈是访存，不是算术。SIMD 打的是算术，靶子选错了。**

**SIMD 的 round 语义（关键）**：`f64::round` 是**四舍五入远离零**；SSE 的 `_MM_FROUND_TO_NEAREST_INT` 是**银行家舍入**（.5 进偶数），差一个量化档。必须用 `sign(x)·floor(|x|+0.5)` 复刻。
（该路径后来随行级分类删除——它服务的"表面行逐点量化"现在每行只算一次 round。）

用户指令："必须支持一刀一刀切割，多刀批量可以尝试。"——单刀语义（`cut_segment`，每段后可查碰撞）必须保留；批量作为新增入口。

```
单线程 418 ms vs 24 线程 349 ms                   ← 并行加速只有 1.2×
```

**之前两轮优化的"求值循环"根本不是主战场。**

### 面板数据层 `cncsim-ui`（TDD，红 → 绿 → 证伪）

### 第二轮落盘优化（用户："继续立铣刀性能优化"，并授权管理员权限跑 VTune）

#### 先修测量方法——这一步推翻了我自己上一轮的结论

上一轮靠"禁用某一部分再看总时间"来拆分，而且每刀 `eprintln!` 打印 PROF。
问题是**打印比被测对象还贵**：一刀总共 0.28 ms，一次 eprintln 几十 µs。
于是我量出"整叶短路 `fill_leaf` 占 18 ms / 32%"，花了两轮去优化它
（tile 直接改值、`count_ne` 分块计数）——**实测它只有 1.9 µs/刀，0.4%**。

改成 `AtomicU64` 累加（~1 ns），跑完一次性读：

```text
20 轮 × 200 刀 = 4000 刀，墙钟 1943 ms
  eval 413 ms（21%）  write 613 ms（32%）  其余 916 ms（建场 47 ms × 20 轮）
  write 内部：whole 7.4  collect 206.6  sort 20.7  blit 219.4  prune 140.6
```

顺手加了 `perf_cut_loop`（20 轮循环）给 VTune 一个足够长的采样窗口——
单跑一次 millout 只有 1 秒，样本全落在 `WaitOnAddress` 上。

#### VTune（user-mode sampling，2.2 s 窗口，CPU 时间 16 s）

| 符号 | CPU | 判读 |
|---|---|---|
| `WaitOnAddress` | 57% | 线程空闲——任务粒度小于唤醒延迟 |
| `SwitchToThread` | 13% | rayon work-stealing |
| `cut_box` | 5.9% | 求值主体 |
| `__rdl_realloc` | 4.5% | 见下（墙钟只有 5%） |
| `fill_box_exact` | 2.7% | 建场（串行写盘） |
| `round` | 0.7% | libm 调用 |

**一个陷阱**：CPU 时间占比不能直接当墙钟占比。16 s CPU / 2.2 s 墙钟 = 7.3 并行度，
`realloc` 的 0.744 s 分散在 48 个并行片上，换算到墙钟只占 5%。

#### 真凶：并行写在小批量上慢 8.4 倍

`CNCSIM_THREADS=1` 一跑，`blit` 从 202 ms 掉到 **24 ms**。

逐刀约 500 块 × 512 字节 = 256 KB，串行写 6 µs（每块 12 ns，源和目标都在 L2）。
24 线程 fork-join 光唤醒就 15–50 µs，再加分派和冷 cache——**并行纯亏**。

修法：按**总字节数**加门槛（不是按块数，`i16` 时一块是 1 KB）：

```rust
const PAR_BLIT_MIN_BYTES: usize = 1 << 20;   // 1 MB 以下走串行
```

#### 五项改动

| 改动 | 收益 |
|---|---|
| **并行写加 1 MB 门槛** | `blit` 202 → **50 ms**（-75%） |
| **`uniform_value` 改 8 字节块比较** | `prune` 141 → **78 ms**（-45%） |
| **`collect` 三个 Vec 预分配 + 去掉 O(n) 的 `l1s.contains`** | 单次 collect 505 → **70 µs**（7×） |
| **`fill_box_exact` 的 `out` 按片内面片体素数预分配** | 建场 realloc 减少（墙钟影响小） |
| **`count_ne`（8 字节一组计数）** | 用于 `count_changed` 与 `fill_leaf` |

**两个诚实的负结果**：

1. **`part.whole` 预留提到满额 → 慢 3 ms**。原来只留 `max_leaves/8`（69 个）而实际用
   580 个，确实在翻倍 realloc；但改成留满 `max_leaves` 反而更慢——**多分配的成本
   超过了 realloc 的节省**。回退了。教训：**"预留了个零头"比"完全不预留"更糟，
   但"预留到满"也不一定更好，得实测。**
2. **tile 路径（整叶填值时直接改 tile 不造叶）对逐刀无效**。它只在**批量**里生效
   （叶数 1028 → 825）：批量"看得见未来"，第一段就整叶短路；逐刀必须先造 Dense 叶、
   后续刀才折叠成 Constant。**优化在 benchmark 里有效 ≠ 在真实调用模式里有效。**

#### TDD 记录

优化前先补安全网（`uniform_value` / `count_ne` 之前**没有直接测试**，只有间接覆盖）：

- `uniform_value_tests` 7 条：全同 / 仅最后一个不同 / 每个 8 字节块首字节不同 /
  块末字节不同 / 正中一个不同 / Constant。
- `count_ne_tests` 7 条：含"与朴素实现对拍"（独立 oracle，不是自证）。
- `fill_leaf_on_tile_keeps_it_a_tile` 等 3 条：**先红**（`改 tile 不该顺手造出一个叶`），
  再实现 tile 快路转绿。

**一个测试要放宽**：`batch_matches_one_cut_at_a_time` 原来断言逐刀与批量
`leaf_count` 严格相等。tile 优化后变成 1028 vs 825——**逐体素比对全部通过**，
只是 tile 与 Constant 的结构差异。改成 `批量 ≤ 逐刀`（批量反而更多才说明短路失效）。

#### 结果

| | 改前 | 改后 |
|---|---|---|
| 铣光 200 刀逐刀 | 56 ms（0.28 ms/刀） | **48 ms（0.24 ms/刀）** |
| 铣光 200 刀整批 | 18 ms | **16 ms** |
| vs OpenVDB 合计 | 7.4× | **8.0×** |
| 4000 刀累计（含建场） | 1943 ms | **1669 ms**（-14%） |

**瓶颈已全部转移到"写叶"本身**：`collect`（新建叶 200 ms）+ `blit`（写叶 50 ms）
占 write 的 72%，都是不可避免的 512 字节搬运。再往下要改数据布局
（叶不再是 `Box<[S;512]>` 而是连续 arena），是另一个量级的改动。

### 第三轮：建场按叶写回（用户："继续性能优化"）

上一轮把切削压到 48 ms 之后，**建场 47 ms 成了最大项**。先给建场加了三阶段计时
（`PROF_BOX`：eval / write / prune）：

```text
20 轮：eval 126 ms   write 615 ms   prune 92 ms     ← 写入占 69%
写入 532 万体素 / 31 ms = 5.8 ns/次
```

每次 `set` 只写 1 字节，却要走三级查找。而边界壳的体素**天然按叶聚集**
（一片 8³ 叶里平均 532 个体素要精确化，接近满叶）。

#### 先补安全网

改之前写 `fill_box_exact_matches_pointwise_reference`：对 3 万多个体素逐个比对
解析盒 SDF 的期望值（带内 / 带内材料 / 带外背景三种情形）。

**写的时候第一版就把期望写错了**：以为盒外是 `0`，实际是 `+MAX`
（`background = S::MAX`，"没有数据"= "没有材料"）。测试当场报
「盒外应为 0，实际 127」——**证明它真在逐体素比对**。

之前只有 `precision.rs`（看过零点位置）和 `ovdb_parity.rs`（看三个过零点），
**没有一条测整场**。"某片叶没写进去"只会表现为精度测试偶然通过。

#### 改成按叶遍历

1. 枚举 6 个面片覆盖的叶 → `sort + dedup`；
2. 每叶按现状取 512 值作初值（`tile` / `Constant` / `Dense` 三种）；
3. 只覆盖落在面片上的体素，`any` 标记有没有改到；
4. 一次 `blit_leaf`。

**两个必须处理的细节**：

- **去重不能省**。并行时同一片叶被两个面各处理一次，第二次读到的是**第一次之前的
  旧值**，后写的会覆盖前面的精确值——结果"大部分是对的"，只有棱角上几十个体素错。
- **末尾 `prune()` 换成增量 `prune_leaves`**。全量版遍历整棵树 + 重算所有 l1 的 blind，
  而建场刚结束时只有 `fill_box` 的 tile（不需折叠）和刚写的边界叶（`any` 保证不可能全同）。

#### 结果

| | 改前 | 改后 |
|---|---|---|
| 建场 | 47 ms | **14 ms**（-70%） |
| └ 求值 | 6.3 ms | 4.0 ms |
| └ 写入 | **30.8 ms** | **3.0 ms** |
| └ prune | 4.7 ms | **0.3 ms** |
| 4000 刀累计（含 20 次建场） | 1674 ms | **998 ms**（-40%） |
| vs OpenVDB 合计 | 8.0× | **12.3×** |

**一个负结果**：顺手把 `blit_leaf` 改成"直接建 `Dense`，不经过 `Constant` 中间态"
（原来 `ensure_leaf` 先 push 一个 `Constant`，再被替换成 `Dense`，等于两次分配 +
一次多余的 512 字节填充）——**实测 collect 209 → 210 ms，零收益**。
成本在三级查找与 520 字节 malloc，不在那个中间态。改动保留（代码更直白），但不算优化。

**428 测试全绿**，端到端自检与改前逐位一致（0.40 mm / 8.64 s），clippy 无新增。

### 第四轮：三次"优化"全部落空，但抓到两条方法论（用户："继续优化"）

这一轮没有提速。四个尝试里有三个是负结果，但每个都值钱。

#### ① 表面行判据整数化 —— **会破坏逐位一致性**

原判据 `(cur as f64) * k_dist < neg_sd`，看起来可以等价换成
`cur < ceil(neg_sd * k_value)`（因为 `k_dist · k_value = 1`）。

**先写测试验证等价性，测试当场红了**：

```text
band=0.8 sd=-0.510236220472 cur=81：浮点 false vs 整数 true（thr=82）
```

根因是两条路径的舍入不同：`81 * (0.8/127)` 是"一次除法 + 一次乘法"两次舍入，
而 `0.510236220472 * (127/0.8)` 是反推回档位。在量化档边界上两者分歧。

**把测试改成反向断言**（"确实存在分歧"）保留下来——哪天它变绿，说明浮点路径
被改了，得重新评估这个优化是否安全。

#### ② `count_ne` 块宽提到 32 —— **更慢**

`uniform_value` 从 8 字节块提到 32，`prune` 46 → 40 ms（真实收益，保留）。
顺手把 `count_ne` 也提到 32 —— 铣光从 48 涨到 56 ms。

原因：这两个函数的"块内不一致"代价**相反**。
`uniform_value` 只判全同，不一致就**早退**，W 越大越快；
`count_ne` 要**数清楚**有多少个不同，不一致时得逐个数，W 越大一次数的越多。

#### ③ 叶心剔除预计算 —— 目标只占 2.5%

`cut_box` 对每个叶调一次 `s.sd(center)` 做剔除，看着像 900 次/刀。
临时禁用一测：eval 404 → 394 ms，**只占 2.5%**。因为 `touches()` 的 AABB 检查
已经先过滤掉大部分叶。不值得改。

#### ④ 分片数扫描 —— 已经最优

新加 `slice_count_sweep` 基准（`#[ignore]`）：

```text
slices= 1  100.3 ms     slices=18  38.5 ms
slices= 4   50.6 ms     slices=24  38.6 ms
slices= 8   49.4 ms     slices=36  35.9 ms   ← 自动模式就是 36
```

自动策略（`min(2×线程数, 叶层数)` = 36）已经取到上限（x 方向只有 36 个叶层）。

#### 最重要的发现：**性能数字有 ±15% 的机器波动**

连续跑了几十轮之后，同一份代码：铣光逐刀 **47 → 56–65 ms**、建场 **14 → 18–21 ms**。
一度以为是自己把代码改慢了，回退也没恢复——**是 CPU 降频**。

这条直接影响前面几轮的结论可信度：**单次测量不可信**。A/B 对比要在同一时间窗口
交替跑，或者看 `perf_cut_loop` 的 20 轮累计值。

**430 测试全绿**（+2 条反向测试 +1 条扫描基准），clippy 无新增。

### 第五轮：水平集 → 网格提速 28%（用户："优化 volumeToMesh 性能与效果"）

先给细格提取加了 `perf_extract_loop`（5 轮，4 秒窗口）——单跑一次 800 ms，

| **`SparseGrid::get`** | **12.0 s（27%）** | 最大实际热点 |
| `vertex_batch` | 6.6 s | |

**根因**：每片叶填一个 `10³` halo 缓冲，**1000 个体素逐个走 `get()`**（root 哈希 →
l2 → l1 → 叶），而其中 512 个就落在当前叶里。

#### 四项改动

| 改动 | 结果 |

| ① 主体 512 从 `leaf_view_with_slot` 一次读 | 798 → **709 ms** |
| ② halo 的 6 个面按邻居叶整面复制（384/488 个） | → **645 ms** |
| ③ `vertex_of` 展开成编译期常量索引 | → **590 ms** |
| ④ `CellMap` 块查找缓存 | → **578 ms** |

**②的实现要点**：`macro_rules! blit_face`，6 段各传"目标索引映射 + 源索引映射"。
剩下 104 个（12 棱 + 8 角）仍逐点查——按棱/角批量要写 20 段映射。

**③的关键是保证逐位一致**：原来 `for a { for ib { for ic { ... } } }` 的累加顺序是
"x 轴 4 条 → y 轴 4 条 → z 轴 4 条"，展开后必须保持同样顺序，否则浮点累加会变。
测试断言顶点数 `16 000 002` 完全一致，坐标一个 ulp 没动。

#### 两个负结果

- **`to_distance` 的除法不能换成预乘倒数**：`band=0.4, v=-122` 时差 0.65 ulp，
  会改变顶点坐标。和上一轮 `cur * k_dist < neg_sd` 是同一类陷阱，已写成反向测试
  （`extract.rs::dist_scale_tests`）。
- **`CellMap` 块缓存只省 2%**：`p−e_b−e_c` 经常跨块，命中率不够。

#### k=2 的异常：找到根因，未修

`LOD k=2` 800 万面要 1707 ms，而 3200 万面的细格只要 578 ms。根因在
`lod_vertex_batch` 的两处叠加：

1. 角点缓存用 `FxHashMap<[i32;3], f64>`，**每格 8 次哈希**（细格用栈上数组，零哈希）；
2. 每个粗格角点的 `sdf()` 要 **8 次细格 `get`** 做三线性插值 →
   400 万格 × 8 角 × 8 次 = **2.56 亿次 `get`**，比细格的 2.5 亿还多。

修法是把角点缓存换成"按细格叶的数组"（和细格的 `10³` 缓冲同思路），改动较大。
**实用档 k=4 只要 257 ms**，所以先记录不动。

#### 与 OpenVDB 对比（新增基准段）

给 `tools/ovdb_bench` 加了 `bench_extract`（对齐 200×200×100 @ h=0.1）：

```text
adapt=0.0  points 16 000 002  tris 32 000 000   510 ms
adapt=0.5  points    276 225  tris    552 446   854 ms
adapt=1.0  points    250 002  tris    500 000   687 ms
```

| | CNCSIM | OpenVDB | 比值 |
|---|---|---|---|
| 细格 | 578 ms | **510 ms** | 慢 1.13× |
| 200 万面档 | **257 ms** | 687 ms（50 万面） | **快 2.7×** |

**顶点数完全一致**——Surface Nets 与 Marching Cubes 两条独立实现给出同样拓扑。
OpenVDB 的 `adapt=0.5` 比 `adapt=0` 还慢，因为它是"先建细网格再折叠"；
我们的 k 是"直接在粗格重采样"，不用先造大网格。

### 第六轮：体素化靠"改窄带宽度"提速 5 倍（用户："继续性能优化"）

先量清 `mesh_to_field` 的两段：**parity 2.4 s、distance 38.7 s（94%）**（h=0.1、
190 万三角形、band=4）。

#### 一个失败的尝试

给 `distance_pass` 加"点到三角形平面"的距离作下界（与 AABB 下界取 max，两者都 ≤
真实距离，合法）。**实测慢 15%**（41.1 → 47.3 s）：三角形只有 0.5 mm 而 AABB 是
1.3 mm，平面距离对"在平面上但离三角形很远"的体素同样是松的，多算一次纯亏。回退。

#### 真正的杠杆：band 宽度

`distance_pass` 的成本 ∝ `(三角形尺寸 + 2·band)³`。而**体素化设计模型根本不需要
band=4**（那是切削用的，因为刀要深入材料）：

| band | 体素化 | 体积误差 | LOD 上限 |
|---|---|---|---|
| 4 | 41.1 s | −0.05% | k=4 |
| **2** | **15.2 s** | **−0.01%** | k=2 |
| 1 | **8.2 s** | **+0.003%** | k=1 |

**反直觉**：带越薄，**量化档 `2·band·h/254` 也越细**，所以体积误差反而更小。
band=1 的误差是 band=4 的 1/4。

#### 顺手排掉一个"假回归"

改完 `--design` 后看到残留从 README 记的 10.92 变成 **5179 mm³**，以为是自己引入的。
查下来：

- `--design` 与无 `--design` 是**两个场景**：后者用解析盒（30×30×11 实心），残留
  10.92 是面铣四角的料；前者用 `design_box.stl`，那个 STL 是**薄壁盒**，内腔被判定
  为"设计气区"，毛坯在内腔的料全算残留。
- **band=4 和 band=2 的残留完全一样**（5179.29），过切深度也一样（707.1）——
  因为过切深度走解析扫掠点测试，不经过体素。
- 无 `--design` 场景跑出来仍是 1638.7 / 10.92，**没有回归**。

`app` 的 `--design` 已改成 band=2，体素化快 2.7 倍、结果不变。

**431 测试全绿**，端到端两个场景都验证过。

### 第七轮：`band` 不是切削的杠杆（用户："窄带半宽优化"）

上一轮发现"体素化 band 减半快 2.7 倍"，自然会问：**切削能不能也用 band=2？**

同窗口 A/B（交替跑，避开 ±15% 降频漂移）：

| band | 铣光 200 刀逐刀 |
|---|---|
| 4 | 53 / 54 / 55 ms |
| 2 | 53 / 55 / 53 ms |

**没有差异。** AABB 只缩了 12%（y/z 各减 2 体素），而切削的成本由"落盘 + 每刀固定
开销"主导——那 12% 落在噪声里。所以 `band` 是**体素化**的杠杆，不是切削的。

#### 顺带查清了一个指标口径

试过把 `--design` 的 band 改成 2，结果 `stl_field_design_agrees_with_box_design` 红了：
残留厚度 0.45 → 0.25。查下来：

`residual_max_thickness = 设计场距离 + h/2`，而那个距离**来自设计模型**：

- `DesignModel::Box`（默认）→ 解析盒 SDF，**精确、无上限**（实测 1.000 mm）
- `DesignModel::Field`（`--design x.stl`）→ 体素场查询，带外钳到 `±band`，
  **上限 = `band + h/2`**（0.450 @ band=4）

所以 band 减半 → 上限减半 → 同一个设计用解析盒和 STL 两种表示给出不同厚度。

**处置**：`--design` 保持 band=4，报告里把上限标出来：

```text
残留 5179.29 mm³，最厚 0.450 mm（**已饱和**：Field 设计的上限 0.450 = band + h/2，真实更厚）
```

判据用"厚度正好等于上限"——Box 是解析距离，几乎不可能恰好落在 `band + h/2` 上
（1.000 vs 0.450），所以不会误标。

**待办**：让 Field 的残留厚度也走解析距离（对残留体素求最近设计三角形），
那样 band 就与这个指标解耦，`--design` 才能安全地用 band=2 换 2.7 倍提速。

**431 测试全绿**，两个 `--export` 场景都验证过。

### 第八轮：把"饱和"变成显式状态，`--design` 换 band=2（用户："继续"）

上一轮留下的待办是"Field 的残留厚度被 band 钳制，导致 `--design` 不能用 band=2"。

这一轮没有去实现"解析精算"（要对几十万残留体素求最近三角形，加 6 秒），而是
**把"饱和"从一个隐含事实变成报告里的显式字段**：

```rust
impl DesignModel {
    pub fn distance_cap(&self) -> Option<f64>   // Box → None，Field → Some(band)
}
// SimReport 新增：
pub residual_thickness_capped: bool,
pub residual_thickness_cap: Option<f64>,
```

`voxel_compare` 在记录最大厚度时顺手判 `dd >= cap`，所以饱和状态是**算出来的**，
不是打印时猜的（上一轮用"厚度是否恰好等于上限"猜，是个脆弱启发式）。

#### 踩到的坑：上限要用设计场的 band

第一版 app 打印时用 `run.grid.config.band_mm()`——那是**毛坯场**的 band（4）。
而 `--design` 的设计场是 band=2。于是输出成：

```text
最厚 0.250 mm（已饱和：上限 0.450）   ← 0.250 却配 0.450，自相矛盾
```

改成把 `design.distance_cap()` 一路传到 `SimReport` 才对。

#### 测试从"放宽"改成"可检查的状态"

`stl_field_design_agrees_with_box_design` 原来断言"残留厚度 == 0.5 ± 0.06"。
band=2 时 Field 报 0.25，直接红。

改成两支：

```rust
if capped { assert!(thickness >= 0.2); }          // 饱和：只要是合理下限
else { assert!((thickness - 0.5).abs() < 0.06); } // 未饱和：必须精确
```

**这不是放宽**——`capped=false` 却对不上 0.5、或者 `capped=true` 却报个离谱值，
都会红。

#### 结果

| | 改前 | 改后 |
|---|---|---|
| `--design` 体素化（190 万三角形，h=0.1） | 41 s（band=4） | **15 s（band=2）** |
| `--design` 残留厚度 | 0.450（未标注） | 0.250（**标"已饱和"**）|
| 默认场景（Box） | 1.000 mm | 1.000 mm（不标，精确）|

**新发现一个待办**：`--design` 的域硬编码 `[300, 300, 120]`（30×30×12 mm），
78×79×87 mm 的大模型装不下。域应该按设计模型包围盒算。

**431 测试全绿**，两个 `--export` 场景都验证过。

### 第九轮：设计场的域改成「模型 ∪ 毛坯」（用户："继续"）

上一轮记的待办：`--design` 的域硬编码 `[300, 300, 120]`，78×79×87 mm 的大模型装不下。

**这个问题的实质不是"装不下"而是"静默裁掉"**：`voxel_compare` 只在**毛坯域**内查

"设计气区" → 残留体积虚高，而报告上看不出任何异常。

|---|---|---|
| `design_box.stl` | 20.0×20.0×9.5 | 300×300×120 → **308×308×128** |
| 大飞鱼 | 77.9×79.4×86.8 | 300×300×120（裁掉大半）→ **788×803×876** |

"被裁掉"变成"完整覆盖"，能正常跑完（过切 1397.6、残留 5502.73）。

顺手在启动时把域尺寸打出来：

```text
模型包围盒 77.9×79.4×86.8 mm → 设计场 788×803×876 体素（78.7×80.2×87.6 mm）
```

**这条对用户是必要的**：设计模型必须与毛坯在同一世界坐标系里，两者不重叠时比对
没有意义（会报满残留）。程序不拦，但至少让人一眼看出域对不对。

**新待办**：毛坯尺寸仍硬编码 `[300, 300, 120]`。换大模型做设计时毛坯也该跟着大，

```glsl
if (uFlat == 1) { o = ...; return; }   // ① 地面先返回
```

### 第十三轮：颜色修正 + 把刀画出来（用户："颜色渲染不对，把刀具展示出来"）

两件事，第二件比第一件值钱。

#### 颜色：sRGB 常量被当成线性值用

着色器里写的是 `vec3(0.70, 0.73, 0.78)`，这是**sRGB** 空间里"中灰"的数值。
片元着色器输出的是**线性**颜色，管线最后再做一次线性→sRGB 编码。
直接输出等于编码了两次 → 整体发白，浅灰变近白。

修法：`let base_lin = pow(base, vec3<f32>(2.2));`，环境项从 `0.35 + d` 收到
`0.25 + d * 0.75`（原来的环境项把暗面也抬起来了）。改完截图对比：
从"一片近白"变成有明暗层次的灰。

#### 刀具：母线 → 旋转体

`cncsim_tool::Profile` 是 `(ρ, z)` 折线，`flat_end_mill(6, 20)` 就是
`[(0,0), (3,0), (3,20), (0,20)]`。绕局部 +Z 旋成网格，**母线与仿真、碰撞用的是同一份**
（`ToolDef::cutter`）——渲染自己造一把"看起来像"的刀，就会出现
"画面上没撞、报告说撞了"。

定位：网格原点是**刀尖**（母线首点 `(0,0)`），所以
`translation = to_world_model(pose.tip)`、
`rotation = Quat::from_rotation_arc(Vec3::Z, to_world_dir(pose.axis))`。
旋转体绕自身轴任意转都不变，所以 `from_rotation_arc` 的最小旋转就够了。

#### 三个只在截图里才看得见的坑

| 坑 | 现象 | 根因 |
|---|---|---|
| 退化三角形 | 端面上一块**黑斑** | 母线端点在轴上 → 四边形塌成三角形，`compute_normals` 给面积 0 的三角形算出**零法向** |
| `metallic: 0.9` | 刀具渲染成一根**发白的亮柱子** | 没有环境贴图时全金属材质只剩两盏方向光的镜面高光 |
| 标记球按 `diag` 缩放 | 球半径 5.6 mm，比 φ6 的刀还大，**正好盖住要看的刀尖** | `diag * 0.012 + 0.3`，`diag` 是整机对角 |

第一个坑的修法是按"母线端点是否在轴上"分三种情况发三角形（3 顶点 / 4 顶点 / 3 顶点），
不再发退化三角形。顺带把顶点数从 `segs·(n−1)·4` 降到 120（12 段 × (3+4+3)）。

#### 新增两个截图用环境变量

- `CNCSIM_CAM_SCALE`：相机距离倍率。φ6 的刀在 30 mm 毛坯里占屏幕高度不到 2%，
  整机视角里认不出朝向对不对，**必须能拉近**。
- `CNCSIM_T`：起始回放时刻。截图永远停在 `t=0` 的话，只能看到"程序开头刀悬在原点上方"，
  看不到进刀。**不自动播放**是刻意的——播放时截到哪一帧取决于帧率，两次截图没法对比。

### 第十四轮：刀具要像刀，颜色要能对上（用户："立铣刀应该是光滑的圆柱体，刀刃和刀柄需要区分，刀刃区域每次切割要变颜色，毛坯被切割的切割面颜色需要与刀刃颜色保持一致"）

四件事，其实是**一条链**：刀刃的颜色和切面的颜色必须是同一个数。

#### ① 光滑圆柱：法向不能靠 `compute_normals`

第一版每个四边形自带 4 个顶点，`compute_normals` 给的是**逐面法向**——48 段看起来
就是 48 条棱的多面体。改成解析法向：母线切向 `(dr, dz)` 顺时针转 90° 得
`(dz, -dr)`，再绕轴旋到各角度。圆柱段完全光滑。

拐点按**折痕角 30°** 决定要不要平均相邻两段的法向：平底刀的底面与圆柱之间是 90°，
硬边保留；球头刀的圆弧段是 11°，自动平滑。

#### ② 刀刃 / 刀柄分开

`ToolDef` 本来就有两份母线（`cutter` / `shank`），只是渲染只用了一份。
现在两段网格挂在同一个 `ToolRig` 下（骨架只带变换，子实体各自在局部原点建模），
刀柄用调色板的固定暗钢色。每帧只改一个 `Transform`。

#### ③ 切面溯源：叶级，不是体素级也不是 brick 级

ADR-005 的设计是"每 brick 记候选表 + 全局扫掠注册表，提取时反查最近的扫掠面"。
落地时选了更省的一档：**每片叶 1 字节**。

| 方案 | 额外内存 | 分辨率 | 提取时 |
|---|---|---|---|
| ADR 的 brick 候选表 | +2 MB 表 + 12 MB 注册表 | 1.6 mm | 每个三角形求一次最近扫掠面 |
| 实际：每叶 1 字节 | **+250 KB** | 0.8 mm | 直接读 |

叶比 brick 还细，而且**不需要扫掠注册表**——`cut` 落盘时顺手盖章。

链路：`run` 每块 `set_creator(creator_of_block(bi))` → `write_parts` 给 `touched`
的叶盖章 → `vertex_batch` 读叶的标记 → `CellMap::build` 合并 → 顶点色 R 通道。

合并必须用 **`fetch_min`** 而不是 `store`：同一格会被相邻两片叶各发一次，并行写的
顺序不定，直接 store 会让结果随线程调度变化，破坏"逐位可复现"。
`creators_dont_depend_on_chunking` 锁这条。

#### ④ 刀刃颜色 = 切面颜色，靠构造不靠约定

两边都调 `cncsim_voxel::creator_of_block`；颜色表只有一份（`render::PALETTE`），
作为**同一个 uniform** 同时给毛坯材质和刀具材质。

#### 材质 uniform 的四个坑

| 现象 | 根因 |
|---|---|
| `array stride must be a multiple of 16` | `[[f32;4];16]` 是 `array<f32,4>`，要用 `Vec4` |
| `Storage class Storage{LOAD} doesn't match the shader Uniform` | **材质 bind group 是 group 3**，不是 2 |
| 网格静默不渲染 | 着色器声明了 `location(5)`，刀具网格没有 COLOR 属性 |
| `Unexpected identifier 'render'` | GLSL 注释里的**反引号**截断了 JS 模板串 |

第二条最坑：写 `@group(2)` 不报"没有这个绑定"，报的是一句看不懂的类型不匹配。
上一版一直潜伏着——那时的 shader 根本没引用材质，多出来的布局条目是合法的。

#### ⑤ 颜色太乱 → 有序渐变

第一版调色板是 12 个定性色（色相铺满一圈）。用户第一句反馈："切割颜色过于混乱"。

诊断：定性色板的前提是"一屏 3–5 个类别"。刀路把顶面铺满时，相邻两刀是任意色相
跳变，就是打翻的调色盘。**区分度不该靠撞色相。**

改成有序渐变：色相 212°→45°，明度 0.50→0.72，相邻两刀只差一点点。索引同时改成
**往返**（周期 22）——取模的话渐变最亮端直接跳回最暗端，会出现一条突变分界线。

**443 测试全绿**，clippy 无新增；预览页在无头 Chromium 里实拍确认（`--export` 的
GLSL 调色板数组真的能编译）。

### 第十六轮：颜色溢出——把四档粒度都试了一遍（用户："可选方案都尝试一遍，找出最优的"）

上一轮把溢出定位到"叶级粒度 + 窄带填充"，这一轮把两个轴都拆开做实验。

#### 轴一：标记粒度参数化

`SparseGrid` 的 creator 从"每叶 1 字节"改成"每叶 `sub³` 字节"，`sub ∈ {1,2,4,8}`：

- `sub = 1`：每叶一个（原状）
- `sub = 2/4`：叶内 2³/4³ 个子块各一个
- `sub = 8`：每体素一个（ADR-005 §2.1 当初否决的那档）

配套：`LeafBlock` 带一个 512 位的"改动子块"位图，`write_parts` 按位盖章；
提取时顶点取**自己那一格最小角**所在子块的颜色。位图按子块整块比较
（`sub=2` 是 8 次 64 字节比，`sub=8` 退化成 512 次单字节比）。

#### 轴二：盖章判据

只判"体素变了"会把**窄带填充**也算进去——`cut` 会把新切面周围 ±band 的距离场
从饱和值精确化，那些体素确实变了，但那一刀并没有在那里造出面。

新判据：**变了 且 新值满足 `|v| < h`**。理由是几何必然：面若在 A、B 两体素之间，
则 `|v_A| + |v_B| = h`，必有一侧 < h。所以真造出的面一定被盖到，而窄带填充被排除。

**踩到的坑**：一开始把 `n` 也改成只数"贴面改动"，结果 `n == 0` 的块被整块跳过——
**几何都变了**（顶点数 334082 → 358996）。`n` 必须数全部改动，它决定要不要写回；
只有位图用新判据。测试里"四档几何逐点相同"这条当场抓到了它。

#### 四档实测（`crates/sim/tests/creator_granularity.rs`）

30×30×12 毛坯、六个不同切深各切一条槽，取**最坏**溢出：

| `creator_sub` | 最坏溢出 | creator 内存 | B/叶 | 切削耗时 |
|---|---|---|---|---|
| 1 | 0.500 mm | 5.6 KB | 1 | 2.1 ms |
| 2 | 0.200 mm | 45 KB | 8 | 2.1 ms |
| **4** | **0.100 mm** | 359 KB | 64 | 2.0 ms |
| 8 | 0.025 mm | 2.87 MB | 512 | 2.7 ms |

- 判据一加，最粗档从 1.0 掉到 0.5，最细档从 0.3 掉到 0.025——**两个轴都要**。
- 内存按叶线性涨，溢出按子块边长线性掉：`sub=8` 花 8 倍内存只换 0.075 mm，
  还把切削拖慢 30%。**拐点在 4**。
- 四档的**几何逐点相同**（都是 334082 顶点），只有颜色不同。

**默认取 4**：溢出压到 0.1 mm（一个体素，看不见），200 mm 毛坯 25 万叶 = 16 MB。

#### 顺手修的：不盖色的场景不该算位图

铣光 200 刀基准里没有 `set_creator`，但位图照样算——48 → 60 ms（慢 25%）。
加 `if pending_creator == 0 { 直接返回 count_changed }` 之后回到 58 ms
（仍在文档记的 47–65 ms 热漂移区间内）。

#### 效果

面铣一层的颜色分布表：

```
    ...
  ── 切割色 10 种，合计 889.0 mm²（其中朝上 882.2 mm²）
  ── 单条 Z 跨度 ≤ 0.10 mm          ← 之前是 0.30
```

切色区域的 Z 下界从 10.70 抬到 10.93，侧壁上那条彩边基本消失
（非朝上面积 22.7 → 6.8 mm²）。

### 第十七轮：溯源开销压回 +5~10%（用户："性能下降了吗"）

**降了。** 但不能拿上次记录的 48 ms 比——那是冷机数字，这台机器连续跑几十轮会降频
（47 → 56–65 ms）。只有在**同一时间窗里交替跑**的相对值可信。

于是新写了一个 A/B 基准 `crates/voxel/tests/creator_perf.rs`：四组配置
（不着色 / sub=1 / sub=4 / sub=8）在同一个进程里交替跑 5 轮，每组只留最好成绩
（噪声只会让它变慢，取最好就是取"最不受干扰"的那次）。

#### 第一次量出来：+23%

| 组 | 切削 ms | 相对 |
|---|---|---|
| 不着色 | 36.8 | 1.00× |
| sub=1 | 38.5 | 1.05× |
| **sub=4** | **45.4** | **1.23×** |
| sub=8 | 63.5 | 1.72× |

原因很清楚：`changed_mask` 写成了四层嵌套

```rust
for sz in 0..sub { for sy in 0..sub { for sx in 0..sub {
    for dz in 0..k { for dy in 0..k { for dx in 0..k {
        let i = x | (y << 3) | (z << 6);     // 每体素现算下标
```

——把原来 SIMD 的 `count_changed`（8 次 64 字节比）换成了 512 次带下标计算的标量比较。

#### 改法：一次连续扫描

```rust
for (i, (&nv, &ov)) in vals.iter().zip(old).enumerate() {
    if nv != ov {                       // 绝大多数体素没变，一次整数比较就跳过
        n += 1;
        if self.to_distance(nv).abs() < h { /* 折算子块下标 */ }
    }
}
```

下标只在**真变了且贴面**的体素上算（一片叶通常几十个），循环本身是顺序的。

#### 第二次量出来：+5~10%

| 组 | 切削 ms | 相对 |
|---|---|---|
| 不着色 | 37.5–39.2 | 1.00× |
| sub=1 | 37.6–39.8 | 0.99–1.05× |
| **sub=4（默认）** | 40.3–41.6 | **1.04–1.11×** |
| sub=8 | 46.1–47.9 | 1.21–1.27× |

`sub=1` 有一轮跑出 0.99×，说明噪声本身就有 ±5%——默认档的代价已经接近测不准了。

#### 提取侧

提取从"每叶取一次颜色"改成"每顶点取一次子块"。1600 万顶点的基准要为此付一次数组寻址。
改法：`sub == 1` 时整叶颜色**提到循环外**（与加粒度之前逐字相同），
只有 `sub > 1` 才走逐顶点分支。基准 682 → 669 ms（同窗口，噪声内）。

**451 测试全绿**，clippy 无新增。

### 第十八轮：缓存与多线程分析（用户："分析带颜色的切割的缓存命中、多线程效率"）

#### 工具先撞墙，后来通了

一开始 `-collect memory-access` 报 `sampling driver is not installed and enabled`。
一路排查：

1. `sepdrv5.sys` / `sepdal.sys` 文件在 `System32\drivers` 里，但**服务没注册**。
2. `sc query` 被安全策略按程序黑名单拦（不绕）；改用 `Get-Service` / `Win32_SystemDriver` 查。
3. 用 VTune 自带的 `amplxe-sepreg.exe -i` 提权注册 → `sepdal` / `sepdrv5` 变 Running。
4. **还是不行**：`hotspots` 报 `Level 2/3 capability: not detected`，并提示
   "run the product as administrator"——**采集器本身也要提权**。
5. 提权拉起 `vtune.exe` 时又静默 `exit=1`：`Start-Process -Verb RunAs` 走 ShellExecute，
   `-ArgumentList` 数组拼的命令行**不给含空格的路径加引号**，而项目路径带
   `WorkBuddy AI`。拼成带引号的字符串后一次通过。
6. 再加一条：提权进程不继承环境，且**提权拉起解释器被安全策略拦**，
   所以配置改用**测试名**（`profile_off`/`profile_s1`/`profile_s4`）。

**第一次采出来的是废数据**：0.35 s 的运行、5 ms 采样间隔只有几十个样本，
VTune 自己警告 `metrics data may be unreliable`——`off` 和 `s4` 的 LLC miss
竟然完全相同（1,950,819），这就是样本不足的铁证。加长到 100 轮（2.6 s）后三组才分开。

#### 多线程效率（可量化，有结论）

`creator_analysis::thread_scaling`，50×50×100 铣光 200 刀，一次进程一个线程数
（线程池是进程级单例，`CNCSIM_THREADS` 只在建池时读一次）：

| 线程 | off | s1 | s4（默认） |
|---|---|---|---|
| 1 | 75.3 | 76.7 | 85.3 |
| 8 | 17.5 | 17.5 | 19.1 |
| 24 | 14.8 | 14.6 | 15.4 |
| 加速比 | 5.07× | 5.24× | **5.53×** |

**溯源没拖慢扩展性**，`s4` 的加速比还最高——因为它的并行占比更大。

| 线程 | 组 | 求值（并行） | 落盘（串行） |

  正好一条 cache line，`touched` 升序，是流式写。

### 第二十一轮：再省 22.7 → 17.2 ms（用户："继续"）

#### 第二处：`leaf_flags` 的逐值分支

`lod_candidates_in` 要先给每片叶算标志（有负 / 有正 / 贴面）。原来是

```
贴面 ⟺ min < MAX_MAG 且 max > −MAX_MAG   （= 不是整叶都饱和在某一端）
```

走树 4.8 → **0.8 ms**（8×）。

### 第二十四轮：0.3 mm 溢出的真因——我上一轮的诊断是错的（用户："有轻微的切割颜色溢出，查" → "已经是最佳修复方案了吗"）

#### 先纠正

上一轮我给的诊断是"判据分不清造新面和把旧面算准"，还提了 `|sd_sweep| < h` 的改法。
用户问"已经是最佳修复方案了吗"，我去验证了一下——**诊断本身就不对**。

#### 一行对比定死根因

在 app 里加了个对照（仿真网格 vs LiveCut 重放网格）：

```
[cmp-grid] 仿真网格 34802 顶点，切色最低 10.900；LiveCut 网格 34802 顶点，切色最低 10.700
  creator 不同 @(0,0,104)：仿真 0 / LiveCut 1
  ...
  creator 不同的采样点：65400
```

**几何逐点相同，creator 大面积不同**。所以既不是提取的差别，也不是判据的差别——
是**网格状态**不同。

`cfg.creator_sub`（默认 4，0.2 mm）。窗口和导出**各用一套粒度**。

#### 修法：消灭第二个来源，而不是补参数

```rust
pub fn new(cfg: &RunConfig, cutter: Profile, cuts: …, tile_mm: f64, k: u32) -> Self
```

毛坯尺寸、原点、网格配置、溯源粒度全从 `RunConfig` 取。8 个位置参数换成 1 个结构体
——补一个 `creator_sub: u8` 参数只能救这一次。

`creator_sub` 正是最后加进 `RunConfig` 的那个字段，加的时候没有检查所有构造点。
**"加一个配置项"必须同时问"还有谁在别处自己造这个状态"**。

### 第二十五轮：台阶竖直面是灰的（用户截图："切割过程中垂直的切割面为什么中间有毛坯的原色"）

#### 根因：LOD 取色按"格角"而不是"顶点"

LOD 顶点取切割色时查的是**格的最小角** `[p*k]`。但：

- 格边长 `k·h`（k=3 → 0.3 mm），面可能落在格的**远端**，最小角离它最远 0.3 mm；
- 溯源子块只有 `sub·h`（sub=4 → 0.2 mm），盖不到 → 查到 0（毛坯灰）。

**地平面恰好凑巧**（面落在最小角所在的子块里），所以只有**竖直面**暴露问题——
这也是为什么之前一直在看顶面、一直没发现。

#### 修法：按顶点位置取色

顶点本身就在面上，离它最近的体素必然 `|v| ≤ h/2 < h`，一定被这一刀盖过章。
所以按位置查是**精确**的，不是近似。

```rust
let v = self.to_voxel_space(pos);
self.creator_of_voxel_cached([v.x.floor(), v.y.floor(), v.z.floor()], &mut cur)
```

修完：台阶竖直面与最后一刀同色。数据没退化——切面颜色分布仍是
889.0 mm²（朝上 882.2）、Z 10.90–11.00，**452 测试全绿**。

#### 残留（不是 bug）

竖直面与顶面的**共用边**上有一条极细的浅色缝：一条边的两个端点一个是灰（顶面）、
一个是彩（立面），逐顶点插值就必然在边上混出中间色。要消掉得改成逐片元/纹理查表，
那是另一个量级的改动。

### 第二十六轮：那条线是两个问题，不是一个（用户："包围线依然存在"）

#### 别靠眼睛，取像素

上一轮改完颜色后用户说还在。我把用户截图**解 PNG 取像素剖面**
（没装 PIL，手写 zlib+反滤波）：

```
x=300: 顶面(78,171,173)青 → (59,104,152)深蓝 → 侧壁(139,145,155)灰
x=520: 顶面(152,186,117)黄绿 → (91,176,137)青绿 → 侧壁灰
```

那条 1px 线是**别的带的颜色**，不是纯阴影。但网格数据查下来每个索引只在自己那条
带子的 Y 范围内（idx 1: 0.02–4.40，idx 10: 28.70–29.86），没有越界顶点。

#### ① 颜色：外棱上 `floor()` 掉到了外侧

顶点正好在 `v = 0` 的边界上，`floor(−1e−9)` 给出 `−1` → 外侧体素（空气）→ creator 0。
所以四条外棱有的顶点取内侧（有色）、有的取外侧（灰）。

修法：沿**法线反方向挪半个体素**再查。法线朝外，`pos − normal·h/2` 一定在材料侧，
且那个体素 `|v| ≤ h/2`、必然被这一刀盖过章。

#### ② 法向：棱上被平均成 45°

改完颜色还有线——量法向：顶棱 108 个顶点里 **107 个法向被平均**（0.25<|nz|<0.95）。
Surface Nets 一格一个顶点，地板和立面共用一个顶点，法向只能折中；两个方向光在 45°
上都变暗 → 棱上塌一条暗线。未切削时两侧同色看不出，一侧变彩色后就显眼。

修法：`MeshData::split_crease_normals(cos 45°)`——夹角超阈值的角为该三角形复制顶点、
用面法向。平面不多顶点，曲面不受影响。

#### 一个必须先想清楚的位置问题

第一版把拆分放进了 `voxel` 的提取里，`cut_slot_surface_is_watertight`

### 三个坑（都写进 `项目记忆.md` §21）

1. **切点取 `(r, r)` 是错的**。规格表里的 4.69° 是"刀尖到刃顶"的弦角，不是切点处的
   锥面角；按 `(r, r)` 接锥面会在刃口留一圈 4.69° 的折角——几何上是棱，仿真里是
   **假过切**。测试用"最后一段弧的方向 vs 锥面段的方向"夹角 < 1.5° 锁住。
2. **设计面采样的容差必须是 0**。`Cavity` 的坑口用"半个采样步"当容差，把坑口内侧
   0.2 mm 的空气点当成设计面，精加工球扫过去 → 报 1.2 mm³ / 0.25 mm 假过切。
3. **锥颈在坑口压顶面 0.05 mm 是固有限制**，不是 bug：坑壁在坑口竖直、锥颈张开
   4.69°，刀尖一落到顶面以下必然压过去。换 8° 锥角干涉涨到 0.15（已实测证伪）。

### 再追加：色号改成「每工序内 10 档」

用户的观感是"渲染颜色一直在变"。查下来是原设计：色号 = 第几刀，12 色往返
（周期 22 刀）。粗加工 4990 刀 + 精加工 3008 刀，精加工每条 `G1` 只有 1.2 mm
→ **每 1.2 mm 换一次色**，加上刀刃跟着每刀换 → 看起来一直在闪。

改成 `creator_of_progress(done, total)`：**每个工序内** 0→100%，每 10% 一档，
索引 1..=10。粗加工、精加工各自从第 1 档走到第 10 档——用全局进度的话粗加工
62% 的刀数会吃掉前 6 档，球面只剩 4 档，而球面恰恰是最想看渐变的地方。

- 切面与刀刃仍用同一个函数，构造保证一致（这条没变）。
- `LiveCut` 在 `new` 里一次算好每刀的 `(工序内序号, 总数)`，回放每帧只查表——
  现算容易和仿真侧算出不同的档。
- 测试从"相邻两刀不同色"改成"单调不减 + 整段只换 9 次"；
  run 侧的 `cut_surface_colors_follow_the_progress` 改判"进度色不倒退"。

**实测**：切割色 **10 种**（原来 12 种跑满），球面 10 条宽色带，
去料/过切/残留数字一字未变（着色不影响几何）。

**红绿过程**：`tapered_ball_end_mill` 先 `unimplemented!()`，5 个测试全红（正确原因），
实现后 2 个仍红——① 我自己把 `sd_profile` 的入参写成了 `(0.3, 0.2, 0)`（它要的是
`(x, y, z)`，ρ=hypot(x,y)），② 刃顶 Ø5.926 与柄径 6 的差 0.074 超过我拍的 0.05 容差。

### 再追加：切割染色改体素级，只认材料去除（11-04）

用户报「染色做不到只染切割的地方，相邻切割互相侵染」。三个叠加根因：

2. `changed_mask` 只要旧值贴面就盖章，不管当前刀是否经过——同子块任意变化

3. WGSL/WebGL 插值调色板编号，跨色三角形内部生成第三种颜色。

修法：默认 `creator_sub = 8`；盖章只认 **材料→空气且新面在窄带内** 的体素，

## 赤道色斑：判据从「跨零」改成「值真的变了」（11-04 晚）

用户把赤道放大发来：「颜色互相侵染」。截图上的棕/紫/绿不是渐变，是 **T1 的 9 号

## 简化 CAM：STL → 高度场 → G 代码（11-04 晚）

用户要「输入毛坯，输出 G 代码，用现有解释器和仿真验证」。新增第 14 个 crate
`cncsim-cam`，依赖只有 `math` + `tool`——**它只生成文本，完全不认识解释器/
仿真器**；验收在 `crates/cam/tests/e2e.rs`，避免"自己验自己"。

**输入**：三角网格 + 轴对齐毛坯。STL 由 app 读；STEP 是 B-rep，明确拒绝
（本机没有 OpenCascade/FreeCAD，先三角化）。

**算法**：
1. XY 高度场：三角形按包围盒分桶，逐列向下射线，取最高 z；法向用 z 的
   中心差分（命中面法向会在折面交界处啃 0.03 mm）。
2. 粗加工：平底刀 Z 层行切；可下刀区 = 刀盘腐蚀（`max(z within r) <= z层 - 余量`）；
   下刀 G1（G0 在仿真里不算切削）。
3. 精加工：球头平行行切，`tip = p + R·n - (0,0,R)`；行距与沿程采样分开，
   沿程用 `sample_mm` 避免弦切过切。
4. 倒扣检测：每列独立表面层数（>10 µm 才算一层）；>2 层超过 2% 直接拒绝。

**红绿过程**：
- 精加工沿程用行距（0.8）→ 过切 0.032；改 0.25 后 0.022。
- 粗加工最低层 0 段：`max_within` 卡 1e-9，零件最低面高 0.02（高斯尾）→
  判断余量 0.05（只放宽腐蚀，不降切削面），2 层 14 段恢复。
- 倒扣检测按"命中次数"→ relief 被共边三角形误报 49%；改成按 z 合并成层后
  relief 2 层通过。
- 端到端：relief 16×16×3.5，G 代码 1509 行，仿真 1496 块，**过切 0 mm³ /
  0.022 mm，残留 3.97 mm³ / 0.18 mm**；全量 **483 绿 / 29 ignored**。

**对比**：`--cam` 除 gouge/residual 外还逐列比 `加工顶面 − 设计顶面`：
relief 平均 |Δz| 0.002 mm、P95 0、最大残料 0.25、过切 0、**99% 在 ±0.1 mm**；
输出 `*.diff.html` 热力图。

**流云花瓶实测**：1 199 996 三角形 / 108×108×250；高度场 **21564/29045 列
（74%）有 2 层以上表面**——薄壁/中空，3 轴高度场加工不了，CAM 在生成前拒绝。
这不是失败，是工艺假设被模型违反；要加工需要 4/5 轴（回转体可先做 A 轴）
或先把模型简化成实心单值面。

**CLI**：
```
cargo run --release -- --cam assets/models/relief.stl --stock 16,16,3.5   --gcode out/relief.nc --diff out/relief.diff.html --export out/cam.html
```

## 回转五轴 RTCP + 悬浮碎屑（11-04 深夜）

用户接着要「五轴带 RTCP」加工同一个花瓶，然后又报了「切割过程中有没切掉的悬浮碎屑」。

### 回转 RTCP

新增 `crates/cam/src/rotary.rs`：绕 Z 的轮廓 + A/C 摆头 + `G43.4 H1`。工艺是
粗 Ø16 球头 + 精 Ø4 球头，A 限位 110°。踩了四个坑，每个都靠**量化**定位：

| 现象 | 定位手段 | 结论 |
|---|---|---|
| 90%+ 采样点整窗读 −3.5 | 打整条径向 SDF 剖面，发现全 +4.0（纯空气） | 5°×1.5 mm 分箱取**最大半径**是包络，平均胖 1.13 mm、最大 7.36 mm |
| 换成真值轮廓后仍 −3 mm | 分开跑「只精加工」：0.976；加粗加工：3.0 | 粗加工竖直刀轴在倒扣面把球心放到曲面下方 |
| 粗加工改法向偏置后仍 −2.4 | 统计 G 代码相邻刀点：|ΔA| P90 25°、|ΔC| 中位 17.7° | **偏置面自交**：偏置 64 mm × 每步 10° → 刀尖横跳 11 mm |
| 最终方案 | —— | 粗加工改**径向让刀**（球心放 z 高度、半径 `max(R_k, r+余量+R)`），可证径向不啃伤，顺带车掉方料四角 |

途中还确认了两件事：`ToolSpec::flute_mm` 是**参与切削的圆柱段**（30 mm 刃长的
Ø4 球头一摆头就把相邻凹面扫平，改 1.25×D）；A 超限时**整点跳过**会让相邻两刀
连出穿过工件的 G1 弦，改成限位 + 沿法向抬刀 `R(1−cosδ)`。

护栏：`rotary_rtcp.rs`（圆锥位姿自检：球心必须在外侧）、`rotary_cylinder.rs`
（圆柱闭环，h=1 下 |Δr|<0.12）、`roughing_keeps_the_allowance`。三个都不跑仿真，
加起来 20 s。

结果：32715 块 / RTCP 段 32714 / 0 条 issue；外轮廓 Δr 平均 1.242、P95 0.175、
|Δr|≤0.5 占 **48.7%**；轮廓需要的最大 A 145.9°，其中 10160 点被限位（最大抬刀 0.38 mm）。

### 悬浮碎屑

预览里一直浮着一层小方块，前一版当成"表面粗糙"。实际是**体素 CSG 只做材料去除、
不管连通性**：切下来的那一块在真实切削里会掉成切屑，场里却原地飘着。

- `voxel/components.rs`：`drop_floating_islands()`，6 邻域连通块标记，只留最大块，
  其余写成空气；花瓶 112×112×250 一次丢 **672087 格**，约 0.3 s。
- `RunConfig::drop_chips`（默认关，CAM 两条链打开），在**体积统计和设计比对之前**做，
  否则碎屑会被算成残留；`SimReport::chip_voxels` 如实报出来。

丢完之后漩涡花瓶的形状才真正露出来——之前看到的"疙瘩"一大半是碎屑。

## 形状保真度该量什么（11-04 更晚）

被问到「你如何判断加工后的模型与原版的形状保持尽可能一致」。原来只有前两层口径，
这次补了第三层，结果顺手把上一节自己的结论推翻了。

### 三层口径

| 层 | 实现 | 能发现 | 盲区 |
|---|---|---|---|
| ① 单向几何量 | `height_diff`（Δz）/ 回转 Δr | 系统性让刀、整圈偏深偏浅 | 只量一个方向；格点之间的小坑读不出 |
| ② 整实体体积 | `compare_with_design` | 设计面之外的残留、成片多切少切、可回溯到 G 代码行 | 体积不是曲面位置，0.1 mm 整体让刀几乎不动 |
| ③ 名义曲面逐点 | 新增 `crates/sim/src/surface_dev.rs` | 形状保真度本身、过切/残料深度分布、可按 A 角分组 | 单边采样；窄带外被钳制；采样非等面积 |

③ 的做法就是三坐标：设计面按 0.8 mm 采点，逐点查毛坯场 SDF——正=过切深度、
负=残料厚度、`|d|≥band` 是钳制值。3 个单测（含"P95 必须取绝对值分位"的反向测试）
+ 圆柱闭环里追加的名义面断言（P95 0.067、100% ≤0.15）校准度量本身。

### 结果：48.6% → 24.9%，并且否掉了上一节的解释

```
① Δr     ：合格(≤0.5) 48.6% / 过切 51.4% / P95 3.500（=窗口边缘，早已饱和）
③ 名义面 ：合格(≤0.15) 24.9% / 过切 51.4% / 残料 23.7% / 最大过切 >4 / 最大残料 0.82
按所需 A：30..60° 0.403；60..90° 0.702；90..110° 0.867；110..180° 0.530
```

上一节写的是"42% 的面 A 超 110° 所以够不到"。A 分组直接把它否了：过切在 A 各区间
**均匀**，110..180° 那组反而最好。三条证据（偏差图上合格区只在漩涡脊线、谷底整片
饱和；`--no-rough` 更差到 99.9%；A 分组均匀）一起指向**Ø4 球头放不进 ~1 mm 级凹谷**，
球头架桥把谷整段切掉。

另外记一个早先修掉的读数坑：`Δr` 的 P95 曾对**带符号**序列取分位，读到的是"有 5% 比它更负"，
于是 3.5 这个窗口边缘值看起来像"偏差 3.5"，其实一半读数是钳制的。

## 平头开粗 + 锥度球头精加工（11-04 深夜）

用户问「平头铣刀开粗、锥度球头铣刀精加工，你之前全是平头切吗」，随后要求
「充分利用不同类型刀具，必要时可以增加刀具」。

**不是全平头**：3 轴那条一直是平头开粗 + 球头精加工；**回转那条之前是球头开粗 +
球头精加工**，既没有平头也没有锥度球头。

### 主因不在刀，在刀路

写了个审计脚本，把 G 代码的刀尖半径和 STL 真值逐点对账：

```
r_tip − 真值(最近格)   ：中位 +0.303  P95 +1.533 mm
r_tip − 包络(3×3 最大) ：中位 +0.026  P95 +0.551 mm
```

刀尖跟着**包络**走，从来没进过凹谷——`RotaryProfile::radius()` 里 3×3 取最大，
把刀顶在波纹的脊上。Ø4 球头一摆，2 mm 以内的谷全被整段削掉。这解释了 §27 里
那 51% 过切，且与 A 行程无关。

修的时候连带揪出两个取样 bug：细网格建格用**截断**（浮点让一半顶点落到前一格）、
查询用**最近格**（0.5° 在 r=20 上就是 0.15 mm 量化）。改成"四舍五入建格 + 双线性
查询"，加回归测试 `profile_follows_the_true_radius_not_the_envelope`（正弦起伏
回转体：旧代码读 +0.26 mm 包络偏差，新代码 <0.05）。

### 换刀

| 项 | 之前 | 现在 |
|---|---|---|
| 粗加工 | Ø16 球头 | **Ø16 平头**（`ToolKind::Flat` 早就支持，回转链路没用上） |
| 精加工 | Ø4 球头 2.5°×1.2 | **Ø2 锥度球头**（尖端 R1、10° 锥颈、2.5×D），1.25°×0.6 |

`ToolSpec` 新增 `ToolKind::TaperedBall` + `ToolSpec::tapered()` + `top_radius()`，
母线接 `cncsim-tool` 已有的 `tapered_ball_end_mill`（仿真早就支持 `CutterKind::TaperedBall`，
差的是 CAM 侧）。刀杆直径按**锥颈**算，否则会出现"刀杆比刀还细"。

### 结果（同一件花瓶、同一套度量）

| | 旧 | 新 |
|---|---|---|
| 合格(≤0.15) | 24.9% | **61.0%** |
| 过切 / 残料 | 51.4% / 23.7% | 37.3% / **1.6%** |
| 平均 \|d\| / P95 | 0.642 / 1.840 | **0.320 / 1.184** |
| 超窄带(≥4 mm) | 24492 | **0** |
| 刀点 / 仿真 | 30450 / 113 s | 120802 / 339 s |

### 一个被证伪的调参方向

想靠缩短锥颈（2.5×D → 1.2×D）压掉 A 60..110° 的过切：**同一份 G 代码**切出来变成
一根圆柱，偏差图整窗全空气/整窗全料交替成斜条。圆柱闭环里两种颈长都 100% 合格，
刀具母线没坏——短颈不是简单收益，机理未查清，已回退并留注释。

## 任意刀轴角度 + 刀杆碰撞（11-05 深夜）

追加两条：**加工角度只要满足机床运动学、G54/G53 要求就能任意**，
**刀路规划要考虑刀杆与工件的碰撞**。

### 角度不再凑 90° 的倍数

轴向 5 道配 45° 坡度门槛，覆盖的是「法向与某根轴夹角 ≤45°」的面，剩下的洞在
**体对角线**附近。斜向道现在可以取任意倾角：

```bash
--tilt 40 --tilt-n 8      # 40° 倾角、8 个方位；默认 54.7°×4（四条体对角线）
```

约束只剩机床：`A = acos(dir.z) ≤ 110°`，超了丢并报「A>110° 运动学挡掉 N 道」。
程序头 `G54`、尾 `G49` → `G53 Z…` → `M30`：回参考点用机床坐标，注释写明
「按 G54 Z 偏置 0 给出」，没假装通用。

### 刀杆碰撞：先证明不需要查，再查该查的

drop-cutter 的几何保证是「球心以上是半径 R 的柱体，而刀盘内没有点在球内 ⇒
柱体也在外」，所以**普通刀 + 无倒扣时不需要查**（零开销）。只有锥度刀（锥颈比
尖端粗）或零件有倒扣（`undercut > 2%`）才建 `MeshIndex` 逐点查。

**踩的坑**：第一版从 `z = R` 开始查、还要求「离工件 ≥ R + 间隙」——球心本来就
贴着曲面 1.5 mm，于是每个刀点都被判碰撞，一次性误杀 **42858** 点。改成**只从
刃长以上查**，同一件只剩 2~34 个点需要避让。

### 数字（桌腿固定器，h=0.3）

| 工序 | 去料 | 过切 | 残留 | 刀杆避让 | 仿真 |
|---|---|---|---|---|---|
| 轴向 5 道 | 62173.7 | 377.8（0.200 mm） | 780.9（1.35 mm） | — | 97 s |
| +4 条 54.7° | — | 246（h=1） | 780（h=1） | 2 | — |
| +8 条 40° | 62366.7 | 381.0（0.230 mm） | **596.5（1.10 mm）** | 34 | 312 s |

残留降 24%，代价是仿真时间 ×3.2。**孔的内圆柱面仍然有台阶**——那是 3 轴高度场
从任何方向都看不到的面（被自身遮挡），只能走五轴联动或专用内孔工序。

## 默认关染色 + 解析过切提速 27×（11-05 深夜）

两件事：染色改成**默认关**（`--color` 显式开），以及把仿真的最大瓶颈从量测里挖出来。

### 158.8 s 里只有 23 s 是切削

```
[cmp] 体素积分 0.2 ms | 解析过切 135761.8 ms（55623 段 / 1071325 设计点）
```

"解析过切"是量测，却占了 85%。三步改：

1. 段按 AABB 分桶（`SegGrid`）——每点不再扫 5.5 万段 → 88.9 s；
2. 解析只在体素报出的过切包围盒里细扫 → 4.9 s，但**最深从 0.2647 掉到 0.0647**：

第 3 步踩了个坑：`DesignModel::Field` 的表面点是**加载时预采样**的，
`design_surface_points(design, step*8)` 对它无效（点数一点没少，还是 114 s），

```

解析过切 135.8 → 16.0 s（8.5×）
指标不变：去料 58023.0 / 过切 216.0 mm³（0.2598）/ 残留 135.0 mm³
```

微基准里开/关只差 0.1 ms（6.1 vs 6.0，5 次取最小）——每片叶盖章本身很便宜，

## 多方向链路加逐点偏差（11-05 深夜）

要求「优化刀路生成，使最后加工的模型与原版更一致」。先把"一致"变成可量的数：
`--multi` 补上 `sim::surface_dev` 的名义曲面逐点有符号偏差（和回转链路同一套口径）。

基准（桌腿件 5+4 道，h=0.6）：

```
平均 |d| 0.132 / P95 0.607 / 合格(≤0.15) 81.6% / 过切 5.6% / 残料 12.8%
```

试了两个旋钮，都不划算：

- 行距 1.2 → 0.5：合格 81.6 → 83.6%、残料 12.8 → 9.3%，但仿真 142 → 339 s；
- 坡度门槛 45° → 70°：残料**一点没降**，仿真 38 → 130 s。

两条都留成 `--finish-step` / `--slope`，默认不用更贵的那档。

**结论**：h=0.6 时 ±0.15 的判据只有半个体素宽，SDF 量化贡献了大半读数——行距减半
只换 2 个点，正是量化噪声盖住刀路误差的表现。再往上只有降 h（仿真 ×4）或处理
底面附近那圈所有轴向都看不到的凹角（要五轴联动/翻面）。没有把 81.6% 粉饰成 95%。

## 可达性 + 工序编排（11-05 深夜）

「不要限定加工方式，三轴 / 3+2 / 五轴 RTCP，只要能让结果更接近原版都可以用」。
上一轮已经能从残料里看出"够不到的面"，这一轮把它变成**决策依据**。

### 一次可见性矩阵 + 贪心集合覆盖

新增 `crates/sim/src/reach.rs`：

- `visibility()`：对每个设计面采样点 × 每个候选方向，判**面朝**（`n·d ≥ cos45°`）
  且**射线不被挡**（球体追踪，每步 `0.8·sdf`）。存两张位图——`facing`（只判面朝）
  和 `masks`（面朝且通）。
- `greedy()`：带权集合覆盖，每次挑新增覆盖最大的方向，收益 < 总面积 0.4% 就停。
  3 轴（+Z）与 3+2（任意倾角定轴）在这里**没有区别**，只是候选方向不同；
  "用哪种"由覆盖面积决定，不由命令行开关决定。
- `report_with()`：够不到的面按**空间连通块**（并查集）分组，每片给建议方向、
  A/C、bbox。

RTCP 不藏：`--multi` 先打印 `rotationality`，回转件直接提示走 `--rotary`
（刀轴逐点跟法向）；非回转件用密集方向集逼近，并且明说"每刀仍是定轴，
没有沿法向恒接触的光洁度优势"。

### 结果：覆盖吃到了几何上限

```
候选 25 个方向（A≤110°）→ 9 道覆盖 78.6% → 上限 86.4%
  +1 道 A101° C23°  新增 589 mm² → 82.5%
  +1 道 A101° C158° 新增 588 mm² → 86.4%   ← 等于上限
```

剩下 13.6%：背面 1732 mm²（要翻面）、遮挡 328 mm²（封闭特征）。

### 形状指标没动，这才是关键发现

| | 9 道 | 11 道 |
|---|---|---|
| 可达面积 | 78.6% | **86.4%** |
| 合格(≤0.15) | 81.6% | 81.6% |
| 平均 \|d\| | 0.132 | 0.129 |

新覆盖的 1177 mm² 里绝大部分**依然是残料**：Ø3 球头在那些窄深特征里放不进去。
**"可达"是必要条件，不是充分条件**——这条写在模块文档第一句，实测坐实了。

### 交叉表：够不到 vs 没切好

```
可达面 42476：合格 86.0% / 过切 6.4% / 残料 7.6%
不可达面 6842：合格 41.3% / 过切 7.1% / 残料 51.6%
```

残料 12.6% ≈ 不可达 13.4%：**残料几乎全在够不到的地方**。不可达面那 41.3% 的
"合格"是读数陷阱——毛坯底面与设计底面重合，从没被切过但偏差为 0。

真正还能动的是可达面上 6.4% 的过切（最大 +1.55 mm）。

### 三个坑

1. 封闭内腔被报成"背面"——只用一张位图，`mask == 0` 混了两种含义，拆成
   `facing` + `masks`。
2. 9 个相连的点碎成 9 片——连通块格距（0.58 mm）小于采样间距（1 mm），
   改成 `max(2.5×间距, 最长边/48)`。
3. 封闭内腔整片消失——球面法向平均为零向量，被"方向必须非零"过滤掉；
   加 `dir_conf`，抵消时如实报"没有单一方向"。

## 特征级形位公差（11-06）

「继续添加模型差异对比算法」——上一轮列的下一步 #5：平面度 / 圆柱度，按
**ISO 1101 最小区域法**。新增 `crates/sim/src/form.rs`，7 个测试。

### 定义

```text
平面度 = max(n·q) − min(n·q)      圆柱度 = max(r_i) − min(r_i)
```

是**区域宽度**，不是"最大偏差"。基准要优化到最小区域：八方向模式搜索，改进不足
千分之一就缩步长。表面点从设计面采样沿**实际场梯度**投影（`q = p + d·∇d/|∇d|`），
一阶精确，不用最近邻。

### 四个坑，前两个是测试抓出来的

| 坑 | 现象 | 处置 |
|---|---|---|
| 坐标下降卡折点 | 四个正交方向都不降、**对角方向能降**，停在第 0.36% 差的位置 | 加四条对角；改进 <0.1% 也缩步长 |
| 平面 → 无穷大圆柱 | 轴挪远后，平面上到轴的距离趋近常数（极差 ∝ w²/2R） | 轴不出 2.5×bbox、`mz ≤ 0.05R`、角向 ≥ 4/12 扇区 |
| 一阶波动当形状误差 | `R + a·cosθ` 平移轴就消掉——那是**偏心** | 一阶 → 圆柱度≈0；二阶（椭圆）才计入 |
| "区域宽度"算成"最大偏差" | 单点凸起 h 会算成 h/2 或 2h | 棋盘双层：平面度 = h |

第一条是用**随机撒 400 个方向找更优解**的测试抓出来的。这类测试比"断言结果等于
某常数"更能证伪：目标函数写错、方向反了、步长不收敛，它立刻找到更好的解。

### 数字（桌腿件，h=0.6，11 道工序）

```
形位（最小区域法）：6 个特征 / 自由曲面占 39.3% 面积 / 丢弃小分片 203
  平面 2709 mm²：平面度 0.028（LSQ 0.029）/ 平均偏差 −0.024
  平面 1634 mm²：平面度 0.360（LSQ 0.362）/ 平均偏差 −0.037
```

同一件活两个平面差 **13 倍**。h=1.5 时同一片是 0.621（≈0.4h）——形位在粗网格上
被离散化主导；降到 h=0.6 掉到 0.028，**不是线性下降**，因为形位是相对基准的区域
宽度，平滑区域的量化噪声大部分互相抵消。

### 已知限制

分割是"位置连通 + 法向 12° 一致"，**曲率大的圆柱会拆成条带**（格距 3.75 mm 在 r=10
上是 21.5°）。阈值放 24° 能连上圆柱，但 90° 相邻面会经棱边并成一片（自由曲面占比
39% → 55%）。要同时成立得做按曲率自适应——没做，分不出的面积归 `Freeform`。

## 三口径 + 刀径：把"过切 6.4%"查清（11-06 晚）

上一轮结尾留了一句"下一步先定位那 6.4% 的过切是设计场边界翻转还是 drop-cutter
抬刀不足"。这轮查完，两个都不是。

### 先加量具，再看问题

1. `compare::attribute_points` —— 逐点扫掠体归因：这一点被**哪把刀、哪一行 G 代码**
   扫过、侵入多深。刀号在多工序里就是 `2i+1 / 2i+2`，能直接反推工序。
2. `compare::sweep_deviation` —— 设计面点到**刀具扫掠体并集**的有符号距离，
   **与体素 h 无关**。`<0` 过切、`≈0` 切到位、`>0` 残料、`+∞` 刀没接近过。

顺带把两个口径的差别做成报告的一等公民（体素 / 解析 / 体积并排）。

### 数字

同一份刀路（11 道、Ø3 精加工、h=0.6）：

| 口径 | 合格 | 过切 | 残料 | 最大过切 |
|---|---|---|---|---|
| 体素 | 81.6% | 5.8% | 12.6% | **+1.55 mm** |
| 解析 | 85.0% | **0.6%** | 14.4% | **+0.27 mm** |
| 可达面·体素 | 86.0% | 6.4% | 7.6% | |
| 可达面·解析 | **90.7%** | **0.9%** | 8.3% | |

归因：h=1.0 时体素报过切的 14834 点，**11699 点（79%）没有任何刀具扫掠体碰过**；
最深点 (12.50, 23.62, 2.32) 体素说 2.23 mm，解析只有 0.098 mm。
所以那 6.4% 里**只有 0.9% 是刀路问题**，其余是"薄于一个体素的尖角被整格判成空气"。

结论：**验收看解析值**；h 只影响体积积分，不再影响合格率。

### 残料是什么

按厚度分档（Ø3）：0.15–0.25 = 5302 / 0.25–0.5 = 9262 / 0.5–1 = 3710 /
>1 = 4595（全部"刀没接近过"）。可达面上 8.3% 的残料里 **3308 点是"刀走过了
但切不到"**（凹角圆角），只有 232 点是覆盖率漏洞。所以残料不是刀花、不是步距，
是球头在凹角留下的 `R(1/sin(θ/2)−1)`。

### 于是刀径是唯一的杠杆

| 精加工刀 | 合格 | 过切 | 残料 | 切长 | 可达面 | 不可达面 |
|---|---|---|---|---|---|---|
| Ø3.0 | 85.0% | 0.6% | 14.4% | 45.0 m | 90.7% | 39.1% |
| Ø1.5 | **91.6%** | 1.2% | 7.2% | 84.1 m | 93.6% | 57.7% |
| Ø1.0 | **94.1%** | 1.9% | 4.0% | 123.2 m | 93.8% | 71.8% |

残料面积 ∝ √R，这与前一轮"行距减半只换 2 个点"完全一致。小刀还白捡了
"不可达面"（39.1% → 71.8%）：`reach` 的可见性判据比刀具保守——看不见 ≠ 进不去。
默认改成 `(短边/18).clamp(0.8, 3.0)`（桌腿件 → Ø1.5），`--finish-d` 覆盖。

全量验证（h=0.6，139527 块 / 135153 段）：仿真 277.9 s，去料 64371.9 mm³，
解析口径 **91.6% / 1.2% / 7.2%**，体素口径 87.1% / 7.1% / 5.8%（最大 +2.23 vs
解析 +0.32）。相似度 F1@0.15 0.896（P 0.909 / R 0.884）、IoU 0.9756。

### 顺手修的两处

- **`--dry` 刀路体检**：`RunConfig::dry_run` 只走刀路不切材料。同一份程序
  424 s → **51 s**（8.3×），解析口径逐位一致（测试钉住段数/端点/刀号）。
  这轮所有刀径实验都是靠它做的，否则每次 7 分钟根本试不动。
- **圆柱 LSQ 口径错**：`form_lsq` 量的其实是"种子轴 + 形心"的区域宽度，标签却写着
  LSQ，在 1311 mm² 的圆角片上给出 20.172 mm（最小区域 0.914）。改成**在真正
  最小二乘轴上**量，并让 LSQ 搜索从最小区域的解出发（从形心起步会卡在半路，
  实测方差 0.40 vs 真解 0.004）。修完同一片是 **0.914 / LSQ 1.020**，符合
  "LSQ 略大于最小区域"的构造性质。加回归测试。

### 没做的

- 凹角清根（Ø1 只走残料区）没做，但已知道上限是 94.1%。
- 翻面装夹没做：不可达面仍占 13.6% 面积、42.3% 残料。

## 叶轮实测：定轴高度场的天花板（11-06 夜）

拿两个真叶轮试现有链路（"要适应各种 STL"的应激测试）：

| | `impeller turbo.STL` | `Turbo_Impeller.stl` |

## 五轴曲面法向点铣：叶轮 61.7% → 78.8%（11-07）

§40 的结论是"叶轮要五轴侧刃铣，本项目没有"。这一轮把那条结论**改掉了一半**：
不做侧刃铣（要直纹面），做**法向点铣**——刀轴沿设计面外法向，球贴上去切。

### 核心那一句

球头各向同性：球在 `p` 相切 ⟺ 球心在 `p + R·n`。而 `球心 = tip + R·a`，所以

```
tip = p + R·(n − a)              a = 刀轴
```

**刀轴是自由的**。`a = n` 时 `tip = p`；法向超出行程（叶片下表面 A=180°，
机床 110°）就把 `a` 拉到 110°，球照样相切，只是刀尖偏出去 `R(n−a)`。
叶轮 1 有 **45% 的残料点栽在 A 超程上**，改这一条之后是 0 个。

### 数字

桌腿件（h=1.5，关清根/翻面隔离变量）：**91.6% → 93.9%**，残料 7.2% → 4.9%，
不可达面 57.9% → **73.5%**，过切和最大过切**一点没变**（1.2% / +0.32）。

叶轮 1（h=1.0，关清根）：**61.7% → 78.8%**，残料 37.0% → 19.8%，
可达面 73.4% → **94.5%**，过切不变（1.3%）。

刀径是决定性的一根：Ø2.3（=精刀）63.1% / Ø1.5 64.1% / **Ø1.0 78.8%** /
Ø0.8 78.5% / Ø0.6 77.4%。默认 `--surface-d = min(精刀, Ø1.0)`。

### 四个坑

1. **刀号只写在 G 代码字符串里**（`ToolSpec` 里是 0）→ 仿真 `by_number` 找不到，
   退回第一把 Ø6 平底刀：过切 1.2% → 6.8%、最深 2.92 mm。
2. **收尾的竖直抬刀**：多工序尾是 `G49` + `G53 Z61`，从刀尖当前位置竖直往上。
   三轴道每列上方都已切空，五轴道结束时刀尖在侧壁上、刀杆还歪着——一抬就是
   从工件里穿出去，`sd_sweep` 在一条 82 mm 的长扫掠上报 0.67 mm。
   → 曲面道自己收尾：沿刀轴退出 → `G49` → `G0 A0 C0` → `G0 Z safe`。
3. **刃部圆柱从来没被查过**：3 轴 drop-cutter 里球已经保证刀柱在料外，五轴不成立。
   → `shank_hits_axis` 分两段（刃部 `R−0.03`、刀杆 `R+0.3`）。
4. **串链穿墙**：接受点和被拒点混在一起，1 mm 的近邻之间可能隔着凸棱。
   → 每条直线段都过 `sweep_ok`（球心 + 刃部圆柱），法向差 >60° 不连。

### 剩下的

叶轮 1 的 13.9 万残料点里 **10.2 万（73%）被刀杆拦掉**——Ø1 的刀伸进叶片通道，
刃长以上那一段必然蹭到对面叶片。这不是刀路能解的：要么更细的颈/更长悬伸的刀，
要么翻面。另外残料 >1 mm 的 3.8 万点需要**五轴开粗**，点铣一遍切不到底。

## 歪刀轴：叶轮 78.8% → 91.2%，第二个件 47.3% → 95.3%（11-07 续）

上一节的结论是"73% 的残料点被刀杆拦掉"。刀杆为什么挡？因为刀轴只能沿法向，
刀杆只能直直插进叶片通道。

**歪一点就绕开了**——球是各向同性的，`tip = p + R(n−a)` 已经把补偿做完了：
歪轴不改变切出来的形状，只改变刀杆去哪。

`axis_candidates`：纯法向 → 24°/40° 两个锥面 × 8 方位，每个候选都过 A 行程；
同圈里按"和上一个点最像"排序（刀轴要连续）；串链 >45° 不连、抽稀不许把两段
30° 合成一块 60°。

| 件 | 只沿法向 | +歪刀轴 |
|---|---|---|
| 桌腿 h=1.5 | 93.9% | **94.9%**（不可达面 73.5 → 78.9） |
| 叶轮 1 | 78.8% | **91.2%**（残料 19.8 → 7.4） |
| 叶轮 2 | —（§40 是 47.3%） | **95.3%**（残料 52.4 → 4.3） |

靠歪轴进来的点：叶轮 1 68%、叶轮 2 71%。过切没恶化（1.4% / 0.3%，最大 +0.49）。

顺手补的判据漏洞：圆柱检查只在 5 个高度取样，z=6 的点从采样缝里漏过（0.49 mm）
→ 改成沿轴步长 0.8R。曲面刀从过切榜第 1 掉出前四。

代价：叶轮 1 的 `--dry` 1.5 → 4.3 min，切长 18 → 55 m（点铣的固有代价）。
