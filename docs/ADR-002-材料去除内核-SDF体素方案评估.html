ADR-002 材料去除内核：自研 SDF 体素 vs 网格布尔

状态：已决策 —— 在"尽可能自研"前提下，SDF 从"可选预览层"升级为唯一的材料去除内核。 本文 §4 得出的"精度不够做验证"这一限制，已由 ADR-003 §4 的解析扫掠点测试补偿（过切判定不经体素，精度 ±0.001 mm）。 §1 的测量仍有价值，但不再是立项前置——它现在用于给自研内核定性能基线。 日期：2026-10-28 关联：技术方案-五轴CNC仿真.md §2.4、§6.1、§11 R3

0. 结论先行

能做，但它不是"更快版本的网格布尔"，而是换了一个精度上限。

三句话：

  1. SDF 体素的结构性优势是真的：单段成本 O(扫掠体积内的体素数)，与已加工细节无关；天然可并行、无分配、无拓扑修复。而网格布尔的成本随 tile 内三角面数增长——这恰恰是五轴精加工最难受的地方。

  2. SDF 体素的精度天花板是硬的：Marching Cubes 会把尖锐棱边倒圆约 h/2。要判定 0.01 mm 级过切，需要 h≈0.01 mm，窄带内存 ∝ 1/h² → 比 h=0.1 mm 贵 100 倍，约 13 GB。不可行。 所以 SDF 永远不能做"验证"路径，只能做"预览"路径。

  3. 因此推荐双层内核：SDF 负责交互式拖动/回放，网格布尔负责出报告。两者共用同一条 SimStep 流与同一套刀具模型，通过 RemovalEngine trait 切换。这正是主方案 §11 R1 预留的接缝。

但在动手前必须先做 §1 的测量。 如果测量显示现有路径的 95 分位单段耗时 < 5 ms 且总时长可接受，那么投入 2.5 个月写第二个几何内核就是浪费——应该只做调参。

1. 先定位：慢在哪里

1.1 网格布尔的成本模型

cutrail 的每次切削做四件事（见其 docs/architecture.md）：

pick overlapping tiles → subtract through kernel → validate → commit

关键在第二步：Manifold 的布尔成本约 O((n+m)·log)，其中 n、m 是两侧三角面数。被切 tile 的三角面数会随加工推进而增长——同一块 10 mm tile 被精加工刀路反复扫过后，面数可能是初始的几十倍。

这解释了 cutrail 官方基准里那个现象：10 万段 1 mm 刀路，每段中位数从 2 ms（前 100 段）涨到 6 ms（后 100 段）。涨的不是段本身，是 tile 里的细节。

对五轴精加工（0.1–0.3 mm 步距、复杂曲面），这个增长会比基准更陡。这是网格布尔唯一的结构性弱点，也是唯一值得为它换内核的理由。但它必须先被测到，不能靠推测。

1.2 必须采集的三个指标

// crates/sim/benches/removal_profile.rs
// 逐段计时，输出 CSV
// segment_idx, tile_tri_before, tile_tri_after, elapsed_us, removed_volume_mm3, sweep_aabb_vol
  1. 单段耗时的分布（不只中位数，要 p50/p95/p99/max）
  2. 单段耗时 vs tile 三角面数 的散点与拟合 —— 这是判别"结构性问题"的唯一证据
  3. 单段耗时 vs 扫掠 AABB 体积 —— 如果这一项相关性更高，说明成本由体积主导，SDF 的收益没那么大

1.3 判别准则（写死，避免事后找理由）

观测 判定 行动
elapsed 与 tile_tri_before 强相关（R² > 0.6），且 p99 > 20 ms 结构性 上 SDF 预览层
elapsed 与 sweep_aabb_vol 强相关，与面数弱相关 非结构性 只调参，不换内核

先跑这一步再谈方案。 这一步 1 人日。

1.4 一个容易被忽略的"慢"的来源

在换内核之前，先确认慢的不是渲染侧：

  • 每帧上传了多少 MB？（§6.2 的 8 MB 预算是否被突破）
  • 是否在每帧重算全部 tile 的法线？
  • changed_since 的增量是否真的只返回了脏块，还是返回了全部？

cutrail 的 2–6 ms 是切削耗时，不含网格上传。如果实测发现瓶颈在 GPU 上传，换 SDF 内核一点用都没有（SDF 也要提取网格再上传）。

2. 网格路径还能榨出多少

在写第二个内核之前，先榨干第一个。按性价比排序：

# 手段 预期收益 成本 备注
1 粗/精分级容差：粗加工 sweep_tolerance 0.05 mm，精加工 0.01 mm 2–3× 1 人日 扫掠凸包的三角面数 ∝ 1/容差
2 启用 parallel feature（manifold 并行布尔） 2–4×（多核） 0.5 人日 官方 feature，可能已默认开
3 tile_size 调优：粗加工用 20 mm，精加工用 5 mm 1.5–2× 1 人日 需实测，非单调
4 只对脏块重算法线/上传 消除卡顿 2 人日 渲染侧，与内核无关
5 把"每段一算"改为"每 N 段一算"（降低时间分辨率） N× 0.5 人日 牺牲回放平滑度，配合缓冲可接受

已被上游否定的路（不要重复走）：

cutrail 架构文档原文："Forming their union first was measured to add triangles without saving time, so it is not done."

即"把连续多段扫掠先求并集、再做一次布尔"——实测只增加三角面，不省时间。所以"批量合并以减少布尔次数"这条常见优化思路在这里无效。这是上游做过对照实验的结论，别再试一遍。

同理，cutrail 也明确否定了 B-rep 路线："Trials with several Rust B-rep kernels failed almost every coincident or touching case"——加工产生的大量共面/相切面会让 B-rep 布尔失败。这也排除了"自己写 B-rep 内核"。

综合手段 1–5：5–20× 是现实区间。2–6 ms → 0.1–1.2 ms。对 10 万段刀路，总时长从 200–600 s 降到 10–120 s。

如果这个量级够用，就不要写 SDF。

3. SDF 体素方案设计

假设 §1 的测量证明必须上，以下是完整设计。

3.1 数据结构：稀疏 brick + 窄带

本节的扁平 brick 方案已被 ADR-006 的三级树取代。 保留本节是因为"窄带 + 三种状态 + CSG"的语义没有变，变的只是组织方式（HashMap → 树 + 位掩码）。下文的 Empty/Full/Band 分别对应 OpenVDB 的 tile 值（正/负）与叶内体素。

不要用稠密网格。 200×200×100 mm @ h=0.1 mm = 2000×2000×1000 = 4×10⁹ 体素，1 字节/体素就是 4 GB。

用稀疏 brick：

pub const BRICK_LOG2: u32 = 4;              // 16³ 体素/brick
pub const BRICK_DIM: usize = 1 << BRICK_LOG2;
pub const BRICK_VOXELS: usize = BRICK_DIM * BRICK_DIM * BRICK_DIM;  // 4096

/// 窄带距离：以体素为单位，钳制到 ±BAND
/// i8 存 ±127，BAND 取 4 → 精度 1/32 体素，足够 MC 插值
pub const BAND: i8 = 4;

#[derive(Clone, Copy, PartialEq)]
pub enum BrickState {
    Empty,          // 全在外（无实体）
    Full,           // 全在内（实心，不分配体素数组）
    Band(Box<[i8; BRICK_VOXELS]>),   // 表面穿过，存窄带距离
}

pub struct SparseGrid {
    origin: DVec3,
    h: f64,                          // 体素边长
    bricks: HashMap<IVec3, BrickState>,
    dirty: HashSet<IVec3>,
}

Empty / Full 两个状态是内存优化的关键：远离表面的 brick 不占体素数组。实测中一个 200 mm 零件 90% 以上的 brick 是 Empty 或 Full。

内存估算（这是决定可行性的核心公式）：

窄带体素数 ≈ 表面积 A × 带宽(k·h) / h³ = k·A / h²

**h 是运行期参数，不是编译期常量**：`GridConfig { h: f64, band_voxels: u8, value_type: ValueType }`，`band_voxels` 固定 4（物理带宽随 h 缩放），于是内存 ∝ 1/h²。可调带来的连带影响（速度 ∝ 1/h²、碰撞采样密度 ∝ h² 但**量化 ∝ h，h≤0.1 时量化主导**）见 [ADR-004](ADR-004-碰撞检查方案.md) §2.5.8 的保证矩阵与预设。

**`value_type` 是精度旋钮**（详见 [`计算精度分析.md`](计算精度分析.md)）：

| 类型 | 每档精度 | 内存（h=0.1） | 用途 |
|---|---|---|---|
| **`I8`（默认）** | 3.15 µm | **206 MB** | 常规验证，检出下限平面 1.6 µm / 曲面 2.0 µm |
| `I16` | **12.2 nm** | 412 MB | µm 级过切判定 |

**注意：这是精度的真正瓶颈，不是 float 宽度。** 换 f64 零收益——量化误差在**存的那一刻**就产生了。

取 A = 3.2×10⁵ mm²（200×200×100 毛坯加工后的内外表面总和），k = 4：

h 窄带体素数 内存（i8） 评价
0.2 mm 3.2×10⁷ ~32 MB 宽裕
0.1 mm 1.3×10⁸ ~130 MB 可接受
0.05 mm 5.1×10⁸ ~510 MB 紧张
0.02 mm 3.2×10⁹ ~3.2 GB 不可行
0.01 mm 1.3×10¹⁰ ~13 GB 不可行

这张表就是精度天花板的物理来源：内存 ∝ 1/h²，想精度翻倍要付 4 倍内存。

⚠️ 上表是理论下限，实际存储要乘约 1.6 倍。 因为它假设"只分配窄带体素"，而叶节点是密集分配的——表面穿过一个 8³ 叶就分配 512 字节，其中只有约一半在窄带内。

修正后的实际值（8³ 叶，mem ≈ 8.25·A/h²）：h=0.2 → 52 MB；h=0.1 → 206 MB；h=0.05 → 825 MB；h=0.025 → 3.3 GB。详见 ADR-006-稀疏体素数据结构.md §4——那里也给出了 4³ 叶（112 MB）与紧凑叶（125 MB）两个省内存选项。

3.2 刀具的解析 SDF（旋转体统一处理）

所有铣刀都是旋转体。旋转体的 SDF 等于其母线轮廓在 (ρ, z) 半平面上的 2D SDF（旋转不改变子午面内的距离）。这一条把所有刀型统一成一个函数：

/// 母线轮廓：从刀尖开始，沿 +Z 的 (半径, 高度) 折线
/// 平底刀: [(0,0),(r,0),(r,L),(0,L)]
/// 球头刀: 圆弧段采样 [(0,0),(r·sinθ, r(1-cosθ))...]
/// 圆鼻刀: 圆弧过渡 + 直段
pub struct Profile(Vec<Vec2>);   // (rho, z)

pub fn sd_tool(p: DVec3, profile: &Profile) -> f64 {
    // 转到子午面
    let q = DVec2::new(p.x.hypot(p.y), p.z);
    sd_polygon_2d(q, profile)     // 标准 2D 多边形 SDF
}

刀杆（shank）与刀柄（holder）作为额外的 profile 段，只在碰撞检测里用，不参与去除。

3.3 一段线性运动的扫掠 SDF

扫掠体 = 工具沿线段平移的并集。距离 = 到所有中间位置的最小值：

/// 平移扫掠的精确 SDF：d(p) = min_{t∈[0,1]} sd_tool(R^T(p - (a + t·v)))
/// d(t) 关于 t 是凸函数（凸体沿直线平移的并集是凸体，到凸体的距离是凸的）
/// → 黄金分割；迭代次数**按行程自适应**，见下
pub fn sd_linear_sweep(p: DVec3, a: DVec3, b: DVec3, rot: DMat3, profile: &Profile) -> f64 {
    let local = |t: f64| rot.transpose() * (p - a.lerp(b, t));
    let mut lo = 0.0; let mut hi = 1.0;
    for _ in 0..iters { /* 黄金分割，每次缩 0.618 */ }
    sd_tool(local((lo + hi) * 0.5), profile)
}

迭代次数不能写死 6。 定位误差 Δx ≈ 行程 × 0.236 × 0.618ⁿ，距离误差 ≈ Δx²/(2R)。 实测（φ6 平底刀、R=3）：0.05 mm 段用 6 次误差 < 1 µm，200 mm 段固定 6 次会到 16 µm （量化档的 5 倍），要加到约 17 次。实现里按 TARGET_RESOLUTION_MM = 0.02 自适应取 6–24 次 （voxel::sweep::golden_iters）。迭代数只依赖几何，结果仍逐位可复现。

注意：这个"min over t"给出的是到平移扫掠体的距离，不是到刀具路径的距离——正好是我们需要的（我们要减掉的是扫掠体，不是中心线管道）。

圆弧段：参数化圆弧后同样做 1D 最小化（弧参数 θ），成本相同。

五轴（段内刀轴旋转）：按弦高容差把一段切成若干子段，每子段内刀轴视为定值，取各子段 SDF 的最小值。这与 cutrail 的旋转细分策略一致，sweep_tolerance 的语义可以复用。

3.4 CSG：减法就是一次 max

// 毛坯减去刀具：d_new = max(d_stock, -d_sweep)
// 只需更新扫掠 AABB 内的体素，且只在 |d| < BAND 时写回
fn apply_cut(grid: &mut SparseGrid, sweep: &Sweep, tool: &Profile) {
    for brick_id in grid.bricks_in(sweep.aabb(), 1) {      // 外扩 1 brick
        match grid.bricks.get_mut(&brick_id) {
            Some(BrickState::Empty) => continue,           // 全在外，不可能被切到
            Some(BrickState::Full) => {
                // 若扫掠体与 brick 相交，需实体化后逐体素更新
                grid.materialize(brick_id);
            }
            Some(BrickState::Band(v)) => {
                for (i, d) in v.iter_mut().enumerate() {
                    let p = grid.voxel_center(brick_id, i);
                    let ds = sweep.sd(p, tool);
                    if ds < (BAND as f64) * grid.h {
                        *d = clamp_i8((*d as f64 * grid.h).max(-ds) / grid.h);
                    }
                }
            }
            None => continue,
        }
    }
}

max(a, -b) 的正确性依赖两边都是真实距离（或至少是钳制后仍保号的距离）。窄带钳制保持符号，所以 CSG 在带外仍然正确——这是窄带 SDF 能做 CSG 的前提。

3.5 网格提取

只对脏 brick 做 Marching Cubes，输出到该 brick 独立的 Mesh：

fn extract_brick(grid: &SparseGrid, id: IVec3) -> Option<Mesh> {
    // 16³ 体素 → 15³ 个 cell → 最多 ~3375 个三角面
    // 顶点位置用 d 线性插值（对平面是精确的）
}
  • MC：简单、成熟、顶点数固定上限。棱边会被倒圆约 h/2。
  • Dual Contouring：用 QEF 把顶点吸附到特征点，能保住尖锐棱边（误差可降到 ~0.01 mm @ h=0.1）。代价是 2–3 周额外工作，且非流形/退化情况要小心处理。

如果 SDF 只做预览，用 MC 就够。如果想让预览"看起来对"，DC 值得投入。

3.6 并行与 SIMD

这是 SDF 真正的性能来源，不是单体素算得快。

  • brick 之间完全独立（没有共享拓扑）→ rayon::par_iter 直接铺满所有核，无锁、无冲突。
  • 内层循环是标量距离函数，SIMD 化需要重构成 SoA（4/8 个体素一组）。可以先不上 SIMD，靠并行拿到 8×。
  • 无分配：brick 数组原地更新，MC 输出走对象池。

对比网格布尔：Manifold 内部虽有并行，但每次布尔要建 BVH、分配中间网格、做拓扑验证——这些固定开销无法摊销（因为上游已实测合并无益）。

单段成本估算（标出这是估算，需实测）：

项 数值
1 mm 位移 + φ6 平底刀的扫掠 AABB 约 70×60×200 体素 @ h=0.1
需遍历的 brick 数（外扩 1） 约 260
实际写入的窄带体素 约 2×10⁴
每体素成本（含 6 次三分搜索） 约 80 flops
单线程标量 约 1.5 ms
8 线程 约 0.2 ms
8 线程 + SIMD4 约 0.06 ms

对比网格布尔 2–6 ms：10–50×。但这个数字必须实测，不要拿估算去立项。

实测（2026-10-29，voxel 存储层 + 扫掠 + CSG 已实现，单线程标量，release）：

场景 遍历体素 耗时 每体素
200 mm 直槽（φ6，切深 1 mm） 1 342 000 893 ms 0.67 µs
0.05 mm 段（真实段长） 20 130 11.0 ms 0.54 µs
外推 10 万段 — 18.3 min —

与上表估算的差距：估算说 8 线程 + SIMD4 是 0.06 ms/段；实测单线程 11 ms/段。 按文档自己的杠杆（SIMD 3–6×、零分配 1.2–2×、8 线程 8×）叠起来约 30–100×， 能落到 0.1–0.4 ms —— 估算方向对，但当前实现离"8.3 分钟跑完 10 万段"还差 2.2× （早期文档的 5 ms/段是乐观值）。差距主要来自 sd_profile 每次重算母线的边距离， 没有内联/向量化。这正是文档 §性能杠杆 里排第一的那项。

成本是"扫掠体 ∩ 材料"的体积除以 h³，与段长线性相关——长段（如 200 mm 一次走完） 必须按段计费，不能指望细分降低总工作量（细分后总体素数不变）。

3.7 与 Bevy 的接法

SDF 内核产出的仍是每 brick 一个三角网格，接口与网格布尔完全一致：

RemovalEngine (trait, cncsim-sim)
├── CutrailEngine   → 调 cutrail::Engine
└── SdfEngine       → 调 SparseGrid + MC
        ↓ 两者都产出
   TileUpdate { tile_id, mesh: TriMesh, version }
        ↓
   cncsim-render 的 apply_tile_updates（完全不变）

渲染层不需要知道用的是哪个内核。 这是 §11 R1 预留 RemovalEngine trait 的直接回报。

一致性要求：两个内核必须用同一份 SimStep 流、同一套 ToolDef、同一个 sweep_tolerance 语义。否则切换内核时画面会跳变，用户会怀疑软件不可信。

4. 精度天花板（决定性因素）

4.1 各类几何的精度表现

设 h = 0.1 mm：

几何特征 MC DC 网格布尔
平面（台阶面、直壁） 优 ~1 µm（线性插值对平面精确） 优 优
圆柱面（刀具半径） 良 弦高 ≈ h²/(8r) ≈ 0.4 µm @ r=3 良 优
凸棱边（90° 台阶） 差 倒圆 ≈ h/2 = 0.05 mm 中 ≈ 0.01 mm 优（锐边保留）
凹棱边（内角） 差 同上 中 优
薄壁 / 细筋 < 2h（0.2 mm） 丢失 丢失 优
过切判定 @ 0.01 mm 不可用 不可用 可用

4.2 为什么"倒圆 0.05 mm"是致命的

对一个做刀路验证的软件，最核心的输出是"这里过切了 0.008 mm"。而 SDF@0.1mm 在每条棱边上都有 0.05 mm 的系统性偏差——比被检测的缺陷大 6 倍。这时的"过切报告"全是噪声。

这不是调参能解决的：把 h 降到 0.01 mm 才能让倒圆降到 0.005 mm，而内存从 130 MB 涨到 13 GB。

4.3 结论

SDF 体素的精度上限由 h 决定，h 由内存决定，内存 ∝ 1/h²。 要 0.01 mm 的判定精度，需要 h ≈ 0.01 mm，内存约 13 GB —— 不可行。 因此 SDF 不能作为验证路径，只能作为预览路径。

这与"网格布尔慢"并不矛盾：两者解决的是不同问题。慢的代价换来的是"报告可信"。

6. 决策规则

是否需要"边拖时间轴边看毛坯变化"的交互？
├─ 否 → 保持网格布尔，做 §2 的调参（1–2 人周，5–20×）
└─ 是
   ├─ 预览精度 0.1–0.2 mm 可接受？
   │  ├─ 否 → SDF 也救不了（要 0.01 mm 得 13 GB）→ 只能优化网格布尔
   │  └─ 是 → 上 SDF 预览层（9 人周），网格布尔保留为验证路径
   └─ 只做预览、不做验证？
      └─ 是 → 可以只做 SDF，省掉 cutrail（但要放弃 STEP/过切报告）

最关键的一问：这个软件的卖点是"验证报告可信"还是"交互体验流畅"？

  • 如果是前者 → 网格布尔是核心资产，不能换。
  • 如果是后者 → SDF 值得做，但要接受"预览看到的和报告里的不完全一样"。

推荐：双层。 理由是这个产品真正的差异化（非线性误差、轴速超限、奇异点、过切量）全部依赖精确几何，不能拿体素糊弄；但交互体验也确实需要体素。

8. 附：为什么先不做 GPU 版

GPU SDF 听起来更快（50–100×），但：

  1. 读回是瓶颈：MC 在 GPU 上做完，顶点要读回 CPU 才能交给 Bevy 的 Mesh；或者走 GPU-driven 渲染 + 间接绘制，那是另一个量级的工程。
  2. Bevy 0.20 的 mesh shader 虽已接入管线缓存，但用它做体素 MC 仍是自研管线，与 Bevy 的材质/阴影/剖切系统耦合困难。
  3. CPU 8 线程已经能到 0.06–0.2 ms/段，对 60 fps 而言单帧可算 80–270 段——远超实际刀路的段密度。

结论：先做 CPU 并行版。GPU 版留到"CPU 版实测不达标"再说，而且那时应该先问"是不是分辨率选高了"。
