ADR-011 显示层：缓冲层先写实，Bevy 外壳后接

ADR显示层

状态：已实现（缓冲层 + HTML 预览 2026-10-30；Bevy 外壳 2026-10-31，window feature） 日期：2026-10-30 关联：ADR-003（L1 呈现层不自研）、ADR-008（显示 LOD）、ADR-010（块索引）

0. 结论

三句话：

  1. 先做不需要窗口的那两层：网格 → 交错顶点缓冲、按空间分块（interleave / split_tiles）。 它们是纯数据变换，可以脱离引擎逐位验证，这一段现在有 10 个测试。
  2. 再加一个自包含 HTML 预览（--export）：单文件、无外链、200 行原生 WebGL2。 解决的是"我切出来的东西长什么样"，而不是"最终的产品界面"。
  3. Bevy 仍然要接，但它只是"把 buffer 交给 Mesh、开窗口、接 UI"。 缓冲层写实之后，这一步不再有几何逻辑，也不改变任何一个字节。 2026-10-31 已落地（见 §6）：cargo run --release --features window -- --window。

1. 为什么现在还没有 Bevy

ADR-003 把 Bevy 划在 L1（呈现层，不自研），check_deps.py 的 BEVY_ALLOWED 也早就 包含了 cncsim-render。所以这不是"要不要引"的问题，是顺序问题。

render 这一层真正难的不是窗口，是把体素网格变成能画的三角形：

步骤 在哪 现在
表面提取（Surface Nets + LOD） cncsim-voxel 已完成
顶点交错 / 索引重映射 / 分块 cncsim-render 已完成 + 测试
上传 GPU、材质、相机、UI Bevy 未接

前两步可以脱离引擎验证。第三步在有窗口的机器上只是适配——而且它不含任何几何决策， 所以现在写它拿不到什么：写完了没显示器也验证不了，还把所有后续任务的编译时间 拖到 5–15 分钟（Bevy 250+ 个包）。

结论：先写能验证的那两层，Bevy 等有窗口的迭代再上。这不是砍需求，是排顺序。

2. 为什么是 HTML 而不是"先开个窗口看看"

预览要解决的问题很具体："这一刀下去，毛坯变成什么样？"

Bevy 窗口 单文件 HTML
有显示器才能看 是 否
能发给别人 否 是（2–3 MB 一个文件）
能塞进 issue / 文档 否 是
能当产品界面 是 否

所以两者不是替代关系：HTML 是调试与沟通工具，Bevy 是产品。这一版把前者做完。

不引 CDN：three.js 之类的方案一旦离线就是白屏。渲染器是 200 行原生 WebGL2 （两个方向光 + 菲涅尔边缘 + 地面参考网格 + 轨道相机），数据内嵌为 base64 的 f32/u32 数组。代价是自己写着色器和矩阵，收益是永远能打开。

3. 分块：不是为了好看

一叶一实体 = 39 万 draw call。按质心把三角形分到 3.2 mm 见方的块（默认）， 每块一个实体，只重建被切到的那些块——面铣一个来回只动几十块。

两条实现纪律：

  • 三角形的归属看质心：每个三角形恰好属于一块，不会跨块重复绘制。
  • 块号必须排序：HashMap 的迭代顺序每次都不一样，直接拿去渲染会让 "同一份数据两次运行 draw call 顺序不同"——逐位复现就断了。

4. 怎么验证一个打不开的页面

这是这一片的真问题：没有浏览器，怎么知道它没白屏？

tools/check_preview.mjs 用桩 WebGL 在 Node 里跑一遍页面自己的 JS：

  1. <script> 能解析、能执行（语法错、API 拼错）
  2. 顶点/索引数量与 HUD 上写的一致（数据没内嵌错）
  3. 真的发出了 drawElements，索引数与数据对得上，类型是 UNSIGNED_INT
  4. 几何探针：把包围盒 8 个角投到 NDC，必须全落在 [-1,1] 内且跨度 > 0.15

第 4 条是关键。lookAt / perspective / 矩阵乘法写错时，浏览器里就是一片空白， 而桩测试里一切正常——它只检查"调用发生了"，不检查"画在哪"。探针把相机数学 也纳入了可测范围。

同理，页面本身带一个错误浮层：着色器编译失败、getContext('webgl2') 返回 null， 都会把原因打在屏幕上而不是留一片黑。

5. 还没做的

  • Bevy 外壳：窗口、相机控制、bevy_egui 面板、剖切平面
  • 增量上传：tiles_per_frame 只是预算函数，还没接到"只重建脏块"的循环上
  • 顶点色：MeshData.colors 里的调色板索引与余量偏差还没进材质（现在统一灰色）
  • LOD 按视距切：extract_surface_lod(k) 有了，选 k 的策略还没有

6. 落地记录：Bevy 外壳（2026-10-31）

做法：window feature 门控。 cncsim-render 的 bevy/bevy_egui 是 optional 依赖， cargo test / 默认构建一点都不编（默认构建 12 s，--features window 才付 Bevy 的税）。 app 转发 feature：cargo run --release --features window -- --window。

外壳（render::shell）只做三件事，零几何计算：

步骤 代码
开窗 + 灯光 + 轨道相机 DefaultPlugins + DefaultPanOrbitCameraPlugins（0.20 的相机控制器是独立 feature，pan_orbit_camera 默认关）+ PanOrbitCamera::default().with_initial_anchor_depth(..)
GpuMesh → Bevy Mesh 交错顶点拆成 Vec<[f32;3]>（Bevy 的属性是带类型数组，传扁平 Vec<f32> 会 panic "expected Float32x3"）+ Indices::U32
egui 面板 报告（时间/去料/过切/残留/非线性）+ 时间轴滑块 + 播放/倍率 + 报警列表

坐标：模型 Z-up → 世界 Y-up，整棵树 R_x(-90°)；回放工具标记用同一个变换。

踩的坑： - DirectionalLight::shadows_enabled 在 0.20 改名 shadow_maps_enabled。 - DefaultPlugins 已包含 picking，再手加 DefaultPickingPlugins 会 panic "already added"。 - Mesh::with_inserted_attribute(POSITION, Vec<f32>) 编译通过、运行时 panic——属性格式在 插入时校验（Float32 vs Float32x3），这类错误只能跑起来才发现。 - 0.20 的 PanOrbitCamera 在 bevy::camera_controller::pan_orbit_camera，锚点深度 last_anchor_depth 决定初始轨道半径（取相机到目标点距离的负值）。

已知缺口（都不阻塞使用）： - ADR-005 的顶点色（调色板索引 + 余量偏差）还没进材质——现在统一灰白材质； 下一步用 ExtendedMaterial 把编码展开写着色器（0.20 是 WESL，不是旧版 WGSL）。 - 剖切平面、按视距切 LOD 档、TileCache 的增量上传循环都还没有（缓冲层已就绪）。 - 释放构建首次编 Bevy 约 5–15 分钟；后续增量 ~1 分钟。
