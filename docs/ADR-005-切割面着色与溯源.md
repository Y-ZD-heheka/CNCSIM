# ADR-005 切割面着色与溯源

> 状态：**设计**
> 日期：2026-10-28
> 关联：主方案 §6、ADR-002 §3

---

## 0. 结论

**"这个面是哪把刀切的"本质是一个溯源（provenance）问题，不是渲染问题。** 渲染只是把溯源结果映射成颜色。

三句话：

1. **在 SDF 架构下几乎免费**：切削时顺手记下"哪次扫掠动了这块砖"，提取网格时按需解析。存储开销约 1 MB。
2. **不要按体素存 ID**：那会让内存翻倍（130 MB → 260 MB）。按 brick 存候选表，提取时用解析 SDF 反查，精确且便宜。
3. **用调色板索引而不是直接存 RGB**：换配色方案、单刀具隔离、按工序着色都只改一张 256×1 的纹理，**不需要重算仿真、不需要重传网格**。

工作量 **6 人日**。

---

## 1. 为什么这是溯源问题

用户看到的是"这个蓝色面是 T7 切的"。程序需要回答的是：

> 毛坯表面上某一点，是被哪一次刀具扫掠"最后切出来"的？

在**网格布尔**架构下，这个信息必须由布尔运算逐三角形携带——Manifold 确实这么做（`cutrail` 的架构文档提到 "Manifold keeps, for every output triangle, the identity of the input it came from"）。但那是几十人年的工程。

在**SDF 架构**下不需要逐三角形携带：毛坯表面本身就是"若干扫掠面的并集 + 原始毛坯面"。所以只要知道**这个点落在哪个扫掠面上**，就得到了创建者：

```
creator(p) = argmax_t { sweep_t 的表面经过 p }        （取时间最晚的那个）
```

这是一个**查询**，不是需要维护的状态。而扫掠 SDF 是解析的、随时可求值——所以查询几乎免费。

## 2. 存储设计：按 brick 存候选表

### 2.1 为什么不按体素存 ID

最直接的做法是给每个窄带体素加一个 `u8` 的 creator id。代价：

| 方案 | 额外内存（h=0.1） | 问题 |
|---|---|---|
| 每体素 `u8` | +130 MB（总 260 MB） | h=0.05 时总 1 GB |
| 每体素 `u16` | +260 MB | 更糟 |
| **每 brick 候选表** | **+1 MB** | 需提取时解析 |

体素 ID 还有个语义问题：MC 的每个三角形跨越 8 个体素，这 8 个的 ID 可能不同，仍要做"多数表决"或"取最近"——**并没有省掉解析这一步**，只是把解析提前到了切削时。既然如此，不如推迟到提取时，那时信息更完整。

### 2.2 候选表

```rust
/// 全局扫掠注册表：每次 cut 注册一条，永不删除
pub struct SweepRegistry {
    sweeps: Vec<SweepRecord>,
}

pub struct SweepRecord {
    pub id: SweepId,              // 单调递增
    pub tool_no: u16,             // 刀具号
    pub op_index: u16,            // 工序/程序段组
    pub block_range: (u32, u32),  // 对应 G 代码行范围（用于点选跳转）
    pub time: f64,                // 仿真时间
    pub tool: ToolProfile,        // 用于 SDF 求值（复用去除引擎的）
    pub seg: MotionSegment,       // 位姿
}
```

每个 brick 记候选：

```rust
/// 每 brick 最多记 8 个候选，溢出则退化为 Mixed
#[derive(Clone, Copy)]
pub struct BrickProvenance {
    ids: [u16; 8],
    len: u8,
}

impl BrickProvenance {
    fn push(&mut self, id: u16) {
        if self.ids[..self.len as usize].contains(&id) { return; }
        if self.len < 8 { self.ids[self.len as usize] = id; self.len += 1; }
        else { self.len = 0xFF; }          // 溢出标记 → 渲染为灰
    }
}
```

内存：125k bricks × 18 B ≈ **2.2 MB**。可忽略。

> 溢出概率极低：一块 1.6 mm 的砖被 8 把以上不同的刀切到，在正常刀路里不会发生。真发生了（比如密集的清角），退化成灰色反而诚实地表达了"这块面来源混杂"。

### 2.3 扫掠注册表的内存

10 万段刀路 → 10 万条 `SweepRecord`，每条约 120 B → **12 MB**。必须全程保留（提取时要用），不能像碰撞那样用完即弃。

如果嫌大，可以只保留 profile 的索引（刀具表里已有），`SweepRecord` 只存 `(tool_idx, seg)` → 约 80 B → 8 MB。可接受。

## 3. 提取时解析

MC 每产出一个三角形，用其重心反查创建者：

```rust
fn resolve_creator(
    centroid: DVec3,
    prov: &BrickProvenance,
    sweeps: &SweepRegistry,
    tol: f64,                          // 取 0.5·h
) -> Creator {
    if prov.len == 0xFF { return Creator::Mixed; }
    // 从最新往回找：最后一次把该处切出来的扫掠
    for &id in prov.ids().iter().rev() {
        let s = &sweeps[id];
        if s.sdf(centroid).abs() < tol {
            return Creator::Sweep(id);
        }
    }
    Creator::Stock                     // 原始毛坯面（方块顶面/侧面）
}
```

**为什么从最新往回找**：同一处被两把刀先后切过时（例如粗加工留量、精加工到位），最后一次才是"当前这个面的制造者"。`argmax` 语义天然对应。

**为什么 `tol = 0.5h`**：毛坯表面位置的不确定度就是半个体素（三线性插值）。取太小会漏（面被误判为原始毛坯面），取太大相邻面会串色。

**成本**：每个三角形最多 8 次 `sdf` 求值（每次约 30 flops）。10 万三角形 → 2.4×10⁷ flops → 约 10 ms。只在脏 brick 上做，摊薄后可忽略。

## 4. 渲染：调色板索引

### 4.1 顶点属性

```rust
// RGBA8：一次上传同时支持"按刀具"和"按余量偏差"两种模式
//   R = 调色板索引（0 = 原始毛坯面，1..=254 = 扫掠/刀具，255 = Mixed）
//   G = 有符号偏差编码（-0.5..+0.5 mm → 0..255），供偏差模式用
//   B, A = 保留
mesh.insert_attribute(Mesh::ATTRIBUTE_COLOR, colors);
```

**为什么不直接存 RGB**：直接存颜色的话，用户一切换配色方案（按刀具 → 按工序 → 单色），所有网格都要重建。存索引只需换一张 256×1 的调色板纹理。

### 4.2 材质

用 `ExtendedMaterial<StandardMaterial, CutFaceExt>`，多一个 `palette: Handle<Image>` 和 `mode: u32` uniform：

```wgsl
// assets/shaders/cut_face.wesl
@group(2) @binding(0) var palette: texture_2d<f32>;
@group(2) @binding(1) var<uniform> mode: u32;      // 0=单色 1=按刀具 2=按工序 3=按偏差

@fragment
fn fragment(in: VertexOutput) -> @location(0) vec4<f32> {
    var base = in.color.rgb;
    if (mode == 1u || mode == 2u) {
        let idx = u32(in.color.r * 255.0);
        base = textureLoad(palette, vec2<i32>(i32(idx), 0), 0).rgb;
    } else if (mode == 3u) {
        let dev = in.color.g * 2.0 - 1.0;          // 还原到 -1..1
        base = deviation_colormap(dev);
    }
    return shade_pbr(in, base);
}
```

`palette` 是 `TextureFormat::Rgba8Unorm` 的 256×1 图，运行时改像素即可换色。

### 4.3 视觉细节（决定这个功能好不好用）

| 问题 | 处理 |
|---|---|
| PBR 金属反射让颜色随角度剧变，认不出 | 着色模式下调高 `emissive` 或把 `metallic` 降到 0、`perceptual_roughness` 提到 0.8。Vericut 的着色模式看起来就偏 unlit，不是偶然 |
| 两把刀交界的 1 体素过渡带产生锯齿 | 0.1 mm 的过渡带肉眼几乎不可见；若碍眼，在解析时按重心距离做软混合 |
| 色盲用户分不清 | 调色板用 ColorBrewer 的定性色板（12 色，色盲安全），超过 12 把刀时按刀号哈希取色并接受重复 |
| 刀具太多看不过来 | 图例可点选隔离；选中某刀时其余面降到 30% 亮度（改调色板即可，不用重算） |
| 剖切面是空的 | 剖切截面不参与着色（它不对应任何扫掠面），保持灰白 |

## 5. 四种着色模式

| 模式 | R 通道语义 | 用途 |
|---|---|---|
| 单色 | 全 0 | 看形状 |
| **按刀具** | 刀具号 → 调色板 | **看每把刀切了哪些面**（主需求） |
| 按工序 | 工序号 → 调色板 | 看粗/半精/精各切了哪里 |
| 按余量偏差 | — | 过切/残留色谱（用 G 通道） |

四种模式**共用同一份网格**，切换只改 uniform + 调色板。这是把索引存进顶点属性的直接回报。

## 6. 交互（这个功能真正的价值所在）

### 6.1 点选反查

点击毛坯表面 → 得到三角形 → 反查 brick → 反查 creator → 显示：

```
刀具：T7  φ6 球头
工序：精加工（第 3 序）
G 代码：N1240 - N1380
仿真时间：00:12:34.5
去除体积：182.4 mm³
```

点击可直接把时间轴跳到该时刻。**这是"看到问题 → 定位到代码"的闭环**，比单纯上色有用得多。

Bevy 0.20 的 `MeshPickingPlugin` 提供射线拾取；需要维护 `triangle_index → brick_entity` 的映射（每砖独立实体，天然有）。

### 6.2 单刀具隔离

选中 T7 → 其余面降到 30% 亮度。实现：改调色板里其他条目的颜色，**不动网格**。

### 6.3 统计

每把刀累加：切削面积（三角形面积和）、去除体积（`SweepRecord` 累计）、碰撞次数。输出成表，可直接用于工艺分析。

## 7. 边界与降级

| 情形 | 处理 |
|---|---|
| brick 候选溢出（>8 把刀） | 渲染为中性灰，图例标注"混合" |
| 原始毛坯面（未加工） | 索引 0，渲染为浅灰 |
| 两把刀共面（同深度分层铣） | 取时间最晚的——语义正确（后切的覆盖先切的） |
| 剖切截面 | 不着色 |
| 重算（改 h 或改刀路） | 扫掠注册表清空重建；候选表随体素场一起重建 |
| 从中间继续仿真 | 不支持（ADR-004 §5.6），所以不存在"恢复溯源状态"的问题 |

## 修订记录

### 2026-11-02：色号从「每刀」改成「每工序内进度 10 档」

原文的"索引 = 第几刀（12 色往返，周期 22）"在刀数上千的场景失效：
半球凸台精加工 3008 条 `G1`，每 1.2 mm 换一次色，12 色装不下，
面上是一片无规律彩虹，刀刃每秒闪好几次。

改成 `creator_of_progress(done, total)`：

- 粗加工、精加工**各自** 0→100%，每 10% 换一档，索引 1..=10。
- 整段加工只换 **9 次**色；换刀处从第 10 档跳回第 1 档，工序分界反而更醒目。
- 相邻两刀多半同色——**这是设计，不是退化**：颜色表达"阶段"，不表达"刀号"。
- 只数切削块（`G1/G2/G3`），快移/停延/换刀不让进度虚涨。
- 刀刃颜色仍与切面同一个函数，构造保证一致。

代价：不能再靠颜色反查"第几刀"。如果将来需要，可以加"点选面 → 反查 creator"
（原 ADR §交互 已列），颜色只做粗粒度阶段提示。
