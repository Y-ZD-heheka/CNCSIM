ADR-006 稀疏体素数据结构：借鉴 OpenVDB / NanoVDB

状态：已实现（存储层）——crates/voxel 的 tree + sdf 模块，22 个测试 修订 2026-10-29：存储层落地，root 条目改成 Node/Tile 二选一（见 §5.1） 修订 2026-10-29：§7 的"显示必须走 LOD"已实现，见 ADR-008 日期：2026-10-28 关联：ADR-002 §3、ADR-004 §2.2、ADR-005 §2

0. 结论

学 OpenVDB 是对的，而且它顺手解决了我方案里的一个真实错误。

四句话：

  1. 采纳 OpenVDB 的树 + 三种值：voxel value（叶内体素）、tile value（整块常量）、background value（根上的默认值）。前两者我已经有对应物（Band / Empty / Full），但缺了"用一棵树把它们组织起来"，导致根层要枚举十万级条目。

  2. 采纳位掩码 + 紧凑子数组：内部节点用 bitmask 标记活动子节点，子指针按 popcount 连续存放。查表从"哈希探测"变成"位测试 + 一次数组访问"。

  3. NanoVDB 只能用于烘焙导出，不能用于仿真——它明确是 read-only 的。仿真每段都在写，必须用可写的树。它的线性化思路可以用在"仿真完成后导出给渲染/GPU 查询"这一侧。

  4. 内存表必须修正：我原来写"h=0.1 → 130 MB"是按"只存窄带体素"算的，但叶节点是密集分配的。真实值是 约 206 MB（8³ 叶）。这个错误源自 ADR-002 §3.1 把 Band brick 定为 4096 体素全分配——表里的公式和存储设计不一致。

1. OpenVDB 的结构（已核实）

1.1 拓扑：Tree4<T, 5, 4, 3> 从叶往根读

using FloatTree = tree::Tree4<float, 5, 4, 3>::Type;

三个数字是各层分支因子的 log₂，且要从叶往根反向解读：

层 log₂ 每维分支 覆盖体素/轴 说明
LeafNode（level 0） 3 8 8 存 8³ = 512 个真实体素
InternalNode（level 1） 4 16 16×8 = 128 每槽是一个叶或一个 tile 值
InternalNode（level 2） 5 32 32×16×8 = 4096 每槽是 level-1 节点或 tile 值
RootNode（level 3） — 不限 — 存 background value

关键数字：一个 level-2 节点覆盖 4096 体素/轴。h=0.1 mm 时是 409.6 mm——所以 200 mm 的毛坯只需要 1 个根条目。这就是我原方案最缺的东西。

1.2 三种值

值类型 存储位置 语义
Voxel value LeafNode 内 该体素的唯一值
Tile value InternalNode 上 该节点覆盖的全部体素统一取这个值
Background value RootNode 既不在 tile 也不在叶里时返回的默认值

查询逻辑：命中 tile → 返回 tile 值；命中叶 → 返回体素值；都没命中 → 返回 background。

1.3 窄带 Level Set 的三区表示（与我们的场景完全对应）

区域 active 存储 值
Outside inactive 常量区域 恒定正距离
Inside inactive 常量区域 恒定负距离
窄带（表面附近，约 ±3 体素） active 叶内真实体素 有符号距离

这正是我们 Empty / Full / Band 的三分法——OpenVDB 用同一套结构表达，只是把它组织进了树。

1.4 prune()：把均匀节点折叠成 tile

把"所含体素值与 active 状态全同"的节点替换成 tile 值，树变稀疏、体积表示不变。

这就是 ADR-004 §5.4 说的 brick 重分类（Band → Empty/Full）。我们已经在做，只是没叫这个名字。

2. NanoVDB：能学什么，不能学什么

2.1 它是只读的

官方博文原文：

"NanoVDB employs a compacted, linearized, read-only representation of the VDB tree structure, which makes it suitable for fast transfer and fast, pointer-less traversal of the tree hierarchy."

"To enable this, the data structure is stored inside a flat contiguous memory buffer."

数据流经对齐处理，可直接 cudaMemcpy 整块上传显存。支持 LevelSets / FogVolumes / PointIndexGrids / PointDataGrids。

"read-only" 是硬约束：仿真每个切削段都在改体素，所以 NanoVDB 不能做仿真结构。

2.2 它的收益（官方基准，1024³ 分辨率）

测试 OpenVDB (TBB) NanoVDB (TBB) NanoVDB (CUDA)
LevelSet 148 ms 11.6 ms 4.2 ms
FogVolume 244 ms 223 ms 5.5 ms

CPU 上 13×，GPU 上 35×。博文的结论是："it really highlights the benefit of using GPU for read-only access to the VDB data for collision detection and raytracing."

2.3 对我们的用法

用途 用什么 理由
仿真（切削写体素） 可写的 OpenVDB 式树 需要随机写
仿真中的碰撞查询 同上（同一份数据） 数据在变，不能烘焙
仿真完成后导出 NanoVDB 式线性快照 只读、可整块上传、可给第三方查看器
未来若做 GPU 渲染/查询 线性快照 + compute shader 但要先证明 CPU 版不够快

结论：NanoVDB 是"导出格式"，不是"运行时结构"。 这一点很容易搞反——看到 75× 加速就想把仿真也搬上去，但仿真要写。

3. 映射到我们的场景

3.1 已有 vs 缺失

OpenVDB 概念 我们已有的 差距
tile value BrickState::Empty / Full 只有两级常量，没有中间粒度
background value 隐含（None brick = 外部） 没显式建模，导致"内部未分配"无法表达
LeafNode BrickState::Band([i8; 4096]) 16³ 太大，浪费 4×
InternalNode + bitmask 没有 用 HashMap<IVec3, BrickState> 代替
RootNode HashMap 兼做根 十万级条目，每条 40+ 字节
prune ADR-004 §5.4 的重分类 已有，只是没叫这个名字

核心问题：扁平 HashMap 把"根"和"内部节点"合并了，于是每 1.6 mm 就要一条哈希条目。200 mm 毛坯 = 12.5 万条 → 仅 map 开销就 5 MB，而且每次查询都要哈希探测。

3.2 树带来的两个实质收益

  1. 根条目从十万级降到个位数：level-2 节点覆盖 409.6 mm，200 mm 毛坯只需 1 条。
  2. 查询从哈希探测变成位测试：mask[slot>>6] >> (slot&63) & 1 + 一次紧凑数组访问。

4. 内存修正（重要）

4.1 原来的表错在哪

ADR-002 §3.1 写：

窄带体素数 ≈ 表面积 A × 带宽(k·h) / h³ = k·A / h²

这个公式假设只分配窄带体素。但同一节的存储设计是：

Band(Box<[i8; BRICK_VOXELS]>)   // 4096 个体素，全分配

只要表面穿过一个 16³ brick，就分配 4096 字节，而其中只有约 1/4 在窄带内。公式和存储设计不一致，低估了 4 倍。

OpenVDB 的词汇让这个错误暴露出来：tile value（常量区）vs. voxel value（叶内密集）——叶是密集的，浪费是固有的；能省的只有"整块均匀"的区域。

4.2 修正后的表

取 A = 2.5×10⁵ mm²（200×200×100 毛坯加工后的内外表面总和），8³ 叶（0.8 mm @ h=0.1），每叶 512 B 值 + 16 B 头 = 528 B：

h 叶边长 叶数 内存 原表（错）
0.2 mm 1.6 mm 98k 52 MB 32 MB
0.1 mm 0.8 mm 390k 206 MB 130 MB
0.05 mm 0.4 mm 1.56M 825 MB 510 MB
0.025 mm 0.2 mm 6.25M 3.3 GB 2.0 GB

统一的公式（8³ 叶）：

mem ≈ 8.25 · A / h²   [字节，A 单位 mm²，h 单位 mm]

4.3 两个可选的省内存手段

手段 效果 代价
4³ 叶（0.4 mm @ h=0.1） 112 MB（≈理论下限） 叶数 ×4 = 1.56M，节点开销与指针跳转变多
紧凑叶（bitmask + 只存活动值） ~125 MB 写入需插入（memmove），切削时大量插入会很慢

建议 v1 用 8³ 叶：OpenVDB 的选择，节点开销与内存的平衡点，写入简单（原地覆盖，无插入）。 h=0.05 的 825 MB 对自用桌面机（32 GB）可接受；真吃紧时再切 4³ 叶——那是纯参数改动，不动算法。

5. 最终结构

pub const LEAF_LOG2:   u32 = 3;   // 8³  = 512 体素
pub const LEVEL1_LOG2: u32 = 4;   // 16³ = 4096 子槽
pub const LEVEL2_LOG2: u32 = 5;   // 32³ = 32768 子槽
// 一个 level-2 节点覆盖 8<<4<<5 = 4096 体素/轴

pub const LEAF_VOXELS: usize = 512;
pub const L1_SLOTS: usize = 4096;
pub const L2_SLOTS: usize = 32768;

/// 叶：要么常量（OpenVDB 的 tile），要么密集体素
pub enum Leaf {
    Constant(i8),                          // 整叶同值（内部 / 外部）
    Dense(Box<[i8; LEAF_VOXELS]>),         // 表面穿过，存窄带距离
}

pub struct Level1 {
    mask: [u64; L1_SLOTS / 64],            // 512 B，位=1 表示该槽有子节点
    children: Vec<u32>,                    // 活动槽的叶索引，按 popcount 顺序
}

pub struct Level2 {
    mask: [u64; L2_SLOTS / 64],            // 4 KB
    children: Vec<u32>,                    // 活动槽的 level-1 索引
}

pub struct SparseGrid {
    pub h: f64,
    pub background: i8,                    // 对应 OpenVDB 的 background value
    leaves:  Vec<Leaf>,
    level1:  Vec<Level1>,
    level2:  Vec<Level2>,
    root:    HashMap<[i32; 3], u32>,       // 通常 1~8 项
}

索引（全是位运算，无哈希）：

fn leaf_slot(i: IVec3) -> (IVec3 /*l2*/, u32 /*l2槽*/, u32 /*l1槽*/, u32 /*叶内*/) {
    let l2 = i >> 12;                        // 4096 体素/轴 → 12 位
    let s2 = ((i >> 7) & 0x1F).dot(Self::PACK_32) as u32;   // 5 位
    let s1 = ((i >> 3) & 0x0F).dot(Self::PACK_16) as u32;   // 4 位
    let v  = (i & 0x07).dot(Self::PACK_8)  as u32;          // 3 位
    (l2, s2, s1, v)
}

查询路径：root 哈希（1 次，通常命中）→ level2.mask 位测试 → children[popcount(mask & 低位)] → level1.mask 位测试 → children[popcount] → Leaf。全程无哈希、无指针追逐（children 是连续 Vec）。

写入路径（切削）：沿路径下降，遇到 Leaf::Constant 且需要改体素时，把它展开成 Dense；改完若整叶重新变成同号且全超带宽，prune 回 Constant。

5.1 实现时的修正：root 条目必须能存 tile

上面草图的 root: HashMap<[i32; 3], u32> 不够——它假定 root 每条都是一个节点。 但实心毛坯的一个 level-2 块（4096³ 体素）整块同值，若强行建节点，每个节点要为 32768 个槽分配 tile 值数组（32 KB），纯属浪费。

所以改成二选一：

pub enum RootEntry<S> { Node(u32), Tile(S) }

这样"完全落在盒内的 level-2 块"是 O(1) 的一条 tile，不分配任何节点。 这与 OpenVDB 的 RootNode 一致（它的值类型是 NodeOrTile），只是上面写漏了。

实测效果（200×200×100 mm 毛坯 @ h=0.1，2000×2000×1000 体素）：

分层填充 5.6 ms
root 条目 1   叶 0   值占用 2.0 MB   （稠密需 4.0 GB）

0 个叶——实心毛坯完全由 tile 表达，2 MB 全是各级的 tile 值数组。 这就是"三级都能存 tile"和"只有叶能存"的差别：后者要 1560 万个叶。

6. 刻意不采纳的部分

OpenVDB 有 我们不采纳 理由
f32 体素值 用 i8 量化窄带距离 我们只要符号 + ~h/8 精度，省 4× 内存
树锁 / 延迟加载（多线程写） 单线程写 仿真线程独占，无需并发写
Grid + Transform 分离 只存 h 与 origin 我们只有一个均匀网格，不需要任意变换
Mipmap / 多分辨率 不做 碰撞与 MC 都在最细层
NanoVDB 运行时结构 只做导出 §2.1 只读

额外采纳一条：blind metadata（每个节点缓存局部 min/max）。对我们最有用的是每个 level-1 节点缓存"到最近表面叶的距离下界"——碰撞粗筛可以直接跳过整个 12.8 mm 块，比逐叶 AABB 测试快得多。 2026-11-01 修订：这条至今没有接上任何读取者（碰撞粗筛走的是刀杆采样，不用 blind）， 而它的维护成本被实测揪出来了——切削热路径 prune_touched 每刀全量重算涉及的一级块 （4096 槽 × 512 体素），占铣光全程的 79%（200 刀里 272 ms）。现改为：写入只标脏 （u8::MAX = 需重算，blind_min_abs() 返回 None），精确值只在离线的 prune() 里重算。 哪天真要接查询，先接读取者、再谈维护。

7. 影响面与工作量

受影响模块 改动
cncsim-voxel 核心 重写存储层（约 800 行），接口不变（sdf(p) / set(p, d) / bricks_overlapping）
去除引擎 只改遍历方式，切削逻辑不变
MC 提取 改为按叶遍历 + 一圈 halo（见 §7.1），不是按 7³ cell

7.1 表面提取：改用 Surface Nets，以及三个踩到的坑

没有用经典 Marching Cubes。 理由：MC 需要 256 项边表 + 256×16 项三角表， 手打必错，而且错了没有中间步骤可查——少一个三角形只是网格上多个小洞， 在几千万个三角形里看不出来。

改用对偶等值面（Surface Nets）：每格一个顶点（取 12 条棱上零点的平均）， 每条符号变化的棱生成一个四边形。水密是结构保证，表数据为零。

经典 MC Surface Nets
表数据 256 + 4096 项 0
水密性 靠查表正确 结构保证
顶点位置 棱上（贴合） 格内（12 条棱零点平均）
锐边 倒圆 ≈ h/2 倒圆 ≈ h/2

锐边倒圆两者都有，而 ADR-002 已把这个短板绕开（过切用解析点测试），所以选可验证的那个。 实测精度：R=3 的球，有向体积 112.97 vs 解析 113.10，误差 0.11%。

坑一：tile 紧贴填充边界会让网格漏洞

fill_box 把"完全落在盒内"的槽做成 tile。但紧贴边界的那层槽不能做 tile： 单元格跨 2 个体素，"tile 的最后一个体素 ↔ 盒外背景"这条符号变化落在没有叶子的区域， 谁都遍历不到 → 实体边界上一圈洞（实测 298 个四边形丢失）。

修法：tile 判定要求四周各留 1 体素余量（tile_safe）。边界那层槽建成常量叶 （16 字节）而不是密集叶（528 字节）——200mm 毛坯的边界层有 25 万个叶槽， 这一步把 130 MB 压回 4 MB。

坑二：halo 重叠导致四边形被重复发射

顶点生成需要处理最小角落在未分配叶里的单元格（halo）。但 halo 会重叠： 同一个单元格被相邻的多片叶各处理一次。顶点有 entry() 去重所以无害， 四边形没有 → 边被共享 4~6 次而不是 2 次（实测 28318 条边）。

修法：四边形按顶点创建顺序（一个 Vec）遍历，天然每格一次。

坑三：HashMap 迭代顺序破坏可复现性

for_each_leaf 走的是 HashMap，迭代顺序每次不同 → 顶点顺序随机 → 仿真结果不可复现（项目硬门槛）。修法：叶坐标先 sort_unstable()。

实测规模（重要）

200×200×100 mm 毛坯 @ h=0.1：顶点 1600 万、三角形 3200 万、834 MB、43 秒。

这不能直接渲染。 三角形数 ≈ A/h² × 2，与表面积成正比、与 h² 成反比。 要在 200 万面以内（render 的预算），显示用的 h 必须 ≈ 0.4 mm。 所以显示必须走 LOD——用 SDF 查询在粗网格上重新采样，而不是直接提取最细层。

已实现（ADR-008，voxel::lod）：200 mm 毛坯 k=4 → 200 万面 / 52 MB / 2.24 s，顶点最大径向偏差 9.8 µm。约束不是"经验参数"而是 k ≤ band_voxels——粗格边长一旦超过窄带宽度，跨符号棱的远端被钳制，插值就不再说真话。 | 碰撞 | bricks_overlapping 改为"遍历叶"，加 level-1 距离下界粗筛 | | 溯源（ADR-005） | BrickProvenance 改为挂在 Leaf 上，粒度从 1.6 mm 变 0.8 mm，更细 |

工作量：存储层重写 6 人日（原 ADR-002 的 18 人日里含存储层，这里是替换而非追加）；碰撞粗筛优化 +1；测试 +2。净增 3 人日。

排期：必须在材料去除内核开工时就用树结构，不要先写扁平 HashMap 再改——存储层是所有东西的地基，改一次等于所有上层重测。

9. 一句话

学 OpenVDB 学的是"用树把常量区和密集区组织起来"，不是学它的 float 精度和多线程写。 学 NanoVDB 学的是"线性化便于导出与 GPU 访问"，但要清楚它只读，进不了仿真主循环。
