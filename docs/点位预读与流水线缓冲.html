点位预读与流水线缓冲

性能流水线

日期：2026-10-28 补充 G代码到轴运动.md，并修正其 §2.3/§2.4 的采样密度设定

0. 结论

三句话：

  1. 生产比消费快约 200 倍（实测估算），所以缓冲不是性能问题，而是响应性问题——缓冲该小不该大。
  2. 点流密度必须按弦高容差，不是固定 1 ms。上一版说"固定 1 ms 跟控制器一致"，这个理由站不住：需要控制器行为的三个量（非线性误差、轴速降额、伺服周期）都有闭式公式，不需要逐周期采样。按 1 ms 采样，一个 3 秒段要 3000 个子步，10 万段要跑 16.7 小时。
  3. "充足"的判据是"消费者永不空转"，不是"越多越好"。生产快 200 倍，几十个点就已经充足。

实现状态（2026-10-30）：v1 落地为块级回放——sim::playback::Playback 预计算每块的时间区间（与 run 同一套口径：同样的圆弧离散、segment_time、 M0/M2/M30 截断，总时长与 SimReport::programmed_time_s 逐位相等）， at(t) 做 tip 线性 + 刀轴 slerp。后台任务用任务并行（整段仿真挪到工作线程， mpsc 事件流，进度 50 ms 节流）——不是本文档第 0 节讨论的点流； 弦高容差点流留给 v2 的高保真拖拽（每段内部按 Δθ 插值），当前块级插值在 段内是直线近似，与 1 ms 点流相比在圆弧段会有弦高量级的偏差（约 0.01 mm 级）。

1. 三级成本（数量级）

以 100k 段、平均每段 30° 摆动、弦高容差 0.01 mm 为例：

阶段 单位成本 总量 说明
解析（文本 → MotionProgram） ~100 ns/行 约 10 ms 一次性，可忽略
插补 + 逆解（段 → 点位） ~1 µs/点 约 2.5 s 25 点/段 × 100k
去除 + 碰撞（消费点位） ~0.2 ms/子步 约 500 s 5 ms/段 × 100k

比例约 200 : 1。

这些数是从 ADR-002（去除 0.2 ms/子步）与 §3 的子步数推出来的估算，不是实测。落地后第一步就该用 benchmark 校正（主方案 §8.7）。

2. 修正：点流密度用弦高容差，不是 1 ms

2.1 上一版错在哪

G代码到轴运动.md §2.4 写：

选固定周期。 理由：我们要模拟控制器的实际行为（含非线性误差、轴速降额），而不是算一个数学上更优的轨迹。

这个理由不成立：

需要控制器行为的量 真的需要逐周期采样吗
非线性误差 不需要——有闭式公式 R·(1−cos(Δθ/2))
轴速降额 不需要——max(|Δq_j|/v_max_j) 用端点即可
插补周期 只是一个参数（1 ms），进公式，不进循环
几何精度（扫掠体） 由弦高容差决定，与 1 ms 无关

结论：1 ms 采样是多余的。 按它算，一个 3 秒段 3000 个子步 × 0.2 ms = 600 ms/段，10 万段 16.7 小时——荒谬。

2.2 正确的密度：弦高容差

刀轴在段内旋转时，扫掠体的真实表面是曲面。用两个姿态的凸包近似会有弦高误差：

弦高 ≈ R · (1 − cos(Δθ/2))          （与非线性误差同一个公式，都是弧与弦的拱高）

要求弦高 ≤ ε，得每个子步的最大转角：

Δθ_max = 2 · acos(1 − ε/R)

于是：

子步数 n = ceil( Δθ_segment / Δθ_max )

2.3 实测子步数（R = 175 mm）

弦高容差 ε Δθ_max 摆 5° 摆 15° 摆 30° 摆 60°
0.05 mm 2.74° 2 6 11 22
0.02 mm 1.73° 3 9 18 35
0.01 mm 1.23° 5 13 25 49
0.005 mm 0.87° 6 18 35 70

对比固定 1 ms：3 秒段 = 3000 子步。弦高容差下只要 25 个——少 120 倍。

2.4 这条修正的连带影响

项 修正前（1 ms） 修正后（弦高容差）
每段点数 3000 5–50（随摆角）
100k 段去除耗时 16.7 小时 约 8 分钟
生产耗时 300 s 2.5 s
内存（若存点流） 3 亿点 250 万点

注意 8 分钟仍不短。5 轴去除的真实成本是"摆角 / 弦高容差"驱动的——摆得越多、容差越紧，越慢。这个关系要写进 UI 的预估里。

3. 生产-消费结构

3.1 环形缓冲 + 背压

pub struct PointStream {
    ring: VecDeque<PreparedPoint>,
    capacity: usize,
}

pub struct PreparedPoint {
    pub time: f64,             // 仿真时间
    pub seg_index: u32,        // 所属段（诊断定位用）
    pub pose: Pose,            // 刀尖 + 刀轴
    pub q: [f64; 5],           // 关节值（碰撞与回放要用）
    pub is_seg_start: bool,    // 段首标记（新段要重置保守推进状态）
}

单点约 104 B。容量 256 点 = 27 KB，可以忽略。

// 生产者（预读）
while !cancel.is_set() {
    if stream.len() < LOW_WATER {          // 低水位补水
        let batch = program.next_points(BATCH);   // 例如一个段的子步
        stream.push_batch(batch)?;               // 满了阻塞
    } else {
        park();                                   // 睡到消费者唤醒
    }
}

// 消费者（仿真）
while let Some(pt) = stream.pop() {
    voxel.cut(&tool, &prev, &pt.pose);
    collide.check(&pt.q, &pt.pose);
    prev = pt.pose;
}

生产者在缓冲满时阻塞是特性不是缺陷——它自动把生产速度压到消费速度，不需要任何限速逻辑。

3.2 缓冲深度：小比大好

因为生产快 200 倍，缓冲很快填满，生产者大部分时间在睡。所以深度不决定吞吐，只决定浪费：

缓冲 内存 生产者最多超前（消费时间） 改参数时丢弃的工作
64 点 7 KB 2.5 段 ≈ 12 ms 可忽略
256 点 27 KB 10 段 ≈ 50 ms 可忽略
4096 点 426 KB 160 段 ≈ 800 ms 值得考虑

建议 256。 理由：需要大于"生产/消费的粒度比"（一个段 25 点），否则会出现"生产者补一批、消费者吃半批、再等"的抖动；但不需要更大，因为没有吞吐收益。

"充足"的正确定义是"消费者永不空转"，而不是"预读越多越好"。 生产快 200 倍这件事本身就保证了充足。

4. 取消与失效

4.1 三种失效场景

场景 影响范围 处理
拖时间轴（回放） 无 回放不走点流（§5），不需要失效
改弦高容差 / h 全部 清空缓冲、从头重算
改刀路文件 全部 同上

4.2 取消要快

pub struct Cancel(Arc<AtomicBool>);

生产者的循环每批检查一次 cancel，消费者在 pop() 返回 None 时检查。取消延迟 ≤ 一批（约 25 点 ≈ 25 µs），用户不会感到卡顿。

不要用 join() 等线程退出——那会让 UI 卡住。改为：置位 cancel → 丢弃缓冲 → 立即启动新任务 → 旧线程自然结束。

5. 回放不走点流

这是容易搞混的一点。回放不需要消费点流：

fn update_joints(time: f64) {
    let seg = program.segment_at(time);     // O(log n)
    let pose = pose_at(seg, time);          // 与计算线程同一个函数
    kin.inverse_into(pose, &mut q);         // 每帧一次，µs 级
}

理由：

  1. pose_at 是闭式函数，任意时刻可求值，不需要"在采样点之间插值"。
  2. 点流的密度是按去除的弦高容差定的（0.01 mm 级），回放用它会浪费；按帧求值更准也更省。
  3. 拖时间轴时不需要重算点流——这是"回放独立于计算"的直接好处。

唯一要求：pose_at 必须是同一个函数（G代码到轴运动.md §4.1）。否则"看到的"和"算的"不一致。

6. 完整线程模型

主线程（Bevy）
  ├─ 回放：pose_at(t) → IK → Transform      【不消费点流】
  ├─ hmi.tick()
  └─ 命令 → cmd channel

解析（一次性，主线程或专用线程，约 10 ms）
  └─ MotionProgram（不可变）

预读线程
  ├─ MotionProgram → 逐段生成子步（弦高容差）
  ├─ 每子步：pose_at + IK
  └─ push → PointStream（容量 256，满则阻塞）

仿真线程
  ├─ pop ← PointStream（空则阻塞）
  ├─ voxel.cut()      0.2 ms/子步   ← 瓶颈
  ├─ collide.check()
  └─ TileUpdate / Episode → channel → 主线程

为什么预读要单独一个线程：不是因为生产慢，而是因为生产与消费的粒度不同（一次一批 vs 一个子步），放同一线程会让消费者偶尔等生产者算完一批。分开后靠缓冲解耦，两边都是流水。

如果实测发现线程切换开销占比大，可以退化成单线程交替（低水位补水、然后消费一批）。架构上留了这个余地：PointStream 既可以跨线程也可以同线程。

7. 与"先算后播"的关系

缓冲是线程间的（预读 → 仿真），与回放缓冲（仿真 → 主线程）是两回事：

缓冲 方向 容量 满了怎么办
PointStream 预读 → 仿真 256 点 生产者阻塞（压速）
PlaybackBuffer 仿真 → 回放 按仿真时间，容量大 丢弃旧的（只保留最近 N 秒）

PlaybackBuffer 满了要丢旧的而不是阻塞——否则仿真会被"用户没在看"拖死。这两个缓冲的背压策略相反，别搞混。

10. 一句话

生产快 200 倍，所以"预读充足"是个假问题——几十个点就够了。 真正要定的是点流密度：按弦高容差而不是 1 ms，这一条把 10 万段的去除从 16.7 小时压到 8 分钟。
