# ADR-010 单元格索引：块 + 位掩码 + popcount

> 状态：**已实现**（2026-10-29，`voxel::cellmap`，4 个测试）
> 日期：2026-10-29
> 关联：ADR-006 §7.1（Surface Nets 三条坑）、ADR-008 §3（LOD 候选格）、ADR-009（并行）

---

## 0. 结论

三句话：

1. **不再用一张 1600 万条的大哈希表**存"单元格 → 顶点索引"。改成每 8³ 个单元格一个块，
   块内用 **512 位掩码**记"哪些格有顶点"，索引 = `base + popcount(掩码前缀)`。
2. 这一手是从 OpenVDB 抄的：**它的树里只有 root 是哈希表**，往下一律
   `children[popcount(mask & 低位)]`。我们把同一个套路用在同一层。
3. 200 mm 毛坯提取：**3.09 s → 0.81 s**（3.8×）。索引内存 **310 MB → 25 MB**，
   另外还省掉了原来那张 192 MB 的 `cells` 数组。

---

## 1. OpenVDB 是怎么做的

它的树是 `root → 32³ → 16³ → 8³`，**只有 root 用哈希表**：

```text
root（哈希，通常 1~8 条）          ← 唯一的哈希
  └ internal 32³：u64 位掩码 + popcount 找子节点
      └ internal 16³：同上
          └ leaf 8³：512 个值的连续数组（+ 1 位/体素的 active mask）
```

取一个体素 = 1 次 root 哈希 + 3 次位运算 + 1 次数组下标。子节点在
`children[popcount(mask & ((1<<slot)-1))]`——**位掩码就是"哪些槽有东西"的压缩索引**，
不需要为每个槽都分配内存（稀疏），也不需要哈希（顺序）。

配套的两件事：

- **`ValueAccessor` 缓存上一次的路径**：连续查询落在同一 leaf 时直接命中缓存，
  连 root 哈希都省掉。这就是"临时局部性"，任何按索引遍历的工具都吃得到。
- **`LeafManager` 给出叶区间**，工具层按区间并行，节点之间零共享。
  （我们的 `par` 做的是同一件事：按叶 / 块区间切。）

对我们最有用的不是它的树，而是那个**思想**：**"有没有"用 1 bit，"是多少"用前缀和算**。

---

## 2. 为什么我们的场景正好适合

顶点按单元格生成，而**每 512 个相邻单元格里只有几十个有顶点**——表面是二维的，
单元格空间是三维的。200 mm 毛坯实测：1600 万个顶点摊在 25 万个块里，块内平均 64/512 = 12.5%。

于是两种做法的内存差一个数量级：

| 方案 | 每块开销 | 25 万块合计 |
|---|---|---|
| 稠密 `[u32; 512]` | 2 KB | **500 MB**（比哈希表还差） |
| 位掩码 `[u64; 8]` + base | 64 B + 4 B | **17 MB** |

加上块表本身（25 万条 `[i32;3] → u32`，8 MB）与坐标数组（3 MB），索引总共 **~25 MB**，
而原来那张 `FxHashMap<[i32;3], u32>` 是 **310 MB**。

> 12.5% 的占用率是"块内位掩码"能赢的前提。如果占用率超过 ~30%，稠密数组反而更划算——
> 这个结构是为"表面在体素空间里稀疏"这件事定制的，不是通用容器。

## 3. 实现

### 3.1 结构

```rust
struct CellMap {
    blocks: FxHashMap<[i32; 3], u32>,  // 块坐标 → 块序号（已按坐标排序）
    coords: Vec<[i32; 3]>,             // 块坐标，按序号
    words:  Vec<u64>,                  // 每块 8 个 u64 = 512 位
    base:   Vec<u32>,                  // 每块第一个顶点的全局索引（前缀和）
}
```

- 块 = `cell >> 3`（算术右移，负坐标正确：`-1 >> 3 == -1`），槽 = `cell & 7` 拼成 9 位。
- `get(cell)`：块表查一次 → 读该块的 8 个 u64 → 没置位就 `None` → 否则
  `base + 前面所有字的 popcount + 本字低位 popcount`。

### 3.2 两遍构建

| 遍 | 做什么 | 并行 | 代价（1600 万顶点） |
|---|---|---|---|
| ① | 建块表、置位、计数 | 串行 | 1600 万次**小表**查找（8 MB，命中缓存） |
| ② | 按块序算 rank、写顶点数组 | **并行** | 索引唯一 → 各块写各自的下标 |

第②遍必须等掩码定稿（rank 依赖它），所以只能两遍。

**重复记录**（相邻叶各算一次同一格）在第①遍天然合并——同一位置两次；
第②遍它们会写同一个下标、写同样的字节，所以顶点数组用 **relaxed 原子写**：
不用 `unsafe`，也不依赖"谁先谁后"。

### 3.3 顶点顺序因此变成空间序

索引 = 块序 + 槽序，所以顶点按坐标排列，不再是"叶迭代顺序"。

这对渲染无影响，但**细格与 LOD 必须走同一个构建器**——`k=1 与细格逐位一致`
那条测试就是靠这个成立的（一开始分开写，它立刻红）。

副产品：顺序**与分块数无关**由构造保证，不再是"合并顺序恰好等于串行顺序"那么脆弱。

### 3.4 顶点色不再逐点写

`colors` 现在是常量（调色板未接，ADR-005），直接 `vec![[0,128,0,255]; n]` 铺满，
省掉 1600 万次写入。

## 4. 数字

| 场景 | 哈希表 | 块 + 位掩码 | |
|---|---|---|---|
| 200 mm 毛坯提取（3200 万面） | 3.09 s | **0.81 s** | 3.8× |
| 200 mm LOD k=4（200 万面） | 0.33 s | **0.25 s** | 1.3× |
| 200 mm LOD k=2（800 万面） | 2.21 s | **1.68 s** | 1.3× |
| 12×12×8 块提取 | 5 ms | **5 ms** | — |
| 索引内存（200 mm） | 310 MB | **25 MB** | 12× |
| `cells` 数组（200 mm） | 192 MB | **0**（从掩码反推） | — |

顶点数 / 三角形数 / 丢洞数与改前**完全一致**（16 000 002 / 32 000 000 / 0）——
这是必须的：换的只是"怎么找到它"，不是"它是什么"。

提取那 3.8× 的来由：原来是 **1600 万次 × 2 次探测**（`contains_key` + `insert`）
打进 310 MB（每次都是 DRAM 延迟）；现在是 1600 万次打进 8 MB（L3 命中），
外加第②遍的写是并行的。

---

## 5. 没做的

| 项 | 为什么 |
|---|---|
| 第①遍也并行 | 需要给块表分片 + 计数归并；串行那 0.25 s 还能忍 |
| 块粒度改 16³（4096 格） | 掩码 512 B/块，块数降到 1/8；但块内占用率会掉到 1.6%，前缀和变长。等实测瓶颈再说 |
| 用 `ValueAccessor` 那种路径缓存 | 现在每次 `get` 是"小表 + 掩码"，已经在缓存里，缓存路径省不了多少 |
| 把这套用到树的 root 上 | root 只有 1~8 条，本来就是缓存友好的 |

---

## 6. 一句话

**"有没有"用 1 bit，"是多少"用前缀和**——同样的信息量，一张 310 MB 的哈希表被压成
25 MB，查找从"随机撞 DRAM"变成"小表 + 位运算"。OpenVDB 十几年前就是这么干的，
它省内存是为了装下更大的体素场，我们顺带把 3.8 倍速度也拿到了。
