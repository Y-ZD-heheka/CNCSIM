# ADR-009 段内并行：零依赖 fork-join

> 状态：**已实现**（2026-10-29，`voxel::par` + 切削 / 提取 / LOD 三条热路径）
> **修订 2026-10-29（晚）**：并行池从手写 `std::thread::scope` 换成 **rayon 常驻池**。
> 手写版每次 fork-join 491 µs，预热线上一段切削才 1.9 ms——**26% 是线程开销**。
> 见 §1（决策过程保留，结论已改）。
> 日期：2026-10-29
> 关联：《并发与性能》§2（段间串行）、ADR-004 §5（切削 AABB）、ADR-008 §3（LOD 候选格）

---

## 0. 结论

四句话：

1. **段与段之间仍然串行**——《并发与性能》§2 的结论不变：第 N+1 段要读第 N 段切完的毛坯。
2. **段内部是并行的**：一次切削里每个体素只读自己那一个值，`max(d_cur, −sd_sweep)` 与邻居无关。**"不能并行"指的是段间，不是段内**——这一点原文没写清楚，本文补上。
3. **并行只改"怎么算"，不改"算出什么"**。分块数从 1 拧到 97，顶点、法向、索引、体素值逐位相同（4 条测试锁住）。
4. **池用 rayon**：手写 `std::thread::scope` 每次 fork-join **491 µs**，而预热线上一段切削只有 **1.9 ms** → 26% 花在建线程上。常驻池把它压到 ~5 µs。**只买池，不买语法糖**——分块与归位仍由本模块说了算。

实测（24 核，release，单线程 → 24 线程）：

| 场景 | 串行 | 并行 | 倍数 |
|---|---|---|---|
| 200 mm 毛坯提取（3200 万面） | 14.9 s | **3.0 s** | 5.0× |
| 200 mm 毛坯 LOD k=4（200 万面） | 2.15 s | **0.32 s** | 6.7× |
| 200 mm 毛坯 LOD k=2（800 万面） | 20.1 s | **2.2 s** | 9.2× |
| 200 mm 直槽切削（207 万体素） | 1002 ms | **142 ms** | 7.1× |
| **200 段连续切削（每段 0.05 mm，预热后）** | 10.35 ms/段 | **1.89 ms/段** | **5.5×** |
| 12×12×8 mm 块提取 | 28 ms | **5 ms** | 5.6× |

10 万段外推：**17.2 分钟 → 3.2 分钟**（段间不能并行，所以这是这条链的下限）。

## 1. 为什么是 rayon（以及第一版为什么不是）

### 1.1 第一版：手写 fork-join

最初用 `std::thread::scope` + 原子领号写了 70 行，理由三条：

| | rayon | 手写 |
|---|---|---|
| 依赖 | 6 个包 | 0 |
| 能力 | work-stealing、`par_iter` | 静态分块 + 原子领号 |
| 代码 | 数万行 | 70 行 |

当时判断"我们只需要一个形态：n 块互不相干的工作，结果按块号收回来"，work-stealing 用不上。
**这个判断在"块数固定、活均匀"时是对的**，漏掉的是另一件事：**池的有无**。

### 1.2 打脸的那组数字

| 场景 | 手写 fork-join 的固定开销 | 该场景的实际耗时 | 占比 |
|---|---|---|---|
| 200 mm 毛坯提取（一次） | 2 × 491 µs | 3.0 s | 0.03% |
| 200 mm 直槽切削（一次） | 491 µs | 142 ms | 0.3% |
| **一段 0.05 mm 切削（预热线）** | **491 µs** | **1.9 ms** | **26%** |

前两行骗人：那是"一次性大活"，线程开销淹没在噪声里。真正的形状是**每段一次 fork**，
而预热线上一段只有 1.9 ms——**四分之一的时间在创建线程**。10 万段就是 49 秒白烧。

rayon 的常驻池把这次往返压到 **~5 µs**（复用已有线程，一次 `park/unpark`）。
这就是引它**唯一**的实质理由；`par_iter` 的写法更短只是顺带。

### 1.3 代价与边界

- **6 个传递包**：rayon / rayon-core / crossbeam-deque / crossbeam-epoch / crossbeam-utils / either。
- 已在 `tools/check_deps.py` 的 `EXTERNAL` 表白名单登记（`cncsim-voxel → rayon`）。
  **没登记的依赖直接判违规退出码 1** —— 引依赖从此需要签字，不是"顺手加"。
- `ADR-003` 的边界是"**L2 领域**全自研，L0 基础设施（`std`/`serde`）不自研"。池属于基础设施，
  与"自研运动学"不冲突：它不承担任何领域语义。
- 抖动：rayon 的 steal 有 µs 级抖动（《并发与性能》§7.1），所以**低延迟路径（UI/回放）不走它**，
  只走批处理。

### 1.4 不共享这条没变

池只负责"分 CPU"，数据面的规矩一字未改（§2）：只读并行、按块号归位，
`SparseGrid` 始终单一所有者。work-stealing 只在块之间搬任务，搬不动共享状态。

## 2. 形态：两相提交

三条热路径都是同一个形状——**只读并行，写入串行**：

```
① 并行求值：&self 只读，每块产出自己的结果（顶点列表 / 改变列表 / 索引列表）
② 串行归并：按**块号顺序**合并，顺序与线程调度无关
```

这样 `SparseGrid` 始终**单一所有者**，不需要 `Arc<Mutex<…>>`，也不需要任何 unsafe：

- **切削**：并行 `cut_box` 求值（只读 `get` + 解析 `sd_sweep`），串行 `set` 落盘。
- **提取**：并行 `vertex_batch`（只读树 + 叶坐标表），串行合并顶点；四边形并行发射、串行拼接。
- **LOD**：并行 `lod_vertex_batch`（只读 `sdf`），串行合并；四边形同上。

> 对比《并发与性能》§3.2 的"办法 A（裸指针 + `&mut`）"：那是**并行写**的方案，
> 用在这里既没必要（写入量远小于求值量）又要 unsafe。**能不共享就不共享，其次才是无锁。**

### 2.1 为什么"按块号归位"就够了

领号是动态的（`fetch_add`，谁空谁拿下一块），但每块的结果先落进 `slots[块号]`，
最后按块号摊平。于是**块完成的先后完全不影响输出**。

提取还有一个额外要求：同一片单元格会被相邻叶各算一次（halo 重叠，ADR-006 §7.1 坑二）。
分块是**连续叶区间**，所以块内先去重、块间按块号合并，与串行"首次出现"的语义完全一致。

## 3. 逐项数字与瓶颈在哪

> **修订 2026-10-29（更晚）**：本章的"合并阶段 2.0 s 是瓶颈"已被
> [ADR-010](ADR-010-单元格索引.md) 解决——块 + 位掩码索引把它压到 0.25 s 量级，
> 提取总时间 3.0 s → **0.81 s**。下面保留原始测量，因为"并行之后剩下的串行段在哪"
> 这个分析方法本身没变，而它正是促使换索引的那一步。

### 3.1 提取（32M 面）

| 阶段 | 24 线程耗时 | 谁在等 |
|---|---|---|
| 叶收集 + 排序 + 叶集合 | 0.2 s | 串行（走一遍树） |
| 顶点生成（250 k 片叶 × 10³ 缓冲） | **0.40 s** | 并行 |
| 合并顶点（16 M 次 `cell_vertex` 插入） | **2.0 s** | **串行** ← 瓶颈 |
| 四边形发射（64 M 次查询） | 0.61 s | 并行 |
| 合计 | **3.0 s** | 串行基线 14.9 s |

**剩下的瓶颈是合并**：16 M 个 `[i32;3] → u32` 插入，一张 300 MB 的哈希表，每次都是 cache miss。
它天然串行——索引必须按顺序分配。真要再快，得把"单元格 → 顶点索引"换成按 level-1 分块的表
（查找落进 16 KB 的块内数组，命中 L2），预估能压到 0.5 s。**没做**：3.0 s 已经够用，
而这是每次仿真只看一次的开销，不是每段都付。

### 3.2 切削

用 1 / 4 / 24 线程三档实测拟合（`T(n) = S + P/n`）：**串行段 S ≈ 87 ms、并行段 P ≈ 915 ms**。

**真实仿真循环的形状更值钱**：连续 200 段 0.05 mm（每段 3.5 万体素，AABB 与上一段重叠）：

| | 每段 | 外推 10 万段 |
|---|---|---|
| 1 线程 | 10.35 ms | 17.2 min |
| 24 线程 | **1.89 ms** | **3.2 min** |

5.5×。冷启动单段是 7.2 ms，因为要吃首次叶分配的页错误——**拿单段数字外推会高估 4 倍**。

| 段 | 内容 | 耗时 |
|---|---|---|
| 并行 | 求值：`get` + `sd_sweep`（6–17 次黄金分割迭代） | **~40 ms**（24 线程） |
| 串行 | 落盘：189 万次 `set`（树下降 + 叶写 + bounds） | **~87 ms** |

Amdahl：`T(24) = 87 + 915/24 = 125 ms`，实测 153 ms（差在 fork 开销与内存带宽）。
**再往上加线程没用**，除非把落盘也并行——那要动树的插入路径，风险远大于收益。

真实段长（0.05 mm）只脏 3.5 万体素，求值 11.6 ms、落盘 1.8 ms，所以只有 1.8×：
**段越小，串行占比越高**，这是段内并行的固有上限。

### 3.3 LOD

LOD 有三段，前两段都能按"叶"或"候选格"切：

| 段 | 做法 | 备注 |
|---|---|---|
| 候选格生成 | 按叶分块、每块一个本地 `HashSet`，最后统一 `sort + dedup` | 675 万次插入 → 297 万个唯一格；排序既去重也保证顺序确定 |
| 顶点生成 | 按候选格分块，块内按格点缓存角点值 | 缓存必须**按块**，跨块共享会变成争用点 |
| 四边形 | 与细格同一套 `split_quads` | — |

**候选格生成必须并行**：k=4 是 675 万次哈希插入，串行做这一项就占掉总时间的一半；
k=1 更极端（每片叶 729 个候选格）。并行后 k=4 从 604 → 320 ms，k=1 从 66 → 49 ms。

## 4. 代价：池往返 ~5 µs，门槛还在

| | 手写 fork-join | rayon 常驻池 |
|---|---|---|
| 24 线程一次往返 | 491 µs | **~5 µs** |
| 8 线程 | 168 µs | 同量级 |

门槛**没有取消**，理由换了：

| 路径 | 门槛 | 现在为什么还留 |
|---|---|---|
| 切削 | 2 万体素 | 每块要分配一个"改变列表" `Vec`，块太碎时分配 + 合并拷贝比省下的算力贵 |
| 提取 / LOD | 128 片叶 | 同上：每块产出顶点 `Vec`，合并是串行的 |

真实段长（3.5 万体素）过线：1.9 ms 里池开销已可忽略，剩下的是**串行落盘**（见 §3.2）。

## 5. 正确性契约

并行只允许改**怎么算**：

| 契约 | 谁来守 |
|---|---|
| 分块数不影响输出（顶点 / 法向 / 色 / 索引 / 丢洞） | `parallel.rs::extract_chunk_count_does_not_change_the_mesh` |
| 同上，LOD 的 k=1/2/4 | `parallel.rs::lod_chunk_count_does_not_change_the_mesh` |
| 切片数不影响体素值与统计 | `parallel.rs::cut_slice_count_does_not_change_the_grid`（逐体素比 115 万点） |
| 同一份数据两次运行逐位相同（调度不同） | `parallel.rs::repeated_parallel_runs_are_bit_identical` |
| 分块本身的结果顺序与完成顺序无关 | `par::tests::results_come_back_in_chunk_order` |

对拍方式是把"分块数 / 切片数"做成显式参数（`extract_surface_chunks(n)` / `cut_segment_with(.., slices)`），
`0` 表示自动。线程数是进程级全局（`OnceLock`），测试里改不了，所以**用块数当旋钮**——
块数 1 就是串行路径，块数 97 就是 97 块并行。

## 6. 已知不做的事

| 项 | 为什么 |
|---|---|
| 段间并行（跨段流水） | 数据依赖，结果不确定（《并发与性能》§2） |
| 并行写 `SparseGrid` | 叶插入顺序会变 → 遍历顺序变（虽然提取已排序，但树的 `blind_min_abs` 等元数据会与串行不一致） |
| 合并阶段分块化 | 提取 3.0 s 里占 2.0 s，但一年只跑几次 |
| 用 rayon 的 `par_iter` 重写热循环 | 池已经用了，但"块 → 结果"的归位逻辑留在 `par::map_indexed`：`par_iter().collect()` 一样保序，可一旦有人写 `for_each` + `push` 就会丢确定性 |

---

## 7. 一句话

**"无锁并发"的正确形态不是把锁换掉，是把共享删掉**：段内按体素 / 叶 / 粗格切开，
只读并行、按块号归位，`SparseGrid` 全程单一所有者——于是既没有锁，也没有
"结果随调度漂移"这个更贵的问题。池是 rayon 的，但**并行只发生在"互不相干的块"之间**这件事，
是这一段代码自己的纪律，不是库给的。
